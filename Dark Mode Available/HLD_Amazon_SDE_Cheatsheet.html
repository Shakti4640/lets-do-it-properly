0. What HLD Interviews Actually Test

Amazon's "System Design" round (sometimes called "Distributed System Design" for SDE-2/3) is 60 minutes. The interviewer is not looking for the "perfect" architecture; they're checking whether you can drive a vague problem into a defensible system, justify each component, and call out the trade-offs.

SignalWeight (SDE-2 / SDE-3)"Strong" looks like
Requirement clarification & scoping15% / 10%3–5 sharp questions, explicit FR + NFR list, clear out-of-scope.
Capacity estimation (back-of-envelope)10% / 10%QPS, storage/yr, bandwidth — to one significant figure, fast.
API design10% / 5%3–5 endpoints with concrete request/response shape.
Data model & storage choice15% / 15%Picks SQL vs NoSQL with one-line justification; partition key chosen on access pattern.
High-level architecture20% / 25%Boxes-and-arrows: client → LB → service → cache → DB → queue → workers. Each box has a reason.
Deep dive on bottlenecks20% / 25%Picks the hottest component, explains contention, fixes with sharding / cache / async.
Trade-offs & failure modes10% / 10%"If region X fails… if Redis evicts hot key… if write QPS doubles…"
Amazon LP signal in HLD:
  • Customer Obsession — frame NFRs in customer terms ("p99 cart-add latency < 100 ms").
  • Dive Deep — when interviewer says "tell me more about the cache", do not stay surface-level.
  • Are Right, A Lot — defend choices, but pivot fast when the interviewer surfaces a constraint you missed.
  • Bias for Action — propose v1 first, then evolve. Don't try to design the final state in one shot.
  • Ownership — call out monitoring, alarms, runbooks. SDE-3 candidates lose points without an ops story.

1. The RESHADED Framework — drive every HLD with this

R-E-S-H-A-D-E-D — write these on the whiteboard first, then walk through them in order:
  1. Requirements — functional + non-functional, in/out of scope.
  2. Estimation — QPS, storage, bandwidth.
  3. Schema / data model — entities + relationships + partition key.
  4. High-level diagram — boxes & arrows.
  5. API design — 3–5 endpoints, concrete payloads.
  6. Deep dive — pick the hottest component, redesign it.
  7. Edge cases & failure modes — what dies, what degrades.
  8. Decisions & trade-offs — why these choices, what changes for v2.

Verbal opening template (memorize)

"Before I jump in, let me confirm scope. I'll assume the system supports A, B, C
for users U with N daily actives. Out of scope: payments, mobile-app UI, ML ranking.
I'll do quick capacity math, sketch the API, then the architecture, and we'll deep-
dive into whichever bottleneck you find most interesting."

The 5 questions you must always ask

  1. Read-heavy or write-heavy? Read:write ratio drives the whole architecture.
  2. Strong or eventual consistency? Money? Strong. Likes count? Eventual.
  3. Latency targets? p50 / p99 — sub-100 ms forces caching + co-located data.
  4. Scale today and in 1 year? 1k users vs 100M users → different stack.
  5. Geographic distribution? Single region vs multi-region changes everything.

Worked example — Twitter-scale capacity

Daily active users (DAU)              = 200 M
Avg tweets per user per day           = 0.5  → writes/day = 100 M
Read:write ratio (timeline reads)     = 100:1 → reads/day = 10 B

Write QPS = 100 M / 86,400 s         ≈ 1.2 K QPS  (peak ≈ 3 K)
Read  QPS = 10 B  / 86,400 s         ≈ 115 K QPS (peak ≈ 350 K)

Tweet size                            = 280 B text + 200 B metadata = 0.5 KB
Storage per day                       = 100 M × 0.5 KB = 50 GB
Storage per year                      = 50 GB × 365   ≈ 18 TB
With media (10% of tweets, 200 KB)    ≈ 2 PB / year
Trick: always compute QPS first, then multiply by payload size for bandwidth, then by retention for storage. State assumptions out loud — "I'll assume 200 M DAU" — and the interviewer will correct you if it matters.

3. CAP and PACELC — what they actually mean

CAP theorem: in the presence of a network Partition, you must trade Consistency for Availability. CP = stop serving to stay correct. AP = keep serving but possibly serve stale data.

SystemCP example (consistent under partition)AP example (available under partition)
DatabaseHBase, MongoDB (with majority writes), Spanner, etcdDynamoDB (default), Cassandra, Riak, CouchDB
What dies in a partitionSome clients get errors / timeoutsSome clients see stale data; reconciliation later
Use whenMoney, inventory, identity, locksLikes, view counts, shopping cart, social feeds

PACELC extends CAP: even when there is no Partition, you still trade Latency for Consistency. DynamoDB is "PA / EL" — chooses Availability under partition, Latency in normal operation.

Interview line: "Strict CAP is binary, but in practice systems tune per request — DynamoDB lets you ask for strongly-consistent reads on critical paths only, paying ~2× cost."

4. Consistency Models — pick deliberately

ModelGuaranteeWhen to use
Strong (linearizable)Reads see the latest committed write, globally ordered.Inventory decrement, money debit, leader-election state.
SequentialAll clients see the same order of writes (not necessarily real-time).Distributed logs, replication streams.
CausalCause-before-effect ordering preserved per chain.Comments under a post, chat threads.
Read-your-writesA client always sees its own writes.User edits their own profile, expects to see it instantly.
Monotonic readsIf you read X=5, you'll never later read an older X.Timeline browsing.
EventualIf writes stop, all replicas converge.Likes, view counts, DNS.
Pattern: route the same user's reads to the primary replica for "read-your-writes" without requiring full strong consistency globally. This is how DynamoDB / Aurora session-affinity works in practice.

5. Scaling Strategies — vertical → horizontal → split

StepWhatWhen you outgrow it
1. Vertical scalingBigger box. r5.24xlarge. RDS instance class up.Hits hardware ceiling; single point of failure.
2. Horizontal scaling (stateless)Run N copies behind a load balancer.State (sessions, sticky data) becomes the bottleneck.
3. CachingRead-through cache for hot data.Cache stampede / hot-key problems.
4. Read replicas1 primary + N read replicas.Primary becomes write bottleneck.
5. Sharding (partitioning)Split data by key across many primaries.Cross-shard queries become expensive.
6. CDN / edgeCache static / semi-static content closer to user.Cache invalidation becomes hard.
7. Async / queuesDecouple write paths; smooth bursts.Eventual consistency lag visible to user.
8. Multi-region active-activePer-region writes; global replication.Conflict resolution becomes the hard problem.

6. Load Balancers — L4 vs L7, algorithms

AspectL4 (transport)L7 (application)
SeesIP + TCP portHTTP path, headers, cookies, body
ExamplesAWS NLB, IPVS, HAProxy TCP modeAWS ALB, Nginx, Envoy, HAProxy HTTP mode
LatencyLower (no TLS termination needed)Slightly higher (parses every request)
RoutingBy IP / portBy URL path, host header, cookie, JWT claim
Use whenPure TCP services, ultra-low latency, gamingHTTP microservices, A/B routing, sticky sessions

Algorithms

  • Round-robin — simple, ignores load.
  • Least connections — sends to the box with fewest active connections.
  • Least response time — fewest connections × latency.
  • IP hash / consistent hash — same client → same backend (sticky without cookies). Mandatory for distributed caches.
  • Weighted — bigger box gets more traffic. Used during canary deploys.
  • Random + power-of-two-choices — pick 2, send to less-loaded — good in practice with low coordination cost.

7. Caching — the most-asked HLD topic

Strategies (interviewer expects you to name these by name)

StrategyReadWritePros / Cons
Cache-aside (lazy)App checks cache; on miss, app reads DB and populates.App writes DB; invalidates / updates cache.Simple, resilient. Race: stale write between miss and load.
Read-throughApp asks cache; cache loads from DB on miss.Same as cache-aside.Cleaner client code. Cache must know schema.
Write-throughRead from cache.App writes cache; cache writes DB synchronously.Cache always consistent. Slow writes.
Write-behind (write-back)Read from cache.App writes cache; cache flushes DB async.Fast writes. Risk: data loss on cache crash.
Refresh-aheadCache predicts hot keys, refreshes proactively.—Avoids cache miss. Wasted work for non-popular keys.

Cache layers (talk in this order)

  1. Browser cache — HTTP headers (Cache-Control, ETag).
  2. CDN — CloudFront, Akamai. Static + cacheable API responses.
  3. Edge / API gateway cache — short TTL, per-region.
  4. Application cache — in-process (Caffeine, Guava). ns-fast.
  5. Distributed cache — Redis, Memcached, ElastiCache.
  6. DB query cache — buffer pool, Redis-as-DB-buffer, materialized views.

Eviction policies

PolicyIdeaBest for
LRUEvict least-recently-used.Default; recency = future use.
LFUEvict least-frequently-used.Strong popularity skew (top-K).
FIFOInsertion order.Simple; rarely best.
TTLTime-bounded.Rate-limit counters, sessions.
W-TinyLFUHybrid LRU + LFU + admission.What Caffeine uses; near-optimal hit rate.

Cache pathologies (and fixes)

ProblemSymptomFix
Cache stampede (thundering herd)Hot key expires; 1000 concurrent clients all miss → DB melts.Single-flight (in-process lock + load-once); request coalescing; "stale-while-revalidate".
Hot keyOne key (celebrity ID) takes 80% of traffic.Replicate hot key to N shards; client picks random replica; or local in-process cache layered over Redis.
Cache penetrationMany requests for keys that don't exist (attack or bad client).Cache "not-found" with short TTL; Bloom filter front-door.
Cache avalancheMany keys expire at the same time → DB spike.Jitter TTLs (±20%); pre-warm; tiered TTL.
Stale dataCache and DB diverge after a write.Invalidate on write (delete, not update); use versioned keys.
Two cache rules of thumb: (1) prefer delete on write over update — fewer race conditions. (2) Always set a TTL even when you don't think you need to — prevents drift across the system.

8. Databases — SQL vs NoSQL (and which NoSQL)

AspectSQL (Postgres, MySQL, Aurora)NoSQL (DynamoDB, Cassandra, Mongo, etc.)
SchemaStrict, enforced.Flexible, per-document.
JoinsFirst-class.Avoid; denormalize instead.
TransactionsStrong ACID across rows / tables.Usually single-item ACID; cross-item via app-level sagas.
ScalingVertical first; read replicas; sharding is hard.Horizontal by design.
ConsistencyStrong (default).Tunable (eventual / strong / quorum).
Best fitFinancial ledger, OMS, inventory ledger, anything that needs SELECT … JOIN … GROUP BY.Sessions, feeds, IoT, catalog, time-series, write-heavy at scale.

NoSQL families — pick the right one

FamilyExamplesUse when
Key-ValueDynamoDB, Redis, RiakLookup by primary key. Sessions, profiles, carts.
Wide-ColumnCassandra, ScyllaDB, HBase, BigtableMassive write throughput, time-series, large rows.

Decision shortcut: "Do I need joins or transactions across multiple entities?" → SQL. "Do I know the access pattern in advance and need scale?" → DynamoDB / Cassandra. "Do I need full-text or aggregations on free-form text?" → Elasticsearch as a secondary index.

9. Sharding & Replication

Sharding strategies

StrategyHowProCon
Range-basedshard = f(key range)Range scans are fast.Hot shards (e.g., latest timestamps).
Hash-basedshard = hash(key) % NEven load.Resharding requires moving most data.
Consistent hashingHash ring + virtual nodes.Adding/removing a shard moves only 1/N of keys.Slightly more complex to implement.
Geo / directoryLookup table maps key → shard.Maximum flexibility, region affinity.Lookup table is itself a SPOF; cache it.

Replication patterns

PatternWritesReadsTrade-off
Single-leaderTo leader only.Leader (strong) or replicas (stale).Simple. Leader = SPOF until failover.
Multi-leaderAny region's leader.Local.Conflict resolution required (LWW, CRDT).
Leaderless (Dynamo-style)To W replicas.From R replicas. Quorum: R + W > N.Tunable C/A. Read repair + Merkle trees handle drift.

Replication lag — what to say in interview

  • "Read your own writes" → route post-write reads to leader for a TTL, or sticky-session to leader, or include a write-token version in the read.
  • "Monotonic reads" → pin a user to the same replica.
  • "Causal consistency" → use vector clocks or version vectors.
Resharding pain: hash-mod sharding looks elegant but doubles your migration pain on every add a shard. Default to consistent hashing with virtual nodes (typical: 100–256 vnodes/shard). Cassandra and DynamoDB both do this internally.

10. Indexes & Storage Engines

AspectB-Tree (Postgres, MySQL InnoDB)LSM-Tree (Cassandra, RocksDB, DynamoDB, LevelDB)
Write pathIn-place update; random I/O.Append-only memtable → flush SSTable; sequential I/O.
Read pathOne tree traversal, ~O(log n).Check memtable + multiple SSTables (Bloom filter helps).
Best forRead-heavy, point + range queries.Write-heavy, time-series, append logs.
Compaction—Background merge of SSTables; can cause spikes.

Index types worth naming

  • Primary / clustered — table is physically sorted by this key.
  • Secondary — extra index, points back to the row.
  • Composite — leftmost-prefix matters; (a, b) serves WHERE a=… and WHERE a=… AND b=…, NOT WHERE b=….
  • Covering index — query satisfied entirely from the index (no row lookup). Big win.
  • Inverted index — token → list of doc IDs. Foundation of search engines.
  • Geo / R-tree / Quadtree / S2 / Geohash — spatial queries (Uber, Yelp).
  • Bloom filter — probabilistic "is this key absent?" — cheap negative test before disk read.

11. Message Queues & Streaming

AspectQueue (SQS, RabbitMQ)Log / Stream (Kafka, Kinesis)
SemanticsEach message consumed once, then deleted.Durable log; consumers track offsets independently.
ReplayNo.Yes, by offset / timestamp.
OrderingFIFO optional, often per-queue.Strict per-partition.
Fan-outOne consumer per message (or via SNS topic).Many consumer groups read independently.
Best forTask queues, decoupling, retry.Event sourcing, analytics, pub-sub at scale.

Delivery guarantees

GuaranteeBehaviorHow
At-most-once0 or 1 delivery; loss possible.Fire and forget, no ack.
At-least-once≥1 delivery; duplicates possible.Ack after processing; redeliver on no-ack.
Exactly-once1 delivery, no duplicates.Idempotent processing + transactional offset commit (Kafka EOS) — usually "effectively once".

Patterns

  • Outbox pattern — write business row + outbox row in same DB transaction; a poller publishes outbox to Kafka. Solves the dual-write problem.
  • Dead-letter queue (DLQ) — after N retries, park the message. Always have one.
  • Saga — long-running multi-service transaction via a sequence of local transactions + compensating actions.
  • CQRS — separate write model (commands) from read model (queries, projections).
  • Event sourcing — store state as an append-only log of events; rebuild current state by replay.
Interview line that scores: "I'll use the outbox pattern so the OrderPlaced event is published if-and-only-if the row is committed — no dual-write race."

12. Consensus — Raft, Paxos, Two-Phase Commit

AlgorithmWhat it doesUsed by
PaxosAgree on a single value despite faults.Google Chubby, Spanner.
Multi-Paxos / RaftAgree on an ordered log of values (replicated state machine).etcd, Consul, CockroachDB, TiKV, MongoDB (modified Raft), Kafka KRaft.
2PC (Two-Phase Commit)Coordinator polls participants → prepare, commit / abort.XA transactions. Blocking if coordinator dies.
3PCAdds a pre-commit phase to avoid 2PC blocking.Rare; 2PC + timeouts is more common in practice.

Raft in 5 bullets (interview-ready)

  1. Cluster has 1 leader at any term; followers replicate the leader's log.
  2. Leader election: nodes timeout, increment term, request votes; majority wins.
  3. Log replication: leader appends, replicates, commits when majority acks.
  4. Safety: only nodes with the most up-to-date log can become leader.
  5. Quorum = ⌊N/2⌋ + 1. Tolerates ⌊(N−1)/2⌋ failures (3 nodes → 1 failure, 5 nodes → 2).
Don't say "we'll use Paxos." Say "we'll use Raft (or an off-the-shelf system like etcd) for leader election and metadata replication." Implementing consensus from scratch is a red flag in an interview.

13. API Design — REST vs gRPC vs GraphQL

AspectREST (JSON / HTTP)gRPC (Protobuf / HTTP/2)
Use whenPublic API, browser clients, broad ecosystem.Internal service-to-service, low latency, streaming.
SchemaOpenAPI (optional, often outdated).Protobuf — compile-time contract, codegen.
StreamingSSE / WebSockets bolted on.Native bidirectional streaming.
VersioningURI (/v1) or header.Field numbers in proto; never re-use.

REST design rules

  • Nouns, not verbs: POST /orders, not POST /createOrder.
  • HTTP methods: GET (safe, idempotent), POST (create), PUT (full replace, idempotent), PATCH (partial), DELETE (idempotent).
  • Status codes: 2xx success, 4xx client error, 5xx server error. Do not return 200 with an error body.
  • Pagination: cursor-based for big sets (?after=opaqueToken); offset-based only for small, stable sets.
  • Idempotency: accept an Idempotency-Key header on POST so retries are safe.
  • Filtering / sorting: ?status=open&sort=-createdAt.
  • Errors: structured body — {code, message, requestId}.

GraphQL — when worth it

Useful when many clients (web, iOS, Android) need different field subsets from the same data graph. Cost: query complexity, N+1 problems (mitigate with DataLoader), caching is harder than REST.

14. Microservices — Patterns & Anti-Patterns

Patterns to mention

PatternPurposeOne-liner
API GatewaySingle entry; auth, rate limit, routing.Don't let clients fan out to 20 services.
BFF (Backend for Frontend)Per-client gateway.Web BFF and Mobile BFF have different aggregation needs.
Service DiscoveryFind healthy instance of a service.Consul, Eureka, AWS Cloud Map. DNS + health checks usually enough.
Circuit BreakerFail fast when downstream is down.Hystrix-style: closed → open → half-open.
BulkheadIsolate resource pools per dependency.Slow service A doesn't drain all threads from caller.
Retry + Backoff + JitterSurvive transient errors.Exponential backoff with full jitter — never lockstep.
Sidecar / Service MeshMove cross-cutting concerns out of app.Envoy, Istio, App Mesh handle TLS, retries, metrics.
SagaMulti-service transactions.Choreography (events) or orchestration (central coordinator).

Anti-patterns

  • Distributed monolith — services that must deploy together.
  • Shared database — two services writing the same table; coupling at the data layer.
  • Chatty RPC — N+1 calls per request; batch or cache.
  • Synchronous chains — A → B → C → D; one slow service kills the whole chain. Add async / events where you can.

15. Rate Limiting & Idempotency

AlgorithmIdeaPros / Cons
Token BucketRefill at fixed rate; consume per request.+ Bursty OK. − Slightly bursty even when you don't want it.
Leaky BucketFixed-rate drain queue.+ Smooth output. − Adds latency.
Fixed WindowCounter per minute / second.+ Simple. − Edge bursts at window boundary (2× limit).
Sliding Window LogTimestamps in last window.+ Exact. − O(N) memory per user.
Sliding Window CounterWeighted blend of two fixed windows.+ O(1) memory, near-exact. — interview favorite.

Distributed rate limiter — Redis recipe

-- INCR + EXPIRE atomically; reject if over limit
local count = redis.call('INCR', KEYS[1])
if count == 1 then redis.call('EXPIRE', KEYS[1], ARGV[1]) end
if count > tonumber(ARGV[2]) then return 0 end
return 1

Idempotency

  • Client sends Idempotency-Key: <uuid> on each POST.
  • Server stores key → response in Redis with TTL (e.g., 24h).
  • On retry with same key + same body, return the stored response. Different body → 409.
  • Stripe and AWS SDKs do exactly this.

16. Search Systems

Pipeline

[Source DB] -> [CDC / Outbox] -> [Indexer] -> [Inverted Index Shards] -> [Query Service] -> [Ranker] ↑ [Cache, suggester]
  • Tokenization — break text into terms (language-aware).
  • Normalization — lowercase, stemming, synonyms.
  • Inverted index — term → posting list of doc IDs (with positions, term frequency).
  • Scoring — BM25 / TF-IDF, then a learned ranker (LTR) on top features.
  • Sharding — by doc ID (scatter-gather) or by term (partitioned).
  • Near-real-time — use a write-ahead log + segment refresh interval (Elasticsearch's 1s default).

17. Observability — Logs, Metrics, Traces

PillarBest forTooling
Metrics"Is anything wrong?" — aggregate, low-cardinality.Prometheus, CloudWatch, Datadog. RED/USE method.
Logs"What happened with this request?"CloudWatch Logs, ELK, Splunk. Structured JSON, correlation IDs.
Traces"Where did latency go?"X-Ray, Jaeger, OpenTelemetry. Span per service hop.

Golden signals (Google SRE)

  • Latency — p50, p99, p99.9 of successful requests (separate from errors).
  • Traffic — requests per second.
  • Errors — error rate (4xx vs 5xx).
  • Saturation — how full the system is (CPU, queue depth, connection pool).
Always answer "how do you debug a production issue?" with: "metrics tell me something is wrong, traces tell me where, logs tell me why."

18. Security in HLD

  • AuthN — OAuth 2 + OIDC for users; mTLS or signed JWT for services.
  • AuthZ — RBAC for simple, ABAC / policy engine (OPA, Cedar) for complex.
  • Encryption in transit — TLS 1.2+ everywhere, including service-to-service.
  • Encryption at rest — KMS-managed keys; envelope encryption for blob storage.
  • Secrets — Secrets Manager / Vault, never env files, never in git.
  • Input validation — schema-validate at the edge; never trust the client.
  • Rate limiting + WAF — at the gateway / CDN, not just app.
  • Tenant isolation — separate data per tenant (DB schema, KMS key per tenant for high-trust).

P1. URL Shortener (TinyURL / bit.ly) — the canonical warm-up

Step 1 — Requirements

  • FR: shorten a URL → return a short code; redirect short code → original URL; analytics on click counts; optional custom alias and expiration.
  • NFR: read-heavy (~100:1 reads:writes); p99 redirect < 50 ms; durable; high availability.

Step 2 — Capacity

  • 500M new URLs / month → ~200 writes/sec.
  • 100:1 read ratio → ~20K reads/sec; peak 5×.
  • Storage: 500B / row × 500M / month × 12 = ~3 TB/year.
  • Short code length: 6 chars × base62 = 56 billion codes — plenty.

Step 3 — High-Level Diagram

[Client] → [CDN] → [API Gateway] → [Write Service] → [DynamoDB / Mongo (long↔short)] ↓ ↑ [Counter / KGS] │ ↓ │ [Analytics Q] → [Kinesis] → [Click DB] [Client GET /xyz] → [CDN] → [Read Service / Redis cache] ─────────────┘

Step 4 — Key code generation (KGS) — the interesting part

ApproachHash of URL (MD5 → base62 → take 7 chars)Pre-generated KGS (key generation service)
HowCompute hash; check collision; retry.A service pre-generates billions of keys offline; hands one out per request.
ConcurrencyCollisions on duplicate URLs.No collisions — each key issued once.
Hot pathHash compute on every shorten.O(1) lookup of next free key.
VerdictSimple; fine for low scale.What real systems do.

Step 5 — Read path

  1. Edge cache (CloudFront) → cache short→long with TTL = expiry-or-7days.
  2. Cache miss → Redis lookup.
  3. Cache miss → DynamoDB GetItem on short code (PK).
  4. Return 301 (permanent) or 302 (so analytics still capture each hit).

Step 6 — Trade-offs to mention

  • 301 vs 302 — 301 caches in browser → fewer analytics; 302 hits the server every time.
  • Custom alias collisions — handle with conditional write (DynamoDB attribute_not_exists).
  • Click analytics async via Kinesis to avoid slowing redirects.

P2. Twitter / News Feed

Requirements

  • Post a tweet (text, images), follow users, see a timeline of tweets from people you follow.

P3. WhatsApp / 1:1 + Group Chat

Requirements

  • Send / receive messages, delivery + read receipts, online presence, group chats up to 256, optional E2E encryption.

Connection layer

  • Persistent WebSocket per online client. Long-lived TCP. ~100M concurrent connections globally.
  • Connection servers are stateless about routing: a session table (Redis) maps userId → connectionServerId.
  • Send: clientA → connServer1 → lookup B → forward to connServer2 → clientB.

Receipts & presence

  • Sent / Delivered / Read are separate ack events flowing back through the same channel.
  • Presence is high-write, low-value; store in Redis with TTL refreshed by heartbeat. Don't put it in your durable DB.

Group fan-out

Server-side fan-out: for a 256-member group, the message is replicated to 256 inboxes. Cap group size to keep this bounded.

E2E encryption note: Signal protocol — server only routes ciphertext. Server cannot do server-side search; clients search locally.

P6. S3-Like Object Storage

Requirements

  • PUT / GET / DELETE objects (key → blob), buckets, versioning, multi-part upload, 11×9 durability.

Architecture

[Client] → [API LB] → [Front-End API] → [Metadata Service: bucket/key → object_id, versions] ↓ [Coordinator] → [Storage Nodes (3-way replicated, erasure-coded)] ↓ [GC / Compaction / Repair]

Key design points

  • Metadata vs Data split. Metadata = small, transactional, sharded by bucket (Spanner / Aurora / DynamoDB). Data = immutable blobs on storage nodes.
  • Erasure coding (e.g., Reed-Solomon 10+4) — store across 14 nodes, tolerate 4 losses; ~1.4× storage overhead vs 3× for pure replication.
  • Multi-part upload — client splits, each part uploaded independently; metadata stitches them on CompleteMultipartUpload.
  • Eventual consistency for list, strong for read-after-write (modern S3 is read-after-write strong).
  • Lifecycle policies — async tier mover.
  • Hot keys — randomize key prefix to spread across partitions.

Stampede protection

  • Per-key in-process lock — only one thread fetches from origin; others wait on the future.
  • "Stale-while-revalidate" — serve slightly stale value while refreshing in background.
  • Probabilistic early refresh — refresh slightly before TTL with probability that grows as TTL approaches.

P8. Web Crawler (Googlebot-style)

Goals

  • Crawl the web politely (respect robots.txt, rate-limit per host).
  • Avoid duplicates; discover new pages; refresh frequently changing pages more often.

Architecture

[Seed URLs] → [URL Frontier (priority queues)] ↓ [Fetcher pool] → [DNS cache] → [HTTP client] ↓ [Parser] → [Content Store (S3, dedup by content hash)] ↓ [URL extractor] → [URL filter / dedup (Bloom filter + DB)] ↓ [URL Frontier] ← (loop)

Key tricks

  • Politeness: per-host queue + min-delay-between-requests; one fetcher per host at a time.
  • Dedup at scale: Bloom filter (memory) for fast "seen?" check + persistent DB for the truth.
  • Content dedup: SHA-256 of normalized HTML; 30% of the web is duplicates.
  • Refresh policy: change-rate estimation per page; crawl high-change pages more often.
  • Trap detection: bound crawl depth, URL length, repeating patterns (calendar pages).

P9. Distributed Rate Limiter

Where does it live?

  • At the API gateway — cheapest, blocks early.
  • At each service — defense in depth; protects against authenticated misuse.

Distributed challenge

Counters must be shared across N gateway nodes. Options:

OptionHowTrade-off
Centralized RedisINCR key + EXPIRE via Lua script.Network hop per request. ~1 ms p99.
Local + syncEach node keeps a local counter; periodically syncs.Faster but counters drift.
Token-leasingNode leases N tokens from a coordinator.Best of both; modest complexity.

Sliding-window-counter algorithm in Redis

// pseudo-code
now    = nowSeconds()
window = 60
key    = userId + ":" + (now / window)
prev   = userId + ":" + (now / window - 1)
prevC  = redis.get(prev) or 0
currC  = redis.incr(key); redis.expire(key, 2*window)
weight = (window - now % window) / window
estimate = prevC * weight + currC
allow  = estimate <= LIMIT

P10. Notification System (Email / SMS / Push)

P11. Top-K / Trending (e.g., trending hashtags, top-selling products)

Approach 1 — Lambda (offline + online)

  • Streams of events go to Kafka.
  • Spark / Flink job computes per-minute counts → writes to Cassandra.
  • Top-K query: scan last N minutes, sum, sort. Acceptable for ~1000 candidate keys.

Approach 2 — Count-Min Sketch + Min-Heap

For high-cardinality streams (millions of candidate keys):

  • Count-Min Sketch in memory: O(1) increment, O(1) approximate count, sub-linear memory.
  • Min-Heap of size K tracks the current top K.
  • Multiple sketches per time window; merge for "top-K in last hour".
// Approximate top-K with bounded memory
on event(key) {
  cms.add(key);                       // O(1)
  est = cms.estimate(key);
  if (heap.size < K) heap.add({key, est});
  else if (est > heap.peek().est) {
    heap.replaceTop({key, est});
  }
}

P12. Amazon Cart & Checkout Amazon-specific

Why this is interesting

Cart is read-heavy (every page render shows item count); checkout is write-heavy and money-touching. They have very different requirements.

Cart Service

  • Storage: DynamoDB, partition key = customer_id. Single-digit-ms reads at any scale.
  • Cache: Redis with the cart JSON; invalidate on write.
  • Persistence: guest carts in cookie + Redis (TTL 30d); signed-in carts merge on login.
  • Stock check at cart-add is "best-effort" — final reservation happens at checkout. Avoids holding inventory for browsers.

Checkout Service

  1. Validate cart — re-fetch latest prices, check availability per FC (fulfillment center).
  2. Reserve inventory — conditional update: SET available = available - qty WHERE available >= qty. Use Inventory service, not cart's view.
  3. Calculate totals — taxes, promotions, shipping options.
  4. Place order — write Order row + Outbox event in one DB transaction.
  5. Charge — call payment service with idempotency key. On failure: compensate (release inventory).
  6. Emit OrderPlaced — drives fulfillment, email, analytics, fraud screening.

Sequence of writes — all idempotent

// each step has idempotencyKey = orderId-stepName
reserveInventory(orderId, items)         // PutIf
chargePayment(orderId, total)            // idempotencyKey = orderId
createOrderRow(orderId, ...)             // PutIf attribute_not_exists
publishOrderPlaced(orderId)              // outbox -→ Kafka
LP signal: "Customer Obsession" → never charge a customer for an item we can't fulfill. Inventory reserve must succeed before payment is authorized; payment failure must release inventory via a saga.

P13. Amazon Inventory Service Amazon-specific

Why this is hard

Same SKU may have stock in 100+ FCs. Reads are global ("can I ship 1 unit of SKU X to ZIP 560001?") and writes are local (FC scans, returns, restocks). Strong consistency required for "available count" — overselling is a lawsuit.

Architecture

[FC scanners / Receiving] -→ [Inventory Service per FC] ↓ [DynamoDB per-FC table] ↓ [Order placement] [DynamoDB Streams] ↓ ↓ [Inventory API] [Aggregation Service] ←-→ [Reservation Service] ↓ ↑ [Global Aggregate Table] │ ↓ │ └──── read by API ─────────────┘

Reservation flow (the key piece)

  • Atomic reserve via conditional write: UPDATE … SET available = available - qty WHERE available >= qty. DynamoDB does this with a condition expression; failure means stockout.
  • TTL on reservation — if checkout doesn't complete in 15 min, auto-release.
  • Per-FC pessimistic; cross-FC optimistic — fan out attempts to FCs ranked by ETA; first that confirms wins.
  • Hot SKU (Prime Day Echo Dot) → shard the SKU into N "buckets" of inventory; reserve from random bucket to spread contention.

P14. Amazon Order Management (full lifecycle) Amazon-specific

Scope

Track an order from placement through delivery / return / refund. State changes over days; many services participate.

Architecture

[Checkout] -→ OrderPlaced -→ [Order Service (DynamoDB, PK orderId)] -→ [DynamoDB Streams] ↓ ↓ [State Machine — Step Functions] [Search index, BI] ↓ ┌─── ┌── Fulfillment ──→ FC pick/pack/ship event ─→ Order: SHIPPED │ │ ↓ │ └── Shipping carrier webhook ──→ Order: DELIVERED │ └── Cancellation / Return / Refund flows (sagas)

State machine

PLACED → PAID → PROCESSING → PACKED → SHIPPED → DELIVERED
   ↘                                           ↘
   CANCELLED                                  RETURN_REQUESTED → RETURNED → REFUNDED

Why an event-sourced log + projection works well here

  • Append-only event log (Kafka or DynamoDB Streams) is the source of truth for order history.
  • Order Service projects events into the current-state row.
  • Other services (search, analytics, customer-care UI) build their own projections from the same log → no shared DB.

Failure handling

  • Idempotent updates — every state transition keyed by event ID.
  • Compensation — refund failure triggers a manual queue; never silently retry forever.
  • Customer-facing read consistency — after the customer hits "cancel" we route their next read to the leader to avoid showing the old state.
Closing LP: "Ownership" — Order Service owns the order's truth. Other services own derived projections. Adding a new consumer (e.g., loyalty points) is a new projection, not a code change in Order Service.

T. Tricky HLD Questions Bank — with hints (auto-revealed in print)

T1. "How would you make a write succeed if the leader is down?"
Reveal hint
You can't, in a CP system — by design. Either fail the write (CP) or accept the write on a replica and merge later (AP, conflict resolution required). What you can do: detect leader failure quickly (heartbeats), elect a new one (Raft), and resume — usually within seconds. Mention RTO / RPO numbers.
T2. "Pick: DynamoDB or Aurora for an order ledger?"
Reveal hint
Aurora wins if you need joins, ad-hoc analytics, or multi-row ACID transactions (typical for an OMS). DynamoDB wins for predictable per-key access at huge scale (carts, sessions, IoT). For Amazon's actual order ledger: relational makes sense for the financial truth; DynamoDB shines for the fast read views.
T3. "What's wrong with using now() % N for sharding?"
Reveal hint
Time-based keys send all current writes to one shard — hot shard. For time-series, use (entityId, time) composite key partitioned by entityId. Or bucket by floor(time / interval) and prefix with a hash to spread.
T4. "Two services need the same data. Should they share the database?"
Reveal hint
No. Shared DB = tightest possible coupling; one's index choice affects the other. Either consolidate the services (if they really are one bounded context) or expose an API / replicate via CDC into a read store the second service owns.
T5. "Your service's p99 latency doubles every Black Friday. What design changes?"
Reveal hint
Pre-warm caches, raise TTLs for stable data, scale stateless tier horizontally before the event, throttle non-critical features (recommendations, reviews) before customer-critical ones, isolate critical paths (cart / checkout) on separate fleets, replicate hot keys, queue writes that don't need to be sync (analytics, notifications). Most importantly — load test at 2× actual peak.
T6. "Why use Kafka over a database table as a queue?"
Reveal hint
DB-as-queue: every consumer hits the same row → contention on the "claim" update. Kafka: append-only log, consumer offsets are independent, throughput scales with partitions. DB-as-queue is OK for low-volume task queues; for ≥10K msg/sec or replay needs, Kafka.
T7. "How do you ensure exactly-once processing?"
Reveal hint
You don't, strictly. You make processing idempotent + use deduplication keys: producer-side (Kafka idempotent producer with PIDs), consumer-side (dedup key in a TTL store, transactional offset commit with output write). Result is "effectively once."
T8. "Why not run everything on Lambda?"
Reveal hint
Cold starts (10s–1s) for low-traffic functions. Concurrency limits per account. Long-running connections (WebSocket, gRPC streaming, DB pools) don't fit. Cost crosses over containers above a steady ~50% utilization.
T9. "Strong vs eventual consistency — which for a like counter?"
Reveal hint
Eventual is fine — users tolerate "1.2M likes" lagging by seconds. Use sharded counters (e.g., 100 counters per post; sum on read). Strong consistency would serialize all writers on one row → throughput ceiling.
T10. "How do you keep cache and DB in sync?"
Reveal hint
Cache-aside + delete-on-write. On write: update DB, then DELETE cache key (don't UPDATE — race). Reader on next miss repopulates. For absolute correctness, use CDC: DB → Kafka → cache invalidator. Avoid write-through across multiple writers.
T11. "Estimate QPS for a service before designing."
Reveal hint
DAU × actions/day / 86400 = avg QPS. Multiply by 3–5 for peak. Multiply by 2 for safety. Show the math out loud — interviewers care about the framework more than the number.
T12. "Read-heavy vs write-heavy — what changes?"
Reveal hint
Read-heavy: cache aggressively, replicate, denormalize; pick B-tree storage; CDN for static. Write-heavy: pick LSM-tree storage (Cassandra, RocksDB); shard early; batch / async writes; no read replicas help write throughput.
T13. "Why not put a database behind a load balancer?"
Reveal hint
Stateful sessions (transactions, prepared statements). Connection pools are sized per app instance. The DB does its own load balancing via leaders / replicas; a TCP LB in front confuses failover. Use the DB driver's built-in routing (e.g., Aurora cluster endpoint).
T14. "Designing pagination for a feed — offset or cursor?"
Reveal hint
Cursor. Offset performance degrades with depth (skip-N), and offset can return duplicates / gaps when the underlying list mutates. Cursor = "give me items after this opaque token" — stable under inserts, O(1) per page.
T15. "Two-phase commit across services — should you?"
Reveal hint
Almost never. 2PC blocks if the coordinator dies between phases. For service-to-service: use a saga (sequence of local transactions + compensations) with eventual consistency. Banks, airlines, Amazon checkout — all sagas, not 2PC.
T16. "How do you scale WebSockets to 100M concurrent connections?"
Reveal hint
Stateless connection servers (~100K connections each → 1000 servers). Session table (Redis / DynamoDB) maps user → server. Horizontal scaling via consistent hashing on user ID. Heartbeat every 30s; reconnect on drop. Use sticky LB only for the initial handshake; routing is done in app via the session table.
T17. "What's wrong with synchronous calls A → B → C → D?"
Reveal hint
Latency adds; one slow link breaks the chain; failure modes multiply (anything along the path). Mitigations: caching, async events for non-essentials, circuit breakers, timeouts decreasing along the chain (A 1000ms, B 800ms, C 600ms…), bulkheads.
T18. "How do you do schema migration in a live system?"
Reveal hint
Expand-migrate-contract: (1) add new column / table, deploy code that reads old + writes both. (2) Backfill async. (3) Switch reads to new. (4) Remove old. Never combine schema change + code change in one deploy. For Cassandra/Dynamo, create new table + dual-write + migrate.
T19. "Hot partition — how do you spread it?"
Reveal hint
Add a random suffix to the key (e.g., celebId#0..9) and write to one bucket; on read, fan out to all buckets and aggregate. Or move that one entity to a dedicated dataset. DynamoDB calls this "write sharding."
T20. "When would you choose CP over AP?"
Reveal hint
CP for systems where stale reads cost money or violate invariants — payments, inventory deduction, voting / consensus, distributed locks. AP for everything where seconds-old data is fine — feeds, search, recommendations, analytics dashboards.
T21. "Designing for multiple regions — what changes?"
Reveal hint
Latency budget — clients should hit nearest region. Data partitioning — pick "data has a home region" (GDPR-style) or "global tables" (DynamoDB / Spanner) accepting last-write-wins or vector-clock conflicts. Cross-region replication delay 100ms+ → can't do strong-consistency cross-region. Failover plan: DNS + health checks (Route 53) + warm standby.
T22. "How do you load-test a new service?"
Reveal hint
(1) Define SLOs (p99 latency, error rate). (2) Replay realistic traffic shape, not uniform — diurnal + bursts. (3) Ramp to 2× expected peak. (4) Shadow real production traffic if possible. (5) Find the breaking point intentionally (chaos engineering). (6) Verify dashboards alert correctly during the test.
T23. "Why ‘delete on write' instead of ‘update on write' for cache?"
Reveal hint
Update can lose to a concurrent write that completes earlier — final cache value reflects the older DB state. Delete forces the next read to repopulate from DB → guaranteed to read the latest. Slightly higher miss rate is the cost.
T24. "Designing the 'this user already followed' check at scale."
Reveal hint
DB lookup works to ~10K QPS. Above that, Bloom filter in front: "definitely not followed" → return false instantly; "might be" → DB confirms. False positive rate tunable (typically 1%). Refresh sketch periodically.
T25. "Open question — what would you do differently if we 10×'d traffic next week?"
Reveal hint
Be specific: "I'd add a layer of CDN caching in front of the read API, scale the stateless tier 5× (it's already fronted by an LB), shard the hot Postgres table by user_id, replace the synchronous notification call with an SQS handoff, and pre-warm the cache from the last 7 days of access logs." Show that you've thought through each component.
