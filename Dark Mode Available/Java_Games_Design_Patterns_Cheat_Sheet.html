Java Games Design Patterns 15 patterns from the book, with hints, tips, tricks and a quiz

Based on Java Games Design Patterns: Learning Programming Design Patterns through Games (Yang Hu). The book teaches each pattern with a small plane-shooter game. This sheet keeps the game examples, adds plain-word explanations, short Java code, "wrong vs right" tables, memory tricks and a self-test. Made for Java / Spring Boot interview prep.

2The three families (your mental map)

Do not learn 15 separate things. Learn 3 families, then place each pattern inside one.

CCreational — "Who makes the object, and how?"

  • Singleton — how many? (one)
  • Factory — which class? (factory picks)
  • Builder — how to assemble? (step by step)

Smell to look for: new ConcreteThing(...) spread all over the code.

SStructural — "How do objects fit together?"

  • Flyweight — share heavy parts
  • Bridge — split two axes
  • Decorator — wrap to add
  • Composite — build a tree

Smell to look for: class names that glue two ideas together, like BluePlaneRedBullet.

BBehavioral — "How do objects act and talk?"

  • Template Method, Strategy, State — vary behavior
  • Command — action as object
  • Iterator — walk a collection
  • Chain, Observer, Mediator — who talks to whom

Smell to look for: long if / else or switch on a type or a state.

TopicWrong way to learnRight way to learn
Order of studyMemorize 15 definitions in book orderLearn the 3 families first, then one pattern at a time inside each family
UMLDraw every class diagram by heartKnow the 2–3 key classes and the one line that joins them (e.g. "Plane holds a Bullet")
ExamplesOnly the game exampleGame example + one backend example (section 10) so you can answer in a Spring interview
❓ Quick check
Which family does Template Method belong to, and why is it not Structural even though it uses inheritance?
Reveal hintBehavioral. It is about what the algorithm does and which steps vary, not about how objects are arranged. Inheritance is just the tool it uses.

4CCreational patterns: Singleton, Factory, Builder

Factory chooses. Builder assembles. Singleton restricts.

4.1 Singleton — "there can be only one"

Intent: make sure a class has one object only, and give one global way to reach it.

Book example: ImageUtil with a private constructor and a static access point. Every part of the game loads plane images through it.

How it works: the constructor is private, so nobody outside can write new ImageUtil(). A static method hands out the single object.

Use when: there truly is one shared thing (a config, a cache, a connection pool).

Benefit: one place to control the shared resource.

Caution: it is hidden global state. It makes tests hard and hides who depends on what. Do not use it just because "it is handy to reach".

public final class ImageUtil {
    // 1. the one and only object, made once
    private static final ImageUtil INSTANCE = new ImageUtil();

    // 2. nobody else can call new
    private ImageUtil() {}

    // 3. the global door
    public static ImageUtil get() { return INSTANCE; }

    public BufferedImage loadImage(String path) {
        return ImageIO.read(getClass().getResource(path));
    }
}
// use:  ImageUtil.get().loadImage("/img/blue_plane.png");
💡 Tips
• The eager static final form above is thread-safe for free; the JVM loads the class once.
• Need lazy creation? Use an enum with one constant, or the "holder class" idiom. Avoid the hand-written double-checked lock unless you also write volatile.
• In Spring you almost never write a Singleton by hand: every @Component bean is a singleton by scope. Say this in interviews — it shows you know the framework does it for you.
Trap: a Singleton that holds mutable state (counters, lists) becomes a shared bug across threads. Keep it stateless or guard the state.

4.2 Factory — "the factory chooses the class"

Intent: move object creation into one place; the caller asks for a type by name or by rule and gets back the right concrete class.

Book example: SpriteFactory returns BluePlane or RedPlane based on what the player picked.

Key classes: SpriteFactory, Sprite (parent), BluePlane, RedPlane.

Use when: the concrete type depends on config, user choice or run-time data.

Benefit: the caller only knows the parent type Sprite. Add a new plane → change the factory, not every caller.

Caution: a factory with 40 case branches is itself a smell. Use a Map of suppliers or let Spring pick the bean.

public class SpriteFactory {
    public static Sprite create(String kind) {
        switch (kind) {
            case "blue": return new BluePlane();
            case "red":  return new RedPlane();
            default: throw new IllegalArgumentException(kind);
        }
    }
}
// caller never writes "new BluePlane()":
Sprite player = SpriteFactory.create(choice);
player.draw(g);

// cleaner for many types: a map of suppliers
Map<String, Supplier<Sprite>> reg = Map.of(
    "blue", BluePlane::new, "red", RedPlane::new);
💡 Tips
• The book uses a simple factory (one static method). Interviewers may also ask about Factory Method (a subclass overrides the creating method) and Abstract Factory (a factory that makes a whole family of related objects). Know the three names.
• Spring tie-in: BeanFactory / ApplicationContext is a factory; @Bean methods are factory methods.

4.3 Builder — "set, set, set, build"

Intent: split the steps of building a complex object from the object itself; collect parts one by one, then produce the final object.

Book example: a builder sets the title and the buttons of a SelectDialog, then creates it.

Key classes: Builder, SelectDialog, Button.

Use when: a constructor would need many parameters, many of them optional, or when the same object has several valid set-ups.

Benefit: readable, step-by-step construction; the result can be immutable.

Caution: extra class for a simple object. If the object has 2 fields, just use a constructor.

public class SelectDialog {
    private final String title;
    private final List<Button> buttons;

    private SelectDialog(Builder b) {
        this.title = b.title;  this.buttons = List.copyOf(b.buttons);
    }

    public static class Builder {
        private String title = "Select";
        private final List<Button> buttons = new ArrayList<>();
        public Builder title(String t) { title = t; return this; }
        public Builder button(Button b) { buttons.add(b); return this; }
        public SelectDialog build() { return new SelectDialog(this); }
    }
}
SelectDialog d = new SelectDialog.Builder()
        .title("Pick your plane")
        .button(new BluePlaneButton())
        .button(new RedPlaneButton())
        .build();
💡 Tips
• Returning this from each setter gives the fluent chain. That is the part interviewers want to see.
• Real-world Java builders: StringBuilder, Stream.Builder, HttpRequest.newBuilder(), Lombok's @Builder, UriComponentsBuilder in Spring.
• Validate inside build() (for example "at least one button"). That is the one place where the whole object is known.

❓ Question
A class needs 9 constructor arguments, 6 of them optional. Factory or Builder?
Reveal hintBuilder. Factory is about which class; Builder is about how many settings. Optional arguments are the Builder's home ground. Bonus: a Factory can use a Builder inside.
❓ Question
Why do people say Singleton is an "anti-pattern" in Spring code?
Reveal hintSpring already gives singleton scope to beans and injects them, so a hand-made getInstance() hides the dependency, blocks mocking in tests, and couples callers to the class. Let the container own the one instance.

5SStructural patterns: Flyweight, Bridge, Decorator, Composite

Flyweight shares. Bridge splits. Decorator wraps. Composite nests.

5.1 Flyweight — "load once, share many"

Intent: many small objects share one copy of heavy data instead of each holding its own.

Book example: ImageCache keeps a Map<String, BufferedImage>. Fifty bullets on screen all point to the same bullet image.

How it works: ask the cache by key; if the image is there, reuse it; if not, load it once and store it.

Use when: many objects would copy the same large, unchanging data.

Benefit: far less memory and load time.

Caution: keep shared state (the image) apart from per-object state (x, y, speed). Never let one bullet change the shared image.

public class ImageCache {
    private final Map<String, BufferedImage> cache = new HashMap<>();

    public BufferedImage get(String key) {
        // load only the first time; share after that
        return cache.computeIfAbsent(key,
                k -> ImageUtil.get().loadImage("/img/" + k + ".png"));
    }
}
// each bullet keeps only its own x, y; the picture is shared
class Bullet {
    int x, y;                         // per-object (extrinsic)
    BufferedImage img = cache.get("bullet"); // shared (intrinsic)
}
💡 Tips
• Interview words: intrinsic = shared, never changes; extrinsic = per object, passed in. Say these two words and you have answered the Flyweight question.
• Java does Flyweight for you in Integer.valueOf(-128..127), String interning, and Boolean.TRUE.
• Flyweight and Singleton both reduce objects, but Flyweight has many shared objects (one per key); Singleton has exactly one.

5.2 Bridge — "two axes, one link"

Intent: keep an abstraction (Plane) and its implementation (Bullet) in two separate class trees, joined by a field, so each tree grows on its own.

Book example: BluePlane can fire BlueBullet or RedBullet; so can RedPlane. Two planes × two bullets, but only 4 classes, not 4 combo classes.

Use when: you spot two independent reasons to change.

Benefit: stops subclass explosion (N × M classes becomes N + M).

Caution: more layers than a simple case needs.

Without Bridge (4 glued classes):
  BluePlaneBlueBullet   BluePlaneRedBullet
  RedPlaneBlueBullet    RedPlaneRedBullet

With Bridge (2 + 2, joined by a field):
  Plane ──────── has-a ──────── Bullet
   │                              │
   ├─ BluePlane                   ├─ BlueBullet
   └─ RedPlane                    └─ RedBullet
abstract class Plane {
    protected Bullet bullet;          // the bridge
    void load(Bullet b) { bullet = b; }
    void fire() { bullet.shoot(x, y); }
}
interface Bullet { void shoot(int x, int y); }
Plane p = new RedPlane();  p.load(new BlueBullet());
🎯 Trick — spot a Bridge by the class name
If you ever want to name a class SomethingWithSomethingElse, stop. That "With" is a Bridge waiting to happen. Make two trees and hold a reference.

5.3 Decorator — "wrap to add"

Intent: add new behavior to one object at run time by wrapping it in another object with the same interface.

Book example: a plane is wrapped by PlaneProps; selected bullets are wrapped to get extra movement.

Key classes: Sprite (shared interface), the real plane, and the wrapper(s) that also implement Sprite and hold a Sprite inside.

Use when: you need many combos of optional features.

Benefit: no subclass for every combo; stack wrappers in any order.

Caution: five nested wrappers are hard to debug; identity checks (==) break because the wrapper is a different object.

Inheritance explodes:
  BluePlane+Shield   BluePlane+Speed   BluePlane+Weapon
  BluePlane+Shield+Speed   BluePlane+Shield+Weapon ...

Decorator stacks:
  BluePlane → ShieldDecorator → SpeedDecorator → WeaponDecorator
abstract class SpriteDecorator extends Sprite {
    protected final Sprite inner;        // the wrapped one
    SpriteDecorator(Sprite s) { inner = s; }
    public void draw(Graphics g) { inner.draw(g); }
    public void move() { inner.move(); }
}
class ShieldDecorator extends SpriteDecorator {
    ShieldDecorator(Sprite s) { super(s); }
    @Override public void draw(Graphics g) {
        super.draw(g);
        g.drawOval(x - 4, y - 4, w + 8, h + 8);   // the extra
    }
}
Sprite p = new SpeedDecorator(new ShieldDecorator(new BluePlane()));
Inheritance changes what a class is. Decoration adds what an object can do.
💡 Tips
• Java I/O is the classic: new BufferedReader(new InputStreamReader(new FileInputStream(f))). Each layer adds one ability.
• Spring: @Transactional, @Cacheable and HandlerInterceptor wrap your bean with a proxy — that is Decorator at framework scale.
• Decorator keeps the same interface as the thing it wraps. If the interface changes, it is an Adapter, not a Decorator.

5.4 Composite — "leaf and branch look alike"

Intent: build a tree where a single item and a group of items share one interface, so the caller treats them the same.

Book example: a Menu holds MenuItems and sub-menus. Drawing the menu draws every child, no matter how deep.

Key classes: component interface, MenuItem (leaf), Menu (composite, has a list of components).

Use when: data is a tree: menus, scene graphs, folders, org charts, categories.

Benefit: one draw() call at the root does the whole tree; no if (isGroup) checks.

Caution: a too-wide component interface forces leaves to carry methods like add() that make no sense for them.

interface MenuComponent { void draw(Graphics g); }

class MenuItem implements MenuComponent {        // leaf
    public void draw(Graphics g) { g.drawString(label, x, y); }
}
class Menu implements MenuComponent {            // branch
    private final List<MenuComponent> children = new ArrayList<>();
    void add(MenuComponent c) { children.add(c); }
    public void draw(Graphics g) {
        for (MenuComponent c : children) c.draw(g);  // same call, leaf or menu
    }
}
💡 Tip
Recursion is the engine of Composite. Whenever a method on the branch just loops and calls the same method on its children, you are looking at Composite. Swing's JComponent tree and the DOM are real examples.
❓ Question
Decorator and Composite both hold a reference to the same interface they implement. What is the difference?
Reveal hintDecorator holds one inner object and adds behavior around it. Composite holds many children and forwards the call to all of them. One = wrap; many = tree.
❓ Question
Bridge and Strategy both use "has-a" a field with an interface type. How do you tell them apart in an interview?
Reveal hintBridge is about structure: two class trees that both grow (Plane tree and Bullet tree), decided at design time. Strategy is about behavior: one algorithm slot that the caller swaps at run time. Bridge = two hierarchies; Strategy = one hierarchy of algorithms.

6BBehavioral patterns I: Template Method, Strategy, State, Command

Template fixes the recipe. Strategy swaps the brain. State changes with mood. Command boxes the action.

6.1 Template Method — "same recipe, your own steps"

Intent: the parent class writes the full algorithm once; it calls some steps that child classes fill in or override.

Book example: Sprite owns draw() and move(). BluePlane gets both for free and changes only what differs (its image, its speed).

Use when: several classes do "the same thing" with small differences in the middle.

Benefit: no copy-paste of the algorithm; the order of steps is fixed in one place.

Caution: it depends on inheritance. Deep trees get rigid, and a child cannot change the order of steps.

abstract class Sprite {
    protected int x, y;
    // the template: fixed order, calls the hooks
    public final void update(Graphics g) {
        move();
        if (isAlive()) draw(g);
    }
    protected void move() { y -= speed(); }          // default step
    protected void draw(Graphics g) { g.drawImage(image(), x, y, null); }
    protected boolean isAlive() { return y > -50; }
    protected abstract BufferedImage image();   // child must fill
    protected abstract int speed();
}
class BluePlane extends Sprite {
    protected BufferedImage image() { return cache.get("blue"); }
    protected int speed() { return 6; }
}
💡 Tips
• Make the template method final so children cannot break the order. Make the step methods protected.
• A step with a default body that children may override is called a hook. isAlive() above is a hook.
• Spring is full of this: JdbcTemplate, RestTemplate, AbstractController, WebSecurityConfigurerAdapter (old). The "Template" in the name is literal.

6.2 Strategy — "plug in a different brain"

Intent: put each algorithm in its own class behind one interface; the caller holds one and can swap it at run time.

Book example: BluePlane can load BlueBullet, RedBullet or MissileBullet. The plane does not care how the bullet flies.

Use when: the behavior must change without touching the object that uses it; big if / switch on a "type".

Benefit: run-time choice, no conditionals, easy to test each strategy alone.

Caution: ten tiny classes for ten trivial lines can be heavier than one switch. Use lambdas for simple ones.

interface ShootStrategy { void shoot(Plane p, List<Bullet> out); }

class SingleShot  implements ShootStrategy { /* one bullet */ }
class MissileShot implements ShootStrategy { /* homing */ }

class BluePlane extends Sprite {
    private ShootStrategy strategy = new SingleShot();
    void setStrategy(ShootStrategy s) { strategy = s; } // swap any time
    void fire(List<Bullet> out) { strategy.shoot(this, out); }
}
// power-up picked → plane.setStrategy(new MissileShot());
// tiny strategy as a lambda:
plane.setStrategy((p, out) -> out.add(new BlueBullet(p.x, p.y)));
💡 Tips
• The single most asked pattern in Java interviews. Have a backend story ready: payment type, discount rule, auth method, file parser.
• Spring trick: inject Map<String, PaymentStrategy> — Spring fills the map with every bean of that type, keyed by bean name. No factory needed.
• Comparator passed to sort() is Strategy in the JDK.

6.3 State — "what do I do in this state?"

Intent: one class per state; the object delegates to its current state object, and the state objects decide the next state.

Book example: the background / scrolling layer (TiledLayer) draws and moves differently depending on its current state.

Use when: behavior changes a lot with the object's lifecycle; if (state == A) ... else if (state == B) repeated in many methods.

Benefit: each state is explicit and small; adding a state = adding a class.

Caution: many states + many transitions = many classes. For simple cases an enum with methods is enough.

interface EnemyState { void update(Enemy e); }

class Idle implements EnemyState {
    public void update(Enemy e) {
        if (e.seesPlayer()) e.setState(new Chasing());   // state picks next state
    }
}
class Chasing implements EnemyState {
    public void update(Enemy e) {
        e.moveToward(e.player());
        if (e.inRange()) e.setState(new Attacking());
    }
}
class Enemy {
    private EnemyState state = new Idle();
    void setState(EnemyState s) { state = s; }
    void update() { state.update(this); }   // no if/else here
}
🎯 Trick — Strategy vs State in one breath
Same shape of code (interface + field + delegate). The difference is who changes the field. In Strategy the caller picks ("use missiles now"). In State the state itself moves to the next state ("I see the player, so I become Chasing"). Caller picks = Strategy. Self-driven = State.

6.4 Command — "the request is an object"

Intent: wrap an action in an object with one method (execute()). The sender just calls it; the object knows what to do.

Book example: each button has an ActionListener. Clicking BluePlaneButton runs its actionPerformed(); the button itself does not know what "select blue plane" means.

Use when: UI actions, undo / redo, job queues, keyboard remapping, anything you need to store, log or delay.

Benefit: sender and receiver are fully apart; commands can be queued, logged, undone.

Caution: lots of small command classes. Lambdas solve most of that in modern Java.

interface Command { void execute(); }

class SelectPlaneCommand implements Command {
    private final Game game; private final String kind;
    SelectPlaneCommand(Game g, String k) { game = g; kind = k; }
    public void execute() { game.setPlayer(SpriteFactory.create(kind)); }
}
// the button is the "invoker": it only knows execute()
blueButton.addActionListener(e -> cmd.execute());

// commands can wait in a queue, or be undone later
Deque<Command> history = new ArrayDeque<>();
history.push(cmd); cmd.execute();
💡 Tips
• Four roles to name in an interview: Command (the object), Receiver (who does the real work, Game), Invoker (who calls execute(), the button), Client (who wires them).
• Add undo() next to execute() and keep a stack — that is how editors do undo / redo.
• Runnable is the JDK's Command. A thread pool is an invoker for Runnables.
❓ Question
Both Strategy and Command hold "a piece of behavior" behind an interface. What is the difference?
Reveal hintStrategy answers "how do I do this one job?" — many ways to do the same job, the caller picks one. Command answers "what should happen?" — each command is a different job, and the point is to store / queue / undo it. Strategy = alternative algorithms; Command = packaged request.

7BBehavioral patterns II: Iterator, Chain of Responsibility, Observer, Mediator

Iterator walks. Chain passes it on. Observer broadcasts. Mediator sits in the middle.

7.1 Iterator — "hasNext / next"

Intent: give a way to walk through a collection one item at a time without showing how the collection is stored.

Book example: an Iterator / IteratorImpl over the bullet list; the game loop calls hasNext() and next() to draw and move every bullet.

Use when: callers need to loop but should not depend on ArrayList vs array vs tree.

Benefit: the collection can change its storage with no change to callers; several loops can run at once with their own cursors.

Caution: Java already gives Iterable / Iterator. Writing your own is rarely needed — know the idea, use the JDK's.

class BulletList implements Iterable<Bullet> {
    private final List<Bullet> items = new ArrayList<>();

    public Iterator<Bullet> iterator() {
        return new Iterator<>() {
            int i = 0;
            public boolean hasNext() { return i < items.size(); }
            public Bullet next() { return items.get(i++); }
        };
    }
}
// caller does not know it is an ArrayList:
for (Bullet b : bullets) { b.move(); b.draw(g); }
Trap: removing from a list while looping with for-each throws ConcurrentModificationException. Use iterator.remove() or removeIf() — this comes up when bullets leave the screen.

7.2 Chain of Responsibility — "pass it on"

Intent: link handlers in a line. A request enters at the front; each handler either deals with it or passes it to the next.

Book example: enemy spawning moves through stages — first 2 planes, then 4, then boss planes. Each stage is a handler; when its condition is met it acts, otherwise the next stage gets a turn.

Use when: several objects might handle a request and the sender should not know which; processing happens in steps.

Benefit: add, remove or reorder handlers without touching the sender.

Caution: a request may fall off the end with nobody handling it. Always decide what happens at the tail.

abstract class SpawnStage {
    private SpawnStage next;
    SpawnStage then(SpawnStage n) { next = n; return n; }

    void handle(GameContext ctx) {
        if (canHandle(ctx)) spawn(ctx);
        else if (next != null) next.handle(ctx);     // pass it on
    }
    abstract boolean canHandle(GameContext c);
    abstract void spawn(GameContext c);
}
class TwoPlanes  extends SpawnStage { /* score < 100 */ }
class FourPlanes extends SpawnStage { /* score < 300 */ }
class Boss       extends SpawnStage { /* otherwise  */ }

SpawnStage chain = new TwoPlanes();
chain.then(new FourPlanes()).then(new Boss());
chain.handle(ctx);
💡 Tips
• Two flavors: stop at first handler (classic) or every handler runs (pipeline / filter chain). Servlet Filter, Spring Security's filter chain, and HandlerInterceptor are the pipeline flavor.
• Interview line: "Chain is a Linked List of handlers where each node decides to act or forward."
• Keep handlers stateless so the chain can be shared across threads.

7.3 Observer — "subscribe and get told"

Intent: one object (the subject) keeps a list of listeners and calls them all when something happens.

Book example: BluePlane is the subject. PlaneScore and PlaneLife are observers. Enemy destroyed → score goes up; collision → life goes down. The plane does not know what the observers do with the news.

Key classes: Observer, ObserverData, NotifyType, PlaneLife, PlaneScore.

Use when: one event, many reactions; you want to add a reaction without touching the source.

Benefit: loose coupling, easy to add listeners.

Caution: many listeners firing listeners makes the flow hard to trace; forgotten listeners cause memory leaks.

enum NotifyType { ENEMY_DOWN, HIT }
interface Observer { void onNotify(NotifyType t, ObserverData d); }

class BluePlane extends Sprite {
    private final List<Observer> observers = new ArrayList<>();
    void addObserver(Observer o) { observers.add(o); }
    void notifyAll(NotifyType t, ObserverData d) {
        for (Observer o : observers) o.onNotify(t, d);   // broadcast
    }
    void onEnemyDestroyed(Enemy e) { notifyAll(NotifyType.ENEMY_DOWN, new ObserverData(e.points)); }
}
class PlaneScore implements Observer {
    int score;
    public void onNotify(NotifyType t, ObserverData d) {
        if (t == NotifyType.ENEMY_DOWN) score += d.value;
    }
}
💡 Tips
• Spring: ApplicationEventPublisher.publishEvent() + @EventListener. Add @Async or @TransactionalEventListener to show depth.
• Push (send the data) vs pull (send "something changed", observer asks). The book pushes an ObserverData.
• Observer is the parent idea behind pub/sub, event buses, Kafka consumers and reactive streams.

7.4 Mediator — "talk to the hub"

Intent: objects stop talking to each other directly; they talk to one mediator, which decides who does what.

Book example: the game's Media / Bom (explosion) system. Plane, enemy and bullet report to the mediator; it plays the sound, shows the explosion and updates the right objects.

Use when: many objects have tangled many-to-many links.

Benefit: N×N links become N links to one hub.

Caution: the hub can swell into a "god object" that knows everything. Split it when it grows.

class GameMediator {
    private final Sound sound; private final List<Explosion> booms;
    private final PlaneScore score;

    // every object reports here instead of to each other
    void bulletHitEnemy(Bullet b, Enemy e) {
        b.destroy();
        e.destroy();
        booms.add(new Explosion(e.x, e.y));
        sound.play("boom");
        score.add(e.points);
    }
}
// Bullet does not know Enemy, Explosion, Sound or Score:
if (bullet.touches(enemy)) mediator.bulletHitEnemy(bullet, enemy);

🎯 Trick
Observer: sender does not care who listens. Mediator: sender does not care how others react, only the hub does. Chain: sender does not care which one handles. Three kinds of "I don't care".
❓ Question
A Spring @Service calls five other services after an order is placed. Observer or Mediator?
Reveal hintIf the service just announces "order placed" and the five react on their own → Observer (publish an event). If the service must order the steps and pass results between them → Mediator (or a Facade / orchestrator). Ask: does the sender need to know the outcome? No → Observer. Yes → Mediator.

❓ Question
@Transactional on a Spring bean: Decorator or Proxy?
Reveal hintTechnically a Proxy (the container creates it, and it controls access by opening and closing the transaction around the call). Many people call it Decorator because it adds behavior. Safe answer: "a proxy that decorates the call with transaction handling" — shows you know both.
❓ Question
An order goes NEW → PAID → SHIPPED → DELIVERED and each step allows different actions. Strategy or State?
Reveal hintState. The allowed behavior depends on where the order is in its life, and each state decides the next one. Strategy would be, for example, choosing between three shipping-cost formulas.

12Self-test: name the pattern

Read the situation, say the pattern and why, then reveal. Aim for 10 of 12 before you call yourself ready.

❓ 1. Fifty bullets on screen each hold their own copy of the same 40 KB image. Memory is climbing.
Reveal hintFlyweight. Put the image in an ImageCache keyed by name; bullets keep only x and y.
❓ 2. You have BluePlaneBlueBullet, BluePlaneRedBullet, RedPlaneBlueBullet… and a third bullet is coming.
Reveal hintBridge. Two trees (Plane, Bullet) joined by a field. 3 planes × 3 bullets stays 6 classes, not 9.
❓ 3. A payment service has switch (type) { case CARD… case UPI… case WALLET… } and each branch is 80 lines.
Reveal hintStrategy. One PaymentStrategy interface, one class per type, pick by key. In Spring inject Map<String, PaymentStrategy>.
❓ 4. When an enemy dies, the score panel, the life bar, the sound system and an achievement tracker must all react. You will add more later.
Reveal hintObserver. The plane publishes ENEMY_DOWN; each part subscribes. Adding a fifth reaction touches nothing in the plane.
❓ 5. You want to add "shield", "speed boost" and "double fire" to a plane in any mix, during the game.
Reveal hintDecorator. Three wrappers that implement Sprite and hold a Sprite. Stack them at run time.
❓ 6. An HTTP request must pass auth, then rate-limit, then validation; any of them may reject it.
Reveal hintChain of Responsibility. Each check is a handler that either rejects or calls the next. Spring Security's filter chain is exactly this.
❓ 7. Every report job does: open connection → run query → map rows → close. Only "run query" and "map rows" differ.
Reveal hintTemplate Method. Parent owns the final flow; children override the two steps. This is JdbcTemplate.
❓ 8. An enemy is Idle, then Chasing when it sees you, then Attacking in range, then Dead. Each phase moves and draws differently.
Reveal hintState. One class per phase; each phase decides the next. Not Strategy, because the enemy switches on its own.
❓ 9. You need a "Settings" screen that has sections, which have sub-sections, which have items. "Draw" must work on any of them.
Reveal hintComposite. One MenuComponent interface; Menu holds children and forwards draw(); MenuItem is the leaf.
❓ 10. Users want undo for the last 20 edits, and edits should also be replayable from a log.
Reveal hintCommand. Each edit is an object with execute() and undo(); keep them on a stack and in the log.
❓ 11. Plane, Enemy, Bullet, Sound and Explosion all call each other directly. Changing one breaks three others.
Reveal hintMediator. They report to a GameMediator; it decides who does what. N×N links become N.
❓ 12. An EmailRequest has to, cc, bcc, subject, body, attachments, priority and reply-to; most are optional.
Reveal hintBuilder. Fluent setters, validate in build(), produce an immutable request.

Harder "why" questions

❓ A. Interviewer: "Strategy and State have identical UML. So are they the same pattern?"
Reveal hintNo. Same structure, different intent and different owner of the switch. Strategy: caller picks an interchangeable algorithm; strategies do not know each other. State: the object's phase picks its behavior and each state knows its neighbors. Patterns are defined by the problem they solve, not by their class diagram.
❓ B. "Why is a Singleton bad for unit tests, and how does Spring avoid the problem?"
Reveal hintA static getInstance() cannot be swapped for a mock, and state leaks between tests. Spring keeps one instance per container but injects it, so a test can inject a fake. One instance is fine; a hidden global door is the problem.
❓ C. "The book's Chain example (2 planes → 4 planes → boss) could be a plain if / else if. Why use a pattern?"
Reveal hintWith 3 fixed stages, if / else is fine — say so; that shows judgment. The chain pays off when stages are added, reordered or configured at run time (levels loaded from a file), or when each stage is big enough to deserve its own class and tests.
❓ D. "Name one trade-off for each of Observer, Decorator and Mediator."
Reveal hintObserver: hard-to-trace flow and listener leaks. Decorator: deep wrapper stacks are hard to debug; identity (==) breaks. Mediator: the hub can become a god object. Always end a pattern answer with its cost.

💡 The one idea to carry away
Do not learn patterns as name → definition → UML → code. Learn them as problem → what changes → what is stuck together → where to cut → which pattern → what it costs. That habit is worth more than all 15 definitions.
