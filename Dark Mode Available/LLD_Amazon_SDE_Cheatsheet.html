0. What LLD Interviews Actually Test

An Amazon LLD round (called "Object-Oriented Design" or "Coding + Design") is 45–60 minutes. The interviewer does not want a giant class diagram. They want to see you turn an ambiguous problem into clean, working, extensible code, while talking through trade-offs.

What is gradedWeightWhat "good" looks like
Requirement gathering & scoping~20%Asks 3–5 sharp questions, lists in/out of scope, calls out NFRs (concurrency, scale).
Class / object identification~20%Right-sized classes (no God class, no anemic models), proper relationships (composition vs inheritance).
Use of OOP & SOLID~20%Encapsulation, dependency inversion, interfaces over implementations.
Design patterns (used, not name-dropped)~15%Strategy, Factory, Observer, State applied where they actually help.
Working code in the language of choice~15%Compiles in your head. Methods have bodies. Edge cases handled.
Extensibility & trade-off articulation~10%"If we add X tomorrow, only class Y changes — here is why."
Amazon LP signal: Are Right, A Lot + Dive Deep show up when you justify a class boundary. Invent and Simplify shows up when you reject over-engineering ("I won't add Visitor here — it adds two classes and we have one operation"). Customer Obsession shows up when you frame requirements in user terms, not table terms.
Tip — common SDE-1 trap: jumping straight to code. Anti-pattern If you start typing within 60 seconds, you skipped requirements. Spend 5–8 minutes on requirements + entity sketch before the first class.

1. The 7-Step LLD Framework (use this every single time)

The 7 steps — write these on the whiteboard / shared doc first:
  1. Clarify Requirements — functional + non-functional. Get scope locked.
  2. Identify Core Entities (Nouns) — pull nouns from the problem statement.
  3. Identify Operations / Use Cases (Verbs) — what does each actor do?
  4. Define Relationships — association, aggregation, composition, inheritance.
  5. Apply SOLID + Patterns — only where they earn their keep.
  6. Code the Skeleton — interfaces first, then concrete classes, then a small main demo.
  7. Discuss Extensions & Trade-offs — concurrency, persistence, "what if we add Z?".

Verbal opening template (memorize)

"Before I jump in, let me clarify scope. I'll assume the system is X with users Y and Z.
Out of scope: payments, auth, persistence — unless you'd like otherwise.
I'll list entities, then sketch interfaces, then implement core flows in Java,
and we'll close with extension points and concurrency."
Tip: Saying "out of scope" out loud is huge. It signals product thinking and prevents the interviewer from holding missing features against you later.

2. Requirements — Functional vs Non-Functional

AspectFunctional Requirements (FR)Non-Functional Requirements (NFR)
Question "What must the system do?" "How well must it do it?"
Examples (Parking Lot) Park / unpark a vehicle, calculate fee, find nearest spot. Thread-safe spot allocation, p99 latency < 50ms, 10k spots.
Drives Class APIs, methods, return types. Concurrency primitives, data structures, caching.

The 5 questions to always ask (steal these)

  1. Who are the actors / users? (admin, end-user, system)
  2. What are the core operations? (3–5 verbs max for the happy path)
  3. Single-instance or distributed? (in-memory vs persisted)
  4. Concurrency expected? (single thread vs many)
  5. What is explicitly out of scope? (state it; don't ask)

4. SOLID — Deep Dive with Java Code

S — Single Responsibility Principle (SRP)

One class = one reason to change. Don't fuse business logic with persistence with notification.

ConceptWrong (one class doing everything)Right (split by reason to change)
Code 
class Invoice {
  double total;
  void calculate() { ... }
  void saveToDB() { ... }     // persistence
  void emailCustomer(){ ... }  // I/O + comms
  void printPDF()    { ... }   // rendering
}

class Invoice           { double calculate(); }
class InvoiceRepository { void save(Invoice i); }
class InvoiceMailer     { void email(Invoice i); }
class InvoicePrinter    { void print(Invoice i); }

O — Open/Closed Principle (OCP)

Open for extension, closed for modification. Adding a new payment type should not require editing existing code.

// WRONG — every new method = edit this class (closed for extension)
class PaymentService {
  void pay(String type, double amt) {
    if (type.equals("CARD")) { ... }
    else if (type.equals("UPI"))  { ... }
    else if (type.equals("COD"))  { ... }
    // adding "WALLET" forces editing here
  }
}

// RIGHT — Strategy + polymorphism. Add new class, edit nothing.
interface PaymentMethod { void pay(double amt); }
class CardPayment   implements PaymentMethod { public void pay(double a){...} }
class UpiPayment    implements PaymentMethod { public void pay(double a){...} }
class WalletPayment implements PaymentMethod { public void pay(double a){...} }

L — Liskov Substitution Principle (LSP)

Subtype must be usable wherever the base type is expected, without surprises.

// CLASSIC LSP violation: Square extends Rectangle
class Rectangle { int w, h;  void setW(int w){...}  void setH(int h){...} }
class Square extends Rectangle {
  @Override void setW(int w){ this.w = w; this.h = w; }   // surprise!
  @Override void setH(int h){ this.w = h; this.h = h; }
}
// Code that expects Rectangle behavior breaks: r.setW(5); r.setH(10); area is 100, not 50.

// FIX: don't model "is-a" by IDE inheritance — model by behavior. Both implement Shape.
interface Shape { int area(); }
class Rectangle implements Shape { ... }
class Square    implements Shape { ... }

I — Interface Segregation Principle (ISP)

Many small interfaces beat one fat interface. Clients should not be forced to depend on methods they don't use.

// WRONG — one fat interface
interface Worker { void work(); void eat(); void sleep(); }
class RobotWorker implements Worker {
  public void work(){...}
  public void eat() { throw new UnsupportedOperationException(); }  // smell!
  public void sleep(){ throw new UnsupportedOperationException(); }
}

// RIGHT — split by capability
interface Workable  { void work(); }
interface Eatable   { void eat(); }
interface Sleepable { void sleep(); }
class Human       implements Workable, Eatable, Sleepable { ... }
class RobotWorker implements Workable { ... }

D — Dependency Inversion Principle (DIP)

Depend on abstractions, not concretes. High-level modules don't know about low-level ones.

// WRONG — OrderService is welded to MySQLOrderRepo
class OrderService {
  private MySQLOrderRepo repo = new MySQLOrderRepo();   // hard dependency
}

// RIGHT — depend on the interface, inject the concrete
interface OrderRepo { void save(Order o); Order find(String id); }
class OrderService {
  private final OrderRepo repo;
  public OrderService(OrderRepo repo) { this.repo = repo; }   // constructor injection
}
// Now MySQL, Postgres, in-memory, mock — all swap in without touching OrderService.
Interview line that scores: "I'll inject the repository through the constructor — it makes OrderService trivially testable with an in-memory fake."

6. Creational Patterns (the "make me an object" patterns)

Singleton — exactly one instance

Most-asked LLD pattern. Get the thread-safe version right.

// Best Java idiom: enum singleton — thread-safe, serialization-safe, reflection-safe
public enum Logger {
  INSTANCE;
  public void log(String msg) { System.out.println(msg); }
}
// Usage: Logger.INSTANCE.log("hi");

// Lazy + thread-safe alternative: double-checked locking
public class Config {
  private static volatile Config instance;       // volatile is mandatory
  private Config() {}
  public static Config get() {
    if (instance == null) {
      synchronized (Config.class) {
        if (instance == null) instance = new Config();
      }
    }
    return instance;
  }
}
Trick Q: "Why volatile?" → without it, another thread could see a partially constructed object due to JVM reordering of new + assignment.

Factory Method — defer instantiation to subclasses

interface Notification { void send(); }
class EmailNotif implements Notification { public void send(){...} }
class SmsNotif   implements Notification { public void send(){...} }

class NotificationFactory {
  public static Notification create(String type) {
    switch (type) {
      case "EMAIL": return new EmailNotif();
      case "SMS":   return new SmsNotif();
      default:        throw new IllegalArgumentException(type);
    }
  }
}

Abstract Factory — family of related products

interface Button { void render(); }
interface Checkbox { void render(); }
interface UIFactory { Button btn(); Checkbox cb(); }

class DarkUIFactory  implements UIFactory { public Button btn(){return new DarkBtn();} public Checkbox cb(){return new DarkCb();} }
class LightUIFactory implements UIFactory { ... }

Builder — many optional params, immutable result

public class Pizza {
  private final String size;
  private final boolean cheese, pepperoni, olives;

  private Pizza(Builder b) { size=b.size; cheese=b.cheese; pepperoni=b.pepperoni; olives=b.olives; }

  public static class Builder {
    private String size; private boolean cheese, pepperoni, olives;
    public Builder size(String s){ size=s; return this; }
    public Builder cheese()    { cheese=true; return this; }
    public Builder pepperoni() { pepperoni=true; return this; }
    public Builder olives()    { olives=true; return this; }
    public Pizza build()      { return new Pizza(this); }
  }
}
// Pizza p = new Pizza.Builder().size("L").cheese().olives().build();

Prototype — clone an existing object

Useful when constructing from scratch is expensive (DB hit, network call). Implement Cloneable or write your own copy().

7. Structural Patterns

Adapter — make incompatible interfaces talk

interface UsbC     { void chargeUsbC(); }
class OldUsbA { public void chargeUsbA(){...} }

class UsbAtoCAdapter implements UsbC {
  private final OldUsbA oldDevice;
  public UsbAtoCAdapter(OldUsbA d){ this.oldDevice=d; }
  public void chargeUsbC() { oldDevice.chargeUsbA(); }
}

Decorator — add behavior without subclassing

interface Coffee { double cost(); String desc(); }
class SimpleCoffee implements Coffee { public double cost(){return 5;} public String desc(){return "coffee";} }

abstract class CoffeeDecorator implements Coffee {
  protected final Coffee inner;
  public CoffeeDecorator(Coffee c){ inner=c; }
}
class Milk  extends CoffeeDecorator { public Milk(Coffee c){super(c);}  public double cost(){return inner.cost()+1.5;} public String desc(){return inner.desc()+"+milk";} }
class Sugar extends CoffeeDecorator { public Sugar(Coffee c){super(c);} public double cost(){return inner.cost()+0.5;} public String desc(){return inner.desc()+"+sugar";} }
// new Sugar(new Milk(new SimpleCoffee())).cost() == 7.0;

Facade — one front door for a tangle of subsystems

class VideoConverterFacade {
  public File convert(File src, String targetFormat) {
    var codec  = new CodecFactory().pick(targetFormat);
    var reader = new VideoReader(src);
    var buf    = new Compressor().compress(reader.read(), codec);
    return new Writer().write(buf, targetFormat);
  }
}
// Caller does: facade.convert(f, "mp4");  no knowledge of codecs/buffers/etc.

Composite — tree of part-whole objects treated uniformly

interface FsNode { long size(); }
class FileNode implements FsNode { long bytes; public long size(){return bytes;} }
class DirNode  implements FsNode {
  List<FsNode> children = new ArrayList<>();
  public long size() { return children.stream().mapToLong(FsNode::size).sum(); }
}

Proxy · Bridge · Flyweight (one-liners)

  • Proxy — same interface, controls access (lazy load, auth check, remote call).
  • Bridge — split abstraction from implementation so they vary independently. Shape hierarchy × Renderer hierarchy.
  • Flyweight — share fine-grained immutable state to save memory (e.g., glyphs in a text editor; Integer.valueOf() cache).

8. Behavioral Patterns (the ones that actually win interviews)

Strategy — interchangeable algorithms (most useful pattern in LLD)

interface SortStrategy { void sort(int[] a); }
class QuickSort  implements SortStrategy { public void sort(int[] a){...} }
class MergeSort  implements SortStrategy { public void sort(int[] a){...} }

class Sorter {
  private SortStrategy s;
  public Sorter(SortStrategy s){ this.s = s; }
  public void setStrategy(SortStrategy s){ this.s = s; }
  public void sort(int[] a){ s.sort(a); }
}

Observer — publish/subscribe

interface Observer<T> { void onEvent(T event); }
class EventBus<T> {
  private final List<Observer<T>> subs = new CopyOnWriteArrayList<>();
  public void subscribe(Observer<T> o){ subs.add(o); }
  public void publish(T e){ for (var s : subs) s.onEvent(e); }
}
Why CopyOnWriteArrayList: publish iterates while subscribers may register/unregister. CoW gives a snapshot iterator with no ConcurrentModificationException.

State — object behavior changes with internal state

interface OrderState { void next(OrderContext c); void cancel(OrderContext c); }
class PlacedState    implements OrderState { public void next(var c){ c.setState(new ShippedState()); } public void cancel(var c){ c.setState(new CancelledState()); } }
class ShippedState   implements OrderState { public void next(var c){ c.setState(new DeliveredState()); } public void cancel(var c){ throw new IllegalStateException("Already shipped"); } }
class DeliveredState implements OrderState { ... }
class CancelledState implements OrderState { ... }

Command — encapsulate a request as an object (undo/redo, queues)

interface Command { void execute(); void undo(); }
class AddTextCmd implements Command {
  private final Editor ed; private final String text;
  public AddTextCmd(Editor e, String t){ ed=e; text=t; }
  public void execute(){ ed.append(text); }
  public void undo()   { ed.delete(text.length()); }
}

Template Method — fix the algorithm skeleton, vary the steps

abstract class Report {
  public final void generate() { fetch(); transform(); render(); }   // final: skeleton frozen
  protected abstract void fetch();
  protected abstract void transform();
  protected void render(){ /* default impl */ }
}

Chain of Responsibility — pass request along until someone handles it

abstract class LogHandler {
  protected LogHandler next;
  public LogHandler chain(LogHandler n){ this.next=n; return n; }
  public void handle(Log log){ if (canHandle(log)) write(log); else if (next!=null) next.handle(log); }
  protected abstract boolean canHandle(Log l);
  protected abstract void write(Log l);
}

Iterator · Mediator · Memento · Visitor (one-liners)

  • Iterator — sequential access without exposing internals (Iterable<T>).
  • Mediator — central object coordinates peers (chat room, air-traffic control). Reduces N×N coupling to N×1.
  • Memento — snapshot state for restore (undo). Pair with Command.
  • Visitor — add operations to a class hierarchy without modifying it. Heavy; use only if hierarchy is stable but operations grow.

public class DbPool {
  private static class Holder { static final DbPool I = new DbPool(); }   // "initialization-on-demand holder"

}
// JLS guarantees Holder is loaded once, lazily, and thread-safely. Cleaner than DCL.

Producer-consumer skeleton

BlockingQueue<Task> q = new LinkedBlockingQueue<>(1000);
ExecutorService pool = Executors.newFixedThreadPool(8);
pool.submit(() -> { while (!Thread.currentThread().isInterrupted()) { Task t = q.take(); t.run(); } });
q.put(new Task());

P1. Parking Lot — the canonical Amazon LLD problem

Step 1 — Requirements (FR + NFR)

  • FR: park a vehicle (Bike / Car / Truck), unpark with ticket, calculate fee by hours, multiple floors with multiple spot types, find nearest available spot.
  • NFR: thread-safe (two cars can't claim the same spot), O(1) park / unpark, single-process.
  • Out of scope: reservations, license-plate OCR, payments — state explicitly.

Step 2 — Entities & relationships

ParkingLot ◆── ParkingFloor ◆── ParkingSpot <|-- {CarSpot, BikeSpot, TruckSpot} Vehicle <|-- {Car, Bike, Truck} Ticket -- references --> ParkingSpot, Vehicle, entryTime FeeStrategy <|-- {HourlyFeeStrategy, FlatFeeStrategy} // Strategy pattern

Step 3 — Code (compilable Java skeleton)

enum VehicleType { BIKE, CAR, TRUCK }

abstract class Vehicle {
  private final String plate; private final VehicleType type;
  protected Vehicle(String p, VehicleType t){ plate=p; type=t; }
  public VehicleType getType(){ return type; }
  public String getPlate(){ return plate; }
}
class Car   extends Vehicle { public Car  (String p){ super(p, VehicleType.CAR);   } }
class Bike  extends Vehicle { public Bike (String p){ super(p, VehicleType.BIKE);  } }
class Truck extends Vehicle { public Truck(String p){ super(p, VehicleType.TRUCK); } }

abstract class ParkingSpot {
  private final String id;
  private final VehicleType allowed;
  private Vehicle parked;             // null = free
  protected ParkingSpot(String id, VehicleType a){ this.id=id; this.allowed=a; }
  public synchronized boolean tryPark(Vehicle v){
    if (parked != null || v.getType() != allowed) return false;
    parked = v; return true;
  }
  public synchronized Vehicle remove(){ Vehicle v=parked; parked=null; return v; }
  public synchronized boolean isFree(){ return parked == null; }
  public String id(){ return id; }
}
class CarSpot   extends ParkingSpot { public CarSpot  (String id){ super(id, VehicleType.CAR);   } }
class BikeSpot  extends ParkingSpot { public BikeSpot (String id){ super(id, VehicleType.BIKE);  } }
class TruckSpot extends ParkingSpot { public TruckSpot(String id){ super(id, VehicleType.TRUCK); } }

class Ticket {
  final String id; final ParkingSpot spot; final Vehicle vehicle; final Instant entry;
  Ticket(ParkingSpot s, Vehicle v){ id=UUID.randomUUID().toString(); spot=s; vehicle=v; entry=Instant.now(); }
}

interface FeeStrategy { double compute(Ticket t, Instant exit); }
class HourlyFeeStrategy implements FeeStrategy {
  private final Map<VehicleType, Double> rates = Map.of(VehicleType.BIKE,10.0, VehicleType.CAR,20.0, VehicleType.TRUCK,40.0);
  public double compute(Ticket t, Instant exit) {
    long hrs = Math.max(1, Duration.between(t.entry, exit).toHours());
    return hrs * rates.get(t.vehicle.getType());
  }
}

class ParkingFloor {
  private final Map<VehicleType, Deque<ParkingSpot>> freeSpots = new EnumMap<>(VehicleType.class);
  public ParkingFloor(List<ParkingSpot> spots){
    for (var t : VehicleType.values()) freeSpots.put(t, new ArrayDeque<>());
    for (var s : spots) freeSpots.get(s instanceof CarSpot ? VehicleType.CAR : s instanceof BikeSpot ? VehicleType.BIKE : VehicleType.TRUCK).add(s);
  }
  public synchronized Optional<ParkingSpot> assign(Vehicle v){
    var q = freeSpots.get(v.getType());
    while (!q.isEmpty()) {
      ParkingSpot s = q.poll();
      if (s.tryPark(v)) return Optional.of(s);
    }
    return Optional.empty();
  }
  public synchronized void release(ParkingSpot s){ s.remove(); freeSpots.get(s instanceof CarSpot ? VehicleType.CAR : s instanceof BikeSpot ? VehicleType.BIKE : VehicleType.TRUCK).add(s); }
}

class ParkingLot {
  private final List<ParkingFloor> floors;
  private final FeeStrategy fees;
  private final Map<String, Ticket> active = new ConcurrentHashMap<>();
  public ParkingLot(List<ParkingFloor> f, FeeStrategy fs){ floors=f; fees=fs; }

  public Ticket park(Vehicle v) {
    for (ParkingFloor f : floors) {
      var spot = f.assign(v);
      if (spot.isPresent()) {
        Ticket t = new Ticket(spot.get(), v);
        active.put(t.id, t);
        return t;
      }
    }
    throw new IllegalStateException("Lot full for " + v.getType());
  }
  public double unpark(String ticketId) {
    Ticket t = active.remove(ticketId);
    if (t == null) throw new IllegalArgumentException("Bad ticket");
    double fee = fees.compute(t, Instant.now());
    floors.stream().filter(f -> true).findFirst().ifPresent(f -> f.release(t.spot));   // in real code, track spot→floor
    return fee;
  }
}
Trade-offs to mention out loud:
  • Used Deque for O(1) free-spot retrieval. Could swap to PriorityQueue if "nearest to entrance" is required (just add distance to spot).
  • Spot-level synchronized + floor-level synchronized = fine for thousands of spots; for millions use lock striping or per-spot AtomicReference<Vehicle> with CAS.
  • FeeStrategy isolates pricing — adding "weekend rate" or "VIP" only adds a class.

P2. Splitwise / Expense Sharing

Requirements

  • Users can add expenses split equally, exactly (custom amounts), or by percent.
  • Show running balance: who owes whom, how much.
  • Support groups (subset of users).

Patterns used

  • Strategy for split type (equal / exact / percent).
  • Domain model: User, Group, Expense, Split, BalanceSheet.
enum SplitType { EQUAL, EXACT, PERCENT }

class User { final String id, name, email; ... }

class Split { User user; double amount; }   // who owes how much for one expense

interface SplitStrategy {
  List<Split> split(double total, List<User> participants, double[] weights);
}
class EqualSplit implements SplitStrategy {
  public List<Split> split(double total, List<User> ps, double[] _w) {
    double share = round(total / ps.size());
    return ps.stream().map(u -> { var s=new Split(); s.user=u; s.amount=share; return s;}).toList();
  }
  private double round(double x){ return Math.round(x*100.0)/100.0; }
}
class ExactSplit  implements SplitStrategy { /* assert sum(weights)==total */ ... }
class PercentSplit implements SplitStrategy { /* assert sum(weights)==100  */ ... }

class Expense {
  final String id; final User paidBy; final double amount; final List<Split> splits;
}

class BalanceSheet {
  // balances[a][b] = a owes b
  private final Map<String, Map<String, Double>> b = new ConcurrentHashMap<>();

  public synchronized void add(Expense e) {
    for (Split s : e.splits) {
      if (s.user.id.equals(e.paidBy.id)) continue;
      add(s.user.id, e.paidBy.id,  s.amount);   // s.user owes paidBy
      add(e.paidBy.id, s.user.id, -s.amount);   // mirror
    }
  }
  private void add(String a, String b1, double amt){
    b.computeIfAbsent(a, k -> new ConcurrentHashMap<>()).merge(b1, amt, Double::sum);
  }
  public Map<String, Double> balancesOf(String userId){ return b.getOrDefault(userId, Map.of()); }
}
Trick Q: "How would you simplify debts so the minimum number of transactions settle everyone?" → Reduce to: for each user compute net balance; then greedily match max creditor with max debtor. Mention O(n log n) with a max-heap.

P3. Elevator System

Requirements

  • N elevators, M floors. External requests (UP / DOWN button on a floor) and internal requests (button inside cabin).
  • Pick the "best" elevator for an external call. Optimize for least travel.
  • States: IDLE, MOVING_UP, MOVING_DOWN, STOPPED, MAINTENANCE.

Pattern map

  • State for elevator state machine.
  • Strategy for dispatch algorithm (nearest-car, scan/look).
  • Observer for floor displays subscribing to elevator events.
enum Direction { UP, DOWN, IDLE }

class Request { final int floor; final Direction dir; }

class Elevator {
  final int id; int currentFloor; Direction dir = Direction.IDLE;
  final NavigableSet<Integer> upStops   = new TreeSet<>();           // pending up stops
  final NavigableSet<Integer> downStops = new TreeSet<>(Comparator.reverseOrder());

  public synchronized void addStop(int floor, Direction d){
    (d == Direction.UP ? upStops : downStops).add(floor);
  }

  public synchronized void step() {
    if (dir == Direction.UP && upStops.isEmpty()) dir = downStops.isEmpty() ? Direction.IDLE : Direction.DOWN;
    if (dir == Direction.DOWN && downStops.isEmpty()) dir = upStops.isEmpty() ? Direction.IDLE : Direction.UP;
    if (dir == Direction.IDLE) return;
    var stops = dir == Direction.UP ? upStops : downStops;
    Integer next = stops.first();
    currentFloor += dir == Direction.UP ? 1 : -1;
    if (currentFloor == next) stops.pollFirst();   // arrived; open doors
  }
}

interface DispatchStrategy { Elevator pick(List<Elevator> pool, Request r); }
class NearestCarStrategy implements DispatchStrategy {
  public Elevator pick(List<Elevator> pool, Request r) {
    return pool.stream()
        .min(Comparator.comparingInt(e -> cost(e, r)))
        .orElseThrow();
  }
  private int cost(Elevator e, Request r) {
    int d = Math.abs(e.currentFloor - r.floor);
    if (e.dir == Direction.IDLE) return d;
    if (e.dir == Direction.UP   && r.floor >= e.currentFloor && r.dir == Direction.UP)   return d;
    if (e.dir == Direction.DOWN && r.floor <= e.currentFloor && r.dir == Direction.DOWN) return d;
    return d + 100;   // penalty: must reverse direction
  }
}

class ElevatorController {
  private final List<Elevator> pool;
  private final DispatchStrategy strategy;
  public synchronized void handleExternal(int floor, Direction d){
    Elevator e = strategy.pick(pool, new Request(){{ this.floor=floor; this.dir=d; }});
    e.addStop(floor, d);
  }
}

P4. LRU Cache (the eternal LLD warm-up)

Requirements

  • O(1) get and put. Evict least-recently-used when capacity exceeded.
  • Thread-safe (extension).

Trick:

doubly-linked list (for O(1) move-to-front + remove-tail) + HashMap (for O(1) lookup). 
public class LRUCache<K, V> {
  private static class Node<K, V> { K k; V v; Node<K,V> prev, next; Node(K k, V v){this.k=k; this.v=v;} }

  private final int cap;
  private final Map<K, Node<K,V>> map = new HashMap<>();
  private final Node<K,V> head = new Node<>(null,null), tail = new Node<>(null,null);

  public LRUCache(int cap){ this.cap = cap; head.next = tail; tail.prev = head; }

  public synchronized V get(K k) {
    Node<K,V> n = map.get(k);
    if (n == null) return null;
    moveToFront(n);
    return n.v;
  }
  public synchronized void put(K k, V v) {
    Node<K,V> n = map.get(k);
    if (n != null) { n.v = v; moveToFront(n); return; }
    n = new Node<>(k, v);
    map.put(k, n);
    addFront(n);
    if (map.size() > cap) {
      Node<K,V> lru = tail.prev;
      remove(lru);
      map.remove(lru.k);
    }
  }

  private void remove(Node<K,V> n){ n.prev.next = n.next; n.next.prev = n.prev; }
  private void addFront(Node<K,V> n){ n.next = head.next; n.prev = head; head.next.prev = n; head.next = n; }
  private void moveToFront(Node<K,V> n){ remove(n); addFront(n); }
}
Java cheat: LinkedHashMap with accessOrder=true + removeEldestEntry override is a 5-line LRU. Mention it as the "production answer" but write the manual version because that's what the interviewer wants to see.

P7. Tic-Tac-Toe (warm-up; show clean OOP fast)

enum Symbol { X, O, EMPTY }

class Board {
  private final Symbol[][] g;
  private final int n;
  public Board(int n){ this.n=n; g=new Symbol[n][n]; for(var r:g) Arrays.fill(r, Symbol.EMPTY); }
  public boolean place(int r, int c, Symbol s){
    if (g[r][c] != Symbol.EMPTY) return false;
    g[r][c] = s; return true;
  }
  public boolean isWin(Symbol s){
    for (int i=0;i<n;i++) if (rowAll(i,s) || colAll(i,s)) return true;
    return diagAll(s) || antiDiagAll(s);
  }
  // rowAll, colAll, diagAll, antiDiagAll trivial
}

class Player { final String name; final Symbol s; }

class Game {
  private final Board board; private final Deque<Player> turnQueue = new ArrayDeque<>();
  public Game(Player p1, Player p2, int n){ board=new Board(n); turnQueue.add(p1); turnQueue.add(p2); }
  public Optional<Player> play(int r, int c){
    Player cur = turnQueue.poll();
    if (!board.place(r, c, cur.s)) { turnQueue.addFirst(cur); throw new IllegalArgumentException("Cell taken"); }
    if (board.isWin(cur.s)) return Optional.of(cur);
    turnQueue.addLast(cur);
    return Optional.empty();
  }
}
Why Deque for turn order: O(1) rotate, easy to extend to N players. Beats currentPlayerIndex + modulo arithmetic.

// Cash dispenser — Chain of Responsibility
abstract class CashDispenser {
  protected CashDispenser next;
  protected final int denomination;
  protected int count;
  public abstract void dispense(int amount);
  public CashDispenser setNext(CashDispenser n){ next=n; return n; }
}
class DefaultDispenser extends CashDispenser {
  public DefaultDispenser(int d, int c){ denomination=d; count=c; }
  public synchronized void dispense(int amount) {
    if (amount >= denomination) {
      int num = Math.min(amount / denomination, count);
      count -= num;
      amount -= num * denomination;
    }
    if (amount > 0) {
      if (next == null) throw new IllegalStateException("Cannot dispense exact amount");
      next.dispense(amount);
    }
  }
}

P9b. Rate Limiter — Token Bucket (most common ask)

public class TokenBucket {
  private final long capacity;          // max tokens
  private final double refillPerMs;       // e.g. 10 req/sec = 0.01 tokens/ms
  private double tokens;
  private long lastRefill;

  public TokenBucket(long cap, double tokensPerSec) {
    capacity = cap; refillPerMs = tokensPerSec / 1000.0;
    tokens = cap; lastRefill = System.currentTimeMillis();
  }

  public synchronized boolean tryAcquire() {
    refill();
    if (tokens >= 1) { tokens -= 1; return true; }
    return false;
  }
  private void refill() {
    long now = System.currentTimeMillis();
    tokens = Math.min(capacity, tokens + (now - lastRefill) * refillPerMs);
    lastRefill = now;
  }
}

IdeaRefill tokens at fixed rate; consume on each request.Track timestamps of last N requests; reject if window full.

// Decorator: add retry with exponential backoff to ANY channel
class RetryingChannel implements NotificationChannel {
  private final NotificationChannel inner; private final int max;
  public RetryingChannel(NotificationChannel c, int m){ inner=c; max=m; }
  public void send(User u, String s, String b){
    Exception last = null;
    for (int i=0; i<max; i++) {
      try { inner.send(u, s, b); return; }
      catch (Exception e) { last=e; sleep(1L << i); }
    }
    throw new RuntimeException("Failed after retries", last);
  }
  private void sleep(long s){ try{ Thread.sleep(s*100); }catch(InterruptedException e){ Thread.currentThread().interrupt(); } }
}

// Observer: events → subscriptions
class NotificationService {
  private final Map<String, List<Subscription>> topics = new ConcurrentHashMap<>();
  public void subscribe(String topic, User u, NotificationChannel ch){
    topics.computeIfAbsent(topic, k -> new CopyOnWriteArrayList<>()).add(new Subscription(u, ch));
  }
  public void publish(String topic, String subject, String body){
    for (var s : topics.getOrDefault(topic, List.of()))
      s.channel.send(s.user, subject, body);
  }
  record Subscription(User user, NotificationChannel channel) {}
}

P11. BookMyShow / Movie Booking

Hard part: concurrent seat booking — two users tap "Book" on the same seat at the same time

enum SeatStatus { AVAILABLE, HELD, BOOKED }

class Seat {
  final String id; final SeatType type;
  private final AtomicReference<SeatStatus> status = new AtomicReference<>(SeatStatus.AVAILABLE);
  private volatile String heldBy;
  private volatile Instant heldUntil;

  public boolean tryHold(String userId, Duration ttl) {
    if (status.compareAndSet(SeatStatus.AVAILABLE, SeatStatus.HELD)) {
      heldBy = userId; heldUntil = Instant.now().plus(ttl);
      return true;
    }
    // release expired hold
    if (status.get() == SeatStatus.HELD && heldUntil.isBefore(Instant.now())) {
      status.set(SeatStatus.AVAILABLE);
      return tryHold(userId, ttl);
    }
    return false;
  }
  public boolean confirm(String userId) {
    if (!userId.equals(heldBy)) return false;
    return status.compareAndSet(SeatStatus.HELD, SeatStatus.BOOKED);
  }
}

class Show { final Movie movie; final Screen screen; final Instant startAt; final Map<String, Seat> seats; }

class BookingService {
  public Booking book(User u, Show show, List<String> seatIds) {
    List<Seat> held = new ArrayList<>();
    for (String id : seatIds) {
      Seat s = show.seats.get(id);
      if (!s.tryHold(u.id, Duration.ofMinutes(5))) {
        held.forEach(h -> h.confirm(null));   // rollback holds
        throw new IllegalStateException("Seat "+id+" unavailable");
      }
      held.add(s);
    }
    // payment...
    held.forEach(s -> s.confirm(u.id));
    return new Booking(u, show, held);
  }
}
Why CAS over synchronized: CAS gives lock-free behavior — a slow "payment provider" call doesn't hold a lock on the seat. Only the state transition is atomic.

P12. Mini Amazon Order Management Amazon-specific

This is the most popular SDE-2 LLD scenario. Combines almost every pattern.

  • State for order lifecycle (PLACED → PAID → PACKED → SHIPPED → DELIVERED, with branches for CANCELLED, RETURNED, REFUNDED).

class Money { final long minor; final Currency cur; /* never use double for money */ }

class SKU { final String id, productId; final Money price; final Map<String,String> attrs; }

class Cart {

  public void add(String skuId, int qty){ lines.merge(skuId, qty, Integer::sum); }
  public void remove(String skuId){ lines.remove(skuId); }
}

interface PricingStrategy { Money quote(SKU sku, int qty, Customer c); }
interface ShippingStrategy { Money cost(Order o); Duration eta(Order o); }
interface Inventory        { boolean reserve(String sku, int qty); void release(String sku, int qty); }
interface OrderRepository  { void save(Order o); Order load(String id); }
interface PaymentGateway   { Payment charge(Customer c, Money m); }

enum OrderStatus { PLACED, PAID, PACKED, SHIPPED, DELIVERED, CANCELLED, RETURNED }

class Order {
  final String id; final Customer customer; final List<OrderItem> items;
  Money total; OrderStatus status = OrderStatus.PLACED;
  final List<OrderObserver> observers = new CopyOnWriteArrayList<>();

  public synchronized void transitionTo(OrderStatus next){
    if (!isValid(this.status, next)) throw new IllegalStateException(status+"→"+next);
    OrderStatus old = this.status; this.status = next;
    observers.forEach(o -> o.onChange(this, old, next));
  }
  private boolean isValid(OrderStatus from, OrderStatus to){
    return switch (from) {
      case PLACED    -> to == OrderStatus.PAID || to == OrderStatus.CANCELLED;
      case PAID      -> to == OrderStatus.PACKED || to == OrderStatus.CANCELLED;
      case PACKED    -> to == OrderStatus.SHIPPED || to == OrderStatus.CANCELLED;
      case SHIPPED   -> to == OrderStatus.DELIVERED;
      case DELIVERED -> to == OrderStatus.RETURNED;
      default        -> false;
    };
  }
}

interface OrderObserver { void onChange(Order o, OrderStatus from, OrderStatus to); }
class EmailObserver      implements OrderObserver { public void onChange(...) {/* notify */} }
class FulfillmentObserverimplements OrderObserver { public void onChange(...) {/* hand off to FC */} }
class AnalyticsObserver  implements OrderObserver { public void onChange(...) {/* metrics */} }

class OrderService {
  private final Inventory inv; private final PaymentGateway pg;
  private final PricingStrategy pricer; private final ShippingStrategy shipper;
  private final OrderRepository repo;
  private final List<OrderObserver> obs;

  public OrderService(Inventory i, PaymentGateway g, PricingStrategy ps, ShippingStrategy ss, OrderRepository r, List<OrderObserver> o){
    inv=i; pg=g; pricer=ps; shipper=ss; repo=r; obs=o;
  }

  public Order place(Customer c, Cart cart) {
    // 1. reserve inventory atomically; rollback on partial failure
    List<OrderItem> items = new ArrayList<>();
    for (var e : cart.lines.entrySet()) {
      if (!inv.reserve(e.getKey(), e.getValue())) {
        items.forEach(it -> inv.release(it.skuId, it.qty));
        throw new IllegalStateException("Out of stock: "+e.getKey());
      }
      items.add(new OrderItem(e.getKey(), e.getValue()));
    }
    Order o = new Order.Builder().customer(c).items(items).build();
    obs.forEach(o.observers::add);
    repo.save(o);

    // 2. payment
    try {
      Money total = items.stream().map(OrderItem::lineTotal).reduce(Money.ZERO, Money::add);
      pg.charge(c, total.add(shipper.cost(o)));
      o.transitionTo(OrderStatus.PAID);
      repo.save(o);
    } catch (Exception e) {
      o.transitionTo(OrderStatus.CANCELLED);
      items.forEach(it -> inv.release(it.skuId, it.qty));
      repo.save(o);
      throw e;
    }
    return o;
  }
}
Amazon LP signal in this design:
  • Customer Obsession — explicit cancellation path with inventory rollback so customer never gets a charge for unfulfilled items.
  • Ownership — observers handle their own concerns (email, fulfillment, analytics) — adding a new concern is a new class, not a code edit.
  • Insist on the Highest Standards — Money is a value object, not a double. State machine prevents DELIVERED → PLACED nonsense.

T. Tricky Questions Bank — with hints (auto-revealed in print)

T1. "When would you choose composition over inheritance?"
Reveal hint
Default to composition. Use inheritance only when (a) a true is-a relationship exists, (b) the subclass needs polymorphic substitution, and (c) the parent's contract is stable. Inheritance leaks parent internals (fragile-base-class problem). Mention Effective Java Item 18: "Favor composition over inheritance."
T2. "Why is HashMap not thread-safe? What's wrong with using Hashtable?"
Reveal hint
HashMap resize during concurrent put historically created cyclic linked lists → infinite loop on get. Hashtable locks the whole map per op → terrible throughput. ConcurrentHashMap uses bucket-level / CAS-based striping; reads are usually lock-free.
T3. "Two threads call singleton.getInstance() simultaneously without DCL. What can go wrong?"
Reveal hint
Two instances created (broken contract). With DCL but no volatile, one thread can see a partially-initialized object because JVM may reorder allocate → assign → run-constructor. volatile establishes happens-before. Better: enum singleton or holder idiom.
T4. "How does Strategy differ from State?"
Reveal hint
Same UML almost. Difference is intent: Strategy = client picks the algorithm, strategies are unaware of each other. State = the object itself transitions between states; states often know about other states (setState(next)).
T5. "Why are factory methods static?"
Reveal hint
Because callers don't have an instance yet — that's literally what they're asking the factory to make. Static is just the language convention; the deeper reason is that the factory has no per-instance state to depend on.
T6. "Difference between equals and ==? Why must hashCode be overridden when equals is?"
Reveal hint
== = reference equality (same object in heap). equals = logical equality. Contract: equal objects must have equal hashCodes. Violating it breaks HashMap, HashSet — entries become "lost" because the bucket lookup uses hashCode.
T7. "How would you make your Money class safe?"
Reveal hint
Immutable, final class, final fields, no setters. Store amount as long in minor units (paise, cents) to avoid IEEE-754 floating-point error. Currency-aware: Money.add throws if currencies differ. Use a factory method Money.of("12.50", "USD") for clarity.
T8. "Why prefer Optional<T> over null?"
Reveal hint
Forces the caller to acknowledge "no value" at the type system level — eliminates whole NPE class of bugs. Caveats: don't use Optional as a field, parameter, or in collections — it's for return types only.
T9. "How do you avoid the constructor explosion (telescoping constructors)?"
Reveal hint
Builder pattern. Or static factory methods with descriptive names. JavaBeans-style setters break immutability. With ≥4 optional params, Builder wins.
T10. "Two threads deposit to the same account. Show three increasingly correct designs."
Reveal hint
(1) balance += amt — broken, lost updates. (2) synchronized void deposit — correct, serial. (3) AtomicLong balance + balance.addAndGet(amt) — correct, lock-free, scales better. For multi-field invariants prefer StampedLock or short critical sections.
T11. "Design an in-memory cache. What's hard about thread-safety here?"
Reveal hint
ConcurrentHashMap alone isn't enough — eviction touches both the map and the order tracker. Use computeIfAbsent for atomic load-on-miss; for LRU pair a ConcurrentHashMap with a ConcurrentLinkedDeque guarded by a single lock for the order, OR use Caffeine which already does this lock-striped.
T12. "What's wrong with throw new RuntimeException(e.getMessage())?"
Reveal hint
You lose the cause and the stack trace of the original exception. Always wrap: throw new BusinessException("context", e). Never swallow exceptions silently.
T13. "Designing an Order class: should cancel() live on Order or OrderService?"
Reveal hint
order.cancel() when behavior depends only on Order's own state (validation: not yet shipped). orderService.cancel(order) when the operation needs collaborators (refund gateway, inventory). Don't make Order an anemic bag — push behavior in unless you genuinely need orchestration.
T14. "When would you NOT use a design pattern?"
Reveal hint
When it adds indirection without adding flexibility you'll actually use. A 3-line switch beats a 5-class Strategy hierarchy when there are exactly 3 cases that never grow. Invent and Simplify.
T15. "Singleton has a config that needs to change at runtime. How?"
Reveal hint
Don't replace the singleton — that breaks references already held. Make the singleton hold an AtomicReference<Config> (or volatile Config) and provide refresh(newConfig). Readers always read the latest snapshot atomically.
T16. "Should Stack extend ArrayList?"
Reveal hint
No — Java's Stack extends Vector is a notorious mistake. It exposes add(int index, E element) which violates LIFO. Composition: class Stack<T> { private final Deque<T> d; }. Better still, just use ArrayDeque directly.
T17. "Why is the Visitor pattern controversial?"
Reveal hint
It pushes changes the wrong way — adding a new visitor is easy, but adding a new element requires editing every visitor. Use only when your hierarchy is stable and you expect many independent operations (compilers, AST tools).
T18. "Two ways to handle a Book with multiple physical copies — which?"
Reveal hint
Don't model Book with int copyCount — you lose per-copy state (condition, location, barcode). Two classes: Book = catalog metadata, BookItem = physical instance. The relationship is Book 1 ──◆ * BookItem.
T19. "Why CopyOnWriteArrayList for observer lists, not ArrayList?"
Reveal hint
Notify iterates while observers may register / unregister. Plain ArrayList throws ConcurrentModificationException. CoW gives a stable snapshot for the iteration; writes copy the underlying array. OK for observer lists — read-heavy, write-rare.
T20. "Interview gives you 'design X'. What are the first 90 seconds?"
Reveal hint
Repeat the problem in your own words. Ask 3 scoping questions (who, what, NFRs). State 2 things that are out of scope. Write the noun list and the verb list. Only then start drawing classes. Talk through, do not type silently.
T21. "What's a 'God object' and why is it bad? Give a real fix."
Reveal hint
A class that knows / does too much (e.g., OrderManager with parsing, validation, persistence, email, analytics, retry). Symptoms: thousands of LOC, every change touches it, untestable. Fix by SRP split: OrderValidator, OrderRepository, OrderNotifier, OrderService (thin orchestrator).
T22. "Why might Builder be a bad fit?"
Reveal hint
With ≤3 params and no optional ones, it's overhead. With required-vs-optional asymmetry, prefer named factory methods or a record + sane defaults. Builder shines when there are 4+ optional fields or you want a fluent DSL.
