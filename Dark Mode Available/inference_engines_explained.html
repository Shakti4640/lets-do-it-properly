Inside LLM Inference

How a model file turns into the next word on your screen. We go from loading the weights, to tokens, attention, the KV cache, picking a token, and finally serving many users fast. Every chapter has a plain summary, a worked example with real numbers, and a common mistake to avoid.

00 · Big picture

Inference is one loop that runs again and again

A trained model is a big file full of numbers. The runtime loads those numbers, reads your prompt, and then guesses the next word piece. Then it does it again. And again.

The whole journey
In short: Load the model → read the prompt → guess one token → add it to the text → guess again, until a stop sign appears.
Model filenumbers + settings + word list
→
Runtime setupread · plan · reserve memory
→
Prompt step (prefill)text → IDs → run all at once
→
Generation loop (decode)one token per step
CPU / GPU / NPUthe chip that does the math
↔
Memoryweights · working data · KV cache
Training vs inference. Training changes the model's numbers. Inference does not change anything. It only reads the numbers and uses them to compute an answer.

Prefill phase

The whole prompt is processed in one go. All prompt tokens travel through the model together, so this part is fast per token.

The model also saves "notes" (called keys and values) about every prompt token. The next phase reuses these notes.

Decode phase

One new token per step. Each step reads the saved notes, so old tokens are never computed again.

This phase is slower per token, because the chip has to read all the model weights from memory for just one small input.

Worked example

You type "The sky is". That is 3 tokens. Prefill handles all 3 together in one pass.

Decode then runs: step 1 → "blue", step 2 → ".", step 3 → a stop token. Total work: 1 prefill pass + 3 decode passes.

Common mistake: thinking the model "writes the whole answer in its head" and then prints it. It does not. Each token is chosen only after the one before it exists.
01 · Startup

What is inside a model file

Before any math can start, the runtime must know the shape of the model: how many layers, how long each vector is, and how big the word list is.

Reading & loading
In short: A model file = settings + weights + tokenizer. The runtime reads the settings first, so it knows where to cut the big block of numbers into separate tensors (grids of numbers).

Settings (config)

n_layersdimn_headsn_kv_headshidden_dimvocab_sizeseq_len

Each number sets the size of a tensor. If one number is wrong, every byte position after it is also wrong, and the math produces garbage.

Weights (the learned numbers)

The embedding table, the norm scales, the attention matrices (Q, K, V, O), the feed-forward matrices, and the output matrix.

These are read-only during inference.

Tokenizer

The list of word pieces, their ID numbers, the merge rules, and the special tokens like "start" and "stop".

Runtime state

Working vectors, attention scores, logits (raw output scores), sampling buffers, and the KV cache. This part changes on every step.

A simple C implementation keeps three structs: Config (the settings), TransformerWeights (read-only numbers) and RunState (the changing scratch space). Keeping "fixed data" and "changing data" apart makes the code much easier to reason about.
address of one number = start of tensor + (index × bytes per number)

In low-level C code, the programmer computes these addresses by hand. The compiler does not check that an address really points at the tensor you meant. A wrong offset gives wrong numbers, not an error.

Worked example: Llama-2 7B

Settings: 32 layers · dim 4096 · 32 heads · hidden_dim 11008 · vocab 32000.

Parameter count ≈ 6.7 billion numbers. Stored in 16-bit (2 bytes each) that is ≈ 13.5 GB. Stored in 4-bit it is ≈ 3.5–4 GB.

Common mistake: reading "7B" as "7 GB". It means 7 billion numbers. The size in bytes depends on how many bits each number uses.
02 · Where the weights live

Memory mapping: use the file where it sits

Copying 13 GB into RAM takes time. Memory mapping (mmap) is a trick where the program asks the operating system to make the file look like normal memory.

mmap idea
In short: No big copy at start. The OS loads each small page of the file only when the program first touches it.
Model file on disktensor bytes in order
→
Address range in the programpages backed by the file
→
CPU reads a tensorpage fault → OS loads that 4 KB page

Plain read and copy

read() copies bytes into a buffer you own. Two copies may exist at once: the OS page cache and your buffer. Startup waits until the whole copy is done.

Memory-mapped file

No copy up front. The OS page cache is the only copy. Startup is almost instant. The first use of each page pays a small cost (a page fault).

mmap does not make the model free. Every page you touch still needs real RAM. If RAM runs short, the OS throws pages out and loads them again later. That is slow and makes the model stutter.
Why 64-bit offsets matter

A 13 GB file has byte positions bigger than 4,294,967,295, which is the largest 32-bit number. If the code uses 32-bit offsets, the number wraps around and points to the wrong place. Offsets and pointer math must use 64-bit types.

Worked example

A 13.5 GB file with 4 KB pages has about 3.3 million pages. The first forward pass touches every weight, so every page is loaded once. After that, pages stay in RAM for as long as there is room.

Common mistake: looking at the process memory (RSS) right after mmap and thinking the model is tiny. RSS only counts pages touched so far. Run one forward pass, then measure.
03 · Input

Text becomes a list of numbers

The model never sees letters. A tokenizer cuts the text into pieces from a fixed list (the vocabulary) and gives each piece an ID number.

BPE example
In short: Text → pieces → IDs. The pieces are not always whole words. Common words are one piece; rare words are split into parts.
"unhappiness" → ["un", "happ", "iness"] → [417, 8921, 304]

Vocabulary lookuppieces + IDs
→
Token ID listarray of integers
BPE (byte pair encoding) in one line: start from single characters, keep joining the two neighbours that appeared together most often in training data, stop when no join rule applies. The join rules are stored in the tokenizer file.

Special tokens

Start-of-text, end-of-text, end-of-turn, and chat role markers like "user" and "assistant". They have IDs but no visible text. The model learns to stop when it produces the end token.

Byte fallback

Text the vocabulary does not know (rare symbols, emoji, other scripts) is split into raw bytes. Each byte has its own token, so nothing is ever "unknown".

Worked example

For English, one token is about 4 characters, or about ¾ of a word. A 1,000-word prompt is about 1,300 tokens.

Code, numbers and non-English text often cost 2–3× more tokens for the same amount of text.

Common mistake: counting words to estimate cost or context use. Count tokens. Also, two models with different tokenizers give different counts for the same text.
04 · Vectors

Each ID becomes a long list of numbers

An embedding is a lookup. Row number 417 of a big table is the vector for token 417. After that, position information is mixed in so the model knows word order.

Embedding + RoPE
In short: Token ID → one row of the embedding table → a vector of dim numbers. Position is added by rotating pairs of numbers.
Token ID 417
→
Embedding tablevocab_size rows × dim columns
→
Vector xdim numbers (e.g. 4096)
0.12−0.480.070.91…−0.22
The vector is not a dictionary meaning. It is a set of learned numbers. The later layers reshape it based on the words around it, so "bank" near "river" ends up different from "bank" near "money".

RoPE: rotary position embedding

RoPE rotates pairs of numbers inside Q and K by an angle that depends on the token's position. Some pairs turn fast, some turn slow, like the hands of a clock.

[x₁, x₂] → [x₁ cos θ − x₂ sin θ, x₁ sin θ + x₂ cos θ]

When a rotated Q meets a rotated K in the dot product, the angle between them equals the distance between their positions. So attention can "feel" how far apart two tokens are, without a separate position number.

Worked example

dim 4096 and vocab 32000 → the table has 32000 × 4096 = 131 million numbers ≈ 262 MB in 16-bit.

Looking up one token is just reading one row: 4096 × 2 bytes = 8 KB. Very cheap.

Common mistake: thinking position is "one extra number added at the end". It is spread across many dimensions by rotation. That is why it survives the dot product and why models can be stretched to longer contexts by changing the rotation speed.
05 · The repeated block

One layer: normalize → attention → add → normalize → MLP → add

A transformer layer makes two small edits to the running vector. It never replaces the vector. It adds to it. The stack of layers repeats this 32, 80 or more times.

Pre-norm block
In short: Keep what you had, add what you learned. The vector that flows through all layers is called the residual stream.

Without the "add back" step, a deep model would lose the input signal after a few layers. With it, each layer only has to learn a small correction.

RMSNorm

Divide the vector by its root-mean-square size (a kind of average length), then multiply each slot by a learned scale. A tiny epsilon (about 1e-5) stops division by zero.

This keeps numbers in a safe range so the next matrix multiply does not blow up.

SwiGLU MLP

Two matrices project the vector up to a wider size (a "gate" and an "up" path). The gate goes through a SiLU curve and is multiplied with the up path. A third matrix projects back down.

This is where most of the model's parameters live.

Worked example: where the 7B parameters are

Per layer, attention matrices ≈ 4 × 4096² = 67 million. MLP matrices ≈ 3 × 4096 × 11008 = 135 million. So the MLP is two thirds of each layer.

32 layers × 202 million ≈ 6.5 billion, plus the embedding and output tables ≈ 6.7 billion total.

Common mistake: assuming attention is the heavy part. For a short context, the MLP does more math and holds more weights. Attention only becomes the biggest cost at very long context, because its work grows with the number of tokens.
06 · Self-attention

Three views of the same vector

The same normalized vector is multiplied by three different matrices. The results have three jobs: Q asks a question, K says "here is what I have", V holds the content to pass on.

Query / Key / Value
In short: Compare Q with every K to decide how much to look at each token. Then collect a mix of their V vectors.
Normalized x
→
Three matrix multipliesWQ, WK, WV
→
Q, K, V vectors

Query (Q)

What the current token is looking for in earlier tokens.

Q = X WQ

Key (K)

What each earlier token offers for matching against a query.

K = X WK

Value (V)

The content that gets blended in when a token is attended to.

V = X WV

Library analogy

Q is your question. K is the label on each book. V is what is written inside. You compare your question with every label, then read a mix of the best-matching books.

Q and K only decide how much to look. V decides what you get. A high score does not copy the token; it blends that token's V vector into the result.

Many heads

The dim is split into heads. Each head has its own small Q, K, V matrices and finds its own pattern (one head may track grammar, another may track names). The outputs are joined back together and passed through one more matrix, WO.

Shapes

dim 4096 with 32 heads → each head is 128 numbers wide. WQ is 4096 × 4096. With grouped-query attention and 8 KV heads, WK and WV shrink to 4096 × 1024 each (4× smaller).

Worked example

Sentence: "The cat sat on the mat because it was tired." For the token "it", one head's Q matches the K of "cat" far more than the K of "mat". So the output for "it" carries mostly the V of "cat". The model has, in effect, resolved what "it" refers to.

Common mistake: thinking different heads see different tokens. All heads see all tokens. They just use different Q, K, V matrices, so they notice different things.
07 · The calculation

Score → softmax → weighted sum

Each query is compared with every allowed key. Softmax turns the scores into weights that add up to one. Those weights blend the value vectors.

Scaled dot-product attention
In short: Attention = softmax( Q·Kᵀ / √dk + mask ) · V. Four small steps, done for every head in every layer.
Attention(Q,K,V) = softmax(QKᵀ / √dk + mask) V

1 · Scores

Dot product of the query with each key. A bigger dot product means "more alike". Dividing by √dk (square root of the head width) keeps the numbers from growing too large as heads get wider.

2 · Softmax

Subtract the largest score (for numeric safety), take e to the power of each score, then divide by the sum. Result: positive weights that add up to 1.

3 · Causal mask

When generating, a token may not look at tokens that come after it. Future positions get a score of minus infinity, so their weight becomes 0.

4 · Weighted sum

Multiply each weight by its V vector and add them up. That sum is this head's output for this token.

Worked example: softmax by hand

Scores for one query: [2.0, 4.0, 3.0]. Subtract the max (4.0) → [−2, 0, −1].

ex → [0.135, 1.000, 0.368]. Sum = 1.503. Divide → [0.09, 0.67, 0.24].

Output = 0.09·V₁ + 0.67·V₂ + 0.24·V₃.

Common mistake: forgetting the mask. Without it, position 2 could peek at position 5 during training, learn to cheat, and then fail at real generation where the future does not exist yet.
08 · Decode speed-up

KV cache: save the keys and values, do not redo them

While generating token by token, the K and V vectors of all earlier tokens are kept in memory. The new token only needs to compute its own K and V and then look at the saved ones.

Memory vs compute
In short: Without the cache, step 100 would recompute K and V for 99 old tokens. With the cache, it computes them for 1 token and reads the other 99.
t = 0K₀ · V₀
t = 1K₁ · V₁
t = 2K₂ · V₂
t = 3K₃ · V₃
t = 4K₄ · V₄
t = 5new K₅ · V₅
Current token
→
Compute Q₅, K₅, V₅
→
Append K₅ / V₅ to the cache
→
Attend over positions 0…5
The cache saves the projection work (X · WK, X · WV). The attention compare still runs against every cached key, so each step still grows a little with context length.
KV bytes per token = 2 × layers × (kv_heads × head_dim) × bytes per number

Grouped-query attention (GQA)

Several query heads share one K/V head. For example 32 query heads share 8 KV heads. The cache gets 4× smaller, and quality stays almost the same.

The trade-off

Longer context and more users at the same time both grow the cache. On a busy server, the KV cache often decides how many users fit on one GPU.

Worked example

Llama-2 7B (32 layers, 32 KV heads × 128 = 4096 wide, 16-bit): per token = 2 × 32 × 4096 × 2 bytes = 512 KB. A 4,096-token context = 2 GB. Ten such users = 20 GB, more than the weights.

Llama-3 8B uses GQA with 8 KV heads: 128 KB per token → 0.5 GB for the same context.

Common mistake: sizing GPU memory for the weights only. With many users, the KV cache can take more memory than the model itself.
09 · Picking a token

Logits are scores; sampling picks one token

The final vector is multiplied by the output matrix. That gives one raw score (a logit) for every token in the vocabulary. A sampling rule turns those scores into one chosen token.

Logits → probabilities → choice
In short: 32,000 scores → softmax (with temperature) → probabilities → pick one. Temperature, top-k and top-p control how adventurous the pick is.

Temperature

Divide the logits by T before softmax. Low T (0.2) makes the top choice even more likely. High T (1.5) flattens the curve and makes rare tokens more likely. T = 0 means "always take the top one" (greedy).

Top-k

Keep only the k most likely tokens (say k = 40), set the rest to zero, re-normalize, then sample. Simple and cheap.

Top-p (nucleus)

Sort tokens by probability. Keep the smallest set whose probabilities add up to p (say 0.9). Sample inside that set. The set is small when the model is sure and large when it is unsure.

Repetition penalty

Lower the logits of tokens that already appeared, so the model does not loop on the same phrase. Too strong a penalty makes text odd, because common words like "the" get punished too.

Worked example: temperature

Logits [3.0, 2.0, 1.0].

T = 1 → probabilities [0.67, 0.24, 0.09].
T = 0.5 → logits become [6, 4, 2] → [0.87, 0.12, 0.02] (sharper).
T = 2 → logits become [1.5, 1.0, 0.5] → [0.51, 0.31, 0.19] (flatter).

Common mistake: setting temperature 0 and expecting a different answer each run. Greedy picks the same top token every time, apart from tiny floating-point differences between hardware.
10 · The loop

One token per pass, until a stop sign

The chosen token is added to the text. Its ID becomes the input for the next pass. The KV cache is carried along, so each pass only does new work.

Autoregressive loop
In short: forward → sample → append → forward → … Stop at an end token, a length limit, or a stop word set by the app.

Each new token is chosen using all earlier text, prompt and answer together. That is why the model can stay on topic, and also why a mistake early in the answer tends to steer what comes next.
while not finished: logits = model.forward(next_token, position, kv_cache) # one pass, reuses the cache next_token = sample(logits, temperature=0.7, top_p=0.9) output.append(next_token) position += 1 finished = next_token == EOS or len(output) >= max_tokens

Worked example: how long does a reply take?

A 200-token reply needs 200 forward passes. If one decode pass takes 25 ms, the reply takes about 5 seconds.

This barely changes with prompt length, because the prompt was handled once in prefill and is now cached.

Common mistake: thinking a long prompt makes every output token much slower. It mostly affects the first token (prefill time) and the KV memory used. Per-token decode time grows only a little with context.
11 · Runtime engineering

What an inference engine does beyond "load and run"

An inference engine (vLLM, TensorRT-LLM, llama.cpp, ONNX Runtime) rewrites the math graph, plans memory, picks the fastest kernel for your chip, and schedules work across requests.

Performance stack
In short: The model says what to compute. The engine decides how: fewer memory trips, smaller numbers, better-packed work.

Graph optimization

Join small operations into one (fusion), remove work whose result never changes (constant folding), and reorder data layouts. Each fused step saves a write and a read of the whole activation vector.

Quantization

Store weights with fewer bits (8-bit, 4-bit). Less memory, less bandwidth, faster decode. Covered in detail in chapter 15.

Memory planning

Reserve buffers once at start, reuse the same scratch memory in every layer, and manage KV blocks. This avoids slow memory allocation during generation.

Kernel choice

A kernel is a small program for one operation (a matrix multiply, a softmax). The engine picks the best one for your GPU, CPU or NPU, often from vendor libraries like cuBLAS or oneDNN.

Paged KV cache

Store the cache in fixed-size blocks instead of one big slab per user. Blocks are handed out as a conversation grows, like pages in an operating system. Almost no wasted memory.

Continuous batching

Let a new request join the batch as soon as another one finishes, instead of waiting for the whole batch. Covered in chapter 16.

Worked example: why fusion matters

Fusing "RMSNorm + matrix multiply" saves one write and one read of a 4096-number vector per layer. That is 16 KB × 2 per layer, × 32 layers, × every token, × every user. On a memory-bound workload, these small savings add up to real speed.

Common mistake: running a raw PyTorch forward loop in production and blaming the GPU. A good engine is often 5–20× faster on the same hardware for a busy server.
12 · Deployment

From one kernel to a serving system

The runtime runs math on hardware. The serving layer sits above it: it queues requests, groups them into batches, hands out cache memory, and streams tokens back to users.

End to end

Streaming matters for how fast the system feels. Users see the first word after prefill, long before the last word is ready.

Latency numbers

TTFT (time to first token): how long until the first word appears. Mostly prefill.
TPOT (time per output token): the pause between words. Mostly decode.
P99: the slowest 1% of requests. Users remember these.

Throughput numbers

Requests per second, input tokens per second, output tokens per second, and how many users fit at once (limited by KV memory). GPU utilization tells you if the chip is actually busy.

Worked example

TTFT 300 ms + 200 output tokens × 25 ms = 5.3 seconds end to end. The user sees text start at 0.3 s and finish at 5.3 s. If you cut TPOT to 15 ms by batching better and quantizing, the same reply takes 3.3 s.

Common mistake: reporting only average latency. A system with a 2 s average but a 30 s P99 feels broken to one user in a hundred, which is many users per day.
13 · Two very different jobs

Prefill is math-heavy; decode is memory-heavy

Prefill multiplies a big block of tokens by the weights at once. Decode multiplies a single token by the weights, over and over. The chip is busy in the first case and mostly waiting in the second.

Compute-bound vs memory-bound
In short: Decode speed is set by how fast the GPU can read the weights, not by how fast it can multiply. Batching many users fixes this by reading once and using many times.

Decode for one user: tiny math, huge read. Time ≈ bytes ÷ memory bandwidth.

Prefill

All prompt tokens go through each layer together. Cost grows with prompt length. Long prompts are often split into chunks so they do not block other users' decode steps.

Decode

Every weight is read from memory for one tiny input. Doubling the GPU's math speed changes almost nothing. Doubling memory bandwidth nearly doubles speed.

Disaggregated serving

Some systems run prefill on one set of GPUs and decode on another, then ship the KV cache across. Each set is tuned for its own kind of work.

Roofline idea

Arithmetic intensity = math operations per byte read. Below the chip's balance point you are memory-bound; above it you are compute-bound. Decode for one user sits far below.

Worked example

7B model in 16-bit = 13.5 GB of weights. An A100 moves about 2 TB/s. Reading the weights once takes 13.5 ÷ 2000 ≈ 6.7 ms. That is the floor for one decode step, however fast the math units are.

With 32 users in one batch, the weights are still read once per step. Now you get 32 tokens for roughly the same time → almost 32× more tokens per second.

Common mistake: choosing a GPU by its TFLOPS number for a single-user chat app. For decode, memory bandwidth (and memory size) is what matters.
14 · Memory traffic

FlashAttention: never write the big score table

Moving data is slower than doing math. Plain attention writes an n × n table of scores to GPU memory, reads it back for softmax, and reads it again to multiply with V. FlashAttention does the same math in small tiles that stay on the chip.

Exact, just reordered
In short: Same answer, 2–4× faster, and memory grows with n instead of n². The trick is a running softmax that can be computed piece by piece.
Plain attentionwrite n×n scores → read → softmax → write → read → × V
vs
FlashAttentionload a tile of K, V into fast on-chip memory → update running result → next tile

Two kinds of memory on a GPU

HBM (main GPU memory): big, 40–80 GB, about 2–3 TB/s.
SRAM (on-chip): tiny, a few MB in total, about 10× faster. FlashAttention keeps the working tile in SRAM.

Online softmax

Softmax needs the maximum and the sum over all scores. FlashAttention keeps a running max and a running sum. When a new tile arrives with a bigger max, it rescales what it already has. Nothing is lost.

mnew = max(mold, mtile)    lnew = lold·e(mold − mnew) + Σ e(s − mnew)

m is the running maximum, l is the running sum. The output vector is rescaled with the same factor, so the final result is identical to doing softmax over everything at once.

Why it is exact

No approximation. Only the order of operations changes. Results match plain attention up to normal floating-point rounding.

Decode-time version

During decode there is only one query but thousands of cached keys. "Flash-decoding" splits the keys across many GPU blocks, computes partial results in parallel, then merges them with the same rescaling rule.

Worked example

8,192 tokens, 32 heads, 16-bit. The score table for one layer is 32 × 8192² × 2 bytes = 4.3 GB. Writing and reading it twice per layer, 32 layers deep, is the whole slow-down. FlashAttention never creates this table at all.

Common mistake: thinking FlashAttention is a shortcut that trades accuracy for speed. It is not an approximation. Sparse attention and sliding-window attention are approximations; FlashAttention is just a smarter order of the same arithmetic.
15 · Smaller numbers

Quantization: store each weight with fewer bits

A 16-bit number has 65,536 possible values. A 4-bit number has 16. Quantization maps each small group of weights onto a short grid, and stores one scale (and often one offset) per group to map back.

FP16 → INT8 → INT4
In short: Fewer bits = less memory and faster decode (less to read). Done well, quality drops only a little. Done badly, the model gets noticeably dumber.
weight ≈ scale × (q − zero_point)    where q is a small integer, e.g. 0…15

FP16 / BF16 (2 bytes)

The normal training precision. The baseline for quality. 7B model ≈ 13.5 GB.

FP8 (1 byte)

A floating-point format with 8 bits. Needs recent GPUs (Hopper, Blackwell). Close to lossless for most models, and the math units run FP8 natively, so it speeds up prefill too.

INT8 (1 byte)

Integers with one scale per row or per group. About half the memory. Very safe for quality.

INT4 (½ byte)

Integers 0–15 with a scale and zero point per group of 32–128 weights. About a quarter of the memory. Quality is good for larger models, weaker for small ones.

GGUF (llama.cpp)

A file format with many block schemes, written like Q4_K_M or Q8_0. Built for CPUs and small GPUs. Mixed precision inside: important tensors keep more bits.

GPTQ

Uses a few hundred sample inputs (calibration data) and second-order information to choose the best rounding for each weight, one column at a time. Mostly 4-bit, GPU-focused.

AWQ

Finds the ~1% of weight channels that matter most (the ones hit by large activations), scales them up before rounding so they keep precision, then scales back. Fast and simple to apply.

Weight-only vs weight + activation

Weight-only (GPTQ, AWQ, GGUF) shrinks memory and speeds up decode; math still runs in 16-bit after de-quantizing. Quantizing activations too (SmoothQuant, FP8) lets the math units run in low precision, which also speeds up prefill.

Where it hurts

Outlier weights, very small models (under 3B), and tasks that need exact recall (long numbers, code) lose the most. Always test on your own prompts.

Worked example: 7B model

FP16: 13.5 GB → INT8: 6.7 GB → Q4 (with scales): about 3.8 GB. Because decode is memory-bound, decode speed rises roughly in line with the smaller read: about 3× faster at 4-bit on the same GPU.

A 4-bit 7B model fits on an 8 GB laptop GPU with room for a few thousand tokens of KV cache.

Common mistake: comparing quantization methods by file size alone. Two 4-bit files can differ a lot in quality. Measure perplexity or task accuracy on your own data before you choose.
16 · Many users at once

Batching: read the weights once, serve many users

Decode for one user reads all the weights for one tiny input. If 32 users are at the decode step together, the same read now produces 32 tokens. This is the single biggest throughput win in serving.

Throughput vs latency
In short: Bigger batch → far more tokens per second for the whole server, with only a small slow-down per user. Continuous batching keeps the batch full all the time.

The curve flattens when the GPU becomes compute-bound or the KV cache runs out of memory. Then the only way up is more GPUs.

Static batching (old way)

Wait for N requests, run them together, and release them all when the longest one is done. Short replies sit idle waiting for long ones. GPU slots go empty.

Continuous batching

At every decode step, finished sequences leave and waiting requests join. The batch is always as full as memory allows. This alone gives several times more throughput.

Paged KV cache

KV memory is handed out in fixed blocks (for example 16 tokens each). No big up-front reservation per user, almost zero waste, and blocks can be freed the moment a request ends.

Prefix caching

Many requests share the same system prompt. Its KV blocks are computed once and shared by all of them. Prefill for those tokens becomes free.

Worked example

Batch 1: step time ≈ 6.7 ms (weights read). Throughput ≈ 150 tokens/s.

Batch 32: weights still read once; extra math is small; step time ≈ 9 ms. Throughput ≈ 32 ÷ 0.009 ≈ 3,500 tokens/s. Each user waits 2.3 ms longer per token; the server does 23× more work.

Common mistake: judging a serving stack by single-user speed. The point of batching is tokens per second per GPU dollar. Test it under load.
17 · Guess, then check

Speculative decoding: a small model drafts, the big model checks

A small fast "draft" model guesses the next few tokens. The big model then checks all of them in one single pass. Correct guesses are kept. The first wrong guess is replaced by the big model's own choice.

Free speed, same output
In short: Because decode is memory-bound, checking 4 tokens costs about the same as producing 1. If most guesses are right, you get 2–3 tokens per big-model pass.

Theskyisgreen

Three guesses accepted. The fourth is rejected and replaced by the big model's token ("blue"). Four tokens of progress for one big-model pass.

The check is done with a rule called rejection sampling. It compares the draft model's probabilities with the big model's. The final text has exactly the same probability distribution as the big model alone. Speed changes; quality does not.

Why it is almost free

The big model reads its weights once per pass anyway. Processing 4 tokens instead of 1 adds a little math but no extra memory traffic. On a memory-bound step, that is nearly free.

Acceptance rate

Predictable text (code, boilerplate, lists) is accepted 70–90% of the time. Creative or unusual text is accepted less, so the speed-up is smaller there.

Variants

Medusa / EAGLE: extra small heads on the big model itself make the draft, so no second model is needed.
N-gram lookup: reuse text already in the prompt as the draft. Great for editing and summarizing tasks.

Costs

The draft model needs memory and its own KV cache. Under heavy batching, the big model is already busy, so the gain shrinks. Best for low-latency, single-user or low-batch settings.

Worked example

Draft 4 tokens per round; 75% of them are accepted on average. Expected progress ≈ 3 tokens per big-model pass instead of 1. After paying for the draft model's time, the end-to-end speed-up is about 2–2.5×.

Common mistake: thinking the small model "writes part of the answer" and quality drops. Every token is either accepted by the big model's own probability or replaced by its own sample. The output is statistically identical.
18 · Sparse models

Mixture of Experts: many small MLPs, only a few used per token

In an MoE layer, the single big MLP is replaced by several smaller MLPs called experts. A tiny router network looks at each token and picks the top 2 experts for it. Only those 2 run.

Big memory, small math
In short: You store all the experts, but each token only pays for two of them. More knowledge for the same compute, at the price of more memory.

Attention layers are shared by all tokens as usual. Only the MLP part is split into experts. The next token may go to completely different experts.

Sparse compute

Mixtral 8×7B has about 47 billion parameters in total but uses about 13 billion per token. So it runs at roughly the speed of a 13B dense model while knowing more.

Memory cost

All 8 experts must sit in GPU memory even though each token touches 2. The memory bill is for 47B, the compute bill for 13B.

Load balance

Training adds a small penalty if some experts get all the work. At serving time, tokens in a batch are grouped by expert so each expert's matrix is read once per step.

Routing is per token

The same word can go to different experts in a different sentence. Routing is learned, not hand-designed.

Worked example

8 experts, top-2. Per token: attention + 2 of 8 MLPs. Weights to store: all 8. In a batch of 64 tokens, each expert gets about 16 tokens, so every expert's weights are read once and used 16 times. That keeps MoE efficient under load.

Common mistake: picturing experts as topic experts, one for maths, one for law, one for code. They are not. Routing happens per token based on vector patterns, and the split is usually not readable by humans.
