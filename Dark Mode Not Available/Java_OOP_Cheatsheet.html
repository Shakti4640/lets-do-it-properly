Q1. Integer a = 127, b = 127; Integer c = 128, d = 128;. What do a == b and c == d return?
Reveal hint
a == b is true (inside the Integer cache -128..127, same object). c == d is false (outside the cache, different Integer objects). Moral: never use == on wrappers.
Q2. int x = null; — does it compile?
Reveal hint
No. Primitives can't be null. Integer x = null; compiles — but unboxing that x anywhere throws NullPointerException.
Q3. Which is faster for summing a million ints: List<Integer> or int[]?
Reveal hint
int[], by a lot. List<Integer> boxes every value, breaks cache locality, and uses ~4x the memory.
Q4. Double d = 0.0; if (d == -0.0) — what do you get, and is that safe?
Reveal hint
true with ==, but Double.compare(0.0, -0.0) returns a positive number and Double.valueOf(0.0).equals(Double.valueOf(-0.0)) returns false. Pick the semantic you actually want.

1. The Four OOP Pillars — Overview

PillarOne-line ideaKey Java hookSmell if misused
EncapsulationHide state, expose behavior via methods.private fields + getters/settersPublic mutable fields; anemic domain
Inheritance"is-a" reuse of behavior.extends, superDeep hierarchies, inheritance for reuse only
PolymorphismSame call, different behavior at runtime.Overriding + upcast referenceinstanceof ladders everywhere
AbstractionModel what not how.abstract, interfaceInterfaces with one concrete impl and no reason
Memory hook (A-PIE): Abstraction · Polymorphism · Inheritance · Encapsulation. If a design violates one pillar, almost always it quietly breaks another too.
Q. Is "inheritance" automatically good because it reuses code?
Reveal hint
Think "is-a" vs "has-a". Prefer composition unless there is a true subtype relationship (LSP). Reuse alone ≠ inheritance.

2. Classes & Objects

TopicWrong / Not allowedBest practice / Right
File / class name Public class name ≠ file name; two public classes in one .java file. One public class per file, file named exactly after that class.
Field defaults Assuming local variables are zero-initialized. Instance fields default (0 / false / null); local variables must be explicitly initialized.
Object creation Foo f; then f.doX() without new. Foo f = new Foo(); before use. Uninitialized object refs are null.
Package Classes in default (unnamed) package for real code. Always declare a package; follow reverse-DNS convention.
Trick: Foo[] a = new Foo[3]; creates an array of 3 null references — the Foo objects themselves are not created.
Q. int x; inside a method — does it default to 0?
Reveal hint
No. Only fields get default values. Local variables must be definitely assigned before use or the compiler complains.

3. Constructors

RuleWrongRight
Return typeGiving a constructor a return type (even void) — it becomes a normal method.No return type. Name must exactly match class name.

class A { A(int x){ /*...*/ } }
class B extends A {
    B() { super(10); /* MUST be first statement */ }
}
Q. Can a constructor be final, static, or abstract?
Reveal hint
No to all three. Ctors are never inherited (so final is meaningless), they run on an instance (so not static), and they must always have a body (so not abstract).

Q. A subclass in another package has a Parent p = new Parent();. Can it call p.protectedMethod()?
Reveal hint

5. Encapsulation

TopicWrongRight
Fieldspublic int balance;private int balance; + controlled methods.
Getter returning collectionreturn this.items; (caller mutates internal list).Return Collections.unmodifiableList(items) or a defensive copy.
SetterBlind setter for everything.Validate in setter; or drop setter and accept only via ctor (immutability).
Mutable inputStoring passed-in Date directly.Defensive copy on input AND output (new Date(d.getTime())), or use java.time (immutable).
Rule of thumb: If a field never changes after construction, make it private final and drop the setter.
Q. My class has only private fields and getters — is it immutable?
Reveal hint
Not necessarily. If the getter returns a mutable object (e.g., List, Date, array) without a defensive copy, outside code can still mutate your state.

6. Inheritance

RuleWrong / Not allowedRight
Multiple class inheritanceclass C extends A, B — not allowed.Extend one class, implement many interfaces.
final classTrying to extend final classes (e.g., String, Integer).Use composition or utility wrappers.
private membersAssuming child inherits private fields.Private members are not inherited; use protected or accessors.
super()Forgetting parent has no no-arg ctor.Explicitly call super(args) as first statement.
Reuse via inheritanceSubclassing just to reuse a few methods.Prefer composition; inherit only for true "is-a".
LSPSubclass strengthens preconditions or weakens postconditions.Subtype must be usable wherever supertype is — no surprises.
Init order: static parent → static child → instance parent (fields + ctor) → instance child (fields + ctor).
Q. Square extends Rectangle — why is this a classic OOP mistake?
Reveal hint
Violates LSP. Setting width independently of height breaks the Rectangle contract for a Square. Model with a shared interface, not inheritance.

7. Polymorphism (Runtime Dispatch)

TopicWrongRight
Field accessExpecting polymorphism on fields.Fields are resolved by reference type (static binding). Only methods dispatch dynamically.
static methodExpecting override on static methods.static methods are hidden, not overridden. Resolved by reference type.
private methodMarking it @Override.private methods are not polymorphic; they can't be overridden.
constructor callsCalling overridable method from ctor.Dangerous: subclass version runs before subclass fields are initialized.
covariant returnChanging return type to unrelated type.Allowed only if new return type is a subtype of the original.
 
class Animal { String name = "animal"; void speak(){ System.out.println("?"); } }
class Dog extends Animal { String name = "dog"; void speak(){ System.out.println("woof"); } }

Animal a = new Dog();
a.speak();    // "woof"  (method = dynamic)
System.out.println(a.name); // "animal" (field = static, by ref type)
Q. Can overriding change the exception signature freely?
Reveal hint
No. An override may throw fewer/narrower checked exceptions, but not broader ones. Unchecked (RuntimeException) are unrestricted.

8. Abstraction

TopicWrongRight
Abstract classInstantiating it: new Shape().Only subclass concrete types can be instantiated.
Abstract methodGiving a body: abstract void x(){}.No body, ends with ;. Class must then be abstract.
MixingPrivate abstract / static abstract / final abstract method.Illegal combinations; abstract needs override, others prevent it.
ModelingExposing raw data (getters/setters) as the API.Expose behavior (verbs). Hide representation.
Q. Can an abstract class have a constructor?
Reveal hint
Yes. It runs when a concrete subclass is instantiated, via super(...). You just can't call new AbstractThing() directly.

9. Abstract Class vs Interface

AspectAbstract classInterface
Multiple inheritanceSingle only (extends).Multiple (implements).
State (fields)Any fields, including mutable.Only public static final constants.
ConstructorYes.No.
Method bodiesAny: abstract or concrete.default, static, private (Java 9+), and abstract.
Access modifiers on methodsAny.Effectively public (abstract/default); private allowed for helpers.

Diamond problem: If two interfaces give conflicting default methods, the implementing class must override and can call InterfaceName.super.method().
Q. Interface fields — can you reassign them?
Reveal hint
No. They are implicitly public static final. They must be initialized at declaration and cannot change.

Q. Does changing only the return type qualify as overloading?
Reveal hint
No. Overloading requires different parameter lists. Same params + different return type = compile error.

11. static keyword

TopicWrongRight
Using thisthis or super inside a static method.Not allowed; no instance context.
Accessing instance dataReferencing instance field from static context.Only access static members or passed-in instances.
Calling via instanceobj.staticMethod() — compiles but misleads.Call as ClassName.staticMethod().
Static init orderAssuming order doesn't matter.Static blocks/fields run top-to-bottom, once, on class init.
Singleton via staticPublic mutable static state.Prefer DI or enum singleton; keep static state immutable.
Q. Can a static method be overridden?
Reveal hint
No — it's hidden. Dispatch is by reference type, not runtime type. @Override on a static method is a compile error.

12. final keyword

Applied toEffectWatch out for
variableAssign-once.For reference types, only the reference is final — the object is still mutable.
methodCannot be overridden.Subclasses can still overload same-name with different params.
classCannot be extended.Breaks plug-in extensibility; use judiciously.

Q. Is final the same as immutable?
Reveal hint
No. final prevents rebinding. Immutability additionally requires that the referenced object's state can't change.

13. this & super

TopicWrongRight
this() / super()Both in same ctor.Only one, and it must be first statement.
In static contextUsing this/super inside static method.Not allowed.
super fieldsExpecting dynamic dispatch with super.field.Fields are static-bound; super.x reads the parent's declared field.

Q. Can this and super reference different objects?
Reveal hint
No. They refer to the same object — super is just a compile-time view of that object as its parent type.

14. Inner / Nested Classes

Q. Lambda vs anonymous inner class — do they share the same this?
Reveal hint
No. In an anonymous inner class, this refers to the inner instance. In a lambda, this refers to the enclosing class's instance.

15. Object Class Methods (equals, hashCode, toString, clone, finalize)

Q. Two objects are equals. Must they have the same hashCode? The reverse?
Reveal hint
Equal ⇒ same hash (mandatory). Same hash ⇒ equal is NOT required (collisions are allowed).

16. Composition vs Inheritance ("has-a" vs "is-a")

TopicInheritance pitfallComposition fix
ReuseSubclass to get a couple methods; inherits unwanted API too.Hold the helper as a field and delegate only what you need.
Fragile base classParent adds a new method; subclass silently inherits or breaks.Composition limits coupling surface.
Liskov violationsSubtypes break supertype contract.No subtype pressure with composition.
DecoratorsHard to add cross-cutting behavior via subclassing.Compose wrappers implementing same interface.
Heuristic: "Favor composition over inheritance" — use inheritance only when every operation on the parent also makes sense on the child, and the subclass truly is-a parent.
Q. Stack extends Vector in JDK — what's the design smell?
Reveal hint
Stack inherits all of Vector's random-access methods, breaking the LIFO contract. A clean design would compose a Vector/Deque inside a Stack, not extend it.

16b. Is-a vs Has-a — Deep Dive with Many Examples

This is the single most under-tested instinct in Java design. Almost every "bad inheritance" bug collapses back to the same sentence: we said "is-a" when we should have said "has-a".

The one-sentence test

RelationshipRead it aloudJava toolMeaning
is-a"A Dog is a Animal."class Dog extends Animal / implementsSubstitutable. Anywhere an Animal is expected, a Dog fits without surprise.
has-a"A Car has an Engine."field of that type inside the classOwnership/usage. Car uses Engine's behavior but is not an Engine.
uses-a (weak has-a)"A Printer uses a PaperTray at runtime."method parameter or short-lived refDependency without ownership.
Rule of thumb: If the sentence "every X is a Y, always and forever, and every operation on Y makes sense on X" is not obviously true, it's not is-a. Make it has-a.

Side-by-side: the same domain done wrong and right

ScenarioWrong ("is-a" abuse)Right ("has-a")
Stack of integers class Stack extends ArrayList<Integer> — inherits get(i), remove(i), add(i, x). LIFO contract broken. class Stack { private final Deque<Integer> data = new ArrayDeque<>(); void push(int x){...} int pop(){...} }
Instrumented HashSet (count added) class CountingSet<E> extends HashSet<E> — addAll internally calls add, double-counting. Fragile-base-class bug. Compose: class CountingSet<E> implements Set<E> { private final Set<E> inner = new HashSet<>(); ... }. Delegate, count in one place.
Square / Rectangle class Square extends Rectangle — setWidth can't keep the square invariant. Both implement Shape; no inheritance between them.
Car / Engine class Car extends Engine — a Car is not an Engine. class Car { private final Engine engine; }
Employee / Address class Employee extends Address — senseless. class Employee { private Address address; }
User / Logger class User extends Logger just to call log(). Inject a Logger: class User { private final Logger log; }
Order / List of items class Order extends ArrayList<Item> — Order is not a list, it owns one. class Order { private final List<Item> items = new ArrayList<>(); }; expose only intended operations.
Timer / Thread class Timer extends Thread — ties lifecycle to Thread and exposes start/interrupt as API. class Timer { private final Thread worker; } or, better, inject an ExecutorService.
PDF report / Exporter class PdfReport extends CsvExporter to "reuse header code". Extract HeaderBuilder; both reports compose it.
Manager / Employee class Manager extends Employee — usually fine, until a manager stops being an employee (contractor, board member). Then you're stuck. Model "role" as has-a: class Person { Set<Role> roles; }. Role can include Manager, Employee, Contractor.

Java snippets — wrong vs right, side by side

1) Stack that lies about itself

// WRONG — exposes list API, breaks LIFO
class IntStack extends ArrayList<Integer> {
    public void push(int x){ add(x); }
    public int pop(){ return remove(size()-1); }
}
// Client can still call s.add(0, 99); or s.remove(0); — LIFO gone.

// RIGHT — has-a
final class IntStack {
    private final Deque<Integer> data = new ArrayDeque<>();
    public void push(int x){ data.push(x); }
    public int pop(){ return data.pop(); }
    public int peek(){ return data.peek(); }
    public int size(){ return data.size(); }
}

2) Car & Engine

// WRONG — "A Car is an Engine" is false
class Car extends Engine { ... }

// RIGHT — "A Car has an Engine"
class Car {
    private final Engine engine;          // composition
    private final List<Wheel> wheels;     // aggregation
    public Car(Engine engine, List<Wheel> wheels){
        this.engine = engine;
        this.wheels = List.copyOf(wheels);
    }
    public void start(){ engine.ignite(); }
}

3) Decorator (both is-a AND has-a, legitimately)

// Reader is the contract; BufferedReader IS-A Reader and HAS-A Reader
class BufferedReader extends Reader {
    private final Reader inner;           // has-a
    BufferedReader(Reader inner){ this.inner = inner; }
    public int read(char[] buf, int off, int len){
        // buffered logic that delegates to inner.read(...)
        return inner.read(buf, off, len);
    }
}

4) Role modeling — avoid "Manager extends Employee" trap

// WRONG — rigid. What if someone is both manager and contractor?
class Employee { ... }
class Manager extends Employee { List<Employee> reports; }

// RIGHT — has-a roles
class Person {
    private final Set<Role> roles = new HashSet<>();
    public boolean hasRole(Role r){ return roles.contains(r); }
    public void assign(Role r){ roles.add(r); }
}
interface Role { String name(); }
class ManagerRole implements Role { List<Person> reports; public String name(){return "Manager";} }
class EmployeeRole implements Role { BigDecimal salary; public String name(){return "Employee";} }

5) Computer composition (strong vs weak ownership)

class Computer {
    private final CPU cpu;               // composition — dies with the computer
    private final RAM ram;               // composition
    private final Disk disk;             // composition
    private final List<UsbDevice> usb;   // aggregation — plugged in, removable
}

6) Service + Repository (dependency inversion in action)

interface OrderRepository { Order find(long id); void save(Order o); }
class OrderService {
    private final OrderRepository repo; // has-a abstraction, not a concrete class
    OrderService(OrderRepository repo){ this.repo = repo; }
}
// Tests inject InMemoryOrderRepository; prod injects JdbcOrderRepository. No subclassing of OrderService needed.

Practical drill: before writing extends, rewrite the sentence as "every X is a Y in every context where Y is used". If you can think of one context where it's not, switch to has-a.
Q1. "Properties extends Hashtable" in the JDK — is-a or design mistake?
Reveal hint
Design mistake. Properties is documented to hold String keys and values, but because it extends Hashtable<Object,Object>, callers can put(123, new Date()). A has-a design (Properties holding a Hashtable) would have enforced the String-only contract.
Q2. A Penguin is a Bird. Birds fly. Penguins don't. How do you model it?
Reveal hint
Don't put fly() on Bird. Make Flyable a separate interface (capability). Sparrow implements Bird, Flyable; Penguin implements Bird, Swimmable. Capability via is-a (interface), not behavior baked into a class hierarchy.
Q3. You want a logging list. Which is better: class LoggingList<E> extends ArrayList<E> or composing a List<E>?
Reveal hint
Composition. Extending ArrayList ties you to its internal method dispatch (self-calls), so overriding add won't necessarily intercept addAll. Wrap a List<E> and implement List<E> — now every entry point is explicit.
Q4. Is "Order has-a List<Item>" composition or aggregation?
Reveal hint
Usually composition: items don't exist without the order, and deleting the order deletes the items. It's aggregation only if line items are meaningful entities referenced from elsewhere (rare).
Q5. "Replace inheritance with composition" — does that mean never use extends?
Reveal hint
No. Use extends when the subtype truly honors the parent's contract in every context (e.g., FileInputStream extends InputStream, IllegalArgumentException extends RuntimeException). The advice is to default to composition and reach for inheritance with evidence.

Q1. List<Integer> list = new ArrayList<>(List.of(1,2,3)); list.remove(1); — what's left?
Reveal hint
[1, 3]. remove(int) wins over remove(Object) for primitive int — removes index 1 (the value 2). Use Integer.valueOf(1) to remove the value 1.
Q2. Why can a HashMap have one null key but ConcurrentHashMap cannot?
Reveal hint
ConcurrentHashMap uses null as a sentinel internally for "absent", so a null value/key would be ambiguous under concurrent reads (can't tell "not there" from "there with null").
Q3. Collections.unmodifiableList(list) vs List.copyOf(list) — which is immutable?
Reveal hint
List.copyOf. unmodifiableList returns a view; mutating the original mutates the view. copyOf makes a defensive copy into a truly immutable list.
Q4. Why does TreeSet consider two objects equal if their compareTo returns 0, even when equals says otherwise?
Reveal hint
Because TreeSet's contract says ordering drives equality. A comparator inconsistent with equals leads to surprising behavior — keep them in sync.
Q5. You insert a Person into a HashSet, then change their name field (used in hashCode). Now set.contains(person) returns false. Why?
Reveal hint
The bucket was chosen using the original hash. After mutation, contains looks in a different bucket and doesn't find it. Treat hash keys as immutable after insertion.
Q6. What's the fastest way to count occurrences of strings in a list?
Reveal hint
Map<String,Integer> counts = new HashMap<>(); list.forEach(s -> counts.merge(s, 1, Integer::sum)); — or stream().collect(Collectors.groupingBy(Function.identity(), Collectors.counting())).

22. Java Streams — Deep Dive

A Stream is a pipeline over a data source. It's not a data structure, does not store elements, and is consumed once. Streams push for declarative data processing, lazy evaluation, and easy parallelism.

Core mental model

  Source  →  [Intermediate ops ... lazy]  →  Terminal op (eager)
  list    →   filter → map → sorted       →   collect / reduce / forEach
PropertyWhat it meansConsequence
LazyIntermediate ops build a plan; nothing runs until a terminal op.No terminal op = no work done.
Consumable onceAfter a terminal op, the stream is closed.Reusing throws IllegalStateException.
Possibly infiniteSources like Stream.iterate / generate.Need a short-circuit op (limit, findFirst).
Non-interferingDon't mutate the source during the pipeline.Use immutable data or functional updates.
Stateless lambdasLambdas shouldn't depend on mutable shared state.Makes parallel streams safe.

Worked examples

// 1) Group orders by customer and sum amount
Map<Long, BigDecimal> totals = orders.stream()
    .collect(groupingBy(Order::customerId,
             reducing(BigDecimal.ZERO, Order::amount, BigDecimal::add)));

// 2) Top-3 highest-rated products
List<Product> top3 = products.stream()
    .sorted(comparing(Product::rating).reversed())
    .limit(3)
    .toList();

// 3) Word frequency from a sentence
Map<String, Long> freq = Arrays.stream(sentence.toLowerCase().split("\\W+"))
    .filter(w -> !w.isBlank())
    .collect(groupingBy(identity(), counting()));

// 4) Flatten nested orders → line items → SKUs
List<String> skus = orders.stream()
    .flatMap(o -> o.lineItems().stream())
    .map(LineItem::sku)
    .distinct()
    .toList();

// 5) Two-stat collection in one pass (Java 12+)
record Stats(long count, double avg) {}
Stats s = list.stream().collect(
    teeing(counting(), averagingDouble(X::amount), Stats::new));

Performance & best practices

  • Pick the right source: arrays and ArrayList split well; LinkedList, Stream.iterate, BufferedReader.lines do not.
  • Order ops for short-circuiting: put cheap filter before expensive map, put limit early.
  • Use primitive streams when dealing with int/long/double.
  • Avoid sorted() + limit(k) for "top k" — prefer a manual heap or Comparator.comparing(...).reversed() via collector when K is small.
  • Prefer collect over manual forEach-and-add patterns for safety & parallelism.
  • Prefer toList() (Java 16+) for immutable results; Collectors.toCollection(ArrayList::new) when you need a mutable list.
  • Measure before parallelizing; the overhead (splitting, joining, task dispatch) often dominates.
Q1. Why does list.stream().count() followed by list.stream().forEach(...) work, but reusing the same stream variable doesn't?
Reveal hint
A stream can be consumed only once. Calling list.stream() each time produces a fresh stream; reusing a stored Stream<T> after a terminal op throws IllegalStateException.
Q2. Stream.iterate(0, i -> i+1).filter(i -> i > 1_000_000).findFirst() — does this finish?
Reveal hint
Yes. findFirst is short-circuiting, and filter is lazy, so the pipeline stops at the first match without evaluating the infinite tail.
Q3. What's wrong with list.parallelStream().forEach(map::put)?
Reveal hint
If map isn't thread-safe (e.g., HashMap), you race. Use collect(toMap(...)) or a ConcurrentHashMap.
Q4. stream.toList() vs stream.collect(Collectors.toList()) — same thing?
Reveal hint
No. Stream.toList() (Java 16+) returns an unmodifiable list that allows nulls. Collectors.toList() returns a mutable list whose exact type is unspecified.
Q5. A stream with .sorted() and a terminal .findFirst() — is it short-circuiting?
Reveal hint
No. sorted is a stateful intermediate op that must see every element before producing any. Short-circuit benefits are lost once a stateful op is in the pipeline.
Q6. Collectors.toMap(X::name, X::value) fails with IllegalStateException. Why?
Reveal hint
Duplicate keys. Provide a merge function: toMap(X::name, X::value, (a, b) -> a) or Integer::sum, depending on what you want.
Q7. When will .parallel() actually hurt performance?
Reveal hint
Small datasets, I/O-bound ops, non-splittable sources (LinkedList, iterate), stateful ops (sorted/distinct), or when the common ForkJoinPool is already busy.
