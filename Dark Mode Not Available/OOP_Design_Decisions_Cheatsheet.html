0. How to read this guide

Most tutorials teach you what a class, interface, or extends keyword does. That is not the hard part. The hard part is standing in front of a blank file and knowing which one to reach for — and being able to defend the choice when a reviewer pushes back.

So every section here is written around a decision, not a definition. The pattern repeats:

StepWhat we doWhy it matters
1. RequirementState what the code must do, in plain English.The relationship words ("is a", "has a", "can do", "varies by") are hiding in the sentence.
2. Naive moveThe first thing most people write.Usually works for today, hurts in six months.
3. The painThe exact line that becomes painful to change.Design quality only shows up at change time, never at write time.
4. The decisionPick the tool and justify it in one sentence.If you can't say the sentence, you picked wrong.
5. The resultThe refactored code.Proof the decision actually paid off.
The whole guide in one line: Inheritance and interfaces model what a thing is; composition models what a thing has or uses. Default to "has", earn the right to say "is".

1. The four tools at a glance

ToolSentence it modelsGives youCosts youReach for it when…
Concrete class "This is a concrete thing with state + behavior." The simplest unit. State, behavior, instances. Nothing — until you need variation it can't express. There is exactly one implementation and no fork in behavior yet.
Interface "X can do Y" / "X plays the role Y." A contract callers depend on; many unrelated impls; multiple roles per class. No shared code (pre-Java 8) — just the promise. Indirection. Behavior varies, callers shouldn't care which impl, or a type needs several roles.
Abstract class "X is a kind of Y, and all Ys share this skeleton." Partial implementation + enforced template + shared state. Single-parent lock-in (extends is used up). Tight coupling. Several impls are genuine subtypes and share real code/state.
Composition "X has a / uses a Y." Reuse without subtype pressure; swap parts at runtime; combine many behaviors. A little wiring/delegation boilerplate. You want a behavior but the "is-a" sentence is false or fragile. (Most of the time.)
How to use this table: read your requirement out loud and listen for the verb. "can / supports / is able to" → interface. "is a kind of … and they share code" → abstract class. "has / uses / is built from / delegates to" → composition. No variation at all yet → plain class, and don't add abstraction on speculation. Verdict: the grammar of the sentence picks the tool more reliably than any rule of thumb.

2. The one master question that drives every choice

Before you type class, interface, or extends, you only have to answer one thing about the relationship between two types A and B:

Read the sentence aloud…RelationshipToolThe test it must pass
"A is a B" — and stays one in every place a B is usedtrue subtypeextends / implementsLiskov: swap an A in for a B and nothing breaks or surprises.
"A can do B" / "A plays the role B"capabilityinterfaceThe role is independent of A's identity; other unrelated types can play it too.
"A has a B" / "A is built from B"ownershipfield (composition)B is a part/collaborator; A is not a kind of B.
"A uses a B for a moment"dependencyparameter / injected fieldA needs B's behavior but doesn't own its lifetime.
The trap everyone falls into: "I can reuse B's code if A extends B." Reuse is not a reason to inherit. Reuse is what composition is for. Inheritance is for substitutability. If you only want the code and not the "is-a", you want a field, not a parent.

Why "is-a" is a stronger claim than it sounds

Saying "A is a B" promises something brutal: every method B exposes must make sense on A, forever, including methods B's author hasn't written yet. That is why a true is-a is rare and a false one is a time bomb.

// The classic broken promise:
class Rectangle { void setWidth(int w){...} void setHeight(int h){...} }
class Square extends Rectangle { /* must keep width == height */ }

Rectangle r = new Square();
r.setWidth(5);
r.setHeight(10);   // a caller written for Rectangle expects 5 x 10...
// ...but a Square can't be 5 x 10. The "is-a" was a lie.
Decision: Square is not a Rectangle in a mutable model, because setWidth doesn't make sense on a Square. Verdict: both implement a read-only Shape interface (area()), and neither extends the other.

3. The decision flow (run this in your head every time)

START: I need type A to have some behavior / fit somewhere.

1. Is there only ONE behavior and no sign of variation yet?
   ├─ YES → plain concrete class. Stop. Don't pre-abstract.
   └─ NO  → go to 2.

2. Do callers need to treat several DIFFERENT types uniformly,
   without caring which concrete one they hold?
   ├─ YES → you need a polymorphic supertype → go to 3.
   └─ NO  → you just need to REUSE some behavior → go to 5.

3. Are the implementations RELATED (share real state + code) or
   UNRELATED (only share a promise)?
   ├─ UNRELATED, or a type needs MULTIPLE roles → INTERFACE.
   └─ RELATED, genuine subtypes sharing a skeleton → go to 4.

4. Is "A is a B in every context" true (passes Liskov)?
   ├─ YES → ABSTRACT CLASS (skeleton) or concrete inheritance.
   └─ NO  → step back: use an INTERFACE for the role +
            COMPOSITION for the shared code.

5. REUSE path: do you want B's behavior inside A?
   └─ Hold a B as a field and delegate (COMPOSITION).
      Add an interface on top only if callers must be polymorphic.
Notice the bias: three of the five exits land on interface or composition. Concrete inheritance is the last door you open, only after Liskov says yes. That bias is the whole point of "favor composition over inheritance".
If you find yourself saying…You probably want (wrong)You actually want (right)
"I'll extend it to reuse two methods."extendsa field + delegate (composition)
"Lots of unrelated classes need to be 'printable'."a base classinterface Printable
"All my parsers share 80% of the steps."copy-paste, or interface onlyabstract class with a template method
"This thing is sometimes a manager, sometimes a contractor."a subclass per combinationcomposition of roles
"I need to add behavior at runtime, stackable."a subclass per combinationdecorators (composition + shared interface)

4. Concrete class — the honest default

The most under-rated decision is not abstracting at all. A plain class with state and methods is the right answer far more often than the patterns crowd admits. Abstraction has a carrying cost: indirection, more files, harder navigation. You pay it only when variation actually arrives.

Requirement

"I need a Money value: an amount and a currency, that can add to another Money."

final class Money {
    private final long minorUnits;   // cents
    private final String currency;

    Money(long minorUnits, String currency){
        this.minorUnits = minorUnits;
        this.currency = currency;
    }
    Money plus(Money other){
        if(!currency.equals(other.currency))
            throw new IllegalArgumentException("currency mismatch");
        return new Money(minorUnits + other.minorUnits, currency);
    }
}
How we decided: there is one representation, one behavior, no second kind of Money on the horizon. No caller needs to swap implementations. So: no interface, no base class. Adding interface MoneyLike here would be abstraction with zero payoff — a classic "speculative generality" smell. Verdict: concrete final class. We can always extract an interface later when a second implementation appears — and not one day before.
Smell — premature interface: a project where every class has a matching IThing interface with exactly one implementation Thing. That is ceremony, not design. Extract the interface at the moment the second implementation (or the first mock you genuinely need) shows up.
Q. "Always code to an interface" — so should Money implement IMoney from day one?
Reveal hint
No. The maxim means depend on the narrowest type that does the job, not "wrap everything in an interface". With one impl and no polymorphic callers, the interface adds indirection and zero flexibility. YAGNI wins until a real second case arrives.

5. Interface — a contract / capability ("can-do")

An interface answers: "what can callers rely on, regardless of who implements it?" It is pure promise. Use it when the behavior varies, the implementations are unrelated, or a single type must play several roles.

The three signals that scream "interface"

SignalExampleWhy a class can't do it
Many unrelated types, one capabilityComparable, Serializable, AutoCloseableA String, a File, and a Socket share no ancestor — but all can be "closed".
A type needs multiple rolesclass Drone implements Flyable, Trackable, ChargeableJava allows only one parent class; you can implement many interfaces.
Callers should be decoupled from implList hides ArrayList vs LinkedListThe contract lets you swap the impl without touching callers.

Worked decision

Requirement: "Different objects in my app need to be exportable to JSON for an audit log: an Order, a User, a Shipment."

// Naive: a base class everything extends to get toJson().
// Problem: Order, User, Shipment are NOT the same kind of thing,
// and they already have their own natural hierarchies. Forcing a
// shared parent just to share toJson() burns the single extends slot.

// Decision: "can be exported" is a CAPABILITY, not an identity. → interface.
interface JsonExportable {
    String toJson();
}

class Order    implements JsonExportable { public String toJson(){ ... } }
class User     implements JsonExportable { public String toJson(){ ... } }
class Shipment implements JsonExportable { public String toJson(){ ... } }

// Callers depend only on the capability:
void audit(JsonExportable item){ log(item.toJson()); }
How we decided: the three types share no state and no identity — only a promise ("I can produce JSON"). They each keep their own class hierarchy free. A class needs can-do, not is-a. Verdict: interface. The single extends slot stays available for each type's real subtype relationship.

When the interface should carry a default method

interface JsonExportable {
    String toJson();
    // default = optional shared behavior callers get for free,
    // WITHOUT forcing a base class or breaking existing impls.
    default String toPrettyJson(){ return prettify(toJson()); }
}
Heuristic: reach for a default method when you want to add behavior to an interface without breaking every existing implementer, or to provide a sensible convenience built on the abstract methods. Do not use defaults to smuggle in shared state — interfaces still can't hold instance fields. State is the line that pushes you toward an abstract class.
Q. Interface gained default methods in Java 8 — so is an abstract class now pointless?
Reveal hint
No. Interfaces still can't hold mutable instance state, can't have constructors, and can't enforce construction invariants. The moment your "shared skeleton" needs fields the subclasses read/write, you've crossed into abstract-class territory.

6. Abstract class — a shared skeleton ("is-a-kind-of" + shared code/state)

An abstract class is the answer when several implementations are genuine subtypes (Liskov holds) and they share real implementation: fields, constructors, and a fixed sequence of steps where only a few vary. The signature move is the Template Method.

Worked decision — Template Method

Requirement: "Every data import follows the same steps — open source, read rows, validate, save, close — but CSV, XML, and JSON differ only in how rows are read."

abstract class DataImporter {
    // shared, fixed algorithm — subclasses can't reorder it
    public final ImportReport run(Path file){
        var src = open(file);                 // shared
        var rows = readRows(src);             // VARIES → abstract
        var clean = validate(rows);           // shared
        save(clean);                          // shared
        close(src);                           // shared
        return report;
    }
    protected abstract List<Row> readRows(Source src);  // the hook

    // shared state + helpers live here — an interface couldn't hold these
    private final ImportReport report = new ImportReport();
    protected List<Row> validate(List<Row> rows){ ... }
    private Source open(Path p){ ... }
    private void save(List<Row> rows){ ... }
    private void close(Source s){ ... }
}

class CsvImporter  extends DataImporter { protected List<Row> readRows(Source s){ ... } }
class JsonImporter extends DataImporter { protected List<Row> readRows(Source s){ ... } }
How we decided: (1) the importers are kinds of importer — a CsvImporter is substitutable anywhere a DataImporter is used → Liskov passes. (2) They share state (report) and a fixed algorithm with one varying step. State + enforced template are exactly what an interface cannot give you. Verdict: abstract class with a final template method and one abstract hook. Mark run() final so subclasses can't break the sequence.
Heuristic — "interface + abstract class" combo: the mature pattern is an interface for the contract callers see, plus an optional abstract skeletal class that implements the boring parts (think Collection ↔ AbstractCollection, List ↔ AbstractList). Callers depend on the interface; implementers extend the skeleton if it helps, or go their own way if it doesn't.
Q. Why mark the template method final?
Reveal hint
Because the whole value of Template Method is that the sequence is fixed and only the hooks vary. If a subclass could override run(), it could skip validation or reorder steps — re-introducing exactly the inconsistency the pattern exists to prevent.

7. Inheritance — only when "is-a" is real (and survives the future)

Concrete inheritance (class B extends A where A is concrete) is the most powerful and the most abused tool. It couples B to A's implementation, not just its contract. Use it only when all of these hold:

GateQuestionIf "no"…
LiskovIs B usable everywhere A is, with no surprises, forever?Use interface for the role + composition for the code.
Stable parentIs A's API stable, and designed for extension (documented, non-final hooks)?Composition — don't bind to a fragile base class.
True specializationDoes B genuinely add or refine behavior, not subtract it?If B removes/forbids parent methods, it's not a subtype.
One axis of variationIs there only ONE dimension B specializes along?Multiple axes → class explosion → composition.

A legitimate inheritance

// Exceptions are the textbook honest hierarchy: each is-a the parent
// in every context, and only refines meaning — never removes behavior.
class AppException        extends RuntimeException { ... }
class PaymentException    extends AppException { ... }
class CardDeclinedException extends PaymentException {
    private final String declineCode;
    CardDeclinedException(String code){ super("card declined: " + code); this.declineCode = code; }
}
// catch(AppException e) genuinely catches all three. Substitutability holds.
How we decided: a CardDeclinedException is a PaymentException is an AppException in every place those are caught. It only adds detail (declineCode); it removes nothing. Single axis (kind of failure), stable parent (the JDK's RuntimeException is designed to be extended). Verdict: concrete inheritance is correct here — and it's one of the few places it clearly is.

The "class explosion" that says STOP inheriting

// Requirement: pizzas vary by SIZE and by CRUST and by TOPPINGS.
// Inheritance tries to encode every combination as a subclass:
class SmallThinMargheritaPizza extends Pizza {}
class LargeThickPepperoniPizza extends Pizza {}
class MediumThinVeggiePizza    extends Pizza {}
// ...3 sizes x 3 crusts x N toppings = combinatorial explosion. Unmaintainable.
Smell — combinatorial subclasses: the number of subclasses multiplies because you're modelling several independent axes of variation with one inheritance tree. Each axis should become a field (composition), not a branch of the hierarchy. 
// Decision: each axis of variation → a field. One Pizza class.
class Pizza {
    private final Size size;            // has-a
    private final Crust crust;          // has-a
    private final List<Topping> toppings; // has-a many
    Pizza(Size s, Crust c, List<Topping> t){ ... }
}
// 3 sizes + 3 crusts + N toppings — additive, not multiplicative.
How we decided: "a pizza has a size, has a crust, has toppings" — three has-a sentences, zero is-a. Inheritance can only specialize one axis; composition lets the axes vary independently. Verdict: composition of value objects. Add a Builder if the constructor gets unwieldy.

8. Composition — the default reuse mechanism

Composition means A holds a reference to B and delegates the work. It's the answer to "I want B's behavior" without claiming "A is a B". It buys you three things inheritance can't: runtime swapping, combining many behaviors, and insulation from the base class changing under you.

The fragile base class problem (why reuse-by-inheritance bites)

// WRONG: extend HashSet to count how many elements were ever added.
class CountingSet<E> extends HashSet<E> {
    private int added = 0;
    public boolean add(E e){ added++; return super.add(e); }
    public boolean addAll(Collection<? extends E> c){
        added += c.size();
        return super.addAll(c);   // BUG: HashSet.addAll calls add() internally...
    }                             // ...so each element is counted TWICE.
}
Smell: the bug exists only because we inherited implementation — we had to know that HashSet.addAll happens to call add. That's an internal detail the base class can change in any release. You are coupled to the parent's private behavior. 
// RIGHT: compose. Wrap a Set, delegate, count in exactly one place.
class CountingSet<E> implements Set<E> {
    private final Set<E> inner = new HashSet<>();
    private int added = 0;

    public boolean add(E e){ added++; return inner.add(e); }
    public boolean addAll(Collection<? extends E> c){
        added += c.size();
        return inner.addAll(c);   // inner.add is HashSet's business, not ours
    }
    public int addedCount(){ return added; }
    // ...delegate the rest of Set to inner...
}
How we decided: we wanted reuse (a working Set) + one new behavior (counting). Reuse is not is-a. By composing, we depend only on the Set contract, not on HashSet's internal call graph — so a future JDK change can't silently double-count. Verdict: implement the interface, hold the impl as a field, delegate. This is the "favor composition over inheritance" rule in its purest form.

Composition also gives you runtime flexibility

// Strategy pattern: the behavior is a swappable field, chosen at runtime.
interface SortStrategy { void sort(int[] a); }
class QuickSort implements SortStrategy { public void sort(int[] a){ ... } }
class TimSort   implements SortStrategy { public void sort(int[] a){ ... } }

class Sorter {
    private SortStrategy strategy;                 // has-a behavior
    Sorter(SortStrategy s){ this.strategy = s; }
    void setStrategy(SortStrategy s){ this.strategy = s; }  // swap at runtime!
    void sort(int[] a){ strategy.sort(a); }
}
How we decided: the sorting behavior must change at runtime (small arrays → insertion, large → quicksort). Inheritance fixes behavior at compile time — a QuickSorter can never become a TimSorter. A composed strategy field can be reassigned whenever you like. Verdict: composition (Strategy). Interface for the contract, field for the swap.

Composition vs Aggregation — the ownership nuance

AspectComposition (strong has-a)Aggregation (weak has-a)
LifetimePart dies with the whole.Part outlives the whole.
ExampleOrder owns its LineItems.Department references shared Employees.
Java hintPart created inside, never leaked.Part passed in, possibly shared.
Delete the whole?Delete the parts too.Parts survive.
Why care? The distinction tells you who is responsible for creating, copying, and disposing the part — and whether a getter may safely hand it out. Composition usually means defensive copies; aggregation means shared references are expected.

Q. Two interfaces both define default void log(){...} and my class implements both. What happens?
Reveal hint
The diamond conflict makes it a compile error until you override log() in your class. You can delegate to a chosen one with InterfaceName.super.log(). This is exactly why defaults are for convenience, not for layering real behavior.

The famous rule, decoded: "Favor composition over inheritance" doesn't mean "never inherit". It means default to composition because it keeps coupling loose and behavior swappable, and only inherit when you have a proven, future-proof is-a that passes Liskov. Inheritance is a commitment; composition is a loan you can repay.

Q. Stack extends Vector ships in the JDK. Inheritance or mistake?
Reveal hint
Mistake. A stack only allows push/pop/peek, but by extending Vector it also exposes get(i), add(i, x), remove(i) — random access that violates the LIFO contract. A composed Deque inside a Stack would have hidden those. It's the canonical "reuse-by-inheritance gone wrong".

11. Example A — Payment methods (interface, because behavior varies & impls are unrelated)

Requirement

"Checkout must charge a customer. Today we support credit card and UPI; tomorrow wallet, net-banking, gift card. The checkout code must not change when we add one."

Naive move & the pain

// Naive: an enum + a giant switch.
double charge(PaymentType type, Money amt){
    switch(type){
        case CARD: /* card logic */ break;
        case UPI:  /* upi logic  */ break;
        // every new method edits THIS method → it never stops changing.
    }
}
Smell: an instanceof/switch ladder on a "type" field. Adding a behavior means editing shared code (violates Open/Closed). The variation belongs in types, not in a branch.

The decision

"A payment method can process a payment" — a capability. The implementations (card vs UPI vs wallet) are unrelated: they share no state, no base behavior, only the promise. That is the textbook interface signal.

interface PaymentMethod {
    PaymentResult pay(Money amount);
}

class CreditCardPayment implements PaymentMethod {
    private final String cardToken;
    public PaymentResult pay(Money amount){ /* gateway call */ }
}
class UpiPayment implements PaymentMethod {
    private final String vpa;
    public PaymentResult pay(Money amount){ /* upi call */ }
}

// Checkout depends on the CONTRACT, never on a concrete method.
class Checkout {
    PaymentResult complete(PaymentMethod method, Money total){
        return method.pay(total);   // adding GiftCardPayment needs ZERO edits here
    }
}
How we decided: verb test → "can pay" → capability → interface. The impls don't share code or identity, so an abstract base would be wrong. Checkout binding to PaymentMethod (not concretes) makes new methods additive — open for extension, closed for modification. Verdict: interface + polymorphism. A new payment type is a new class, not an edit to existing code.
Q. All payment methods need to "log the attempt and validate the amount > 0". Where does that go now?
Reveal hint
Two clean options: (1) a default method or static helper on the interface for the validation; or (2) if there's real shared state (a logger, a retry counter), introduce an abstract class AbstractPayment implements PaymentMethod as a skeletal base. Choose abstract class only once shared state appears — otherwise keep it an interface.

12. Example B — Notifications (interface for the role, composition to combine channels)

Requirement

"Send a notification by email, SMS, or push. Some events must go out on several channels at once. Users configure their preferred channels at runtime."

Why not inheritance?

// Tempting: EmailNotifier, then EmailAndSmsNotifier extends EmailNotifier...
// → combinatorial explosion again (Email, SMS, Push, Email+SMS, All, ...).
// Also: "send on several channels" is runtime config, not a compile-time type.

The decision

"A channel can send" → interface. "A multi-channel notifier has a list of channels" → composition. The composite is itself a channel (it implements the same interface) — that's the Composite pattern.

interface NotificationChannel {
    void send(User u, String msg);
}
class EmailChannel implements NotificationChannel { public void send(User u,String m){ ... } }
class SmsChannel   implements NotificationChannel { public void send(User u,String m){ ... } }
class PushChannel  implements NotificationChannel { public void send(User u,String m){ ... } }

// Composite: HAS-A list of channels, and IS-A channel itself.
class MultiChannel implements NotificationChannel {
    private final List<NotificationChannel> channels;
    MultiChannel(List<NotificationChannel> channels){ this.channels = List.copyOf(channels); }
    public void send(User u, String msg){
        for (NotificationChannel c : channels) c.send(u, msg);
    }
}

// Runtime assembly from user preferences — no new classes per combo:
NotificationChannel chosen = new MultiChannel(List.of(new EmailChannel(), new PushChannel()));
chosen.send(user, "Your order shipped");
How we decided: the "send" behavior varies and callers shouldn't care which channel → interface. "Send on many" is a collection assembled at runtime from config → composition, not a subclass per combination. Making the composite implement the same interface means callers treat one channel and many channels identically. Verdict: interface for the role + Composite (composition) for "many". Combinations become data, not types.
Pattern spotting: whenever "one or many of X behave like a single X", that's Composite — and Composite is just disciplined composition behind a shared interface.

13. Example C — Coffee pricing (Decorator: when "is-a AND has-a" is the right answer)

Requirement

"Price a coffee. A base coffee can be wrapped with add-ons — milk, sugar, extra shot, whipped cream — in any combination and any order, each adding to the price and the description."

Naive move & the pain

// Subclass per combination → explosion (CoffeeWithMilk, CoffeeWithMilkAndSugar, ...).
// And a customer can ask for "double milk, one sugar" — unbounded combos.

The decision

Each add-on must (a) be usable anywhere a coffee is used → it is-a coffee (same interface), and (b) wrap an existing coffee to extend it → it has-a coffee. That dual relationship is exactly the Decorator pattern: composition for the wrapping, a shared interface for substitutability.

interface Coffee {
    String description();
    int cost();   // in cents
}
class Espresso implements Coffee {
    public String description(){ return "Espresso"; }
    public int cost(){ return 200; }
}

// Base decorator: IS-A Coffee (implements) AND HAS-A Coffee (wraps).
abstract class AddOn implements Coffee {
    protected final Coffee base;          // has-a (composition)
    protected AddOn(Coffee base){ this.base = base; }
}
class Milk extends AddOn {
    Milk(Coffee base){ super(base); }
    public String description(){ return base.description() + " + Milk"; }
    public int cost(){ return base.cost() + 50; }
}
class Sugar extends AddOn {
    Sugar(Coffee base){ super(base); }
    public String description(){ return base.description() + " + Sugar"; }
    public int cost(){ return base.cost() + 10; }
}

// Stack add-ons in any order/quantity at runtime — no new classes per combo:
Coffee order = new Sugar(new Milk(new Milk(new Espresso())));
order.description(); // "Espresso + Milk + Milk + Sugar"
order.cost();        // 200 + 50 + 50 + 10 = 310
How we decided: we needed both substitutability (a decorated coffee must still be a Coffee to callers → implement the interface) and dynamic, stackable extension (→ wrap a Coffee field). Inheritance alone gives substitutability but explodes on combinations; composition alone loses substitutability. Decorator uses both deliberately. Verdict: Decorator — interface for "is-a Coffee", composed wrapped field for "has-a Coffee". The combinations live in object graphs, not in the type system.
Q. This uses extends AddOn — didn't we say avoid inheritance?
Reveal hint
The real reuse here is the composition (the wrapped base field). extends AddOn only shares the tiny "hold a base" boilerplate and is a legitimate is-a (every Milk truly is an AddOn is a Coffee). The behavior that varies (cost/description) is delegated to the composed object, not inherited. Inheritance here is structural sugar; composition does the heavy lifting.

14. Example D — Game characters & abilities (composition over a "Character" hierarchy)

Requirement

"Characters can walk, some can fly, some can swim, some can cast spells. Abilities are mixed freely: a Mage walks + casts, a Dragon flies + swims + casts, a Fish only swims."

Naive move & the pain

// Put every ability on a base class:
class Character {
    void walk(){...} void fly(){...} void swim(){...} void cast(){...}
}
class Fish extends Character { /* but Fish.fly()/walk()/cast() are nonsense */ }
Smell: subclasses inherit methods that don't apply, forcing empty overrides or throw new UnsupportedOperationException(). That's a Liskov violation and the loudest "this isn't really is-a" alarm there is. (Same root cause as a Penguin inheriting fly() from Bird.)

The decision

An ability is something a character can do → interface. Which abilities a character has is a free combination → implement multiple interfaces, and delegate the actual work to composed ability objects so the logic is reused without inheritance.

interface Walks { void walk(); }
interface Flies { void fly(); }
interface Swims { void swim(); }
interface Casts { void cast(); }

// Reusable behavior objects (composition targets):
class WalkBehavior { void walk(){ System.out.println("walking"); } }
class FlyBehavior  { void fly(){  System.out.println("flying");  } }

class Mage implements Walks, Casts {
    private final WalkBehavior walk = new WalkBehavior();   // has-a
    public void walk(){ walk.walk(); }                       // delegate
    public void cast(){ /* spell logic */ }
}
class Dragon implements Flies, Swims, Casts {
    private final FlyBehavior fly = new FlyBehavior();
    public void fly(){ fly.fly(); }
    public void swim(){ ... }
    public void cast(){ ... }
}
class Fish implements Swims {            // only the role it truly has
    public void swim(){ ... }
}

// Systems target the capability, not the character type:
void launch(Flies f){ f.fly(); }   // works for Dragon, never offered a Fish
How we decided: abilities are independent axes combined per character → multiple interfaces (capabilities), not a fat base class. The implementation of each ability is shared by composing behavior objects and delegating — so two flyers reuse FlyBehavior without an inheritance chain. A Fish never even sees fly(), so it can't be misused. Verdict: multiple interfaces for roles + composition for the shared ability code. Zero nonsense-method inheritance.
Generalizes to: "mixins / capabilities". Whenever traits combine freely and not every type has every trait, model traits as interfaces and reuse their code by composition (or interface defaults for tiny stateless bits), never by piling them onto one base class.

15. Example E — Service + Repository (interface + composition = dependency inversion)

Requirement

"OrderService needs to load and save orders. In production it uses a SQL database; in tests it should use an in-memory fake so tests are fast and don't need a DB."

Naive move & the pain

// Service news-up a concrete DB class itself:
class OrderService {
    private final JdbcOrderRepository repo = new JdbcOrderRepository(); // hard-wired
}
// Now you CANNOT test OrderService without a real database. The dependency
// is welded in. Swapping storage means editing OrderService.
Smell: a high-level policy class (OrderService) depends directly on a low-level detail (JdbcOrderRepository). That's the dependency arrow pointing the wrong way.

The decision

"The service uses a repository" → composition (a field). But it should use the abstraction, not a concrete class → the field's type is an interface, injected through the constructor. That combination is the Dependency Inversion Principle.

interface OrderRepository {            // the contract (abstraction)
    Order find(long id);
    void save(Order o);
}

class OrderService {
    private final OrderRepository repo;        // has-a an ABSTRACTION
    OrderService(OrderRepository repo){        // injected, not new-ed
        this.repo = repo;
    }
    void reprice(long id){
        Order o = repo.find(id);
        o.applyDiscount();
        repo.save(o);
    }
}

class JdbcOrderRepository    implements OrderRepository { ... }  // prod
class InMemoryOrderRepository implements OrderRepository { ... } // tests

new OrderService(new JdbcOrderRepository());     // production wiring
new OrderService(new InMemoryOrderRepository()); // test wiring — no DB needed
How we decided: the relationship is "uses-a" → composition via a field, not inheritance (an OrderService extends JdbcOrderRepository would be absurd). To make it swappable and testable, the field is typed as an interface and supplied from outside. High-level code now depends on a promise, and both prod and test implementations satisfy it. Verdict: interface for the contract + constructor-injected composition. This is why "program to an interface" and "favor composition" are really the same advice viewed from two angles.
Q. Why inject through the constructor instead of new-ing inside, or using a setter?
Reveal hint
Constructor injection makes the dependency required and the object fully formed and immutable after construction — no half-built state, no forgetting to set it. new-ing inside re-welds the coupling you were trying to break. Setter injection allows the object to exist in an invalid state before the setter is called.

16. Example F — Report exporters (abstract class earns its place)

Requirement

"Export a report to PDF, CSV, and HTML. All three do the same dance: write a header, write rows, write a footer, then flush — but each formats those pieces differently. They also share a buffer, a row counter, and the flush logic."

Why this one is an abstract class, not just an interface

Two things are true at once: (1) the three exporters are genuine kinds of exporter (Liskov holds), and (2) they share real state (buffer, counter) and a fixed algorithm. Shared state is the line an interface cannot cross.

abstract class ReportExporter {
    private final StringBuilder buffer = new StringBuilder(); // shared STATE
    private int rowCount = 0;                                 // shared STATE

    // fixed algorithm — subclasses cannot reorder or skip steps
    public final String export(Report r){
        writeHeader(r);                       // hook
        for (Row row : r.rows()){ writeRow(row); rowCount++; }  // hook + shared count
        writeFooter(rowCount);                // hook, uses shared state
        return flush();                       // shared
    }
    protected void emit(String s){ buffer.append(s); }  // shared helper
    private String flush(){ return buffer.toString(); } // shared

    protected abstract void writeHeader(Report r);  // VARIES
    protected abstract void writeRow(Row row);       // VARIES
    protected abstract void writeFooter(int total);  // VARIES
}

class CsvExporter extends ReportExporter {
    protected void writeHeader(Report r){ emit(String.join(",", r.columns()) + "\n"); }
    protected void writeRow(Row row){ emit(row.csv() + "\n"); }
    protected void writeFooter(int total){ /* CSV: no footer */ }
}
class HtmlExporter extends ReportExporter {
    protected void writeHeader(Report r){ emit("<table>"); }
    protected void writeRow(Row row){ emit("<tr>" + row.html() + "</tr>"); }
    protected void writeFooter(int total){ emit("</table><p>" + total + " rows</p>"); }
}
How we decided: ran the flow. Callers need polymorphism (interface-ish), but the impls are related, share state and a fixed sequence with varying hooks → step 3/4 of the flow lands on abstract class with Template Method. An interface couldn't hold buffer/rowCount; pure composition would duplicate the export sequence in every exporter. Verdict: abstract class. If callers also need to treat exporters alongside unrelated "exportable" things, add a thin interface Exporter on top — the List/AbstractList combo.
Counter-check: if the three exporters turned out to share no state and no code (each totally independent), the abstract class would be dead weight — drop it back to a plain interface Exporter { String export(Report r); }. The shared state is what justifies the abstract class here.

17. Decision heuristics & the smells that override them

Heuristics, in priority order

#HeuristicWhat it really protects
1Don't abstract until the second case arrives.Avoids speculative generality; keeps code navigable.
2Program to an interface (the narrowest type that works).Decouples callers from implementations.
3Favor composition over inheritance.Keeps coupling loose and behavior swappable.
4Inherit only on a future-proof is-a (Liskov).Prevents the broken-substitution time bomb.
5Abstract class only when subtypes share state + algorithm.Stops you forcing state into interfaces or duplicating code.
6One axis of variation per inheritance tree.Prevents combinatorial subclass explosion.
7Keep interfaces small & role-focused (ISP).No client forced to depend on methods it doesn't use.

18. Anti-pattern gallery — wrong vs right, with the reason

ScenarioWrongRight (and why)
Reuse a couple of utility methods class Report extends StringUtils Call the static helpers, or hold a formatter field. Utilities are uses-a, never is-a.
Add timestamps to a list class TimedList<E> extends ArrayList<E> implements List<E>, wrap an inner list, delegate. Avoids self-call surprises & fragile base.
A type with several roles class SmartDevice extends Phone extends Camera (illegal) implements Phone, Camera, MusicPlayer. Roles = interfaces, combine freely.
Square & Rectangle class Square extends Rectangle Both implements Shape { double area(); }; no inheritance. setWidth can't honor a square invariant.
Behavior chosen at runtime class FastSorter extends Sorter + class SlowSorter extends Sorter Compose a SortStrategy field, reassignable at runtime (Strategy).
Manager who might also be a contractor class Manager extends Employee class Person { Set<Role> roles; } — roles are has-a, so they combine and change over time.
Service tied to a database new JdbcRepository() inside the service Inject a Repository interface (composition + DI). Now testable & swappable.
Penguin in a bird hierarchy class Penguin extends Bird inheriting fly() fly() lives on a Flyable interface; Penguin implements Bird, Swimmable only.
Q. "Replace inheritance with composition" — does that mean never write extends?
Reveal hint
No. Use extends when the subtype honors the parent's contract in every context — FileInputStream extends InputStream, CardDeclinedException extends RuntimeException, framework base classes designed for extension. The rule says default to composition and reach for inheritance with evidence (a proven, stable is-a), not "never inherit".
