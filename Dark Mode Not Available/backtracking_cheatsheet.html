1. What is backtracking?

Backtracking is a brute-force search done smartly: build a candidate solution one decision at a time, and the moment a partial decision can no longer lead to a valid answer, retract it and try the next option. It is DFS over a decision tree with state mutation + undo.

  • Decision tree Each node = a partial state, each edge = one choice.
  • Pruning Skip whole subtrees as soon as constraints break.
  • Cheap memory One mutable state object instead of many copies.

2. The canonical template

Every backtracking solution follows the same three-line dance inside the recursion:

Choose → Explore (recurse) → Unchoose (undo) 
void backtrack(State s, List<Result> out) {
    if (isComplete(s)) {           // base case
        out.add(snapshot(s));
        return;
    }
    for (Choice c : choices(s)) {  // branch
        if (!isValid(s, c)) continue; // prune

        apply(s, c);                // 1. CHOOSE
        backtrack(s, out);          // 2. EXPLORE
        undo(s, c);                 // 3. UNCHOOSE
    }
}

3. Why do we undo?

Because we share one mutable state across all recursion branches. After exploring a choice, the state must look exactly like it did before that choice, so the next sibling branch starts from a clean slate.

If you forget to undo

  • State leaks across branches.
  • Permutations contain stale picks.
  • "Used" flags stay true forever, killing valid paths.
  • You'd have to deep-copy state on every call — memory blows up.

What "undo" actually means

  • Pop the last element you pushed.
  • Flip the used[i] flag back.
  • Clear the cell you just filled on the board.
  • Decrement counters / sums you bumped.
Rule of thumb: every line of code that mutates state in Choose must have a mirror line in Unchoose.

4. Flavours of backtracking

4.1 Include / Exclude — Subsets

At each index decide: include this element or exclude it. Two recursive calls per index, no loop needed.

void subsets(int[] nums, int i, List<Integer> cur, List<List<Integer>> out) {
    if (i == nums.length) {
        out.add(new ArrayList<>(cur));   // snapshot
        return;
    }
    // EXCLUDE: don't touch state, just move on
    subsets(nums, i + 1, cur, out);

    // INCLUDE: choose -> explore -> unchoose
    cur.add(nums[i]);                       // choose
    subsets(nums, i + 1, cur, out);     // explore
    cur.remove(cur.size() - 1);          // unchoose
}

Why undo here The same cur list is reused for the exclude branch of the parent and for sibling subtrees.

4.2 Pick / Unpick at index — Permutations

Order matters → loop over all unused indices at every level. The classic used[] flag flavour.

void permute(int[] nums, boolean[] used,
                    List<Integer> cur, List<List<Integer>> out) {
    if (cur.size() == nums.length) {
        out.add(new ArrayList<>(cur));
        return;
    }
    for (int i = 0; i < nums.length; i++) {
        if (used[i]) continue;            // prune

        used[i] = true;                   // CHOOSE
        cur.add(nums[i]);
        permute(nums, used, cur, out);        // EXPLORE
        cur.remove(cur.size() - 1);        // UNCHOOSE
        used[i] = false;
    }
}

4.3 Pick from a start index — Combinations

Order does not matter → pass a start so we never look back. This avoids duplicate combinations naturally.

void combine(int n, int k, int start,
                    List<Integer> cur, List<List<Integer>> out) {
    if (cur.size() == k) { out.add(new ArrayList<>(cur)); return; }

    for (int i = start; i <= n; i++) {
        cur.add(i);                              // CHOOSE
        combine(n, k, i + 1, cur, out);     // EXPLORE (note i+1)
        cur.remove(cur.size() - 1);          // UNCHOOSE
    }
}

4.4 Place / Unplace with constraints — N-Queens

The choice mutates a richer state (a board + attack sets). Undo must restore all of them.

void solveNQ(int row, int n, int[] queenCol,
                    Set<Integer> cols, Set<Integer> diag1, Set<Integer> diag2,
                    List<int[]> out) {
    if (row == n) { out.add(queenCol.clone()); return; }

    for (int c = 0; c < n; c++) {
        if (cols.contains(c) || diag1.contains(row - c) || diag2.contains(row + c))
            continue;                    // prune by constraints

        queenCol[row] = c;                  // CHOOSE
        cols.add(c); diag1.add(row - c); diag2.add(row + c);

        solveNQ(row + 1, n, queenCol, cols, diag1, diag2, out); // EXPLORE

        cols.remove(c);                     // UNCHOOSE (mirror every mutation)
        diag1.remove(row - c);
        diag2.remove(row + c);
    }
}

4.5 Path on a grid — DFS with visited

Word Search style. Mark the cell, recurse to neighbours, unmark on the way out.

boolean dfs(char[][] g, int r, int c, String w, int k) {
    if (k == w.length()) return true;
    if (r < 0 || c < 0 || r >= g.length || c >= g[0].length) return false;
    if (g[r][c] != w.charAt(k)) return false;

    char tmp = g[r][c];
    g[r][c] = '#';                              // CHOOSE (mark visited)

    boolean ok = dfs(g, r+1, c, w, k+1) || dfs(g, r-1, c, w, k+1)
              || dfs(g, r, c+1, w, k+1) || dfs(g, r, c-1, w, k+1); // EXPLORE

    g[r][c] = tmp;                                 // UNCHOOSE (restore cell)
    return ok;
}

5. Plain-English deep dive (why we need each piece)

The big picture, in one line: imagine you are walking through a giant maze where each junction has many doors. You walk down a path; if it dead-ends, you walk back to the last junction and try a different door. Backtracking is that walk.

Why "Choose"?

You can't solve a big problem in one shot. You have to commit to one small decision at a time — pick this number, place this queen, mark this cell. "Choose" is just you saying: "OK, let me try this option and see where it leads."

  • Why we need it: Without committing to a choice, the recursion has nothing new to work with. The state never changes, so the next call would be identical to the current one — infinite loop.
  • Real-world feel: like trying on a shirt before deciding if it fits. You have to actually put it on first.

Why "Explore"?

After making one decision, you ask: "Given this decision, can the rest of the problem be solved?" That question is exactly the same kind of question you started with — just smaller. So you call the same function on the smaller problem. That's the recursion.

  • Why we need it: One decision alone doesn't give you a complete answer. You need to keep stacking decisions until the solution is fully built (base case) or proven impossible.
  • Real-world feel: after picking the first piece of a jigsaw, you keep adding pieces. Each piece you add changes the puzzle for the next one.

Why "Unchoose" (Undo)?

This is the part most beginners skip and then wonder why their answer is wrong. Here is the simple truth:

You only have ONE notebook. You write your current attempt in it. When the attempt fails (or succeeds and is recorded), you must erase your last line before trying a different option — otherwise the new attempt starts on a dirty page.
  • Why we need it: The list cur, the board, the used[] array — they are shared across every branch of the recursion tree. If you don't undo, branch B inherits the leftovers of branch A and produces garbage.
  • Why not just copy the state? You could (and for tiny problems it works), but copying a 9x9 Sudoku board millions of times is slow and memory-hungry. Mutate-and-undo is faster.
  • Real-world feel: trying outfits in a fitting room. You take the shirt off before trying the next one. You don't pile every shirt on top of each other.

Why "Include / Exclude" (Subsets flavour)?

For each item in the input, there are exactly two truths in the universe of subsets: either the item is in the subset, or it isn't. So at every step we just split into those two branches.

  • Why we need it: Subsets are about membership, not order. Asking "include or exclude?" naturally generates every possible membership combination.
  • Why no for-loop: Because the only two choices are binary, two recursive calls cover everything. A loop would over-complicate it.
  • Real-world feel: packing for a trip. For each item on the shelf you ask "take it, or leave it?" By the time you reach the end of the shelf, your bag is one of the possible packing combinations.

Why "Pick / Unpick at index" (Permutations flavour)?

Permutations care about order: [1,2,3] and [3,2,1] are different answers. So at every position we must consider every remaining number, not just the ones after the current index.

  • Why we need a used[] flag: A number can appear at most once in a permutation. The flag answers the question "have I already placed this in the current arrangement?" without scanning the list.
  • Why we flip the flag back: Same notebook problem. After we finish exploring "what if 2 is in position 0?", we have to release 2 so it's free to be picked at position 1 in the next branch.
  • Real-world feel: seating 5 friends in 5 chairs. For chair 1 you can try anyone. After seating Alice in chair 1 and exploring all arrangements, you stand Alice up before trying Bob in chair 1.

Why "Start index" (Combinations flavour)?

Combinations don't care about order: {1,2} and {2,1} are the same. If we let the loop look at all indices like permutations do, we'd produce both — duplicates.

  • Why we need start: By forcing the next pick to come from indices > the last picked index, every combination comes out in a fixed (sorted) order. Duplicates simply can't be generated.
  • Why i + 1 vs i: i + 1 = "each element used at most once". i = "element can be reused" (combination sum problem).
  • Real-world feel: picking 3 toppings from a menu of 10. You read the menu top-to-bottom and only pick toppings below your last pick. You never go back up — that's how you avoid counting "pepperoni + olives" and "olives + pepperoni" twice.

Why "Place / Unplace with constraints" (N-Queens flavour)?

Some problems aren't just "build a list" — they have rules that some choices break instantly. N-Queens says: no two queens may share a column or diagonal. We don't want to wait until the board is full to discover a clash; we want to detect it the moment we try to place a bad queen and skip that whole branch.

  • Why we track sets (cols, diag1, diag2): Constant-time lookup. Asking "is this column already taken?" should not require scanning the board.
  • Why we undo all three sets: One queen affects three things at once (column + two diagonals). Choose adds to all three; Unchoose must remove from all three. Mismatched undo = ghost queens still "blocking" cells they no longer occupy.
  • Real-world feel: assigning meeting rooms with rules ("no two teams in adjacent rooms"). Before booking room 5 for Team A, check the rule book. If you cancel, free every reservation that booking caused.

Why "Mark / Unmark" on a grid (DFS flavour)?

Grid problems (word search, islands, paths) need to remember "I've already stepped here in this path so I don't loop forever." But that memory is only valid for the current path — once the path backs out, the cell becomes available again for a different path.

  • Why we mark the cell: To prevent the recursion from re-entering it and walking in circles.
  • Why we unmark: A different path might legitimately go through this cell. If we leave it marked forever, we'd block valid solutions.
  • Real-world feel: exploring a cave with chalk. You chalk-mark each room you enter so you don't go in circles. When you backtrack out of a dead-end, you wipe the chalk so a different route can use the room.

Why "Prune" (the if (!isValid) continue line)?

The naive backtracking tree is huge — often exponential. Pruning cuts off entire branches early so you never waste time exploring obviously doomed paths.

  • Why we need it: Without pruning, N-Queens at N=12 already takes minutes; with pruning it's milliseconds. Same algorithm, dramatically different speed.
  • Where to prune: Before the recursive call, never after. Once you've recursed, the work is done — too late to save it.
  • Real-world feel: if you're filling a Sudoku and notice a row already has two 5s, you stop right there. You don't keep filling the rest of the puzzle "just to see".

Why "Snapshot" the result (new ArrayList<>(cur))?

Remember: cur is the same physical list across all branches. If you store a reference to it directly, every entry in your result list points to the same list — and by the time recursion ends, that list is empty (because every push was undone).

  • Why we need a copy: A snapshot freezes the contents at the moment of success, so future undos can't disturb it.
  • Real-world feel: taking a photo of your whiteboard before erasing it. The photo survives even after the whiteboard is wiped clean.
One sentence summary: Backtracking is "try, recurse, undo" on a single shared scratchpad — the undo is what makes the scratchpad reusable for the next attempt.

6. 5-step recipe to apply backtracking

  1. Define the state. What does a partial solution look like? (a list, a board, indices, sums…)
  2. Define the choices. At this state, what are the next legal options? Loop or two-way include/exclude?
  3. Define the goal. When is the state a complete answer? Snapshot it (new ArrayList<>(cur)).
  4. Define the constraints & prune. Skip a choice before recursing whenever it can't lead to a valid solution.
  5. Mirror Choose with Unchoose. Every mutation done before recurse() must be reverted after it.

7. Common mistakes & tips

MistakeSymptomFix
Forgetting to snapshot the result All results in out end up identical (or empty) out.add(new ArrayList<>(cur)) — never add cur directly
Forgetting unchoose Wrong/duplicate results, "used" cells stay locked Mirror every mutation symmetrically
Recursing with i instead of i + 1 in combinations Element repeats / infinite recursion Use i + 1 for "no repeat", i only when reuse is allowed
Not pruning early TLE on large inputs Check constraints before the recursive call, sort input to enable early break
Mutating shared collections without undo Cross-branch contamination Either undo, or pass an immutable copy (slower but simpler)
Duplicates in input (e.g. [1,1,2]) Duplicate subsets/permutations in output Sort first, then if (i > start && nums[i] == nums[i-1]) continue;
Mental model: backtracking = DFS + writable state + a strict "leave the state how you found it" contract on every recursive call.
