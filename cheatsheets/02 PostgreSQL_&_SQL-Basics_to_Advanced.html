0. How PostgreSQL works (the big picture)

PostgreSQL is a process-per-connection relational database. Every client connection gets its own backend process. Data lives in 8 KB pages on disk, cached in shared_buffers; every change is first written to the WAL (write-ahead log) so a crash can be replayed. Rows are never updated in place — a new row version is written and the old one is marked dead (MVCC). That one fact explains VACUUM, bloat, and why readers never block writers.

PiecePlain meaningWhy you care
Backend processOne OS process per connection (~5–10 MB each).500 idle connections is already heavy → use a pool (Section 8).
Shared buffersPostgres' own page cache in RAM.Typical 25% of RAM. The OS file cache holds the rest.
WALAppend-only log of every change, fsync'd at commit.Commit speed = WAL disk speed. Also feeds replication.
HeapThe table file: pages of row versions (tuples).Updates add tuples; dead ones need VACUUM.
IndexesSeparate files pointing at heap tuples.Every index slows writes; pick carefully.
PlannerTurns SQL into a plan using table statistics.Stale stats = bad plans. ANALYZE.
AutovacuumBackground workers that clean dead tuples and refresh stats.Never turn it off. Tune it for hot tables.
Checkpointer / bgwriterFlush dirty pages from RAM to the data files.Checkpoint spikes show up as latency bumps.

What happens to one query

#Step
1Parse the SQL text; rewrite views and rules.
2Plan: estimate row counts from pg_statistic, cost each way (seq scan vs index scan, hash vs nested loop join), pick the cheapest.
3Execute: pull pages into shared buffers, check each tuple's visibility against your snapshot, produce rows.
4On write: new tuple into heap, index entries added, WAL record written; at COMMIT the WAL is flushed to disk.
Mental model: a table is a notebook where you only ever append new versions of a line and cross out the old one. Readers look at the version that was current when they started reading. A janitor (VACUUM) later erases the crossed-out lines so the space can be reused.
Q. Why does an UPDATE of one column on a 50-column row cost as much as an insert?
Reveal hint
MVCC: Postgres writes a whole new row version and must add index entries for it (unless the update is HOT — no indexed column changed and the new version fits on the same page). That is why wide tables with many indexes have expensive updates.

Q. You have index (status, created_at). Query: WHERE created_at > now() - interval '1 day'. Index used?
Reveal hint
Almost never — status is the leading column and is not constrained. Postgres would have to scan the whole index. Add an index led by created_at, or add status IN (…) to the query if that is what you mean.

EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)

  Buffers: shared hit=24

        (cost=0.43..1270.55 rows=568 width=16) (actual time=0.029..0.083 rows=20 loops=1)
        Index Cond: ((customer_id = 42) AND (created_at > (now() - '30 days'::interval)))

Execution Time: 0.112 ms
Read thisIt means
cost=0.43..45.12Planner's guess: start-up cost .. total cost, in abstract units. Compare between plans, not to time.
rows=568 vs actual rows=20Estimated vs real. A gap of 10× or more = stale or missing statistics → bad plan choices higher up.
loops=1How many times this node ran. In a Nested Loop the inner side shows loops=N; multiply actual rows × loops.
Buffers: shared hit=24 read=0Pages from cache vs from disk. Big read = I/O bound. temp read/written = spilled to disk (raise work_mem).
Seq ScanRead the whole table. Fine for small tables or when returning most rows; bad with Filter dropping 99%.
Index ScanWalk the index, fetch each matching heap row.
Index Only ScanEverything from the index; Heap Fetches: 0 is the goal (needs a recently vacuumed table).
Bitmap Heap ScanIndex finds many rows; Postgres sorts pointers by page then reads. Middle ground.
Nested Loop / Hash Join / Merge JoinSmall × indexed · build hash on smaller side · both sorted. A Nested Loop with a big inner loops count is the classic slow spot.
Sort + Sort Method: external merge DiskSorted on disk. Add an index that provides the order, or more work_mem.
Rows Removed by Filter: 98000Read then thrown away. An index on that predicate would help.
OptionDoes
EXPLAINPlan only, does not run. Safe for huge queries.
EXPLAIN ANALYZERuns the query and shows real times. Wrap writes in BEGIN; … ROLLBACK;.
BUFFERSCache vs disk per node. Always add it.
SETTINGSShows non-default planner settings in effect.
FORMAT JSONPaste into explain.dalibo.com or explain.depesz.com for a visual.
 
-- fix bad estimates

ALTER TABLE orders ALTER COLUMN status SET STATISTICS 1000;  -- more histogram buckets for a skewed column

CREATE EXTENSION pg_stat_statements;
SELECT calls, round(total_exec_time) AS ms, round(mean_exec_time,2) AS avg_ms, left(query,90)
FROM pg_stat_statements ORDER BY total_exec_time DESC LIMIT 15;
TopicWrongRight
Reading cost as time"cost 1200 = 1.2 seconds".Cost is relative. Use ANALYZE for real ms.
Testing with tiny dataPlan looks great on 100 dev rows.Planner changes plans with size. Test on production-like volumes (or copy stats).
Forcing plansSET enable_seqscan = off in app code.Fix the root cause: index, statistics, query shape. Hints (pg_hint_plan) are a last resort.
Ignoring slow query logFinding slow queries by user complaints.log_min_duration_statement = 500ms, auto_explain, and pg_stat_statements.
Q. The plan shows a Nested Loop with the inner Index Scan at loops=250000. Each loop is 0.02 ms. Is that fine?
Reveal hint
250,000 × 0.02 ms = 5 s. The planner expected far fewer outer rows (check its rows=). Fix the estimate (ANALYZE, statistics target) so it switches to a Hash Join, or rewrite so the outer side is filtered first.

3. Transactions and isolation levels

A transaction makes several statements act as one: all or nothing (atomic), rules kept (consistent), hidden from others until commit (isolated), safe once committed (durable). Isolation has levels, and the default is weaker than many people think.

LevelWhat you can seeAnomalies still possibleUse
READ COMMITTED (default)Each statement sees data committed before that statement started.Non-repeatable read (same row, two values in one txn), phantom rows, lost update with read-then-write.Most OLTP. Fast, few serialization errors.
REPEATABLE READThe whole transaction sees one snapshot taken at its first statement.Write skew (two txns each check a rule, both pass, together they break it). Updates of rows changed by others fail with a serialization error.Reports that must be consistent; multi-step reads.
SERIALIZABLEAs if transactions ran one after another. Postgres uses SSI: detects dangerous patterns and aborts one.None — but you must retry on error 40001.Money, inventory, anything with invariants across rows.
READ UNCOMMITTEDAccepted but behaves as READ COMMITTED. No dirty reads in Postgres, ever.——
 
BEGIN ISOLATION LEVEL SERIALIZABLE;
SELECT balance FROM accounts WHERE id = 1;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;        -- may fail: ERROR 40001 could not serialize access → retry the whole transaction

-- the lost-update problem under READ COMMITTED, and three fixes
-- bad: read, compute in app, write
SELECT qty FROM stock WHERE sku = 'A';      -- 10   (another txn also reads 10)
UPDATE stock SET qty = 9 WHERE sku = 'A';    -- both write 9; one decrement lost
-- fix 1: atomic update
UPDATE stock SET qty = qty - 1 WHERE sku = 'A' AND qty > 0 RETURNING qty;
-- fix 2: pessimistic lock
SELECT qty FROM stock WHERE sku = 'A' FOR UPDATE;   -- others wait here until you commit
-- fix 3: optimistic lock (what JPA @Version does)
UPDATE stock SET qty = 9, version = version + 1 WHERE sku = 'A' AND version = 7;   -- 0 rows updated → someone else won, retry
StatementDoes
BEGIN / COMMIT / ROLLBACKStart / save / discard. Without BEGIN, each statement is its own transaction (autocommit).
SAVEPOINT sp; … ROLLBACK TO sp;Undo part of a transaction. Note: after any error, the whole txn is aborted until you rollback (to a savepoint or fully).
SET TRANSACTION ISOLATION LEVEL …Must be the first statement in the transaction.
SELECT … FOR UPDATE / FOR SHARERow locks: exclusive / shared. FOR NO KEY UPDATE is lighter when you won't change the key.
SELECT … FOR UPDATE SKIP LOCKEDTake rows nobody else holds — perfect for job queues.
SELECT … FOR UPDATE NOWAITError instead of waiting.
SET idle_in_transaction_session_timeout = '30s'Kill sessions that opened a txn and went quiet — the #1 cause of lock pile-ups and VACUUM blocking.
TopicWrongRight
Read-modify-writeLoad in Java, change, save — under READ COMMITTED two users overwrite each other.Atomic SQL (SET x = x - 1), FOR UPDATE, or a version column with retry.
Long transactionsOpen a txn, call a payment API (3 s), then commit. Locks held and VACUUM blocked the whole time.Do external calls outside the transaction. Transactions should last milliseconds.
No retry on 40001Using SERIALIZABLE and surfacing serialization errors to users.Retry loop (3 tries with backoff). Spring: @Retryable(retryFor = CannotSerializeTransactionException.class).
Assuming REPEATABLE READ is enough"Check balance ≥ 0 for both accounts, then withdraw" — write skew lets both pass.SERIALIZABLE, or lock the rows you base the decision on.
Continuing after an errorCatching an SQL error mid-transaction and running more statements → "current transaction is aborted".Rollback (to a savepoint) first.
Job queue in pure SQL: UPDATE jobs SET state='running', worker=$1 WHERE id = (SELECT id FROM jobs WHERE state='queued' ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING *; — safe with many workers, no external queue needed for modest volumes.
Q. Under READ COMMITTED you run SELECT count(*) FROM t twice in one transaction and get different numbers. Bug?
Reveal hint
No. READ COMMITTED takes a fresh snapshot per statement, so commits by others between your two selects are visible. If you need a stable view, use REPEATABLE READ for that transaction.

4. MVCC, VACUUM, bloat, and transaction ID wraparound

TermPlain meaning
TupleOne row version. Each has hidden columns xmin (txn that created it) and xmax (txn that deleted/updated it).
Snapshot"Which transaction IDs were committed when I started." Decides which tuple versions you see.
Dead tupleA version no running transaction can see any more. Pure waste until vacuumed.
VACUUMMarks dead tuples' space reusable, updates the visibility map (for index-only scans), freezes old tuples. Does not shrink the file.
VACUUM FULLRewrites the table into a new file, returns space to the OS. Takes an exclusive lock — avoid on live tables; use pg_repack.
ANALYZERefreshes planner statistics. Autovacuum does it too.
BloatTable/index much larger than its live data because dead space is not reused fast enough.
HOT updateHeap-Only Tuple: new version on the same page and no indexed column changed → no index writes. Keep fillfactor < 100 on hot tables to allow it.
XID wraparoundTransaction IDs are 32-bit. Very old unfrozen tuples would "flip" to the future; Postgres forces an aggressive vacuum, and eventually refuses writes. Autovacuum prevents it — unless blocked.
 
-- how bloated / how far behind?
SELECT relname, n_live_tup, n_dead_tup,
       round(100.0 * n_dead_tup / greatest(n_live_tup,1), 1) AS dead_pct,
       last_autovacuum, last_autoanalyze
FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10;

-- wraparound danger (age close to 2 billion = emergency; alert at ~ 500M)
SELECT datname, age(datfrozenxid) FROM pg_database ORDER BY 2 DESC;

-- what blocks vacuum: long transactions and idle-in-transaction sessions
SELECT pid, state, now() - xact_start AS age, left(query,60)
FROM pg_stat_activity WHERE xact_start IS NOT NULL ORDER BY xact_start LIMIT 5;

-- make autovacuum visit a hot table sooner (defaults: 20% of rows + 50)
ALTER TABLE orders SET (autovacuum_vacuum_scale_factor = 0.02, autovacuum_vacuum_threshold = 1000,
                        autovacuum_analyze_scale_factor = 0.01);
VACUUM (VERBOSE, ANALYZE) orders;                 -- manual, online, no exclusive lock
TopicWrongRight
Turning autovacuum off"It slows my batch job" → off for months → bloat and wraparound shutdown.Never off. Tune per-table thresholds; raise autovacuum_vacuum_cost_limit so it keeps up.
Giant deleteDELETE FROM events WHERE created_at < … on 500M rows: hours of dead tuples, WAL flood.Partition by time and DROP old partitions (Section 6), or delete in batches of 10k with a pause.
Replica holding back vacuumLong reports on a replica with hot_standby_feedback=on keep dead tuples alive on the primary.Know the trade-off; set max_standby_streaming_delay or run heavy reports off a snapshot.
Counting rowsSELECT count(*) on a 1B-row table for a dashboard.MVCC means a full scan. Use pg_class.reltuples (estimate) or a counter table.
Queue tablesInsert + update + delete millions of rows a day in one table → index bloat.Aggressive autovacuum settings, fillfactor=70, periodic REINDEX CONCURRENTLY; or a real queue.
Q. You deleted 90% of a 100 GB table and ran VACUUM. Disk usage is still 100 GB. Why?
Reveal hint
Plain VACUUM only marks space inside the file as free for reuse; it releases the file tail only if the last pages are empty. To return space to the OS you need VACUUM FULL (exclusive lock) or pg_repack (online). Better: design so you drop partitions instead of deleting.

-- who is waiting on whom
SELECT a.pid, a.state, a.wait_event_type, left(a.query,50) AS query,
       pg_blocking_pids(a.pid) AS blocked_by
FROM pg_stat_activity a WHERE cardinality(pg_blocking_pids(a.pid)) > 0;

SELECT pg_cancel_backend(12345);     -- stop the query
SELECT pg_terminate_backend(12345);  -- kill the session

-- safe DDL on a busy table: never wait forever for the lock
SET lock_timeout = '3s';
ALTER TABLE orders ADD COLUMN note text;                     -- instant (no default rewrite since PG 11)
ALTER TABLE orders ADD CONSTRAINT fk_cust FOREIGN KEY (customer_id) REFERENCES customers NOT VALID;
ALTER TABLE orders VALIDATE CONSTRAINT fk_cust;            -- validation takes only a weak lock

-- one-at-a-time job across many app instances
SELECT pg_try_advisory_lock(hashtext('nightly-report'));  -- true = you got it; false = someone else runs it

Deadlocks

Transaction A locks row 1 then wants row 2; B locks row 2 then wants row 1. Postgres detects this after deadlock_timeout (1 s) and kills one with ERROR 40P01. The other proceeds.

TopicWrongRight
Lock orderCode path 1 updates account A then B; path 2 updates B then A.Always lock in a fixed order (e.g. by primary key ascending). SELECT … ORDER BY id FOR UPDATE.
Big updatesUPDATE … WHERE status='X' touching 1M rows while users edit single rows.Batches in key order; off-peak.
DDL in peakALTER TABLE waits for a lock; meanwhile every new query queues behind it → outage.lock_timeout + retry; CONCURRENTLY; NOT VALID + VALIDATE; add columns without volatile defaults.
FK without indexDeleting a parent row holds locks while seq-scanning children.Index FK columns.
Treating deadlock as a bug to catchCatch 40P01 and give up.Deadlocks can be made rare, not impossible. Retry the transaction.
Which ALTERs are cheap? Add nullable column, add column with constant default (PG 11+), drop column (marks it hidden), rename, add NOT VALID constraint: fast. Change column type, add NOT NULL to a big table (PG < 12 without a check constraint), set a volatile default: table rewrite — plan a window.
Q. A plain SELECT is stuck for minutes. Postgres readers never block… so what is happening?
Reveal hint
Readers do not block on rows, but a SELECT needs an ACCESS SHARE lock on the table, and something is holding (or waiting for) ACCESS EXCLUSIVE — typically an ALTER TABLE or VACUUM FULL that is itself queued behind an idle-in-transaction session. pg_blocking_pids will show the chain.

JSONB in practice

CREATE TABLE products (
  id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name     text NOT NULL,
  attrs    jsonb NOT NULL DEFAULT '{}'
);
CREATE INDEX ON products USING gin (attrs jsonb_path_ops);         -- fast @> containment
CREATE INDEX ON products ((attrs->>'brand'));                      -- B-tree on one key for = and ORDER BY

INSERT INTO products (name, attrs) VALUES ('Phone', '{"brand":"Acme","color":"red","specs":{"ram_gb":8}}');

SELECT attrs->>'brand'                 AS brand,            -- ->> text, -> jsonb
       (attrs->'specs'->>'ram_gb')::int AS ram,
       attrs #>> '{specs,ram_gb}'      AS ram_path
FROM products
WHERE attrs @> '{"color":"red"}'                                   -- contains (uses GIN)
  AND attrs ? 'brand'                                             -- key exists
  AND jsonb_path_exists(attrs, '$.specs.ram_gb ? (@ >= 8)');        -- SQL/JSON path

UPDATE products SET attrs = attrs || '{"color":"blue"}' WHERE id = 1;     -- merge / overwrite keys
UPDATE products SET attrs = attrs - 'color' WHERE id = 1;                -- remove key
UPDATE products SET attrs = jsonb_set(attrs, '{specs,ram_gb}', '16') WHERE id = 1;

-- explode an array of objects into rows
SELECT p.id, e->>'sku' FROM orders p, jsonb_array_elements(p.payload->'items') e;
-- build JSON from rows (great for API responses)
SELECT jsonb_build_object('id', id, 'name', name) FROM products;
SELECT jsonb_agg(jsonb_build_object('id', id)) FROM products;

Partitioning (declarative)

CREATE TABLE events (
  id         bigint GENERATED ALWAYS AS IDENTITY,
  created_at timestamptz NOT NULL,
  payload    jsonb,
  PRIMARY KEY (id, created_at)                       -- the partition key must be part of any unique key
) PARTITION BY RANGE (created_at);

CREATE TABLE events_2026_10 PARTITION OF events FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
CREATE TABLE events_2026_11 PARTITION OF events FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
CREATE TABLE events_default PARTITION OF events DEFAULT;    -- catch-all so inserts never fail

CREATE INDEX ON events (created_at);                        -- created on every partition automatically

-- retention: instant, no dead tuples, no vacuum storm
ALTER TABLE events DETACH PARTITION events_2026_10 CONCURRENTLY;
DROP TABLE events_2026_10;

Partitioning small tablesPartitioning a 2 GB table "for performance".Partition when the table is tens of GB+, or when you need to drop old data fast. Each partition adds planning cost.
Queries without the keyWHERE user_id = 7 on a table partitioned by created_at → scans every partition.Always include the partition key in hot queries, or partition by what you filter on.
Creating partitions by handForgetting to make next month's partition → inserts fail at midnight.A DEFAULT partition as a safety net plus pg_partman or a cron job to pre-create.
Soft deletes everywheredeleted_at on every table, every query must remember WHERE deleted_at IS NULL.Only where you need recovery/audit; add a partial index WHERE deleted_at IS NULL; or move to an archive table.
EAV tablesentity_id, attribute, value for everything.Real columns; jsonb for the variable part.
Natural keys as PKEmail as primary key; user changes email → update 12 tables.Surrogate bigint/uuid PK, unique constraint on the natural key.
Schema per tenant vs row per tenant: few big tenants → separate schemas (easy isolation, painful migrations ×N). Many small tenants → a tenant_id column on every table, composite indexes led by it, and Row Level Security (CREATE POLICY … USING (tenant_id = current_setting('app.tenant')::int)) so a missing WHERE can never leak data.
Q. Can a partitioned table have a unique constraint on email alone when partitioned by created_at?
Reveal hint
No. Unique constraints and primary keys must include all partition key columns, because each partition has its own index and Postgres cannot check uniqueness across them. Enforce global uniqueness in a separate non-partitioned table, or partition by that key.

8. Connections, pooling, and the Java side

FactConsequence
Each connection = one backend process.Connecting is slow (~ms) and memory-heavy. Never open a connection per request.
max_connections (default 100) is a hard cap.Too many app instances × pool size → "too many clients already".
Postgres is fastest with few active connections.Sweet spot ≈ (CPU cores × 2) + disks. 500 active connections on 8 cores is slower than 20.

      socketTimeout: 30              # seconds; a dead DB host no longer hangs threads forever

Prepared statementspgjdbc sends unnamed prepared statements; after 5 uses of the same SQL it switches to a server-side named one (prepareThreshold). Great for OLTP; with PgBouncer transaction mode set prepareThreshold=0 or use PgBouncer ≥ 1.21.

Type mappingtimestamptz ↔ OffsetDateTime/Instant; uuid ↔ UUID; jsonb ↔ String or a mapped type (Hibernate 6 @JdbcTypeCode(SqlTypes.JSON)); numeric ↔ BigDecimal; arrays ↔ String[]/List with Hibernate 6.

Q. Hikari says 10 connections, 5 pods, but Postgres shows 80 connections from the app. Where from?

9. Migrations, roles, backups, replication

Schema migrations (Flyway / Liquibase)

-- src/main/resources/db/migration/V7__orders_add_note.sql   (Flyway: V<version>__<desc>.sql)
SET lock_timeout = '5s';
ALTER TABLE orders ADD COLUMN note text;
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_orders_note ON orders (note);   -- needs a non-transactional migration file
RuleWhy
Migrations are append-only; never edit a run one.Checksums fail and environments drift.
Expand → migrate → contract.Add the new column/table, deploy code that writes both, backfill, switch reads, then drop the old. Zero-downtime and rollback-friendly.
Big backfills outside the migration tool.A 2-hour UPDATE inside Flyway blocks start-up and holds locks. Run batched jobs instead.
CONCURRENTLY cannot run in a transaction.Flyway: name the file V8__… and add -- flyway:executeInTransaction=false, or use a Java migration.
Hibernate ddl-auto=validate.Catches entity/schema mismatch at start-up without ever changing the DB.

Q. Flyway fails with "Migration checksum mismatch" on production. What happened and what do you do?
Reveal hint
Someone edited an already-applied migration file. Do not edit production history: restore the file to its original content, and put the intended change in a new V<next>__ migration. flyway repair only resyncs checksums when you are sure the DB really has the new content.

SHOW shared_buffers;                                 -- read one
SELECT name, setting, unit, source FROM pg_settings WHERE source <> 'default';   -- everything you changed
ALTER SYSTEM SET work_mem = '32MB';  SELECT pg_reload_conf();   -- most settings: no restart

-- cache hit ratio (want > 99% for OLTP)
SELECT round(100.0 * sum(blks_hit) / greatest(sum(blks_hit) + sum(blks_read),1), 2) AS hit_pct FROM pg_stat_database;
-- biggest tables and indexes
SELECT relname, pg_size_pretty(pg_total_relation_size(oid)) FROM pg_class WHERE relkind = 'r' ORDER BY pg_total_relation_size(oid) DESC LIMIT 10;
-- current activity
SELECT state, count(*) FROM pg_stat_activity GROUP BY 1;
Order of attack when the DB is slow: 1) pg_stat_statements — which queries eat total time; 2) EXPLAIN (ANALYZE, BUFFERS) the top 3; 3) fix indexes / statistics / query shape; 4) check locks and idle-in-transaction; 5) check autovacuum is keeping up; 6) only then touch memory settings. Use pgtune for a first config.
Q. You set work_mem = '1GB' globally to stop sorts spilling to disk. Next morning the server was OOM-killed. Why?
Reveal hint
work_mem is per sort/hash operation, per query, per connection. A report with 4 hash joins on 50 connections can ask for 200 GB. Keep the global value modest and raise it only in the sessions that need it (SET LOCAL work_mem inside the reporting transaction).

Catalog queries you will reuse

-- columns of a table
SELECT column_name, data_type, is_nullable FROM information_schema.columns WHERE table_name = 'orders' ORDER BY ordinal_position;
-- all indexes with definition
SELECT indexname, indexdef FROM pg_indexes WHERE tablename = 'orders';
-- foreign keys without an index on the referencing column
SELECT c.conrelid::regclass AS tbl, a.attname
FROM pg_constraint c JOIN pg_attribute a ON a.attrelid = c.conrelid AND a.attnum = ANY(c.conkey)
WHERE c.contype = 'f' AND NOT EXISTS (
  SELECT 1 FROM pg_index i WHERE i.indrelid = c.conrelid AND a.attnum = i.indkey[0]);
-- long-running queries right now
SELECT pid, now() - query_start AS runtime, state, left(query, 80)
FROM pg_stat_activity WHERE state <> 'idle' ORDER BY runtime DESC;

SELECT version(), now() - pg_postmaster_start_time() AS uptime;

Functions, triggers, and when to use them

CREATE OR REPLACE FUNCTION set_updated_at() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  NEW.updated_at := now();
  RETURN NEW;
END $$;
CREATE TRIGGER trg_orders_updated BEFORE UPDATE ON orders FOR EACH ROW EXECUTE FUNCTION set_updated_at();
TopicWrongRight
Business logic in triggersTriggers that call other triggers that send notifications; nobody knows why a row changed.Triggers for mechanical things only (timestamps, audit copies, denormalized counters). Business rules in the service layer or as constraints.
SELECT * in app codeBreaks when columns are added; drags bytea/jsonb blobs you don't need; blocks index-only scans.List the columns. Projections in JPA.
Ignoring NULL semanticsWHERE col <> 'x' silently drops NULL rows; NOT IN (subquery with a NULL) returns nothing.IS DISTINCT FROM; NOT EXISTS instead of NOT IN; coalesce deliberately.
String-built SQL"… WHERE name = '" + name + "'" — injection and no plan reuse.Bind parameters, always. JPA, JdbcClient, prepared statements.
The 7 rules to remember: 1) index for your query shapes, not your columns, and index every FK; 2) EXPLAIN (ANALYZE, BUFFERS) before guessing; 3) READ COMMITTED is the default — use atomic updates, FOR UPDATE, or versions for read-modify-write; 4) short transactions, idle_in_transaction_session_timeout on; 5) never disable autovacuum; drop partitions instead of mass deletes; 6) timestamptz, bigint/uuid keys, numeric for money, jsonb only for the variable part; 7) small Hikari pools, timeouts everywhere, pg_stat_statements always on.
Q. SELECT * FROM users WHERE id NOT IN (SELECT user_id FROM orders) returns zero rows, but you know many users have no orders. Why?
Reveal hint
At least one orders.user_id is NULL. x NOT IN (…, NULL) is never true because x <> NULL is unknown. Use NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id) — it also plans better.
