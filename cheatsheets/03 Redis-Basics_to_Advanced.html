0. What is Redis? (the big idea)

Redis is an in-memory key-value store. Every key maps to a value that has a type (string, hash, list, set, sorted set, stream…), and each type has its own fast commands. Because everything lives in RAM and commands are tiny, a single Redis server answers ~100k+ requests per second with sub-millisecond latency. It is used as a cache, a session store, a counter, a queue, a lock, a leaderboard, and a pub/sub bus.

FactConsequence
Single-threaded command executionCommands run one at a time, in order. No locks needed, every command is atomic. One slow command (KEYS *, a huge SMEMBERS) blocks everyone.
Everything in RAMData size ≤ memory. Set maxmemory and an eviction policy, or Redis will refuse writes (or the OS will kill it).
Optional persistenceSnapshots (RDB) and/or an append-only log (AOF). Default durability is weaker than a database.
Binary-safe stringsKeys and values are byte arrays. JSON, protobuf, images — anything up to 512 MB (keep values small).
Replication & clusterReplicas for reads and failover (Sentinel); Cluster for sharding across nodes.

Mental model: a giant, very fast HashMap<String, Something> that lives on a server, where every Something knows a few clever tricks (increment, push, rank, expire) and the whole map can be shared by all your app instances.
Q. Redis is single-threaded. So how does it serve 100k requests per second?
Reveal hint
Each command touches RAM and takes microseconds, and the event loop never waits on disk. Network I/O is handled by extra threads since Redis 6 (io-threads), but command execution stays on one thread — which is exactly what makes every command atomic without locks.

Q. INCR counter when counter holds "abc". What happens?
Reveal hint
Error: "value is not an integer or out of range". Redis strings are untyped bytes; INCR works only if the bytes parse as a 64-bit integer. If the key does not exist, INCR treats it as 0 and returns 1.

How expiry really works

MechanismMeaning
LazyWhen a key is accessed and found expired, it is deleted then.
Active10× per second Redis samples 20 keys with TTL and deletes expired ones; repeats while > 25% were expired.
ResultExpired keys may linger a bit in memory, but are never returned to a client. INFO shows expired_keys.

Q. You SET k v EX 60, then SET k v2. What is the TTL now?
Reveal hint
Gone — plain SET replaces the key and clears the TTL. Use SET k v2 KEEPTTL (Redis 6+) or set the TTL again. Commands that modify a value (INCR, HSET, LPUSH) keep the TTL; commands that replace it do not.

3. Caching patterns and their failure modes

PatternHowProsCons
Cache-aside (lazy loading)App: GET cache → miss → read DB → SET cache with TTL → return.Simple; only requested data is cached; cache failure = slower, not broken.First request is slow; stale until TTL unless you evict on write.
Read-throughCache library loads on miss (@Cacheable does this).Same as above, less code.Same.
Write-throughWrite to cache and DB together (@CachePut).Cache always fresh for written keys.Write latency ×2; caches data never read.
Write-behindWrite to cache; flush to DB async.Very fast writes.Data loss if Redis dies before flush. Rare in Java shops.
Evict on writeOn update: write DB, then DEL the cache key (@CacheEvict).Next read refills with fresh data.Race: a concurrent reader can refill with the old value (see below).

The three classic cache problems

ProblemWhat happensFix
Stampede / dog-pileA hot key expires; 500 requests miss at once and all hit the DB.Lock the refill (SET lock:k NX PX 5000; others wait or serve stale), jittered TTLs, early refresh (refresh when TTL < 10%), Caffeine's refreshAfterWrite locally.
PenetrationRequests for ids that do not exist always miss and always hit the DB.Cache the negative result ("NULL" with a short TTL), or a Bloom filter of valid ids.
AvalancheMany keys expire at the same second (all loaded at deploy time), or Redis restarts empty.TTL jitter; warm-up on start; circuit breaker + rate limit toward the DB; persistence so Redis comes back warm.
Stale after update (race)T1 reads DB (old), T2 writes DB + DELs cache, T1 SETs cache (old) → stale until TTL.Short TTLs as a safety net; delete after the DB commit; "delayed double delete"; or version the key.
 
// cache-aside by hand with Spring's StringRedisTemplate
public Product find(long id) {
    String key = "cache:product:v1:" + id;
    String json = redis.opsForValue().get(key);
    if (json != null) return "NULL".equals(json) ? null : mapper.readValue(json, Product.class);

    Product p = repo.findById(id).orElse(null);
    Duration ttl = p == null ? Duration.ofSeconds(60)                       // negative cache, short
                           : Duration.ofMinutes(10).plusSeconds(rnd.nextInt(60)); // jitter
    redis.opsForValue().set(key, p == null ? "NULL" : mapper.writeValueAsString(p), ttl);
    return p;
}

@Transactional
public void update(Product p) {
    repo.save(p);
    TransactionSynchronizationManager.registerSynchronization(new TransactionSynchronization() {
        public void afterCommit() { redis.delete("cache:product:v1:" + p.getId()); }   // evict AFTER commit
    });
}
TopicWrongRight
Caching everythingEvery repository call wrapped in @Cacheable.Cache what is read often, changes rarely, and is expensive. Measure hit ratio; < 80% usually means the cache is not paying for itself.
Evict before commitDEL inside the transaction; a reader refills from the still-old DB row before commit.Evict after commit (above), or accept a short TTL.
Cache as source of truthBusiness data lives only in Redis with allkeys-lru.Cache is disposable. If a key must not vanish, it is not a cache — use noeviction + persistence, or a database.
Two-level ignoranceHitting Redis over the network for a value read 10k times per second per instance.Local Caffeine (ms TTL) in front of Redis in front of the DB.
SerializationJava serialization (JdkSerializationRedisSerializer): big, slow, breaks on class change.JSON (Jackson) or a compact binary (Kryo/protobuf); version the key prefix when the shape changes.
Q. After a deploy, the API is slow for 2 minutes and the DB is at 100% CPU, then it recovers. What is it?
Reveal hint
Cold cache (avalanche). Either Redis was flushed/restarted without persistence, or the key prefix changed. Mitigate with persistence, a warm-up job for the hottest keys, and a rate limiter / bulkhead between the app and the DB.

5. Atomicity — transactions, pipelining, Lua scripts

ToolWhat it isUse
Single commandAlways atomic (INCR, HSET multiple fields, SET NX).Prefer a command that does it all in one step.
MULTI / EXECQueue several commands; run them together with no other client in between. No rollback — a failing command does not undo the others."Do these 3 writes together." Not for read-then-decide logic (reads return only at EXEC).
WATCHOptimistic lock: EXEC fails if a watched key changed.Check-and-set loops. Clunky; Lua is usually cleaner.
PipeliningSend N commands without waiting for each reply. Not atomic, just fewer round trips.Bulk loads, 1000 GETs → one network round trip.
Lua script (EVAL / EVALSHA)A small program that runs atomically on the server. Can read, decide, and write.Rate limiters, locks with owner check, pop-and-remove, any compare-and-act.
Functions (Redis 7)Named, persisted Lua libraries (FUNCTION LOAD, FCALL).Same as scripts, better lifecycle.

Q. Why is "GET the lock value, compare in Java, then DEL" an unsafe way to release a lock?
Reveal hint
Between your GET and DEL the lock can expire and another worker can acquire it; your DEL then removes their lock. The compare-and-delete must be atomic — hence the Lua script.

6. Distributed locks, rate limiting, idempotency

Distributed lock

# acquire: unique owner token + TTL, in one atomic command
SET lock:order:9 "7f3a-…-uuid" NX PX 30000       # OK = got it; nil = someone else has it
# release: Lua compare-and-delete (Section 5)
# extend (if work takes longer): Lua — if GET == token then PEXPIRE
// Redisson does all of this (watchdog auto-extends while the thread lives)
RLock lock = redisson.getLock("lock:order:9");
if (lock.tryLock(2, 30, TimeUnit.SECONDS)) {       // wait up to 2 s, hold max 30 s
    try { process(order); } finally { lock.unlock(); }
}
RuleWhy
Always set a TTL.A crashed holder must not lock forever.
Store a unique token; release only if it matches.You must not delete someone else's lock after yours expired.
TTL > worst-case work time, or extend it.If the lock expires mid-work, two workers run at once.
A single Redis is not a perfectly safe lock.Failover to a replica that missed the SET can hand the lock to two clients. Redlock (N independent masters) narrows this; for money-critical mutual exclusion use the database (SELECT … FOR UPDATE, advisory locks) or a fencing token.

Rate limiting

AlgorithmHow in RedisTrade-off
Fixed windowINCR rl:user:42:2026-10-25T10:31 + EXPIRE 60; allow if ≤ limit.Simplest. Allows 2× burst at window edges.
Sliding window logZSET of timestamps: ZADD now now, ZREMRANGEBYSCORE 0 now-60s, ZCARD ≤ limit. In Lua.Exact. Memory per request.
Sliding window counterWeighted mix of current and previous fixed window.Cheap and smooth; approximate.
Token bucketHash {tokens, last_refill}; Lua refills by elapsed time and takes one.Allows controlled bursts. What Resilience4j/Bucket4j implement (Bucket4j has a Redis backend).

Idempotency keys

SETNX then EXPIRETwo commands: crash between them = lock with no TTL.SET k v NX PX ms — one command.
Lock without owner checkDEL lock on release.Token + Lua compare-and-delete.
Redis lock for correctness-critical moneyTrusting a single Redis to prevent double payment.DB-level uniqueness/locks as the final guard; Redis lock to reduce contention only.

Q. Worker A takes a lock with TTL 30 s, then a GC pause of 40 s hits. What happens?
Reveal hint
The lock expires at 30 s; worker B acquires it; A wakes up and keeps working believing it still holds the lock → two writers. Defences: watchdog extension (only helps if the thread is alive, not paused), short critical sections, and a fencing token (increasing number stored with the lock) that the downstream store rejects if stale.

7. Pub/Sub, Lists as queues, and Streams

MechanismDeliveryPersistenceConsumersUse
Pub/Sub (PUBLISH / SUBSCRIBE)Fire-and-forget to whoever is listening right now.None. Offline subscribers miss messages.All subscribers get every message.Cache invalidation broadcasts, live UI updates, chat presence.
List queue (LPUSH / BRPOP)Each item to exactly one popper.Yes (as long as Redis persists). Lost if the worker crashes after pop.Competing workers.Simple background jobs.

Q. Two consumers in the same group and two in a different group read a stream. Who gets an entry?
Reveal hint
Exactly one consumer in each group. Groups are independent cursors over the same log (like Kafka consumer groups); within a group, entries are load-balanced. So billing gets every order once, analytics gets every order once.

Q. With appendfsync everysec, Redis replied OK to your write. Is it on disk?
Reveal hint
Not necessarily — it is in the OS buffer and will be fsynced within about a second. A power loss in that window loses it. Redis trades a little durability for speed; if you need the DB-like guarantee, your data belongs in a DB (or appendfsync always at a big cost).

Q. Your lock survived a Sentinel failover — or did it?
Reveal hint
Maybe not. If the primary died right after acknowledging SET lock NX and before the replica received it, the promoted replica has no lock and another client can take it. Async replication means Redis locks are "probably exclusive". WAIT reduces the window; a DB or fencing token closes it.

The 7 rules to remember: 1) every cache key gets a TTL with jitter; 2) SCAN, never KEYS; small keys, never giant collections; 3) allkeys-lru for caches, noeviction + AOF for data you cannot lose; 4) one atomic command or a Lua script for check-and-act; 5) SET NX PX + owner token for locks, and don't trust them with money; 6) Pub/Sub for broadcasts, Streams for work; 7) JSON serializer + versioned key prefixes in Spring.
Q. Redis uses 6 GB but DBSIZE says 1 million small keys (~200 MB of data). Where is the memory?
Reveal hint
Check mem_fragmentation_ratio (allocator fragmentation after churn), a few huge keys hiding in the count (--bigkeys), client output buffers (a slow subscriber on Pub/Sub can hold GBs — CLIENT LIST shows omem), and the replication backlog. Each has its own fix: activedefrag, split keys, client-output-buffer-limit.
