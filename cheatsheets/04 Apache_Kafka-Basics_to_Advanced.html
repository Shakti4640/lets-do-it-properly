0. What is Kafka? (the big idea)

Kafka is a distributed, append-only log. Producers write records to the end of a topic; consumers read from any position they like, at their own pace, and many different consumers can read the same data without affecting each other. Records are kept on disk for a set time (days, weeks, forever), not deleted when read. This makes Kafka a message bus, an event store, and a data pipeline backbone in one.

Queue (RabbitMQ, SQS) thinkingKafka thinking
A message is consumed and gone.A record stays in the log until retention expires. Consumers just move a pointer (offset).
The broker pushes to consumers and tracks delivery per message.Consumers pull in batches and own their offsets. The broker is dumb and fast.
One consumer gets the message.Every consumer group gets every record; inside a group, partitions are split among members.
Order is per queue, often lost with multiple consumers.Order is guaranteed per partition. Same key → same partition → ordered.
Replay is hard.Reset the offset and re-read a week of events.
WordPlain meaning
BrokerOne Kafka server. A cluster is several brokers.
TopicA named stream of records, e.g. orders.
PartitionA topic is split into N ordered logs. Unit of parallelism and ordering.
OffsetThe position of a record in a partition (0, 1, 2…). Consumers store "I have processed up to offset X".
RecordKey (optional), value, headers, timestamp. Both key and value are bytes to Kafka.
Producer / ConsumerWrites records / reads records.
Consumer groupA set of consumers sharing a group.id; each partition is read by exactly one member.
Replication factorHow many brokers hold a copy of each partition (3 in production).
Leader / follower (ISR)One broker leads each partition; followers copy it. In-Sync Replicas are followers that are caught up.
KRaftKafka's built-in consensus (replaces ZooKeeper since 3.x; ZooKeeper removed in 4.0).

Mental model: a topic is a set of numbered notebooks (partitions). Writers append lines to the end of one notebook, chosen by the key. Each reader group keeps its own bookmark per notebook. Nobody tears pages out; old pages fall off after the retention period.
Q. Two services (billing, analytics) both need every order event. How many copies does the producer send?
Reveal hint
One. Each service uses its own group.id, so each group reads the whole topic independently with its own offsets. Adding a third reader later costs the producer nothing.

1. Topics, partitions, replication, retention

SettingMeaningGuidance
partitionsParallelism and ordering units. Max useful consumers in a group = partitions.Start with 6–12 for a normal topic; more for high throughput. You can add partitions later but not remove them, and adding changes key→partition mapping.
replication.factorCopies of each partition.3 in production. 1 only in dev.
min.insync.replicasHow many replicas must ack a write when acks=all.2 with RF 3: survives one broker loss without losing acked data.
retention.ms / retention.bytesHow long / how much to keep per partition.Default 7 days. -1 = forever (event sourcing). Size caps protect disks.
cleanup.policydelete (by time/size) or compact (keep latest record per key) or both.Compact for "current state" topics (user profile, inventory level). Null value = tombstone = delete key.
segment.bytes / segment.msLog is stored as segment files; only closed segments can be deleted/compacted.Smaller segments → retention applies sooner. Default 1 GB.
max.message.bytesLargest record.Default ~1 MB. Keep records small; put blobs in S3 and send a pointer.
unclean.leader.election.enableAllow an out-of-sync replica to become leader.false — availability vs data loss; choose no loss.

Changing partition count breaks key ordering for keys that now hash to a different partition: new records go to the new partition while old ones sit in the old. If per-key order matters, over-provision partitions from the start, or create a new topic and migrate.
Q. A compacted topic has records for key user-7 at offsets 10, 55, 200. After compaction, what is left?
Reveal hint
Only offset 200 (the latest), and only in already-closed segments — the active segment is never compacted, so the "head" may still hold duplicates. A later record with a null value (tombstone) deletes the key after delete.retention.ms.

2. Producers — batching, acks, idempotence

// plain client
Properties p = new Properties();
p.put("bootstrap.servers", "b1:9092,b2:9092");
p.put("key.serializer",   StringSerializer.class.getName());
p.put("value.serializer", StringSerializer.class.getName());
p.put("acks", "all");
p.put("enable.idempotence", "true");      // default since 3.0: no duplicates on retry, ordered per partition
p.put("linger.ms", "5");                  // wait up to 5 ms to fill a batch
p.put("batch.size", "65536");
p.put("compression.type", "lz4");         // or zstd; compresses whole batches

try (var producer = new KafkaProducer<String, String>(p)) {
    var rec = new ProducerRecord<>("orders", "cust-42", json);
    rec.headers().add("traceId", traceId.getBytes());
    producer.send(rec, (meta, ex) -> {                       // async; callback on ack or failure
        if (ex != null) log.error("send failed", ex);
        else log.debug("p={} o={}", meta.partition(), meta.offset());
    });
    producer.flush();                                         // before exit; close() flushes too
}

How a send really works

#Step
1send() serializes key/value, picks the partition, and appends to an in-memory batch for that partition. Returns a Future immediately.
2A background Sender thread ships batches when batch.size fills or linger.ms passes — one request per broker carrying many batches.
3The partition leader appends to its log; followers fetch; with acks=all the leader replies once min.insync.replicas have it.
4On a retriable error (leader moved, timeout) the producer retries; idempotence (producer id + sequence number) lets the broker drop duplicates.
SettingOptionsPick
acks0 fire-and-forget · 1 leader wrote it · all ISR wrote itall for anything you care about. 1 can lose acked data on leader failure.
enable.idempotencetrue/falsetrue (default). Forces acks=all, retries>0, max.in.flight ≤ 5 — and still keeps order.
retries / delivery.timeout.msRetry count / total time budgetLeave retries at MAX_INT; control with delivery.timeout.ms (default 120 s).
linger.ms / batch.sizeLatency vs throughputlinger.ms=5–20 gives big wins in throughput for ~ms latency. batch.size is a cap, not a minimum.
compression.typenone, gzip, snappy, lz4, zstdlz4 or zstd. Compression happens per batch — bigger batches compress better.
max.request.sizePer requestMust match broker max.message.bytes.
buffer.memory / max.block.msMemory for unsent batches / how long send() blocks when fullIf the broker is slow, send() blocks after 60 s → make your threads aware.
transactional.idEnables transactions (exactly-once, Section 4)Only for consume-transform-produce or multi-topic atomic writes.
TopicWrongRight
Blocking per recordproducer.send(rec).get() for every record → throughput of a few hundred/s.Async send with callback; flush() at the end of a unit of work. Use .get() only when you need the ack before replying to a caller.
Producer per requestCreating a KafkaProducer per HTTP request.One producer per application (it is thread-safe and heavy). Spring's KafkaTemplate does this.
Ignoring the callbacksend() with no callback; failures vanish.Always handle the exception path: log, metric, dead-letter.
Big messages5 MB PDFs through Kafka.Store in S3; send a reference. Keep records < 100 KB.
No key when order mattersOrder "created", "paid", "shipped" with null keys → land on different partitions → consumed out of order.Key by order id (or customer id).
Q. acks=all, RF 3, min.insync.replicas=1. Two brokers die. Does the write succeed, and is it safe?
Reveal hint
It succeeds — the leader alone satisfies min ISR 1 — but if that last broker dies before the others catch up, the acked data is lost. min.insync.replicas=2 would instead reject writes (NotEnoughReplicasException) until a replica returns: unavailable but never lying about durability.

3. Consumers, groups, offsets, rebalancing

Properties p = new Properties();
p.put("bootstrap.servers", "b1:9092");
p.put("group.id", "billing");                      // the group; all members share partitions
p.put("key.deserializer",   StringDeserializer.class.getName());
p.put("value.deserializer", StringDeserializer.class.getName());
p.put("enable.auto.commit", "false");              // commit by hand after processing
p.put("auto.offset.reset", "earliest");           // no committed offset yet → start from the beginning
p.put("max.poll.records", "200");

try (var consumer = new KafkaConsumer<String, String>(p)) {
    consumer.subscribe(List.of("orders"));
    while (running) {
        ConsumerRecords<String, String> batch = consumer.poll(Duration.ofMillis(500));
        for (var r : batch) handle(r.key(), r.value(), r.partition(), r.offset());
        consumer.commitSync();                        // "I have processed everything poll() gave me"
    }
}
ConceptMeaning
Committed offsetStored in the internal topic __consumer_offsets per (group, topic, partition). It is the offset of the next record to read. On restart the consumer resumes there.
LagLatest offset in the partition − committed offset. The key health metric: growing lag = consumers can't keep up.
RebalanceWhen a member joins/leaves (deploy, crash, scale), partitions are reassigned. During a rebalance nothing is consumed (eager) or only moved partitions pause (cooperative).
Group coordinatorA broker that tracks members via heartbeats and runs rebalances.
AssignorHow partitions are split: RangeAssignor (default, uneven across topics), CooperativeStickyAssignor (minimal movement, incremental). Use cooperative sticky.
Static membershipgroup.instance.id — a restarting pod keeps its partitions without a rebalance (within session.timeout.ms).
Idle consumersMore members than partitions → extras sit idle. Parallelism = partitions.
SettingDefaultMeaning / guidance
enable.auto.committrue (every 5 s)Auto-commit commits what poll() returned, possibly before you processed it → loss on crash. Prefer manual commit (Spring does this for you).
auto.offset.resetlatestWhere a new group starts: earliest (replay everything) or latest (only new). Irrelevant once offsets exist.
max.poll.records500Records per poll. Smaller = less work per loop = safer against the next setting.
max.poll.interval.ms5 minIf processing a batch takes longer, the consumer is kicked out → rebalance → duplicates. Raise it or process faster.
session.timeout.ms / heartbeat.interval.ms45 s / 3 sHeartbeats run on a background thread; missing them = dead member.
fetch.min.bytes / fetch.max.wait.ms1 / 500Batch fetches for throughput.
isolation.levelread_uncommittedread_committed to skip records from aborted transactions.
partition.assignment.strategyRange + CooperativeStickySet to CooperativeStickyAssignor.

TopicWrongRight
Slow processing in the poll loopCalling a 10-second API per record with max.poll.records=500 → exceeds max.poll.interval.ms → endless rebalances.Fewer records per poll, async processing with care, or raise the interval. Watch for "consumer poll timeout has expired" in logs.
Commit before processingAuto-commit, or commitAsync() right after poll().Commit after the batch is processed (at-least-once). Make handlers idempotent.
One consumer per topic per app50 topics → 50 consumer threads idling.One consumer can subscribe to many topics; or a regex subscription.
Scaling past partitions20 pods on a 6-partition topic; 14 do nothing.Partitions ≥ expected max consumers; or parallel processing inside a consumer with per-key ordering.
Sharing a consumer across threadsKafkaConsumer used from two threads → ConcurrentModificationException.One consumer per thread. Spring's concurrency creates N consumers.
Resetting a live groupReset offsets while consumers run → error / no effect.Stop the consumers, reset, start.
Lag monitoring is the one alert you need: export kafka_consumergroup_lag (Burrow, kafka-exporter, or Micrometer kafka.consumer.fetch.manager.records.lag) and alert when it grows for more than a few minutes.
Q. A consumer processes 100 records, crashes before committing, restarts. What happens?
Reveal hint
It re-reads from the last committed offset and processes those 100 again — at-least-once. This is the normal Kafka contract; the fix is on your side: idempotent handlers (unique constraint on event id, upsert, dedupe table), not fighting Kafka.

4. Delivery guarantees — at-most-once, at-least-once, exactly-once

GuaranteeProducer sideConsumer sideResult
At-most-onceacks=0 or no retriesCommit before processing (auto-commit)Fast; may lose records. Metrics, logs where gaps are OK.
At-least-once (the default to aim for)acks=all, idempotent producer, retriesProcess, then commitNever loses; may duplicate. Make handlers idempotent.
Exactly-once (EOS)Transactions: transactional.id, initTransactions, beginTransaction, sendOffsetsToTransaction, commitTransactionisolation.level=read_committedExactly once within Kafka: consume from A → produce to B + commit offsets atomically. Does not cover side effects (DB writes, emails).
 
// consume-transform-produce with exactly-once (plain client; Kafka Streams does this for you)
producer.initTransactions();
while (running) {
    var records = consumer.poll(Duration.ofMillis(200));
    if (records.isEmpty()) continue;
    producer.beginTransaction();
    try {
        for (var r : records) producer.send(new ProducerRecord<>("invoices", r.key(), toInvoice(r.value())));
        producer.sendOffsetsToTransaction(currentOffsets(records), consumer.groupMetadata());   // offsets ride in the txn
        producer.commitTransaction();
    } catch (Exception e) {
        producer.abortTransaction();                   // output and offsets both rolled back
    }
}

Idempotent consumers — the practical path to "effectively once"

TechniqueHow
Natural idempotencyUpserts (INSERT … ON CONFLICT DO UPDATE), "set status = PAID" instead of "increment".
Dedupe keyEvent id (or topic-partition-offset) stored in a processed_events table with a unique constraint; insert it in the same DB transaction as the business change.
Transactional outboxFor the produce side: write the event to an outbox table in the same DB txn as the state change; a relay (Debezium / poller) publishes it. No "DB saved but Kafka failed" gap.
Version checksIgnore events older than the current entity version.
TopicWrongRight
"Exactly-once solves duplicates in my DB"Turning on Kafka transactions and expecting the Postgres write to be exactly once.EOS is Kafka-to-Kafka only. For external systems: idempotent handler + dedupe table, or outbox.
Dual writeSave to DB, then send() to Kafka. Crash in between → DB has it, Kafka does not (or vice versa).Transactional outbox / CDC.
Non-idempotent side effectsConsumer sends an email per record; redelivery → duplicate emails.Dedupe on event id before the side effect; or make the side effect idempotent (idempotency key to the email API).
Transactions for everythingtransactional.id on a simple fire-and-forget producer.Transactions add latency and complexity. Idempotent producer + at-least-once consumer covers most needs.
Q. With read_committed, can a consumer see a record from an open (not yet committed) transaction?
Reveal hint
No. The consumer stops at the Last Stable Offset — it will not read past the first open transaction in the partition. That is also why a stuck producer transaction blocks downstream readers until transaction.timeout.ms (default 60 s) aborts it.

// producing
@Service
class OrderEvents {
    private final KafkaTemplate<String, OrderEvent> kafka;
    OrderEvents(KafkaTemplate<String, OrderEvent> kafka) { this.kafka = kafka; }

    void placed(Order o) {
        kafka.send("orders", o.customerId(), OrderEvent.placed(o))          // key = customer → ordered per customer
             .whenComplete((res, ex) -> { if (ex != null) log.error("publish failed {}", o.id(), ex); });
    }
}

// consuming
@Component
class BillingListener {
    @KafkaListener(topics = "orders", groupId = "billing")
    void on(OrderEvent e,
            @Header(KafkaHeaders.RECEIVED_KEY) String key,
            @Header(KafkaHeaders.OFFSET) long offset) {
        billing.handle(e);                 // throw → retries/DLT via the error handler; return → offset committed
    }

    @KafkaListener(topics = "audit", batch = "true")
    void onBatch(List<ConsumerRecord<String, AuditEvent>> records, Acknowledgment ack) {   // ack-mode: MANUAL
        repo.saveAll(records.stream().map(ConsumerRecord::value).toList());
        ack.acknowledge();
    }
}

// retries + dead-letter topic: 3 tries with backoff, then publish to orders.DLT and move on
@Bean
DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
    var recoverer = new DeadLetterPublishingRecoverer(template);         // default: <topic>.DLT, same partition
    var handler = new DefaultErrorHandler(recoverer, new ExponentialBackOffWithMaxRetries(3));
    handler.addNotRetryableExceptions(ValidationException.class);      // straight to DLT
    return handler;
}

// non-blocking retries on separate topics (orders-retry-1000, orders-retry-2000, orders-dlt)
@RetryableTopic(attempts = "4", backoff = @Backoff(delay = 1000, multiplier = 2.0))
@KafkaListener(topics = "orders")
void on(OrderEvent e) { ... }
@DltHandler
void dlt(OrderEvent e, @Header(KafkaHeaders.EXCEPTION_MESSAGE) String why) { alert(e, why); }

// topics as code
@Bean NewTopic orders() { return TopicBuilder.name("orders").partitions(12).replicas(3).config("min.insync.replicas", "2").build(); }
PieceNote
KafkaTemplateThread-safe wrapper over one producer. send() returns CompletableFuture<SendResult>.
@KafkaListenerCreates a container with concurrency consumers. Each consumer = one thread = one or more partitions.
Ack modesRECORD (commit per record), BATCH (after each poll's batch, default), MANUAL/MANUAL_IMMEDIATE (you call ack.acknowledge()).
ErrorHandlingDeserializerWraps the real deserializer so a poison message (bad JSON) goes to the error handler instead of killing the consumer loop forever.
DefaultErrorHandlerBlocking retries in place (pauses the partition) then recoverer. Fine for short backoffs.
@RetryableTopicNon-blocking: failed records go to retry topics with delays; the main partition keeps flowing. Loses strict ordering for retried records.
Transactionsspring.kafka.producer.transaction-id-prefix=tx- enables KafkaTransactionManager; @Transactional on a method that sends → atomic. Chain with JPA via ChainedKafkaTransactionManager is deprecated — prefer outbox.
Testing@EmbeddedKafka (fast, in-JVM) or Testcontainers KafkaContainer with @ServiceConnection.
HeadersSpring adds type info headers (__TypeId__) with JsonSerializer; disable (spring.json.add.type.headers=false) when non-Spring consumers read the topic.
TopicWrongRight
Poison pillPlain JsonDeserializer; one malformed record → infinite deserialization error loop, partition stuck.ErrorHandlingDeserializer + DLT.
Swallowing exceptionstry { … } catch (Exception e) { log.error(…) } in the listener → offset committed, record silently lost.Let it throw; the error handler retries and dead-letters. Log and rethrow if you must log.
Concurrency > partitionsconcurrency: 10 on a 3-partition topic.7 threads idle. Match partitions, or raise partitions.
Blocking retry with long backoffDefaultErrorHandler with 5 retries × 1 minute: that partition is frozen for 5 minutes.@RetryableTopic for long backoffs; blocking only for sub-second retries.

Q. Your listener method is @Transactional (JPA) and the DB commit succeeds, but then the offset commit fails. What do you see?
Reveal hint
The record is redelivered and your JPA transaction runs again → duplicate DB row unless the handler is idempotent (unique constraint on event id, upsert). Kafka and JPA are two separate transactions; make the handler idempotent rather than trying to glue them.

Q. A consumer gets SerializationException: Unknown magic byte!. What happened?
Reveal hint
The record was not written by a Schema Registry serializer (no 0x00 magic byte + schema id prefix) — probably a JSON producer or the console producer wrote to an Avro topic. Fix the producer; protect the consumer with ErrorHandlingDeserializer so one bad record goes to the DLT.

7. Kafka Streams and Kafka Connect

Kafka Streams — a Java library for processing topics into topics

StreamsBuilder b = new StreamsBuilder();
KStream<String, OrderEvent> orders = b.stream("orders", Consumed.with(Serdes.String(), orderSerde));

// stateless: filter + map → new topic
orders.filter((k, o) -> o.total() > 1000)
      .mapValues(OrderEvent::toBigOrderAlert)
      .to("big-orders");

// stateful: revenue per customer per hour (windowed aggregate, state in RocksDB + changelog topic)
orders.groupByKey()
      .windowedBy(TimeWindows.ofSizeWithNoGrace(Duration.ofHours(1)))
      .aggregate(() -> 0L, (k, o, sum) -> sum + o.total(), Materialized.with(Serdes.String(), Serdes.Long()))
      .toStream()
      .to("revenue-hourly");

// join a stream with a table (compacted topic) — enrich orders with customer tier
KTable<String, Customer> customers = b.table("customer-profile");
orders.join(customers, (o, c) -> o.withTier(c.tier())).to("orders-enriched");

var streams = new KafkaStreams(b.build(), props);   // props: application.id, bootstrap.servers, processing.guarantee=exactly_once_v2
streams.start();

Q. Your Streams app has 3 instances and the input topic has 4 partitions. One instance dies. What happens to its state?
Reveal hint
Its tasks are reassigned; the new owner replays the task's changelog topic into a fresh RocksDB store before processing (restore time ∝ state size). Standby replicas (num.standby.replicas=1) keep a warm copy so failover is near-instant.

Q. Everything works from inside Docker, but the app on your laptop gets "Connection to node 1 (kafka/172.18.0.3:9092) could not be established". Why?
Reveal hint
The broker's advertised.listeners says kafka:9092. Your laptop cannot resolve kafka. Clients connect to bootstrap, then are redirected to advertised addresses. Configure two listeners (INTERNAL://kafka:29092, EXTERNAL://localhost:9092) and map both.

The 7 rules to remember: 1) ordering is per partition — choose the key on purpose; 2) partitions set your max parallelism and can only grow; 3) acks=all + idempotent producer + min.insync.replicas=2; 4) at-least-once + idempotent consumers beats chasing exactly-once; 5) outbox for DB + Kafka writes; 6) poison pills and retries need ErrorHandlingDeserializer and a DLT; 7) alert on lag, and never let a slow handler exceed max.poll.interval.ms.
Q. Interviewer: "Why not just use a database table as a queue instead of Kafka?"
Reveal hint
A table queue works for modest volume (with FOR UPDATE SKIP LOCKED) and has transactions with your data. Kafka wins when you need many independent consumers, replay, very high throughput, long retention, and decoupled teams — and it does not bloat your OLTP database with millions of dead rows. Pick by volume and number of consumers, not fashion.
