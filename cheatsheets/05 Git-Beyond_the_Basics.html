0. How Git really stores things (the model that explains every command)

Git is a content-addressed object store plus a few pointers. Once you see that, rebase, reset, reflog, and "detached HEAD" stop being scary.

Object / pointerWhat it isWhy you care
BlobFile contents, named by the SHA-1 (or SHA-256) of the content.Same content = same blob, stored once. Renames are free.
TreeA folder: list of names → blobs/trees.A snapshot of the whole project, not a diff.
CommitPointer to a tree + parent commit(s) + author/committer + message.Commits are snapshots. Diffs are computed on demand. A commit's SHA covers its parents, so history cannot change without new SHAs.
TagLightweight: a ref to a commit. Annotated: an object with tagger, date, message, optional signature.Use annotated tags for releases.
BranchA file in .git/refs/heads/ holding one commit SHA. That is all.Creating a branch is writing 41 bytes. Deleting one deletes a pointer, not commits.
HEADPoints at the current branch (normally) or directly at a commit ("detached").Commits move whatever HEAD points at.
Remote-tracking branchorigin/main: your last-known position of the remote's main. Updated by fetch.You never commit to it; you compare against it.
Index (staging area)A proposed next tree.add writes into it; commit turns it into a tree + commit.
ReflogA local journal of where HEAD and each branch pointed, for ~90 days.Your undo button for "I lost commits".
 
git cat-file -p HEAD              # see a commit object: tree, parent, author, message
git cat-file -p HEAD^{tree}       # the tree it points at
git rev-parse HEAD main origin/main   # resolve names to SHAs
git log --oneline --graph --decorate --all   # the picture to keep in your head
git status -sb                     # short status + ahead/behind

The three areas and the commands that move things between them

From → ToCommand
Working tree → Indexgit add -p (hunk by hunk — use this), git add file
Index → Commitgit commit, git commit --amend
Index → Working tree (unstage)git restore --staged file
Commit → Working tree (discard local edits)git restore file (destructive to uncommitted edits)
Working tree ↔ shelfgit stash push -m "wip", git stash pop, git stash list, git stash push -p (partial), -u (include untracked)
Mental model: commits are immovable rocks in a graph; branches are sticky notes you move between rocks. "Deleting history" only ever means moving sticky notes so some rocks have no note — the rocks stay (reachable via reflog) until garbage collection weeks later.
Q. "Detached HEAD" — what is detached from what, and is anything lost?
Reveal hint
HEAD points at a commit directly instead of at a branch. Nothing is lost, but new commits move no branch, so when you switch away they are only reachable via reflog. Fix: git switch -c my-branch to put a sticky note on them.

1. Branching strategies — trunk-based, GitHub Flow, GitFlow, release branches

StrategyHow it worksGood forCost
Trunk-based developmentEveryone merges to main at least daily via short-lived branches (hours–2 days). Unfinished work hidden behind feature flags. main is always releasable; releases are tags or cut from main.Teams with good CI and tests; continuous delivery. The DORA-recommended default.Needs discipline: small PRs, flags, fast CI.
GitHub FlowBranch from main, PR, review, CI, merge, deploy. No develop branch.Most web services.Same as trunk-based with slightly longer branches.
GitFlowdevelop for integration, feature/*, release/* for stabilising, hotfix/* from main, merges back both ways.Versioned products shipped to customers on a schedule (mobile apps, on-prem software).Many long-lived branches, big merges, merge hell. Overkill for SaaS.
Release branchesTrunk + release/1.4 cut at freeze; only fixes go there (cherry-picked from main).Supporting several versions at once.Cherry-pick bookkeeping.
Environment branches (dev, staging, prod)Merge to a branch = deploy to that environment.—Anti-pattern: environments drift, hotfixes skip stages, same commit never promoted. Promote artifacts, not branches.
NamingExample
Feature / fix with ticketfeat/SHOP-123-cart-coupons, fix/SHOP-130-null-total
Releaserelease/2.4
Hotfixhotfix/2.4.1-payment-timeout
Personal spikespike/asha-virtual-threads
 
# daily trunk-based loop
git switch main && git pull --rebase
git switch -c feat/SHOP-123-cart-coupons
# … small commits …
git fetch origin && git rebase origin/main      # keep current with main before the PR
git push -u origin HEAD
gh pr create --fill                            # GitHub CLI
# after merge (squash) on the server:
git switch main && git pull --rebase && git branch -d feat/SHOP-123-cart-coupons
git fetch --prune                            # drop remote-tracking refs for deleted branches
TopicWrongRight
Branch lifetimeA feature branch alive for 3 weeks; the merge takes a day and breaks two things.Merge daily. Split the feature; hide incomplete paths behind a flag.
Long-lived developGitFlow for a web service deployed 10×/day.Trunk-based / GitHub Flow. GitFlow's own author says so for CD teams.
Environment branchesgit merge main into prod to deploy.Build once from main, tag it, promote the same artifact through environments.
Protected branches offAnyone pushes to main.Branch protection: PR required, CI green, 1+ review, linear history, no force-push.
Q. Trunk-based says merge unfinished work to main. How is that not shipping broken code?
Reveal hint
The code is merged but not reachable: behind a feature flag, an unused class, or a disabled endpoint. Tests still run on it. The feature is "turned on" by config later, independently of deploys — which also gives you instant rollback.

2. Merge vs rebase vs squash — and when to use each

OperationWhat happens to historyUse when
Merge (git merge feature)A new commit with two parents; both histories kept as-is.Integrating a finished branch when you want to keep the branch's shape. Default on main ← release branches.
Fast-forward (--ff-only)No new commit; the pointer just moves. Only possible if target has no new commits.Pulling main; landing a rebased branch for linear history.
Rebase (git rebase main)Your commits are re-created on top of main with new SHAs; the old ones become unreachable.Updating your own unpushed or personal branch to current main; cleaning up before a PR.
Squash merge (PR button / merge --squash)All branch commits become one commit on main; the branch itself is not in the graph.Landing PRs: main reads as one meaningful commit per change. Loses fine-grained history (which is often noise).
Rebase and merge (PR button)Branch commits replayed on main individually, linear.When each commit in the PR is meaningful on its own.
Cherry-pick (git cherry-pick sha)Copy one commit onto the current branch (new SHA).Hotfix from main onto release/2.4. -x appends "(cherry picked from …)".
 
# update a feature branch onto latest main (your branch, not shared)
git fetch origin
git rebase origin/main
# … fix conflicts, then:
git add . && git rebase --continue          # or --skip, or --abort to go back to before the rebase
git push --force-with-lease                 # rewrite the remote branch, but refuse if someone else pushed meanwhile

# make pull do rebase by default and refuse messy merges
git config --global pull.rebase true
git config --global rebase.autoStash true    # stash/unstash around rebase automatically
git config --global merge.ff only             # explicit merges only when intended

# keep the other side's fix across rebases of the same conflict
git config --global rerere.enabled true

Merge strategies and options

OptionDoes
git merge -X ours / -X theirsOn conflict hunks only, prefer our/their side. (Not the whole file.)
git merge -s ours branchRecord a merge but keep our tree entirely (mark a branch as merged without taking changes).
git merge --no-ffForce a merge commit even when fast-forward is possible (visible feature boundary).
git rebase --onto new-base old-base branchMove a range of commits elsewhere (e.g. branched off the wrong branch).
git rebase -i --autosquashAutomatically fold fixup! / squash! commits (made with git commit --fixup sha).
git rebase --update-refsRebase a stack of branches at once (Git 2.38+).
TopicWrongRight
Rebasing shared branchesRebase main or a branch others pulled → everyone's history diverges; "your branch and origin have diverged" for the whole team.The golden rule: rebase only commits nobody else has based work on. Public history is merge-only.
push --forceOverwrites a colleague's commits pushed a minute ago.--force-with-lease (fails if the remote moved since your last fetch). Set a push alias.
Merge commits from pullDefault git pull creating "Merge branch 'main' of github.com:…" noise.pull.rebase=true or git pull --ff-only.
Resolving with -X theirs blindlyPicking a side without reading.Open the conflict; usually both changes are needed.
Squash hiding too muchSquashing a 40-commit refactor + feature into one 3,000-line commit.Split the PR; or "rebase and merge" with curated commits.
When a rebase conflict says "ours" and "theirs" backwards: during rebase, ours = the branch you are rebasing onto (upstream), theirs = your own commit being replayed. It is the reverse of merge. git checkout --theirs file keeps your change in a rebase.
Q. After rebasing, git status says "Your branch and 'origin/feat' have diverged, 5 and 5 commits". Did you break something?
Reveal hint
No — it is expected. The 5 old commits on the remote and your 5 rebased copies have different SHAs. Push with --force-with-lease to replace the remote branch. If this were main, that would be the problem.

3. Rewriting history — interactive rebase, amend, fixup, filter-repo

git rebase -i origin/main        # open an editor listing your commits, oldest first:

pick   3f1a2b0 Add coupon entity
reword 9c8d7e6 add coupon repo              # change the message
squash 1b2c3d4 fix typo                     # fold into the previous commit, keep both messages to edit
fixup  5e6f7a8 fix typo again               # fold in, discard this message
edit   a9b8c7d Wire coupon service          # stop here to split or change the commit
drop   d4c3b2a Debug logging                # delete
exec   ./mvnw -q test                       # run a command after the previous commit (catch broken intermediate commits)
# reorder lines to reorder commits
TaskCommand
Fix the last commit (message or contents)git add -p && git commit --amend · message only: git commit --amend -m "…" · keep message: --no-edit
Fix an older commit without opening the editorgit commit --fixup <sha> then git rebase -i --autosquash origin/main
Split a commitMark it edit; git reset HEAD^; git add -p + commit several times; git rebase --continue
Change author of all your commitsgit rebase -i … --exec 'git commit --amend --no-edit --reset-author' after fixing user.email
Move the branch to another basegit rebase --onto main wrong-base feat
Remove a secret / huge file from all historygit filter-repo --path secrets.env --invert-paths (install git-filter-repo; never filter-branch). Then force-push every branch, rotate the secret anyway, and have everyone re-clone.
Abort anythinggit rebase --abort, git merge --abort, git cherry-pick --abort
TopicWrongRight
Amending pushed commits--amend on a commit a teammate already has → divergence.Amend only unpushed work (or your own PR branch, then --force-with-lease).
"Secret removed" by a new commitDeleting the file in a follow-up commit; it is still in history and on every fork.filter-repo + force-push + rotate the credential. Assume it leaked.
Giant squash before reviewSquashing before the reviewer sees the steps.Keep logical commits during review; squash at merge if your team prefers one commit per PR.
Broken intermediate commitsReordered commits where the middle ones don't compile — bisect becomes useless.rebase -i --exec "./mvnw -q compile" to check every commit.
Rule of thumb: history you share is a contract; history you have not shared is a draft. Edit drafts freely; never edit contracts.
Q. You ran filter-repo to purge a password and force-pushed. A colleague runs git pull. What happens to the secret?
Reveal hint
Their local clone still has the old commits (and may push them back via a merge). Everyone must re-clone or hard-reset, and GitHub keeps cached views/forks until support purges them. Treat the secret as compromised regardless.

4. Undo anything — reset, revert, restore, reflog, recovery

I want to…CommandSafe for shared history?
Undo a commit that is already pushedgit revert <sha> → a new commit that inverts it. git revert -m 1 <merge-sha> for a merge commit.Yes. The only correct way on main.
Un-commit but keep the changes stagedgit reset --soft HEAD~1Local only.
Un-commit and unstage, keep edits in filesgit reset HEAD~1 (--mixed, the default)Local only.
Throw away commits and editsgit reset --hard origin/mainLocal only; destroys uncommitted work.
Discard edits to one filegit restore path · from a commit: git restore --source=HEAD~2 path—
Unstage one filegit restore --staged path—
Get a file from another branchgit restore --source=feat/x -- path (or git show feat/x:path > path)—
Recover a deleted branch / lost commitsgit reflog → find the SHA → git branch rescued <sha>—
Undo a bad rebase / resetgit reflog, then git reset --hard HEAD@{5} (or ORIG_HEAD right after)—
Find a dropped stashgit fsck --unreachable | grep commit → git stash apply <sha>—
Remove untracked filesgit clean -n (dry run!) then git clean -fd; -x also ignored files (build output)Destructive.
 
git reflog                                    # every place HEAD has been
a1b2c3d HEAD@{0}: reset: moving to origin/main
f0e9d8c HEAD@{1}: commit: Add coupon service        #  ← the commit you "lost"
git branch rescue f0e9d8c                     # it is back
git reflog show feat/x                        # reflog of one branch
git log -g --all --grep="coupon"             # search reflog entries by message
TopicWrongRight
Reset on maingit reset --hard HEAD~1 && git push --force on main to "remove" a bad commit.git revert. It is visible, auditable, and does not break anyone.
Panic re-cloneDeleting the repo and cloning again after a bad rebase.git reflog — 30 seconds, nothing lost.
git checkout for everythingConfusing branch switch and file restore in one command.git switch for branches, git restore for files (Git 2.23+).
clean -f without a dry runDeleting an un-added file you spent a day on.git clean -n first. Commit or stash often.
Q. Reverting a merge commit with -m 1 and later re-merging the same branch — why does Git say "Already up to date" and bring nothing in?
Reveal hint
The branch's commits are already ancestors of main (the revert only added inverse changes). Git sees nothing new to merge. Fix: revert the revert (git revert <revert-sha>), or rebase the branch so its commits get new SHAs.

5. Conflicts — resolving them well

# what a conflict looks like in the file
<<<<<<< HEAD                       # "ours" (current branch) — in a rebase: upstream
total = subtotal + tax;
||||||| merged common ancestor      # shown with merge.conflictStyle = zdiff3 — what both sides started from
total = subtotal;
=======
total = subtotal - discount;
>>>>>>> feat/coupons                # "theirs" — in a rebase: your commit
# correct answer here is almost always BOTH: total = subtotal + tax - discount;
CommandDoes
git config --global merge.conflictStyle zdiff3Shows the common ancestor in conflicts. Turn it on today; it makes conflicts understandable.
git status / git diff --name-only --diff-filter=UList conflicted files.
git diff (during conflict)Combined diff showing both sides.
git mergetoolOpen your 3-way tool (IntelliJ, VS Code, Beyond Compare, meld).
git checkout --ours path / --theirs pathTake one whole side for a file (generated files, lockfiles — then regenerate).
git add path → git rebase --continue / git merge --continueMark resolved and go on.
git log --merge -p pathShow the commits on both sides that touched the file.
git rerereReuse recorded resolutions — the same conflict resolves itself next time.
TopicWrongRight
Resolving blindDelete the markers, keep whichever block looks newer.Read both sides and the ancestor (zdiff3); ask the other author if unsure; compile and run tests before continuing.
Leftover markersCommitting <<<<<<< into the code.git diff --check flags them; a pre-commit hook can block it.
Lockfile conflictsHand-merging package-lock.json or pom.xml version lines.Take one side, re-run the tool (npm install, Maven versions plugin), commit the regenerated file.
Conflicts as a surpriseFirst rebase after 3 weeks: 40 conflicted files.Rebase onto main daily; small PRs; agree who touches shared files.
Format warsHalf the team reformats files → every merge conflicts.One formatter (Spotless/google-java-format) enforced in CI; format-only commits done once, together.
Reduce conflicts structurally: smaller files and classes, append-only patterns (new migration file instead of editing one), avoid mass renames in feature branches, and keep import ordering automated.
Q. In a rebase conflict you run git checkout --ours file. Whose version did you keep?
Reveal hint
The upstream version (e.g. main's), not yours — in a rebase, "ours" is the branch being rebased onto, because Git is replaying your commits on top of it. Use --theirs to keep your own change. zdiff3 labels make this visible.

# log filters
git log --oneline -20

git shortlog -sn --since="1 month"                  # commits per author

git diff main...feat/x --stat                     # what the PR changes vs merge-base

# who / why
git blame -w -C -L 40,60 OrderService.java        # -w ignore whitespace, -C follow moved code
git blame --ignore-revs-file .git-blame-ignore-revs OrderService.java   # skip the big-reformat commit

# bisect: find the commit that broke something
git bisect start
git bisect bad                                    # HEAD is broken
git bisect good v2.3.0                            # this tag worked
git bisect run ./mvnw -q -Dtest=CouponTest test  # exit 0 = good, non-zero = bad; Git binary-searches ~log2(n) builds
git bisect reset

# grep the tree (fast, respects .gitignore)
git grep -n "@Deprecated" -- "*.java"
git grep "feature.flag" v2.3.0                     # in an old version

# work on two branches at once without stashing
git worktree add ../shop-hotfix hotfix/2.4.1
git worktree list  ·  git worktree remove ../shop-hotfix
Revision syntaxMeaning
HEAD~33 first-parent steps back.
HEAD^2Second parent (of a merge).
main..featReachable from feat, not from main.
main...featSymmetric difference (log) / diff from merge-base (diff).

Bisect works even with a flaky middle: use git bisect skip for commits that do not build. Combine with exec rebases that keep every commit green and bisect becomes a 2-minute root cause tool.
Q. git blame shows the whole file was "changed" by one reformat commit. How do you see the real authors?
Reveal hint
Add the reformat commit's SHA to .git-blame-ignore-revs and set git config blame.ignoreRevsFile .git-blame-ignore-revs (GitHub honours the file too). Also -w ignores whitespace-only changes.

Q. Your squash-merge PR has 12 commits with mixed types. What does the release tool read?
Reveal hint
Only the final squash commit's message — which GitHub defaults to the PR title + a list of commit lines. Make the PR title follow Conventional Commits (enforce with a PR-title linter) and put the body in the PR description.

8. Pull requests and code review

PracticeWhy
Small PRs (≤ ~400 lines changed)Review quality collapses past that; defects per line rise; merges get easier. Stack PRs for big features.
Description templateWhat / why / how to test / screenshots / risk / rollback. Reviewers should not have to reverse-engineer intent.
Self-review firstRead your own diff on the PR page; you will find 30% of the comments yourself.
Draft PRsEarly visibility without asking for review.
CODEOWNERS.github/CODEOWNERS: /src/main/java/com/shop/payment/ @shop/payments-team auto-requests the right reviewers and can be required.
Required checksBuild, tests, lint, security scan, PR-title lint must pass; branch up to date with main (or a merge queue).
Merge queueGitHub/GitLab serialize merges and test each PR against the actual future main — kills "green PR, red main".
Suggested changesReviewers propose exact code; author applies in one click.
Review etiquetteComment on the code, not the person; label nits as nits; explain the why; approve with comments when nothing blocks; turn around within a day.

Mega PR"Refactor payments" — 90 files, 4,000 lines, 2 weeks of review ping-pong.Split: (1) pure refactor, no behaviour change; (2) feature; (3) cleanup. Each reviewable in 20 minutes.

Q. Two PRs both pass CI against main. Both merge. main is now red. How?
Reveal hint
Each was tested against main without the other. Their combination breaks (semantic conflict — no textual conflict). Require branches to be up to date before merge, or use a merge queue that tests the combined result.

The 7 rules to remember: 1) commits are snapshots, branches are pointers, reflog saves you; 2) short-lived branches, merge to main daily, flags for unfinished work; 3) rebase your own work, merge/revert shared history, --force-with-lease only; 4) zdiff3 and read both sides of a conflict; 5) Conventional Commits + annotated tags + SemVer, versions derived from tags; 6) small PRs, CODEOWNERS, required checks, merge queue; 7) hooks in the repo, .gitattributes for line endings, secrets never — and if they leak, rotate.
Q. git clone --depth 1 in CI, then the release step runs git describe --tags and fails. Why?
Reveal hint
A shallow clone has no history and often no tags, so describe has nothing to describe. Use fetch-depth: 0 for release jobs (or git fetch --unshallow --tags), and keep shallow clones for plain build/test jobs.
