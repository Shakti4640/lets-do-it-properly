0. What a build tool does — and Maven vs Gradle in one table

A build tool turns source code into something you can run or ship, the same way every time, on every machine. It (1) downloads the libraries you depend on, (2) compiles, (3) runs tests, (4) packages a jar or image, (5) publishes it. Both Maven and Gradle use the same repository model (Maven Central, your company Nexus/Artifactory) and the same coordinates: groupId:artifactId:version.

AspectMavenGradle
Config filepom.xml (XML, declarative)build.gradle.kts (Kotlin DSL) or build.gradle (Groovy) — code
ModelFixed lifecycle of phases; plugins bind goals to phasesGraph of tasks with inputs/outputs; plugins add tasks
SpeedRebuilds a module fully each time (no incremental compile by default)Incremental, build cache, daemon, configuration cache, parallel — much faster on big repos

Typical inSpring Boot services, enterprise Java, librariesAndroid (mandatory), Kotlin, large monorepos, Spring projects that need speed
Spring Boot supportspring-boot-starter-parent + spring-boot-maven-pluginorg.springframework.boot plugin + io.spring.dependency-management (or Gradle platforms)
WordPlain meaning
ArtifactA built file: jar, war, pom, sources jar, javadoc jar.
GAV coordinatesorg.postgresql:postgresql:42.7.4 — group, artifact, version. Plus optional classifier (sources) and type (pom).
RepositoryWhere artifacts live: Maven Central, Google, JitPack; your local cache ~/.m2/repository / ~/.gradle/caches; company proxy (Nexus/Artifactory) in front of all of them.
Transitive dependencyA dependency of your dependency. 20 direct deps often pull 300 transitive ones.
SNAPSHOT1.5.0-SNAPSHOT: a moving version re-downloaded daily. Dev only. Releases are immutable.
BOM (Bill of Materials)A POM that only lists versions for a family of libraries, so you declare them without versions.

# always use the wrapper, never a globally installed mvn/gradle
./mvnw -v          ·   ./gradlew --version
./mvnw wrapper:wrapper -Dmaven=3.9.9          # add / upgrade the Maven wrapper
./gradlew wrapper --gradle-version 8.11 --distribution-type bin   # upgrade the Gradle wrapper
Mental model: Maven is a train on fixed tracks — the stations (phases) are always the same; you choose which plugins get on at each station. Gradle is a road network — tasks are towns, dependencies are roads, and Gradle drives only the roads needed for your destination, skipping towns it has visited with the same inputs.
Q. Your laptop has Maven 3.6 installed; the repo has mvnw for 3.9. Which should CI use?
Reveal hint
The wrapper, always. It pins the version in .mvn/wrapper/maven-wrapper.properties so the build is reproducible; a global install varies per machine. Same for gradlew — and commit the wrapper jar/script.

The default lifecycle — each phase runs all the ones before it

PhaseDefault plugin goalDoes
validate—POM is valid.
compilecompiler:compilesrc/main/java → target/classes. Resources copied in process-resources just before.
testsurefire:testCompile and run unit tests (*Test, Test*, *Tests).
packagejar:jar (+ spring-boot:repackage)Build target/shop-api-1.4.0.jar.
verifyfailsafe:integration-test + verifyRun integration tests (*IT), checks (JaCoCo thresholds, OWASP).

./mvnw clean verify                              # the CI command: clean, compile, unit tests, package, integration tests, checks
./mvnw package -DskipTests                       # compile tests but do not run them (-Dmaven.test.skip=true skips compiling too)
./mvnw test -Dtest=OrderServiceTest#createsOrder  # one test method
./mvnw spring-boot:run                           # run a plugin goal directly: plugin:goal
./mvnw verify -pl services/orders -am             # one module (-pl) and what it depends on (-am)
./mvnw verify -T 1C                              # parallel: 1 thread per core (modules in parallel)
./mvnw verify -o                                 # offline
./mvnw verify -P ci -Denv=staging               # activate a profile; set a property
./mvnw help:effective-pom                        # the POM after all inheritance and defaults — read this when confused
./mvnw dependency:tree -Dincludes=com.fasterxml.jackson.core   # who brings Jackson in
./mvnw versions:display-dependency-updates       # what is outdated
./mvnw -B -ntp -q verify                          # CI flags: batch mode, no transfer progress, quiet
TopicWrongRight
Phase vs goalThinking mvn test runs "just the tests".It runs every phase up to test (compile too). plugin:goal runs one goal only.
install in CImvn clean install as the CI command.mvn verify. install pollutes the runner's ~/.m2 and is slower. Use install only for local cross-project work.
Versions everywhereEvery dependency has its own <version>; two modules disagree.Versions in <dependencyManagement> of the parent (or BOMs); children declare without versions.
-Dmaven.test.skip=true by habitTests never compile; broken test code ships unnoticed for weeks.-DskipTests when you must skip; CI never skips.
Unit and integration tests mixedTestcontainers tests named *Test run on every mvn test, 10 minutes each time.*IT via Failsafe in verify; fast unit tests in test.
Q. dependencyManagement lists guava 33.0, but Guava is not on the classpath. Why?
Reveal hint
dependencyManagement only manages versions; it adds nothing. A module must still declare <dependency> (without version) in <dependencies> to actually get it.

How conflicts are resolved (the one thing that differs most)

ToolRuleExample: A→X 1.0 (depth 1), B→C→X 2.0 (depth 2)Override
MavenNearest wins; tie → first declared in the POM.X 1.0 wins (closer) — even though 2.0 is newer. Silent downgrade!Declare X 2.0 directly, or in dependencyManagement (which wins over everything transitive).
GradleHighest version wins.X 2.0 wins.strictly("1.0"), force, resolutionStrategy, dependency locking.

./mvnw dependency:tree -Dverbose -Dincludes=org.slf4j      # "(omitted for conflict with 2.0.16)"
./mvnw dependency:analyze                                  # used-but-undeclared / declared-but-unused

<dependency>
  <groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-web</artifactId>
  <exclusions><exclusion>
    <groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-tomcat</artifactId>   <!-- then add starter-undertow -->
  </exclusion></exclusions>
</dependency>

<plugin><groupId>org.apache.maven.plugins</groupId><artifactId>maven-enforcer-plugin</artifactId>
  <executions><execution><goals><goal>enforce</goal></goals>
    <configuration><rules>
      <dependencyConvergence/>                                 <!-- all paths must agree on a version -->
      <banDuplicatePomDependencyVersions/>
      <requireMavenVersion><version>[3.9,)</version></requireMavenVersion>
      <requireJavaVersion><version>[21,)</version></requireJavaVersion>
    </rules></configuration>
  </execution></executions>

dependencies {
    implementation(platform("org.springframework.boot:spring-boot-dependencies:3.4.1"))   // BOM
    implementation("org.springframework.boot:spring-boot-starter-web") {
        exclude(group = "org.springframework.boot", module = "spring-boot-starter-tomcat")
    }
    implementation("com.google.guava:guava") { version { strictly("33.3.1-jre") } }     // pin hard
    constraints { implementation("org.yaml:snakeyaml:2.3") { because("CVE-2022-1471") } }   // bump a transitive
}

TopicWrongRight
Version ranges[1.0,2.0) or 1.+ — the build changes without a commit.Exact versions (or BOM-managed); upgrade via Dependabot/Renovate PRs.
Silent downgrade (Maven)A transitive brings an old Jackson that wins by "nearest"; NoSuchMethodError in prod.Enforcer dependencyConvergence; manage the version explicitly.
compile for everythingJDBC driver and Logback on the compile classpath.runtime/runtimeOnly: code can't accidentally depend on them.
Gradle api everywhereEvery dependency leaks to consumers; any change recompiles the world.implementation by default; api only for types in your public signatures.
Snapshots in releasesA release jar depends on lib-1.2-SNAPSHOT.Enforcer requireReleaseDeps; snapshots only on dev branches.
Fat jar conflictsTwo jars provide the same class; which one loads depends on the order.dependency:analyze / duplicate-finder-maven-plugin; exclude one.
Spring Boot's BOM does most of the work: with the starter parent (Maven) or the dependency-management plugin / platform() (Gradle), ~1,000 library versions are already chosen to work together. Override one with a property like <jackson-bom.version> rather than hard-coding versions.
Q. Maven and Gradle resolve the same POM differently. Which resolution is "right"?
Reveal hint
Neither — they are different policies. Maven's nearest-wins can downgrade; Gradle's highest-wins can upgrade past what a library was tested with. Both are fine as long as you make the choice explicit (dependencyManagement / constraints) and fail the build on hidden conflicts.

3. Gradle — tasks, the Kotlin DSL, version catalogs

// settings.gradle.kts
rootProject.name = "shop"
include("services:orders", "services:payments", "libs:common")
dependencyResolutionManagement {
    repositories { mavenCentral() }                            // repos in one place
}
plugins { id("org.gradle.toolchains.foojay-resolver-convention") version "0.9.0" }   // auto-download JDKs

// build.gradle.kts (a service module)
plugins {
    java
    alias(libs.plugins.spring.boot)                             // from the version catalog
    alias(libs.plugins.spring.dependency.management)
}
group = "com.shop"
version = "1.4.0"
java { toolchain { languageVersion = JavaLanguageVersion.of(21) } }   // build with JDK 21 regardless of the JDK running Gradle

dependencies {
    implementation(project(":libs:common"))
    implementation(libs.spring.boot.starter.web)
    runtimeOnly(libs.postgresql)
    compileOnly(libs.lombok);  annotationProcessor(libs.lombok)
    testImplementation(libs.spring.boot.starter.test)
    testImplementation(libs.bundles.testcontainers)              // a bundle = several libs
}

tasks.withType<Test>().configureEach {
    useJUnitPlatform()
    maxParallelForks = (Runtime.getRuntime().availableProcessors() / 2).coerceAtLeast(1)
    testLogging { events("failed"); exceptionFormat = TestExceptionFormat.FULL }
}
tasks.named<Jar>("jar") { enabled = false }                     // only the boot jar

// a custom task with declared inputs/outputs (so it is cacheable and skippable)
val generateBuildInfo by tasks.registering {
    val out = layout.buildDirectory.file("generated/build-info.properties")
    inputs.property("version", version)
    outputs.file(out)
    doLast { out.get().asFile.writeText("version=$version\n") }
}
tasks.processResources { from(generateBuildInfo) }

[bundles]

ConceptMeaning
TaskA unit of work with inputs and outputs. compileJava, test, bootJar, build (= assemble + check).
Up-to-date checkIf inputs and outputs are unchanged since last run, the task is skipped (UP-TO-DATE). This is where Gradle's speed comes from.
Build cacheOutputs keyed by input hashes, reused across branches, clones, and machines (remote cache). FROM-CACHE.
Configuration cacheCaches the result of evaluating build scripts. Big win on large builds (org.gradle.configuration-cache=true).
DaemonA warm JVM that stays alive between builds. Always on locally; --no-daemon in some CI setups.
Configuration phase vs execution phaseAll build scripts are evaluated first (fast, no work), then only the needed tasks run. Doing work at configuration time (exec in a script body) slows every build.
Lazy APItasks.register / Providers — tasks are created only if needed. Avoid eager tasks.create / .get().
Convention pluginYour shared build logic in buildSrc/ or an included build-logic project (id("shop.java-conventions")), applied by every module.
ToolchainsPick the JDK for compiling/testing independent of the one running Gradle.
 
./gradlew build                                   # compile + test + jar + checks
./gradlew test --tests "com.shop.order.*"          # filter tests
./gradlew :services:orders:bootRun                # a task in one module
./gradlew build -x test                           # exclude a task
./gradlew tasks --all  ·  ./gradlew projects        # what exists
./gradlew build --scan                            # build scan: timeline, cache hits, slow tasks (develocity)
./gradlew build --build-cache --parallel --configuration-cache   # or put them in gradle.properties
./gradlew dependencyUpdates                       # (ben-manes versions plugin)
./gradlew help --task bootJar                     # task docs
./gradlew --stop                                  # kill daemons
# gradle.properties (committed)
org.gradle.parallel=true
org.gradle.caching=true
org.gradle.configuration-cache=true
org.gradle.jvmargs=-Xmx2g -XX:+UseParallelGC
org.gradle.daemon=true
TopicWrongRight
Groovy DSL for new projectsbuild.gradle with dynamic typing: no IDE completion, typos found at runtime.Kotlin DSL (.kts): typed, completable, the default since Gradle 8.
Versions in every build file12 modules each pinning Jackson differently.Version catalog (libs.versions.toml) + BOM platform.
Copy-pasted build logic60 identical lines in each module's build file.Convention plugins in build-logic/; modules apply one line.
Work at configuration timeval sha = "git rev-parse HEAD".runCommand() in the script body → runs on every invocation, even gradlew help.Inside a task's doLast or a Provider; or a plugin like gradle-git-properties.
allprojects { } cross-configRoot build file configuring children — breaks configuration cache and isolation.Convention plugins.

Q. ./gradlew test says "UP-TO-DATE" and runs no tests even though you changed a resource file. Why?
Reveal hint
If the resource is not under a declared input (e.g. it is read from an absolute path or an undeclared directory), Gradle cannot know it matters. Put it under src/test/resources, or declare it as a task input. --rerun-tasks forces one run; fix the inputs for real.

Q. You run ./mvnw -pl services/orders verify (no -am) after changing libs/common. Which common does orders compile against?
Reveal hint
Whatever common jar is in ~/.m2 (from the last install) — possibly days old. Without -am, Maven does not rebuild siblings. Use -am, or install the lib first. Gradle avoids this: project(":libs:common") always builds the current source.

Q. Surefire runs your *Test classes but ignores OrderRepositoryIT. Where does it run?
Reveal hint
Nowhere, unless Failsafe is configured. Surefire's default pattern excludes *IT; Failsafe's includes it, but Failsafe is not bound by default — add the plugin with integration-test and verify goals. That gap is why "all tests pass" sometimes means half the tests never ran.

Q. Gradle's remote build cache gives a FROM-CACHE hit for test on a PR. Were the tests run?
Reveal hint
Not on this run — the task's inputs (classes, resources, test classpath, JVM args) were identical to a previous run whose outputs were cached, so the result (test report XML) is replayed. That is correct if inputs are fully declared. Tests that read the clock, network, or undeclared files must be marked non-cacheable.

The 7 rules to remember: 1) wrapper always, never a global install; 2) versions in one place (parent dependencyManagement + BOMs / version catalog + platform), exact, no ranges; 3) verify not install in CI; unit tests in test, ITs in verify; 4) right scopes (runtime/compileOnly/test; Gradle implementation over api); 5) fail on conflicts (enforcer / failOnVersionConflict), know nearest-wins vs highest-wins; 6) credentials and repos outside the build file; one artifact for all environments; 7) cache dependencies and build outputs, build only what changed, make jars reproducible.
Q. Interviewer: "Why do you add -SNAPSHOT during development and remove it at release?"
Reveal hint
A SNAPSHOT version is mutable: the repo keeps re-publishing under the same name and consumers re-check for newer uploads, so teams can share work in progress. A release version must be immutable — same coordinates, same bytes, forever — so repos reject redeploys. The suffix tells both tools and humans which rules apply.
