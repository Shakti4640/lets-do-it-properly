0. What is Docker? (the big idea)

Docker packs your app and everything it needs (code, libraries, settings) into one box called an image. You run that image as a container. The same box runs the same way on your laptop, a test server, and the cloud. No more "it works on my machine".

WordPlain meaningThink of it as
ImageA read-only snapshot of a file system plus a start command. Built once, shared many times.A recipe or a class
ContainerA running copy of an image, with its own process, file layer, and network.A cooked dish or an object
DockerfileA text file with steps that build an image.The recipe card
RegistryA server that stores images (Docker Hub, ECR, GHCR).A cookbook library
Docker EngineThe background service (dockerd) that builds and runs containers.The kitchen
Docker CLIThe docker command you type. It talks to the engine.Your order slip

Container vs Virtual Machine

PointContainerVirtual Machine
What it sharesShares the host's Linux kernel.Has its own full OS and kernel.
SizeMBs. Starts in under a second.GBs. Starts in minutes.
IsolationProcess-level (namespaces + cgroups). Good, not perfect.Hardware-level. Stronger.
Best forPackaging and running one app or service.Running a whole different OS.
How it works under the hood: a container is just a normal Linux process. Namespaces give it its own view of files, network, and process IDs. cgroups cap how much CPU and memory it can use. There is no "mini OS" inside.
Q. Can one image run as many containers at the same time?
Reveal hint
Yes. The image is read-only. Each container adds its own thin writable layer on top. Many containers from one image is the normal case.

1. First steps — check, run, see

docker version                  # client + engine version (engine must be running)
docker info                     # storage driver, number of containers, etc.
docker run hello-world          # pulls image if missing, runs it, prints a message
docker run -it ubuntu bash        # -i keep input open, -t give a terminal -> a shell inside
docker run -d -p 8080:80 --name web nginx   # -d run in background, host 8080 -> container 80
docker ps                       # running containers
docker ps -a                    # all, even stopped ones
docker logs -f web               # follow the output of 'web'
docker stop web && docker rm web  # stop, then remove

The most used docker run flags

FlagDoesExample
-dRun in the background (detached).docker run -d nginx
-itInteractive terminal. Use for shells.docker run -it alpine sh
-p host:containerPublish a port to the host.-p 3000:3000
--nameGive the container a name (else you get a random one).--name api
-e KEY=VALSet an environment variable.-e NODE_ENV=prod
-v / --mountAttach a volume or a host folder.-v data:/var/lib/mysql
--rmDelete the container when it stops. Great for one-off runs.docker run --rm alpine echo hi
--restartRestart rule: no, on-failure, always, unless-stopped.--restart unless-stopped
--networkJoin a network.--network mynet
--cpus / --memoryCap CPU and RAM.--cpus 1 --memory 512m
Tip: docker run = docker create + docker start. It always makes a new container. To get back into an existing one, use docker exec or docker start, not run.
Q. You ran docker run ubuntu and it exited at once. Why?
Reveal hint
The default command for ubuntu is bash. With no terminal attached, bash has nothing to read, so it quits. A container lives only as long as its main process. Use -it for a shell, or give it a long-running command.

Q. Does :latest mean the newest version of the image?
Reveal hint
No. latest is only a default tag name. It points to whatever the publisher last pushed with that tag. It may be old, or not even the newest release. Pin real versions.

3. Containers — life cycle and daily commands

A container moves through states: created → running → paused / stopped → removed. The container ends when its main process (PID 1) ends.

TaskCommandNote
Start / stop / restartdocker start web · docker stop web · docker restart webstop sends SIGTERM, waits 10s, then SIGKILL.
Force killdocker kill webSIGKILL right away. Data may be lost.
Run a command insidedocker exec -it web shOpens a shell in a running container.
See outputdocker logs --tail 100 -f webOnly stdout/stderr of PID 1 is captured.
Live resource usedocker statsCPU, memory, network per container.
Processes insidedocker top webLike ps but from outside.
Copy filesdocker cp web:/etc/nginx/nginx.conf .Works both ways.
What changeddocker diff webA = added, C = changed, D = deleted.
Removedocker rm web · docker rm -f web-f stops it first.
Remove all stoppeddocker container pruneSafe: only stopped ones.
Exit codedocker inspect -f '{{.State.ExitCode}}' web137 = killed (often out of memory). 0 = clean.
TopicWrongRight
Saving workEditing files inside a container and hoping they stay.Container layers vanish on rm. Put data in a volume; put code changes in the Dockerfile.
Getting a shelldocker run -it myimage sh to "look inside the running app" — this makes a new container.docker exec -it <name> sh to enter the one already running.
ShutdownApp ignores SIGTERM; every stop waits 10s then is killed.Handle SIGTERM in the app, and run it as PID 1 (see exec form, Section 4).
Many processesRunning the web server, a cron job, and a DB in one container.One main process per container. Use Compose to link several.
Tip: docker stop waits 10 seconds by default. Change it with docker stop -t 30 web. If your app needs time to flush data, raise it.
Q. A container shows exit code 137. What happened?
Reveal hint
137 = 128 + 9, which means signal 9 (SIGKILL). Either someone ran docker kill, or the kernel OOM-killer shot it for using more memory than its limit. Check docker inspect for OOMKilled: true.

4. Dockerfile — every instruction

InstructionDoesExample
FROMBase image. First real line. scratch = empty.FROM node:20-alpine
WORKDIRSet the folder for later steps (makes it if missing).WORKDIR /app
COPYCopy files from build context into the image.COPY . .
ADDLike COPY, but also unpacks tar files and can fetch URLs.ADD app.tar.gz /opt/
RUNRun a shell command at build time. Makes a new layer.RUN npm ci
ENVSet an env var for build and run time.ENV PORT=3000
ARGA build-time only variable. Passed with --build-arg.ARG VERSION=1.0
EXPOSEDocument a port. Does not publish it.EXPOSE 3000
VOLUMEMark a path as a data mount point.VOLUME /data
USERSwitch to a non-root user for later steps and at run time.USER node
CMDDefault command when the container starts. Can be overridden.CMD ["node","server.js"]
ENTRYPOINTFixed command; CMD becomes its arguments.ENTRYPOINT ["python","app.py"]
HEALTHCHECKA command Docker runs to see if the app is healthy.HEALTHCHECK CMD curl -f http://localhost/ || exit 1
LABELAdd metadata.LABEL org.opencontainers.image.source=…
SHELLChange the shell used by RUN.SHELL ["powershell","-Command"]

A simple, good Dockerfile (Node app)

# syntax=docker/dockerfile:1
FROM node:20-alpine
WORKDIR /app
# copy only the dependency files first -> this layer is cached until they change
COPY package*.json ./
RUN npm ci --omit=dev
# now copy the rest of the code
COPY . .
ENV NODE_ENV=production PORT=3000
EXPOSE 3000
USER node
HEALTHCHECK --interval=30s --timeout=3s CMD wget -qO- http://localhost:3000/health || exit 1
CMD ["node", "server.js"]

CMD vs ENTRYPOINT · shell form vs exec form

FormLooks likeWhat really runsUse when
Exec formCMD ["node","app.js"]node is PID 1. Gets signals directly.Almost always.
Shell formCMD node app.js/bin/sh -c "node app.js". sh is PID 1; your app is a child and may miss SIGTERM.Only if you need shell features like $VAR or pipes.
ENTRYPOINT + CMDENTRYPOINT ["python"] + CMD ["app.py"]python app.py. docker run img other.py → python other.py.Image is "a tool"; user passes arguments.
TopicWrongRight
Layer cacheCOPY . . then RUN npm install — any code change re-installs everything.Copy lock files first, install, then copy code. Rarely-changing steps go on top.
Layer countMany RUN apt-get … lines; cache files left in layers.Chain in one RUN with && and clean up in the same step (rm -rf /var/lib/apt/lists/*).
SecretsENV API_KEY=abc123 or COPY .env . — baked into the image forever.Pass at run time (-e, secret files) or use RUN --mount=type=secret at build.
ADD vs COPYUsing ADD for normal files.Use COPY. ADD only for local tar auto-extract.
Root userNever setting USER; the app runs as root.Make a user and switch to it before CMD.
Build contextSending node_modules, .git, logs to the engine.Add a .dockerignore file. Smaller context = faster builds.
EXPOSEThinking EXPOSE 80 opens the port on the host.It is only a note. You still need -p 80:80.
Cache rule: Docker rebuilds a step when its instruction text changes, or when the files it copies change. Every step after that one is rebuilt too. So order lines from "changes rarely" (top) to "changes often" (bottom).
Q. A Dockerfile has two CMD lines. Which one runs?
Reveal hint
Only the last one. Each CMD (and ENTRYPOINT) replaces the earlier one. Same for HEALTHCHECK.
Q. RUN rm secret.txt after COPY secret.txt . — is the secret gone from the image?
Reveal hint
No. Each step is a layer. The file still lives in the COPY layer; the RUN only hides it in the top layer. Anyone with the image can read it. Never copy secrets in, or use multi-stage builds / build secrets.

5. Multi-stage builds — small, safe images

A multi-stage build uses one stage to compile or install, and a second clean stage that copies only the final files. Build tools, source code, and caches never reach the shipped image.

# ---- stage 1: build (has JDK, Maven, source) ----
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /src
COPY pom.xml .
RUN mvn -q dependency:go-offline
COPY src ./src
RUN mvn -q package -DskipTests

# ---- stage 2: run (only the JRE + the jar) ----
FROM eclipse-temurin:21-jre-alpine
WORKDIR /app
COPY --from=build /src/target/app.jar app.jar
USER 1001
ENTRYPOINT ["java", "-jar", "app.jar"]
TrickCommand / lineWhy
Build only one stagedocker build --target build -t app:dev .Debug the build stage or make a dev image.
Copy from another imageCOPY --from=nginx:alpine /etc/nginx/nginx.conf /tmp/Any image can be a source, not just a stage.
Name every stageFROM … AS depsNumbers (--from=0) break when you add a stage.
Tiny basealpine (~5 MB), distroless (no shell), scratch (nothing)Fewer files = fewer security holes and faster pulls.

BuildKit extras (on by default in modern Docker)

# keep a package cache between builds without putting it in the image
RUN --mount=type=cache,target=/root/.npm npm ci
# read a secret file at build time; it never lands in a layer
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
# build command:
docker build --secret id=npmrc,src=$HOME/.npmrc -t app .
# build for more than one CPU type at once
docker buildx build --platform linux/amd64,linux/arm64 -t user/app:1.0 --push .
Why distroless or alpine? A 1 GB image built on ubuntu with a full JDK can drop to ~80 MB with a JRE on alpine. Smaller image = faster deploys, less to scan, less to attack.
Q. Your final image is still huge after a multi-stage build. Common cause?
Reveal hint
You copied the whole build folder (COPY --from=build /src .) instead of just the output file. Or the final FROM is still a fat image. Copy only what you need, and use a slim/JRE/alpine base.

6. Data — volumes, bind mounts, tmpfs

A container's own file layer is thrown away when the container is removed. To keep data, store it outside the container.

TypeWhere data livesSyntaxUse for
Named volumeDocker-managed folder on the host (/var/lib/docker/volumes/…).-v pgdata:/var/lib/postgresql/dataDatabases, uploads. Best default.
Bind mountAny host folder you pick.-v $(pwd)/src:/app/srcLive code reload in dev; config files.
tmpfsRAM only. Gone on stop.--tmpfs /tmpSecrets, scratch files.
Anonymous volumeDocker-managed, random name.-v /data or VOLUME /data in DockerfileAvoid; hard to track.
 
docker volume create pgdata
docker volume ls
docker volume inspect pgdata                  # shows the real host path (Mountpoint)
docker run -d -v pgdata:/var/lib/postgresql/data postgres:16
# the long, clearer form of -v:
docker run --mount type=bind,source="$(pwd)"/conf,target=/etc/app,readonly app
docker volume rm pgdata                        # fails while a container uses it
docker volume prune                            # remove volumes no container uses
# back up a volume to a tar file on the host
docker run --rm -v pgdata:/data -v "$(pwd)":/backup alpine tar czf /backup/pgdata.tgz -C /data .
TopicWrongRight
Database dataRunning postgres with no volume. docker rm wipes the DB.Always mount a named volume on the data folder.
Bind in prodBind-mounting host code paths on servers.Bind mounts are for dev. In prod, bake code into the image; use volumes for state.
PermissionsFiles written by the container are owned by root on the host.Run as a fixed UID (--user 1000:1000) that matches the host user.
node_modules clashBind-mounting ./app hides the node_modules built in the image.Add an extra volume on /app/node_modules so the image copy wins.
Volume vs bind rule: if Docker should own the data, use a volume. If you need to see and edit the files from the host, use a bind mount.
Q. You mount an empty named volume on /usr/share/nginx/html. Does the image's HTML vanish?
Reveal hint
No. On first use, Docker copies the image's files into the empty named volume. A bind mount of an empty host folder, on the other hand, hides the image content. That difference surprises many people.

7. Networking — how containers talk

DriverWhat it doesUse for
bridge (default)Private network on the host. Containers get their own IP. Reach the outside through NAT.Most single-host setups.
user-defined bridgeSame, but containers can find each other by name (built-in DNS).Linking app + DB on one host. Use this, not the default bridge.
hostNo isolation. Container uses the host's network stack directly.Max speed, or tools that need raw host ports. Linux only.
noneNo network at all.Batch jobs that must be offline.
overlayNetwork across many hosts (Swarm).Multi-host clusters.
macvlanContainer gets a real MAC/IP on the LAN.Rare: legacy apps that need to look like a physical box.
 
docker network create mynet
docker run -d --name db  --network mynet postgres:16
docker run -d --name api --network mynet -p 8080:8080 myapi
# inside 'api', the database is reachable at host name "db" on port 5432
docker network ls
docker network inspect mynet                  # who is connected, IP ranges
docker network connect mynet other            # add a running container
docker port api                               # 8080/tcp -> 0.0.0.0:8080

Port publishing (-p) made clear

FormMeaning
-p 8080:80Host port 8080 → container port 80, on all host interfaces.
-p 127.0.0.1:8080:80Only reachable from the host itself. Safer for admin tools.
-p 80Container port 80 → a random free host port. See it with docker port.
-PPublish every EXPOSEd port to random host ports.
-p 5000:5000/udpUDP instead of TCP.
TopicWrongRight
Finding another containerHard-coding a container IP like 172.17.0.3. It changes on restart.Put both on a user-defined network and use the container name as host name.
Reaching the hostUsing localhost inside a container to hit a service on the host. That is the container itself.Use host.docker.internal (Desktop) or --add-host=host.docker.internal:host-gateway (Linux).
Default bridgeRelying on the old --link flag.--link is legacy. Use a user-defined bridge network.
App bind addressApp listens on 127.0.0.1 inside the container; -p does nothing.Listen on 0.0.0.0 inside the container.
Q. -p 8080:80 is set, but curl localhost:8080 gives "connection reset". The app is running. Why?
Reveal hint
Most often the app inside listens only on 127.0.0.1. Docker forwards to the container's IP, not its loopback. Make the app listen on 0.0.0.0. Also check the port numbers are the right way round (host:container).

8. Docker Compose — many containers, one file

Compose describes a whole app (web + API + DB + cache) in one compose.yaml file and starts it with one command. It makes a network for you, so services find each other by name.

# compose.yaml
services:
  api:
    build: .                          # build from the Dockerfile in this folder
    image: myapi:1.0
    ports: ["8080:8080"]
    environment:
      DATABASE_URL: postgres://app:secret@db:5432/app
    env_file: .env
    depends_on:
      db: { condition: service_healthy }   # wait for the DB health check
    restart: unless-stopped
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: app
      POSTGRES_PASSWORD: secret
    volumes: ["pgdata:/var/lib/postgresql/data"]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      retries: 10
volumes:
  pgdata: {}
CommandDoes
docker compose up -dBuild if needed, create network, start all services in the background.
docker compose up --buildForce a rebuild of images first.
docker compose psStatus of this project's containers.
docker compose logs -f apiFollow one service's output (drop the name for all).
docker compose exec api shShell into a service container.
docker compose stop / startStop or start without removing.
docker compose downStop and remove containers and network. Volumes stay.
docker compose down -vAlso delete named volumes. Data gone.
docker compose pullFetch newer images.
docker compose configPrint the final merged file (checks syntax, shows variable values).
docker compose -f a.yaml -f b.yaml upMerge files: base + override (dev / prod).
docker compose --profile debug upStart only services tagged with that profile too.

Useful service keys

KeyMeaning
build / imageBuild from folder, or use a ready image. Both = build, then tag with that name.
ports vs exposeports publishes to the host. expose is only between services (and only a note).
depends_onStart order. Add condition: service_healthy to also wait for readiness.
networksCustom networks. Default: one network named <project>_default.
deploy.resources.limitsCPU / memory caps.
${VAR:-default}Variables from shell or .env file next to the compose file.
TopicWrongRight
Startup orderdepends_on: [db] and assuming the DB is ready. Only the container is started; Postgres may still be booting.Add a healthcheck on db and condition: service_healthy. Also make the app retry its connection.
Secrets in YAMLReal passwords typed into compose.yaml and committed.Use .env (git-ignored), env_file, or secrets:.
Old commanddocker-compose (v1, Python, with a dash).docker compose (v2 plugin, no dash). v1 is retired.
version keyAdding version: "3.8" at the top.Not needed any more; it is ignored and gives a warning.
Dev trick: keep compose.yaml for the base, and compose.override.yaml (auto-loaded) for dev extras like bind mounts and debug ports. Prod uses -f compose.yaml -f compose.prod.yaml.
Q. After docker compose down, is your database data gone?
Reveal hint
No. down removes containers and the network but keeps named volumes. Only down -v (or docker volume rm) deletes the data.

9. Debugging — when it does not work

SymptomCheckLikely cause
Container exits right awaydocker logs <c>, docker ps -a for exit codeMain process ended (crash, or no long-running command). Exit 1 = app error; 127 = command not found; 137 = killed.
"port is already allocated"netstat -ano | findstr 8080 / lsof -i :8080Another process or container owns the host port. Pick another.
Can't reach the appdocker port <c>, docker exec <c> wget -qO- localhost:PORTApp binds to 127.0.0.1, wrong -p order, or firewall.
"no such file" at buildIs the file inside the build context? In .dockerignore?Files outside the . folder can't be copied.
Changes not showingdocker build --no-cache, or check you re-created the containerCached layer, or an old container still running the old image.
Permission denieddocker exec <c> id, ls -ln on the mountUID inside ≠ owner of the mounted folder.
Slow / OOMdocker stats, docker inspect → OOMKilledNo or too-small memory limit; JVM not seeing container limits (use a modern JDK).
Disk fulldocker system dfOld images, stopped containers, build cache. docker system prune -a.
DNS fails insidedocker exec <c> nslookup dbContainers on different networks, or default bridge (no name lookup).
 
docker inspect -f '{{json .State}}' web | jq       # status, exit code, OOMKilled, PID
docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' web
docker run --rm -it --entrypoint sh myimage     # skip the normal start command, poke around
docker events --since 10m                     # what the engine did lately
docker build --progress=plain --no-cache .     # see every build line, no cache
Image has no shell? (distroless, scratch) Use docker debug (Docker Desktop) or copy a static busybox in via a debug stage. Or run the container with --pid=container:<name> from a tools image to see its processes.
Q. You fixed the Dockerfile and rebuilt, but the running site still shows the old bug. Why?
Reveal hint
Rebuilding the image does not touch running containers. They still run the old image layers. Remove and re-create the container (docker compose up -d does this for you when the image changed).

10. Security — safe by default

TopicWrongRight
UserApp runs as root inside the container (the default).USER appuser in the Dockerfile; or --user 1000:1000 at run.
Privileges--privileged "to make it work".Give only what is needed: --cap-drop ALL --cap-add NET_BIND_SERVICE.
Docker socketMounting /var/run/docker.sock into an app container.That is root on the host. Avoid, or use a socket proxy with limited rights.
SecretsPasswords in ENV, build args, or image layers.Runtime env from a vault, Docker/Compose secrets, or mounted files. Scan images for leaks.
Writable FSContainer can write anywhere.--read-only plus --tmpfs /tmp for scratch space.
Base imageOld, unpinned, bloated base.Pinned slim base; rebuild often; scan with docker scout cves or Trivy.
ResourcesNo CPU or memory limit; one bad container starves the host.--memory 512m --cpus 1 --pids-limit 100.
PortsAdmin ports published on 0.0.0.0.Bind to 127.0.0.1:port or do not publish; reach via the network.
 
docker run -d --name api \
  --user 1000:1000 --read-only --tmpfs /tmp \
  --cap-drop ALL --security-opt no-new-privileges \
  --memory 512m --cpus 1 --pids-limit 200 \
  -p 127.0.0.1:8080:8080 myapi:1.0
docker scout cves myapi:1.0       # list known holes in the image
docker sbom myapi:1.0             # list every package inside
Rootless Docker runs the engine itself as a normal user, so even a container break-out does not land as root on the host. Worth it on shared machines.
Q. Is a container a strong security wall like a VM?
Reveal hint
No. It shares the host kernel. A kernel bug or a misused flag (--privileged, docker.sock mount) can break out. Treat containers as a packaging tool with some isolation, and add the hardening above.

11. Under the hood — how it really works

PieceJob
docker CLISends REST calls to the engine over a Unix socket or TCP.
dockerdThe engine. Handles images, networks, volumes, the API.
containerdRuns and watches containers for dockerd (also used by Kubernetes directly).
runcThe tiny tool that actually creates the Linux process with namespaces and cgroups (OCI runtime).
Namespacespid, net, mnt, uts, ipc, user — each gives the process its own "view".
cgroupsLimit and measure CPU, memory, I/O, process count.
Union file system (overlay2)Stacks read-only image layers plus one writable layer into one tree. Copy-on-write.
OCIOpen standards for image format and runtime, so images work in Docker, Podman, Kubernetes…
Copy-on-write: when a container edits a file from an image layer, the file is first copied to the top writable layer, then changed. The image stays untouched. That is why many containers can share one image cheaply.
Windows / macOS: Docker Desktop runs a small Linux VM (WSL 2 on Windows). Your containers really run inside that VM. This is why bind mounts can be slower there and why host network mode does not work the same.
Q. Does Kubernetes need Docker?
Reveal hint
No. Kubernetes talks to containerd or CRI-O directly. Docker is a great tool to build images; the images are OCI-standard, so any runtime can run them.
