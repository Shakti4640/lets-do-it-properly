0. What is Kubernetes? (the big idea)

Kubernetes (K8s) runs your containers across many machines. You tell it the state you want ("3 copies of my API, always up, reachable on port 80"). It makes that happen and keeps it true: if a container dies, it starts a new one; if a machine dies, it moves the work.

Problem without K8sWhat K8s does
A container crashes at 3 am.Restarts it. Nobody wakes up.
Traffic triples.Adds more copies (scales out), then removes them later.
You have 50 servers. Which one runs what?Picks a machine for each container (scheduling) based on free CPU and RAM.
New version to ship, no downtime allowed.Rolling update: swaps old copies for new ones a few at a time; rolls back if they fail.
Containers need to find each other.Gives each group a stable name and IP (Service) plus built-in DNS.
Passwords and config differ per environment.ConfigMaps and Secrets, mounted as files or env vars.
Mental model: you write a wish list (YAML). A set of loops called controllers watch the real world and keep nudging it until it matches your list. This is "desired state vs actual state". You never say "start a container"; you say "I want 3 of these".
Docker vs Kubernetes: Docker builds and runs one container on one machine. Kubernetes runs many containers on many machines and keeps them healthy. K8s does not need Docker; it uses any OCI runtime (containerd, CRI-O) to run the same images.
Q. You delete a Pod that a Deployment made. What happens?
Reveal hint
A new Pod appears within seconds. The Deployment's controller sees "want 3, have 2" and fixes it. To really remove it, delete or scale down the Deployment, not the Pod.

1. Cluster parts — control plane and nodes

A cluster = a control plane (the brain) + worker nodes (the muscles, where your Pods run).

PartWhereJob (plain words)
kube-apiserverControl planeThe front door. Every command (kubectl, controllers, kubelets) talks to it over REST. Checks who you are and what you may do.
etcdControl planeThe database. Stores every object (Pods, Services, Secrets…) as key-value. Lose etcd = lose the cluster state. Back it up.
kube-schedulerControl planeSees a new Pod with no node, picks the best node (free resources, rules, affinities), writes the choice.
kube-controller-managerControl planeRuns the control loops: ReplicaSet, Deployment, Node, Job, Endpoint controllers…
cloud-controller-managerControl planeTalks to the cloud (make a load balancer, attach a disk).
kubeletEvery nodeThe node agent. Reads which Pods should run here, tells the container runtime to start them, reports health back.
kube-proxyEvery nodeSets up network rules (iptables / IPVS) so Service IPs reach the right Pods.
Container runtimeEvery nodecontainerd or CRI-O. Pulls images and runs containers.
CNI pluginEvery nodeGives Pods IPs and connects them (Calico, Cilium, Flannel, AWS VPC CNI…).
CoreDNSRuns as PodsName lookup inside the cluster: my-svc.my-ns.svc.cluster.local.

What happens when you run kubectl apply -f deploy.yaml

#Step
1kubectl sends the YAML to the API server. It checks auth and admission rules, then saves the Deployment in etcd.
2Deployment controller sees it and makes a ReplicaSet. ReplicaSet controller makes 3 Pod objects (no node yet).
3Scheduler sees Pods with no node, picks a node for each, writes nodeName.
4The kubelet on each chosen node sees "a Pod for me", pulls the image, asks containerd to start it, reports status.
5If a Service matches the Pod labels, the Endpoints update and kube-proxy adds the new Pod IP to its rules.
Local clusters to learn on: minikube, kind (Kubernetes in Docker), k3d, or Docker Desktop's built-in cluster. All run a full control plane on your laptop.
Q. The control plane goes down. Do your running apps stop?
Reveal hint
No. Pods already running keep running — kubelets and kube-proxy on the nodes keep working. But nothing new happens: no rescheduling, no scaling, no kubectl. That is why production uses 3 or 5 control-plane nodes.

2. Objects and YAML — the shape of everything

Every Kubernetes object is a YAML (or JSON) document with the same four top-level parts.

apiVersion: apps/v1          # which API group and version defines this kind
kind: Deployment              # what type of object
metadata:                     # name, namespace, labels, annotations
  name: api
  namespace: shop
  labels: { app: api, tier: backend }
spec:                         # what you WANT (you write this)
  ...
status:                       # what IS (the cluster writes this; never edit it)
  ...
FieldMeaning
apiVersionv1 for core kinds (Pod, Service, ConfigMap). apps/v1 for Deployment, StatefulSet, DaemonSet. batch/v1 for Job, CronJob. networking.k8s.io/v1 for Ingress, NetworkPolicy.
metadata.nameUnique inside its namespace and kind. Lowercase, dashes.
metadata.labelsKey/value tags. Used for selection (Services and Deployments find Pods by labels).
metadata.annotationsKey/value notes for tools (e.g. ingress class settings). Not used for selection.
specDesired state. Different for each kind.
statusObserved state. Read with kubectl get -o yaml or describe.

Namespaces — folders for objects

NamespaceHolds
defaultWhere things go if you give no namespace. Avoid using it for real apps.
kube-systemCluster parts: CoreDNS, kube-proxy, CNI, metrics-server.
kube-publicReadable by everyone; rarely used.
yours (shop, team-a)One per team or app or environment. Quotas and RBAC attach here.
TopicWrongRight
LabelsNo labels, or labels that differ between Deployment and Service by one letter.Use a fixed set: app, version, tier. Copy-paste the same selector block.
NamespacesEverything in default.One namespace per app or team; set kubectl config set-context --current --namespace=shop.
Editing statusWriting fields under status.Never. Only controllers write status.
IndentationTabs in YAML.Two spaces. Run kubectl apply --dry-run=client -f x.yaml to check syntax.
Cluster-wide vs namespaced: Nodes, PersistentVolumes, Namespaces, ClusterRoles, StorageClasses live at cluster level. Pods, Services, Deployments, ConfigMaps, Secrets, PVCs live inside a namespace. kubectl api-resources lists both.
Q. Are labels and annotations the same thing?
Reveal hint
No. Labels are for selecting and grouping (short values, indexed). Annotations are free-form notes for tools and humans (can be long JSON). A Service picks Pods by labels, never by annotations.

3. Pods — the smallest unit

A Pod is one or more containers that share one IP, one network namespace, and can share volumes. Usually a Pod holds one main container. You almost never create Pods by hand; a Deployment does it.

apiVersion: v1
kind: Pod
metadata:
  name: api
  labels: { app: api }
spec:
  containers:
  - name: api
    image: ghcr.io/shop/api:1.4.2
    ports: [{ containerPort: 8080 }]
    env:
    - { name: LOG_LEVEL, value: "info" }
    resources:
      requests: { cpu: "250m", memory: "256Mi" }   # what the scheduler reserves
      limits:   { cpu: "1",    memory: "512Mi" }   # hard cap; over memory = OOMKilled
    readinessProbe:                                # "can I get traffic?"
      httpGet: { path: /ready, port: 8080 }
      periodSeconds: 5
    livenessProbe:                                 # "am I stuck? restart me"
      httpGet: { path: /health, port: 8080 }
      initialDelaySeconds: 10
  restartPolicy: Always

Pod phases and what they mean

Status you seeMeaningUsual fix
PendingNot placed on a node yet, or image still pulling.describe pod: not enough CPU/RAM, no node matches, PVC not bound.
ContainerCreatingNode is setting up volumes, network, pulling image.Wait; if stuck, check volume mounts and secrets exist.
RunningAt least one container is up.—
CrashLoopBackOffContainer keeps dying; K8s waits longer each time before restart.logs --previous. App error, bad command, missing env.
ImagePullBackOff / ErrImagePullCannot fetch the image.Wrong name/tag, private registry with no imagePullSecrets.
OOMKilledUsed more memory than its limit.Raise the limit or fix the leak.
CompletedRan to the end (Jobs).Normal for batch work.
TerminatingBeing shut down; waiting for terminationGracePeriodSeconds (default 30s).If stuck: a finalizer or a process ignoring SIGTERM.

The three probes

ProbeQuestionOn failure
startupProbeHas the app finished booting?Other probes wait. After the limit, container restarts. Use for slow starters (JVM).
readinessProbeCan it serve requests right now?Pod is removed from the Service's endpoints. No restart.
livenessProbeIs it alive, or stuck for good?Container is restarted.

Multi-container patterns

PatternWhat the extra container doesExample
Init containerRuns first, to the end, before the main one starts.Wait for DB, run migrations, fetch config.
SidecarRuns beside the main container for its whole life.Log shipper, service-mesh proxy (Envoy), config reloader.
AmbassadorProxies outbound calls on localhost.Connection pool to a DB.
AdapterReshapes output for the outside.Turn app logs into Prometheus metrics.
TopicWrongRight
Bare Podskind: Pod in production. If the node dies, the Pod is gone for good.Use a Deployment (or StatefulSet / DaemonSet / Job). They re-create Pods.
ResourcesNo requests / limits. The scheduler packs blindly; one Pod can starve the node.Always set requests; set memory limits. Be careful with CPU limits (throttling).
Liveness probeLiveness that calls the database. DB hiccup → every Pod restarts → outage.Liveness checks only the process itself. Readiness can check dependencies.
Tagimage: api:latest. Nodes may run different builds; rollbacks impossible.Pin a version or digest.
Containers per PodApp + DB in one Pod.One app per Pod. Different Pods scale and fail on their own.
CPU units: 1 = one core, 500m = half a core (m = milli). Memory: Mi / Gi are powers of 2 (1 Mi = 1,048,576 bytes); M / G are powers of 10. Mixing them up is a classic slip.
Q. Readiness probe fails on 1 of 3 Pods. Does K8s restart it?
Reveal hint
No. Readiness only pulls the Pod out of the Service so it gets no traffic. When the probe passes again, traffic returns. Only the liveness probe restarts containers.

4. Workloads — Deployment, ReplicaSet, StatefulSet, DaemonSet, Job

KindUse forKey trait
DeploymentStateless apps: web, API, workers.Rolling updates and rollbacks. Manages ReplicaSets, which manage Pods.
ReplicaSet"Keep N identical Pods". You rarely write one directly.Made by Deployments. One per Deployment version.
StatefulSetDatabases, queues, anything with identity and its own disk.Stable names (db-0, db-1), one PVC per Pod, ordered start/stop.
DaemonSetOne Pod on every node.Log agents, monitoring, CNI, node tools.
JobRun to completion once.Retries on failure; completions, parallelism.
CronJobJobs on a schedule.Cron syntax; makes a Job each tick.

A production-shaped Deployment

apiVersion: apps/v1
kind: Deployment
metadata: { name: api, namespace: shop }
spec:
  replicas: 3
  selector:
    matchLabels: { app: api }          # MUST match template.metadata.labels
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 1, maxUnavailable: 0 }   # add 1 new, never drop below 3
  template:                            # the Pod recipe
    metadata:
      labels: { app: api }
    spec:
      containers:
      - name: api
        image: ghcr.io/shop/api:1.4.2
        ports: [{ containerPort: 8080 }]
        resources:
          requests: { cpu: "250m", memory: "256Mi" }
          limits:   { memory: "512Mi" }
        readinessProbe: { httpGet: { path: /ready, port: 8080 } }

Rollouts

kubectl set image deployment/api api=ghcr.io/shop/api:1.5.0   # or edit the YAML and apply
kubectl rollout status deployment/api        # watch the swap
kubectl rollout history deployment/api
kubectl rollout undo deployment/api          # back to the previous ReplicaSet
kubectl rollout undo deployment/api --to-revision=2
kubectl rollout restart deployment/api       # re-create all Pods (e.g. after a ConfigMap change)
kubectl scale deployment/api --replicas=5
StrategyHowWhen
RollingUpdate (default)Replace a few Pods at a time. maxSurge = extra Pods allowed; maxUnavailable = how many may be down.Most apps. Zero downtime if readiness probes are honest.
RecreateKill all old, then start new.App cannot run two versions at once (schema locks, singletons).
Blue/green, canaryNot built in. Done with two Deployments + Service label switch, or tools like Argo Rollouts / Flagger.Safer releases with live traffic tests.
TopicWrongRight
Selector mismatchselector.matchLabels ≠ template.labels. The apply fails, or the Deployment adopts the wrong Pods.Keep them identical. The selector is immutable after creation.
Rolling with no readinessNew Pods counted "ready" the instant they start; users hit half-booted apps.Add a readiness probe. Rolling updates wait for it.
Database as DeploymentPostgres in a Deployment with one shared PVC.StatefulSet with volumeClaimTemplates, or a managed cloud DB.
Config change, no restartEdit ConfigMap and wait. Env vars from it never refresh.rollout restart, or hash the ConfigMap into a Pod annotation so a change triggers a rollout.
How a rollout works: the Deployment makes a new ReplicaSet, scales it up while scaling the old one down. The old ReplicaSet stays at 0 replicas so rollout undo can scale it back. revisionHistoryLimit (default 10) controls how many are kept.
Q. kubectl get rs shows 4 ReplicaSets for one Deployment. Is something broken?
Reveal hint
No. Each past version keeps an empty ReplicaSet (0/0/0) for rollback history. Only one should have running Pods. Lower revisionHistoryLimit if the list bothers you.

5. Services — a stable address for moving Pods

Pods come and go and their IPs change. A Service gives a group of Pods (picked by labels) one fixed name and IP, and spreads traffic across them.

apiVersion: v1
kind: Service
metadata: { name: api, namespace: shop }
spec:
  type: ClusterIP                 # default: reachable only inside the cluster
  selector: { app: api }          # which Pods — must match the Pod labels
  ports:
  - port: 80                      # the Service's own port
    targetPort: 8080              # the container's port
    protocol: TCP
# inside the cluster: http://api.shop.svc.cluster.local  (or just http://api from the same namespace)
TypeReachable fromHowUse for
ClusterIP (default)Inside the cluster onlyVirtual IP + DNS nameService-to-service calls (API → DB).
NodePortOutside, via <any-node-ip>:30000-32767Opens the same port on every nodeDev, demos, bare metal without a load balancer.
LoadBalancerInternetCloud makes a real LB that points at the NodePortsPublic entry point. One LB per Service = costly.
ExternalNameInsideDNS CNAME to an outside hostPoint db at mydb.rds.amazonaws.com.
Headless (clusterIP: None)InsideDNS returns every Pod IP, no load balancingStatefulSets: talk to db-0.db directly.

How traffic flows

PieceRole
Endpoints / EndpointSliceThe live list of ready Pod IPs behind a Service. Updated when Pods pass or fail readiness.
kube-proxyWrites iptables / IPVS rules on each node: "traffic to Service IP:80 → pick one of these Pod IPs:8080".
CoreDNSMaps api.shop.svc.cluster.local → the Service's ClusterIP.
TopicWrongRight
No endpointsService exists but kubectl get endpoints api is empty. Selector does not match Pod labels, or Pods are not Ready.Compare kubectl get pods --show-labels with the selector. Check readiness.
Port mix-upport and targetPort swapped.port = Service side, targetPort = container side. If omitted, targetPort = port.
Public per serviceA LoadBalancer Service for each of 20 microservices.One Ingress (or Gateway) in front; services stay ClusterIP.
Hard-coded IPsApp config with a Pod IP.Always use the Service DNS name.
Debug trick: kubectl run tmp --rm -it --image=busybox -- sh then nslookup api.shop and wget -qO- http://api.shop. If DNS works but the request hangs, look at endpoints and NetworkPolicies.
Q. Two Pods behind one Service. One fails its readiness probe. What does the Service do?
Reveal hint
It drops that Pod from its endpoint list, so all traffic goes to the healthy one. When the probe passes again, the Pod comes back. No restart happens.

6. Ingress and Gateway — HTTP from the outside world

An Ingress is a set of HTTP routing rules (host and path → Service). It does nothing by itself; an Ingress controller (NGINX, Traefik, HAProxy, cloud ALB) reads the rules and does the routing. One public IP can serve many apps.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: shop
  annotations:
    cert-manager.io/cluster-issuer: letsencrypt      # auto TLS certificate
spec:
  ingressClassName: nginx                           # which controller handles this
  tls:
  - { hosts: [shop.example.com], secretName: shop-tls }
  rules:
  - host: shop.example.com
    http:
      paths:
      - { path: /api, pathType: Prefix, backend: { service: { name: api, port: { number: 80 } } } }
      - { path: /,    pathType: Prefix, backend: { service: { name: web, port: { number: 80 } } } }
TermMeaning
pathType: Prefix/api matches /api, /api/users…
pathType: ExactOnly the exact path.
ingressClassNamePicks the controller when more than one is installed.
AnnotationsController-specific extras: rewrites, timeouts, rate limits, sticky sessions.
Gateway APIThe newer, richer replacement: GatewayClass → Gateway → HTTPRoute. Role-split (platform team owns Gateway, app team owns routes), header matching, traffic splits — no annotations needed.
TopicWrongRight
Nothing happensIngress applied but no controller installed. The object just sits there.Install a controller (helm install ingress-nginx …); check kubectl get ingressclass.
404 from controllerHost header does not match rules.host, or backend Service name/port wrong.curl -H "Host: shop.example.com" http://<lb-ip>/api. describe ingress shows the backends and their endpoints.
TLS by handCopying certificates into Secrets every 90 days.cert-manager + Let's Encrypt renews for you.
Q. Ingress vs LoadBalancer Service — when do you need each?
Reveal hint
A LoadBalancer Service exposes one Service on one IP, any protocol (TCP/UDP). An Ingress routes HTTP(S) by host/path to many Services behind one IP, with TLS. In practice: one LoadBalancer Service for the Ingress controller, then Ingress rules for all your apps.

7. Config and Secrets

Keep settings out of the image. A ConfigMap holds plain settings; a Secret holds passwords, tokens, keys. Both can be used as env vars or mounted as files.

apiVersion: v1
kind: ConfigMap
metadata: { name: api-config }
data:
  LOG_LEVEL: "debug"
  app.properties: |                 # a whole file as one key
    server.port=8080
    feature.x=true
---
apiVersion: v1
kind: Secret
metadata: { name: db-secret }
type: Opaque
stringData:                       # plain text here; K8s base64-encodes it for you
  DB_PASSWORD: s3cr3t
---
# using them in a Pod spec
containers:
- name: api
  envFrom:
  - configMapRef: { name: api-config }   # every key becomes an env var
  env:
  - name: DB_PASSWORD
    valueFrom: { secretKeyRef: { name: db-secret, key: DB_PASSWORD } }
  volumeMounts:
  - { name: cfg, mountPath: /etc/app, readOnly: true }
volumes:
- name: cfg
  configMap: { name: api-config }      # /etc/app/app.properties appears as a file
kubectl create configmap api-config --from-literal=LOG_LEVEL=debug --from-file=app.properties
kubectl create secret generic db-secret --from-literal=DB_PASSWORD=s3cr3t
kubectl create secret docker-registry regcred --docker-server=ghcr.io --docker-username=u --docker-password=t
kubectl create secret tls shop-tls --cert=tls.crt --key=tls.key
kubectl get secret db-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d   # read it back
Env var vs file mountEnv varMounted file
Updates when the ConfigMap changes?No. Pod must restart.Yes, within about a minute (not for subPath mounts).
Good forA few simple flags.Whole config files, certificates.
Visible inkubectl describe pod, process list, crash dumps.Only inside the container's file system.
TopicWrongRight
"Secrets are encrypted"Trusting base64. It is encoding, not encryption. Anyone with get secret can read it.Turn on etcd encryption at rest, lock down RBAC on Secrets, or use an external store (Vault, AWS Secrets Manager via External Secrets Operator / CSI driver).
Secrets in gitCommitting Secret YAML with real values.Sealed Secrets, SOPS, or External Secrets — the repo holds only encrypted or reference data.
Env var secretsPasswords as env vars; they leak into logs and describe.Mount as files when the app supports it.
SizeStuffing a 5 MB file into a ConfigMap.Limit is 1 MiB. Use a volume or an image for big files.
Q. You edit a ConfigMap used as env vars. The app still shows old values. Why?
Reveal hint
Env vars are set once at container start. Run kubectl rollout restart deployment/api, or mount the ConfigMap as a file and make the app re-read it.

8. Storage — Volumes, PV, PVC, StorageClass

A container's disk is wiped on restart. For data that must last, a Pod asks for storage with a PersistentVolumeClaim (PVC). The cluster fills the claim with a PersistentVolume (PV) — a real disk — made on demand by a StorageClass.

ObjectWho writes itMeaning
Volume (in a Pod)App teamA folder mounted into containers. Many kinds: emptyDir, configMap, secret, persistentVolumeClaim, hostPath…
PVCApp team"I need 20 Gi, read-write, fast class." Lives in a namespace.
PVCluster / storage driverThe actual disk (EBS, Azure Disk, NFS, Ceph…). Cluster-wide.
StorageClassPlatform teamA recipe: which driver, what disk type, reclaim policy. Enables dynamic provisioning.
CSI driverVendorThe plugin that actually creates, attaches and mounts disks.
 
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: pg-data }
spec:
  accessModes: [ReadWriteOnce]       # one node may mount it read-write
  storageClassName: gp3
  resources: { requests: { storage: 20Gi } }
---
# in the Pod spec
volumes:
- name: data
  persistentVolumeClaim: { claimName: pg-data }
containers:
- name: db
  volumeMounts: [{ name: data, mountPath: /var/lib/postgresql/data }]
Access modeMeaningTypical disk
ReadWriteOnce (RWO)One node, read-write.Block disks (EBS, PD, Azure Disk).
ReadOnlyMany (ROX)Many nodes, read only.Shared file systems.
ReadWriteMany (RWX)Many nodes, read-write.NFS, EFS, Azure Files, CephFS.
ReadWriteOncePodOne Pod only.Strictest.
Reclaim policyWhen the PVC is deleted…
Delete (default for dynamic)The PV and the real disk are deleted. Data gone.
RetainPV stays as Released; disk is kept. Admin cleans up by hand.
TopicWrongRight
hostPath in prodMounting a node folder. The Pod moves to another node and the data "disappears".PVC with a real StorageClass. hostPath is for single-node dev or node agents.
RWO shared by many PodsDeployment with 3 replicas all mounting one RWO PVC → Pods stuck in ContainerCreating (Multi-Attach error).Use RWX storage, or a StatefulSet with one PVC per Pod.
emptyDir for dataKeeping uploads in emptyDir. It lives only as long as the Pod.emptyDir is scratch space only. Use a PVC or object storage (S3).
Pending PVCWaiting forever.describe pvc: wrong StorageClass name, no default class, or WaitForFirstConsumer (binds only when a Pod uses it — normal).
Default StorageClass: kubectl get sc shows one marked (default). A PVC with no storageClassName uses it. No default = PVC stays Pending.
Q. You kubectl delete pvc pg-data. Is the database data gone?
Reveal hint
Depends on the StorageClass's reclaimPolicy. Delete (the common default) removes the disk too. Retain keeps it. Check before you delete, and take snapshots of real data.

Where does a Pod land? (scheduler rules)

ToolSaysExample
Requests"Only nodes with this much free CPU/RAM."requests: { cpu: 500m }

apiVersion: autoscaling/v2

  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource

Staying up during disruption

ObjectDoes
PodDisruptionBudget"At least 2 of my Pods must stay up" during drains and upgrades. minAvailable: 2 or maxUnavailable: 1.
ResourceQuotaCaps total CPU/RAM/objects a namespace may use.

TopicWrongRight

Q. A Pod is Pending with "0/5 nodes are available: 5 Insufficient memory". Nodes have free RAM. Why?
Reveal hint
The scheduler counts requests, not real usage. If other Pods have reserved (requested) the memory, it is "taken" even if idle. Lower over-sized requests, add nodes, or let the Cluster Autoscaler act.

10. Security — RBAC, ServiceAccounts, NetworkPolicy, Pod hardening

Who may do what: RBAC

ObjectMeaning
ServiceAccountAn identity for Pods (apps), not humans. Each namespace has default. Its token is mounted into the Pod.
Role / ClusterRoleA list of allowed verbs on resources. Role = one namespace; ClusterRole = cluster-wide or reusable.
RoleBinding / ClusterRoleBindingGives a Role to a user, group, or ServiceAccount.
 
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata: { name: pod-reader, namespace: shop }
rules:
- apiGroups: [""]                         # "" = core group
  resources: [pods, pods/log]
  verbs: [get, list, watch]
---
kind: RoleBinding
apiVersion: rbac.authorization.k8s.io/v1
metadata: { name: read-pods, namespace: shop }

Network rules: NetworkPolicy

By default every Pod can talk to every Pod. A NetworkPolicy is a firewall at the Pod level. Once any policy selects a Pod, everything not allowed is blocked (for that direction). Needs a CNI that enforces it (Calico, Cilium — not plain Flannel).

apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: db-only-from-api, namespace: shop }
spec:
  podSelector: { matchLabels: { app: db } }     # applies to the DB Pods
  policyTypes: [Ingress]
  ingress:
  - from:
    - podSelector: { matchLabels: { app: api } }
    ports: [{ protocol: TCP, port: 5432 }]

Pod hardening: securityContext

spec:
  serviceAccountName: api
  automountServiceAccountToken: false        # most apps never call the K8s API
  securityContext:
    runAsNonRoot: true
    runAsUser: 10001
    fsGroup: 10001
    seccompProfile: { type: RuntimeDefault }
  containers:
  - name: api
    securityContext:
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true
      capabilities: { drop: [ALL] }

Pod Security Admission: label a namespace pod-security.kubernetes.io/enforce=restricted and the API server rejects Pods that run as root, mount hostPath, add capabilities, and so on. Free, built in, no extra install.
Q. You apply a NetworkPolicy that allows API → DB. Now the DB cannot resolve DNS. Why?
Reveal hint
If the policy has policyTypes: [Egress] (or an egress rule), all egress not listed is blocked — including UDP 53 to CoreDNS. Add an egress rule to kube-system on port 53. Ingress-only policies do not have this problem.

Debug order when a Pod is unhappy

kubectl get pods -o wide                     # 1. status, restarts, node
kubectl describe pod <name>                 # 2. Events at the bottom: pull errors, probe failures, scheduling
kubectl logs <name> --previous              # 3. why did the last run die
kubectl exec -it <name> -- sh                # 4. look around (env, files, curl localhost)
kubectl get endpoints <svc>                 # 5. is the Service actually pointing at Pods?
kubectl get events --sort-by=.lastTimestamp  # 6. anything else going on in the namespace
kubectl debug -it <name> --image=busybox --target=api   # 7. attach a debug container (distroless images)
Imperative vs declarative: kubectl create / run / expose are quick and good for learning. For real systems, write YAML, keep it in git, and use kubectl apply (or a GitOps tool like Argo CD / Flux) so the repo is the source of truth.
Q. kubectl apply says "field is immutable" when you change a Deployment's selector. How do you fix it?
Reveal hint
Selectors cannot change after creation. Delete and re-create the Deployment (kubectl delete deploy api then apply), or keep the old selector. Plan labels up front.

The 6 rules to remember: 1) Deployments, not bare Pods; 2) labels must match selectors; 3) set requests and limits; 4) readiness probes make rollouts safe; 5) Secrets are not encrypted by default; 6) YAML in git, apply from git.
Q. Helm or Kustomize?
Reveal hint
Both, often. Helm for software you install (charts others wrote). Kustomize for YAML you own and want to keep simple per environment. Many teams render a Helm chart and then patch it with Kustomize.
