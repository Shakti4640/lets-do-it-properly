0. The pyramid as a time and trust budget

LayerWhat it checksSpeed per testShare of testsWhen it runsJava tools
UnitOne class or function, collaborators faked. Logic, edge cases, calculations.ms~70%Every PR, every local buildJUnit 5, AssertJ, Mockito
Slice / componentOne layer with Spring wiring: controller + JSON + validation; repository + real DB.100 ms–2 s (context start, cached)~15%Every PR@WebMvcTest, @DataJpaTest, @JsonTest, Testcontainers
IntegrationThe whole service with real dependencies (DB, Kafka, Redis) in containers; HTTP in, effects out.1–10 s~10%Every PR (fast subset) + main@SpringBootTest + Testcontainers, WireMock for third parties

Why the shape mattersConsequence
Feedback timeA 2-minute PR suite gets run before every push; a 40-minute one gets skipped and batched.
Precision of failureA unit test names the broken class; an e2e test says "checkout failed somewhere".
FlakinessEach network hop, clock, and container is a new way to fail randomly. Push logic down the pyramid.
CostE2E needs an environment per run; unit tests need a JVM.
TrustTests that are fast and deterministic get fixed when red; slow flaky ones get re-run and ignored.
 
# what a healthy Spring service repo looks like in numbers (rough)
src/test/java …   800 unit tests          ~20 s
                   120 slice tests          ~40 s   (3–4 cached Spring contexts)
                    40 integration tests    ~90 s   (Testcontainers: Postgres + Kafka + Redis started once)
                     6 consumer contracts   ~5 s
                     8 e2e journeys          ~4 min  (against the preview environment, separate job)
PR gate: unit + slice + integration + contracts ≈ 3 min on a 4-core runner (with Gradle/Maven caches)
Mental model: the pyramid is a budget, not a rule. You have ~5 minutes of PR time and ~1 hour of nightly time to spend. Buy as much confidence as you can per second: unit tests are cheap bulk, e2e tests are expensive luxuries you keep to a few.
Q. The team has 900 tests and they all go through @SpringBootTest. The suite takes 25 minutes. What is the actual problem?
Reveal hint
Everything is an integration test. Most of those 900 are testing logic that needs no Spring context at all. Move them to plain JUnit (ms each), keep a few dozen true integration tests, and make the remaining @SpringBootTests share one context (same config → cached). 25 min becomes 3.

1. Unit tests that are worth running

// pure logic, no Spring, no I/O — the bulk of the suite
class CouponEngineTest {
    private final Clock clock = Clock.fixed(Instant.parse("2026-10-25T10:00:00Z"), ZoneOffset.UTC);   // inject time
    private final CouponEngine engine = new CouponEngine(clock);

    @Test
    void percentageCouponAppliesAfterTax() {
        var cart = Cart.of(line("A1", 2, "199.50"), line("B7", 1, "100.00"));
        var total = engine.total(cart, Coupon.percent(10));
        assertThat(total.amount()).isEqualByComparingTo("449.10");     // AssertJ: readable failure messages
    }

    @ParameterizedTest(name = "{0} → {1}")
    @CsvSource({ "0, 499.00", "10, 449.10", "100, 0.00" })
    void percentTable(int pct, String expected) { … }

    @Test
    void expiredCouponIsRejected() {
        assertThatThrownBy(() -> engine.total(cart, Coupon.expiredAt("2026-10-24T00:00:00Z")))
            .isInstanceOf(CouponExpiredException.class)
            .hasMessageContaining("expired");
    }
}

// collaborator boundary: mock what you don't own, keep the thing under test real
@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
    @Mock OrderRepository repo;
    @Mock PaymentClient payments;
    @InjectMocks OrderService service;

    @Test
    void paymentFailureLeavesOrderPending() {
        when(payments.charge(any())).thenThrow(new PaymentDeclined());
        assertThatThrownBy(() -> service.place(cmd)).isInstanceOf(PaymentDeclined.class);
        verify(repo).save(argThat(o -> o.status() == OrderStatus.PENDING));
        verifyNoMoreInteractions(payments);
    }
}
RuleWhy
One behaviour per test; name it as a sentenceA red test tells you what broke without reading the body.
Arrange–Act–Assert, no logic in testsTests with if/loops have bugs too.
Inject Clock, random, and IDsDeterministic; no Thread.sleep, no LocalDate.now().
Mock at the boundary you own (ports), not inside the domainMocking every class means tests re-state the implementation and break on refactor.
Test behaviour, not getters/setters/LombokCoverage theatre.
Builders / fixtures for test dataanOrder().withStatus(PAID).build() keeps tests readable and resilient to constructor changes.
Property-based tests for pure functionsjqwik generates thousands of inputs: money rounding, parsers, serializers.
ArchUnit for structure"Controllers must not depend on repositories", "no cycles between packages" — enforced in a test.
TopicWrongRight
Spring in unit tests@SpringBootTest to test a price calculation.Plain class, new it, 2 ms.
Over-mockingMocks returning mocks; verify on every internal call.Mock external systems; assert outcomes (returned value, state saved, message published).
Time bombsTest asserts "expires in 30 days" using LocalDate.now(); fails on month ends and leap years.Fixed Clock.
Shared mutable fixturesStatic list mutated by tests; order-dependent failures.Fresh fixtures per test (@BeforeEach), or immutable constants.
Asserting with assertTrue(a.equals(b))Failure says "expected true".AssertJ assertThat(a).isEqualTo(b) → prints both values.
Catching exceptions to failtry { … } catch (Exception e) { fail(); }assertThatThrownBy / assertThrows.
Q. A test passes with the real implementation and still passes when you delete the method body. What is it worth?
Reveal hint
Nothing — it asserts nothing meaningful (or only mock interactions). This is exactly what mutation testing (PIT) finds: it mutates the code and reports tests that stay green. Fix the assertion or delete the test; it is costing CI time for no information.

2. Integration tests with Testcontainers — real dependencies, fast enough

// one shared set of containers for the whole suite (reused across test classes in the same JVM)
public abstract class IntegrationTestBase {
    static final PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine").withReuse(true);
    static final KafkaContainer kafka = new KafkaContainer(DockerImageName.parse("apache/kafka-native:3.9.0")).withReuse(true);
    static final GenericContainer<?> redis = new GenericContainer<>("redis:7-alpine").withExposedPorts(6379).withReuse(true);

    static { Startables.deepStart(postgres, kafka, redis).join(); }        // start in parallel, once per JVM

    @DynamicPropertySource
    static void props(DynamicPropertyRegistry r) {
        r.add("spring.datasource.url", postgres::getJdbcUrl);
        r.add("spring.datasource.username", postgres::getUsername);
        r.add("spring.datasource.password", postgres::getPassword);
        r.add("spring.kafka.bootstrap-servers", kafka::getBootstrapServers);
        r.add("spring.data.redis.host", redis::getHost);
        r.add("spring.data.redis.port", () -> redis.getMappedPort(6379));
    }
}
// Boot 3.1+: @ServiceConnection on the container field replaces the DynamicPropertySource for supported types

@SpringBootTest(webEnvironment = RANDOM_PORT)
@ActiveProfiles("test")
class OrderFlowIT extends IntegrationTestBase {
    @Autowired TestRestTemplate http;        // or RestClient / WebTestClient
    @Autowired OrderRepository orders;
    static WireMockServer payments = new WireMockServer(options().dynamicPort());   // fake the third party

    @Test
    void placingAnOrderStoresItAndPublishesEvent() {
        payments.stubFor(post("/charge").willReturn(okJson("{\"status\":\"APPROVED\"}")));

        var resp = http.postForEntity("/api/orders", newOrderRequest(), OrderDto.class);

        assertThat(resp.getStatusCode()).isEqualTo(HttpStatus.CREATED);
        assertThat(orders.findById(resp.getBody().id())).isPresent();
        try (var consumer = testConsumer(kafka, "orders")) {                   // assert the side effect
            var records = KafkaTestUtils.getRecords(consumer, Duration.ofSeconds(10));
            assertThat(records).extracting(r -> r.key()).contains(resp.getBody().customerId());
        }
        payments.verify(postRequestedFor(urlEqualTo("/charge")));
    }
}
TechniqueWhy
Singleton containers (static + base class, or JUnit extension)Start Postgres once (3 s), not per class (3 s × 40).
Context cachingSpring caches the ApplicationContext per unique config. Keep @MockitoBean sets and profiles identical across integration tests → one context.
Reuse (withReuse(true) + testcontainers.reuse.enable=true in ~/.testcontainers.properties)Locally, containers survive between runs (seconds saved per run). Off in CI (fresh runner anyway).
Isolation per test@Transactional rollback for repository tests; for HTTP tests (separate thread, no rollback) truncate tables in @BeforeEach or use unique data per test.
Same DB engine as prodPostgres 16 image, not H2. Flyway runs the real migrations against it — free migration testing.
WireMock / MockServer for third partiesDeterministic, offline, can simulate timeouts and 500s.
Awaitility for asyncawait().atMost(10, SECONDS).untilAsserted(() -> …) — never Thread.sleep.
LocalStack for AWSS3/SQS/SNS/Secrets Manager in a container.
Failsafe + *IT naming (Maven) / separate integrationTest source set (Gradle)Unit and integration tests run and report separately; mvn test stays fast.
TopicWrongRight
H2 in testsPasses on H2, fails on Postgres (JSONB, ON CONFLICT, window functions).Testcontainers with the production engine and version.
Container per test class40 classes × 3 s Postgres start = 2 minutes wasted.Static singleton containers.
New context per classEach class has its own @MockitoBean → 40 contexts × 8 s.Standardise test configuration; group by context; check the log line "Spring test ApplicationContext cache statistics".
Thread.sleep(5000) for KafkaSlow and still flaky.Awaitility with a sensible timeout.
Calling the real third-party sandboxNetwork, rate limits, their downtime = your red build.WireMock; contract tests for the shape.
Tests depend on orderTest B assumes A created the customer.Each test creates what it needs; random order (junit.jupiter.testmethod.order.default = random) to expose coupling.
Docker not available in CI"Could not find a valid Docker environment".Hosted runners have Docker; in a container: job or K8s runner use Testcontainers Cloud, a DinD sidecar, or run those tests on a VM runner.
Q. @SpringBootTest with @Transactional on the test: the HTTP call hits the controller but the repository assertion finds no row. Why?
Reveal hint
The HTTP request is served on a different thread with its own transaction; your test's transaction (which you were hoping would roll back) is separate and sees nothing uncommitted — and the controller's commit is real, so rollback does not clean it. For HTTP-level tests drop @Transactional and clean the DB explicitly.

3. Contract tests — Pact and Spring Cloud Contract

Service A (consumer) calls service B (provider). An e2e test needs both deployed. A contract test splits that: the consumer writes down what it expects (the contract), tests itself against a stub generated from it, and the provider replays the same contract against its real code in its CI. Both sides verify independently; a broker tracks which versions are compatible.

// CONSUMER side (orders-service calls payments-service) — Pact JVM, JUnit 5
@ExtendWith(PactConsumerTestExt.class)
@PactTestFor(providerName = "payments-service")
class PaymentsClientPactTest {

    @Pact(consumer = "orders-service")
    V4Pact chargeApproved(PactDslWithProvider builder) {
        return builder
            .given("customer 42 has a valid card")                    // provider state
            .uponReceiving("a charge request")
                .path("/charges").method("POST")
                .body(newJsonBody(b -> { b.stringType("customerId", "42"); b.decimalType("amount", 499.00); }).build())
            .willRespondWith()
                .status(201)
                .body(newJsonBody(b -> { b.stringType("status", "APPROVED"); b.uuid("chargeId"); }).build())   // types, not exact values
            .toPact(V4Pact.class);
    }

    @Test
    @PactTestFor(pactMethod = "chargeApproved")
    void clientParsesApprovedCharge(MockServer server) {
        var client = new PaymentsClient(RestClient.create(server.getUrl()));
        var result = client.charge("42", new BigDecimal("499.00"));
        assertThat(result.status()).isEqualTo(ChargeStatus.APPROVED);     // test passes → pact file written to target/pacts
    }
}
// CI: ./mvnw test pact:publish  → Pact Broker (or PactFlow) with consumer version = git sha, branch = main

// PROVIDER side (payments-service) — verify every consumer's pact against the real app
@Provider("payments-service")
@PactBroker(url = "${PACT_BROKER_URL}", consumerVersionSelectors = { @VersionSelector(mainBranch = true), @VersionSelector(deployedOrReleased = true) })
@SpringBootTest(webEnvironment = RANDOM_PORT)
class PaymentsProviderPactTest {
    @LocalServerPort int port;
    @MockitoBean CardGateway gateway;                  // fake the provider's own downstream

    @BeforeEach void target(PactVerificationContext ctx) { ctx.setTarget(new HttpTestTarget("localhost", port)); }

    @TestTemplate @ExtendWith(PactVerificationSpringProvider.class)
    void verify(PactVerificationContext ctx) { ctx.verifyInteraction(); }

    @State("customer 42 has a valid card")
    void validCard() { when(gateway.authorize(any())).thenReturn(Authorization.approved()); }
}
// CI gate before deploying either side:  pact-broker can-i-deploy --pacticipant payments-service --version $SHA --to-environment production
ConceptMeaning
Consumer-drivenThe consumer states only the fields it uses → the provider can change everything else freely.
Matchers"a string", "a UUID", "a number ≥ 0" — not literal values. Literal contracts break on every data change.
Provider states"given customer 42 exists": the provider sets up that state (mock or seed) before replay.
Pact Broker / PactFlowStores pacts and verification results per version; can-i-deploy answers "is this version compatible with what is in prod?".
WebhooksNew pact published → trigger the provider's verification build. Breakage found in minutes, in the right repo.
Spring Cloud ContractProvider-driven alternative: contracts in Groovy/YAML in the provider repo; generates provider tests + consumer stubs (stub runner). Good when one team owns both sides.
Messaging contractsPact and SCC both support async messages (Kafka events): consumer states the event shape it needs.
OpenAPI as a contractLighter option: validate provider responses against the spec (openapi-validator, Schemathesis) and generate consumer clients. Catches shape drift, not consumer needs.
TopicWrongRight
Exact-value contracts"chargeId": "a1b2…" literal → provider's random UUID fails verification.Type/regex matchers.
Contract = full API testConsumer asserts 40 fields it never reads.Only what the consumer uses; that is the point.
Pacts in git, no brokerVersions and environments impossible to track; can-i-deploy unavailable.Broker (self-hosted docker image) or PactFlow.
Provider verifies only main pactsA consumer's feature branch publishes a pact; provider never sees it until merge.Version selectors: main branch + deployed/released + matching branch name.
Business logic in provider statesState setup calls the real DB and payment gateway.Mock the provider's downstreams in the verification test; states only set up data.
Q. Contract tests pass on both sides. Can you skip integration tests between the two services?
Reveal hint
You can skip the deployed-together integration test for API shape — that is what contracts replace. They do not test network config, auth between services, timeouts, or whether the provider's DB has the data. Keep a thin e2e smoke journey for those; let contracts carry the field-level detail.

4. End-to-end tests — few, stable, against a real environment

DecisionGuidance
How many5–15 critical journeys (sign up, search, add to cart, pay, see order). Everything else lives lower in the pyramid.
Where they runAgainst an ephemeral preview environment per PR (best), or staging after deploy. Never against prod except read-only smoke/synthetics.
Who owns themThe team that owns the journey; e2e in a separate "QA repo" rots.
ToolsAPI: REST Assured, Karate, Playwright's APIRequest. UI: Playwright (auto-wait, traces, parallel), Selenium if you must.
DataEach run seeds its own data via API/SQL and cleans up; or a fresh DB per preview env. Never depend on "the test user from last year".
StabilityAuto-waiting selectors (getByRole), retries at the step level, no fixed sleeps, isolated test accounts.
ArtifactsPlaywright trace + video + HAR on failure uploaded as CI artifacts; otherwise debugging is guesswork.
Smoke after deploy3–5 of those journeys run in the deploy pipeline right after rollout; failure triggers rollback.
 
// REST Assured journey against the preview env (BASE_URL from CI)
@Tag("e2e")
class CheckoutJourneyE2E {
    static final String BASE = System.getenv().getOrDefault("BASE_URL", "http://localhost:8080");
    static String token;

    @BeforeAll static void login() { token = given().baseUri(BASE).body(testUser()).post("/auth/login").then().statusCode(200).extract().path("token"); }

    @Test
    void addToCartAndPay() {
        String cartId = given().baseUri(BASE).auth().oauth2(token)
            .body("""{"sku":"E2E-SKU-1","qty":1}""").contentType(JSON)
            .post("/api/cart/items").then().statusCode(201).extract().path("cartId");

        given().baseUri(BASE).auth().oauth2(token)
            .post("/api/cart/{id}/checkout", cartId).then()
            .statusCode(201)
            .body("status", equalTo("PAID"))
            .time(lessThan(2000L));                                      // a crude latency guard
    }
}

Q. An e2e test fails only in CI, never locally. Top three causes?
Reveal hint
(1) Timing — CI is slower; a hidden fixed wait or a race the auto-wait doesn't cover. (2) Data — CI env lacks the record your local DB has, or a parallel run changed it. (3) Environment — different base URL/feature flag/time zone/locale, or a dependency (payments sandbox) unreachable from the runner. Grab the trace first; guess second.

5. Flaky tests — detect, quarantine, fix

CauseSymptomFix
Timing / asyncPasses with a sleep, fails under load.Awaitility / Playwright auto-wait; assert on the condition, not on elapsed time.
Order dependence / shared stateFails only when run with another test or in parallel.Fresh state per test; random method order to surface it; no static mutable fields.
Time & localeFails on the 31st, at midnight UTC, on a CI runner in another TZ, or because String.format used a comma decimal.Injected Clock; -Duser.timezone=UTC -Duser.language=en in Surefire/Gradle; explicit Locale in formatting.
Ports and files"Address already in use"; temp files colliding.Random ports (RANDOM_PORT, Testcontainers mapped ports); @TempDir.
RandomnessFails 1 in 50 with a different generated value.Seeded random; print the seed on failure (jqwik does).
Resource limitsOOM / timeouts on small runners; container start timeouts.Right-size the runner; -Xmx for forks; longer container startup timeouts; fewer parallel forks.
NetworkDocker Hub rate limit; third-party sandbox down.Registry mirror/login; WireMock instead of sandboxes.
Hash/iteration orderAsserting on HashMap/Set order.Order-insensitive assertions (containsExactlyInAnyOrder).

ProcessWhy
Track flake rate per test (CI test reports, Develocity, BuildPulse, Datadog CI)You can't fix what you don't measure; 1% flaky × 1,000 tests = a red build every run.
Quarantine within a day, fix within a sprint, delete if nobody owns itA quarantined test is a known gap; an ignored red test is noise that hides real failures.
Retries report, never hide"Passed on retry" must be visible — it is a bug with a 50% detection rate.
Flakiness budgetTreat suite reliability like an SLO (e.g. < 0.5% of runs fail for non-code reasons).
TopicWrongRight
"Re-run until green"The team's muscle memory is the re-run button; a real regression gets re-run 3 times too.Automatic retry with reporting; flaky tests quarantined and tracked.
Deleting flaky testsThe behaviour is now untested.Quarantine with a ticket; fix the root cause (usually async or shared state).
Bigger sleepsThread.sleep(5000) → 10000; suite slower, still flaky under load.Condition-based waiting with a generous timeout: fast when ready, tolerant when slow.
Running flaky tests in the PR gateEvery PR has a 20% chance of a false red.Exclude the flaky tag from the gate; run it separately and visibly.
Q. A test fails 1 in 30 runs with expected [PAID] but was [PENDING]. It reads the order right after posting it. What is it?
Reveal hint
Asynchrony: payment is confirmed via a Kafka/SQS consumer after the HTTP response. The test races the consumer. Use Awaitility to wait for PAID (up to N seconds), and consider asserting the event rather than the eventual state if that is the actual contract.

Q. You enabled JUnit parallel execution and the suite got slower. How?
Reveal hint

Q. TRUNCATE between tests is fast, but a repository test using @Transactional rollback is faster still. Why not use rollback everywhere?
Reveal hint
Rollback only works when the test and the code under test share one transaction/thread. HTTP-level tests, async listeners, REQUIRES_NEW paths, and anything that commits (outbox pollers) escape it. Use rollback for @DataJpaTest-style tests, truncate for full-stack ones.

// Gatling (Java DSL, runs as a Maven/Gradle plugin or standalone)
public class CheckoutSimulation extends Simulation {
    HttpProtocolBuilder http = http.baseUrl(System.getProperty("baseUrl", "https://staging.shop.example"))
        .acceptHeader("application/json").userAgentHeader("gatling");

    ScenarioBuilder browseAndBuy = scenario("browse and buy")
        .feed(csv("skus.csv").circular())
        .exec(http("search").get("/api/products?q=#{sku}").check(status().is(200)))
        .pause(Duration.ofSeconds(1), Duration.ofSeconds(3))
        .exec(http("add").post("/api/cart/items").body(StringBody("{\"sku\":\"#{sku}\",\"qty\":1}")).asJson()
            .check(status().is(201), jsonPath("$.cartId").saveAs("cartId")))
        .exec(http("checkout").post("/api/cart/#{cartId}/checkout").check(status().is(201)));

    {
        setUp(browseAndBuy.injectOpen(
                rampUsersPerSec(1).to(50).during(Duration.ofMinutes(2)),     // ramp
                constantUsersPerSec(50).during(Duration.ofMinutes(5))))      // steady state
            .protocols(http)
            .assertions(                                                       // the gate: fail the build if violated
                global().responseTime().percentile(99.0).lt(500),
                global().failedRequests().percent().lt(1.0),
                details("checkout").responseTime().percentile(95.0).lt(800));
    }
}

Q. At 50 rps p99 is 300 ms; at 60 rps it jumps to 5 s and never recovers. What kind of limit is that, and what metric confirms it?
Reveal hint
A saturated fixed-size resource: the DB connection pool (Hikari pending > 0, acquire time rising), Tomcat threads, or CPU throttling. Requests queue, latency explodes, and with an open-model load the queue only grows. The fix is capacity or backpressure (timeouts, bulkheads, rate limits), not a bigger timeout.

Checklist for a CI-ready test suite
Unit tests need no Spring, no Docker, no network; run in parallel; < 1 minute total.
Slice and integration tests share Spring contexts and singleton Testcontainers; real DB engine; Flyway migrations run in tests.
Third parties stubbed with WireMock; AWS with LocalStack; time with Clock.
Unit (*Test, Surefire) and integration (*IT, Failsafe) separated; JUnit XML uploaded and summarised on the PR.
Contracts published to a broker; can-i-deploy before deploy.
E2E: a dozen journeys, against an ephemeral env, traces on failure, not blocking drafts.
Flaky tests retried with reporting, quarantined by tag, tracked with owners.
Coverage merged (unit + IT), gated on new code and per-package branch floors; PIT on core modules.
Perf tests nightly with SLO thresholds from a dedicated runner against a sized environment; results trended.

The 7 rules to remember: 1) the pyramid is a time budget — logic in unit tests, wiring in slices, a few real-dependency integration tests, a handful of e2e journeys; 2) real engines via Testcontainers, singleton containers, shared Spring contexts; 3) contracts (Pact) replace deployed-together API tests; can-i-deploy gates releases; 4) no sleeps, no now(), no shared state — Awaitility, Clock, fresh data; 5) flaky tests are bugs: retry with reporting, quarantine with an owner, fix within a sprint; 6) parallelise and shard for wall time, cache for repeat runs, merge reports into one check; 7) gate coverage on new code, measure mutation score where it matters, run perf tests nightly against SLO thresholds.
Q. Interviewer: "Your PR pipeline takes 25 minutes. What do you do first?"
Reveal hint
Measure, don't guess: pull the per-test timings and context/container start counts from the last run. Nine times out of ten the answer is "60 Spring contexts and 40 Postgres starts" → unify test configuration and use singleton containers (25 → 8 min), then move @SpringBootTest logic tests to plain JUnit, then shard what's left across jobs. Only after that look at caching and test selection.
