0. Deploy ≠ release — the vocabulary that makes everything else make sense

WordPlain meaning
BuildTurn a commit into an immutable artifact (image by digest). Happens once.
DeployPut the artifact onto infrastructure so it can serve. A technical act.
ReleaseExpose the new behaviour to users. A business act. With flags, release ≠ deploy.
PromoteMove the same artifact to the next environment (dev → staging → prod). Never rebuild.
RolloutThe process of shifting traffic from old to new (rolling, blue/green, canary).
Rollback vs roll forwardReturn to the previous artifact vs ship a fix on top. Rollback must be a button, not a project.
EnvironmentA complete, isolated copy of the system (its own DB, queues, config). Ephemeral preview environments per PR are the modern dev tier.
Progressive deliveryRolling out to a growing slice of users while measuring, with automatic abort.
GitOpsThe desired state of each environment lives in git; an agent in the cluster makes reality match. Deploy = merge.
Change failure rate / MTTR / lead time / deploy frequencyThe four DORA metrics. Elite: multiple deploys a day, < 1 hour to restore, < 5% changes fail.
 
# the pipeline shape every section below plugs into
commit → CI: build + test → image ghcr.io/shop/api@sha256:… → (scan, sign) → write digest to the GitOps repo (dev)
      → Argo CD syncs dev → smoke tests → PR promotes digest to staging → e2e → PR promotes digest to prod
      → Argo Rollouts canary 5% → 25% → 50% → 100% with metric analysis; abort = automatic rollback
      → feature flag turned on for 1% of users → 100%     ← the *release*
Mental model: deploying is putting the new car in the garage; releasing is handing the keys to drivers. Progressive delivery hands keys to a few drivers first and watches the dashboard. Feature flags are a switch on the dashboard that works even after everyone has the keys.
Q. Why should the production artifact never be rebuilt from the same commit for production?
Reveal hint
Two builds are not guaranteed identical: a snapshot dependency moved, a base image tag changed, a plugin version drifted. Only the exact bytes that passed staging have been tested. Promote the digest; tags are labels, digests are facts.

# Kubernetes rolling update knobs (Deployment)
spec:
  replicas: 6
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 25%, maxUnavailable: 0 }      # never below 6 ready; up to 8 during rollout
  minReadySeconds: 15                                      # a pod must stay Ready 15 s before counting (catches crash-after-start)
  progressDeadlineSeconds: 600                             # mark the rollout failed after 10 min (alert on it)

    terminationGracePeriodSeconds: 40                      # ≥ Spring graceful timeout + preStop

Q. A rolling update of a 6-replica Deployment with maxSurge: 1, maxUnavailable: 1. How many pods serve traffic at the lowest point?
Reveal hint
5. maxUnavailable: 1 allows one fewer than desired. At peak you have 7 (6 + surge 1). For latency-sensitive services set maxUnavailable: 0 so capacity never dips; you pay with a slightly slower rollout.

// OpenFeature (vendor-neutral API) + a provider (LaunchDarkly, Unleash, Flagsmith, flagd, Split, ConfigCat…)
// pom: dev.openfeature:sdk + a provider; Spring: dev.openfeature.contrib:spring-boot-starter
@Service
class CheckoutService {
    private final Client flags;        // OpenFeatureAPI.getInstance().getClient()

    Total total(Cart cart, User user) {
        var ctx = new ImmutableContext(user.id(), Map.of("tenant", new Value(user.tenant()), "plan", new Value(user.plan())));
        if (flags.getBooleanValue("checkout.new-coupon-engine", false, ctx)) {   // default = OFF when the flag service is unreachable
            return newEngine.total(cart);
        }
        return legacyEngine.total(cart);
    }
}

Flags + canary are complementary: canary tests the deploy (new binary, same behaviour); flags test the feature (same binary, new behaviour). Use both: ship dark via canary, then release via flag.
Q. You roll a feature to 5% of users by flag. A user complains the page changes between refreshes. What is missing?
Reveal hint
Stickiness. Percentage rollouts must hash a stable key (user id, not request id or random) so the same user always lands in the same bucket. Every flag SDK does this if you pass a stable targeting key.

3. Database changes without downtime — expand / migrate / contract

During any rollout two app versions run at once, and a rollback may put the old version on the new schema. So every schema change must be split so that each step is compatible with both the version before it and after it.

PhaseSchemaApp releaseRollback-safe?
1. ExpandAdd the new column/table/index (nullable, no default that rewrites the table, index CONCURRENTLY). Old column stays.v1 still running; ignores the new column.Yes — nothing depends on it yet.
2. Dual-write—v2 writes both old and new columns; reads old (or new with fallback).Yes — v1 keeps working on the old column; v2 → v1 rollback loses nothing.
3. BackfillBatched job copies old → new for existing rows (10k rows per txn, sleep between).v2.Yes.
4. Switch readsAdd NOT NULL / constraints now that data is complete (NOT VALID → VALIDATE).v3 reads new, still writes both.Yes — v2 reads old which is still written.
5. ContractDrop the old column (after v3 has been stable for a release cycle).v4 stops writing old.Only to v3; that is fine — v2 is long gone.
 
-- example: split customers.full_name into first_name + last_name (Flyway, one migration per deploy)
-- V21__expand_names.sql   (ships with v2 = dual-write)
ALTER TABLE customers ADD COLUMN first_name text, ADD COLUMN last_name text;      -- nullable, instant

-- backfill job (NOT a Flyway migration; a batched script or a Spring @Scheduled one-off)
UPDATE customers SET first_name = split_part(full_name,' ',1), last_name = substr(full_name, length(split_part(full_name,' ',1))+2)
WHERE id IN (SELECT id FROM customers WHERE first_name IS NULL LIMIT 10000);   -- loop until 0 rows

-- V22__names_not_null.sql   (ships with v3 = read new)
ALTER TABLE customers ADD CONSTRAINT first_name_nn CHECK (first_name IS NOT NULL) NOT VALID;
ALTER TABLE customers VALIDATE CONSTRAINT first_name_nn;                           -- weak lock, scans once

-- V23__contract_names.sql   (ships with v4, one release later)
ALTER TABLE customers DROP COLUMN full_name;
ChangeSafe form
Add columnNullable, or constant default (PG 11+). Never a volatile default (now()) — full rewrite.
Rename columnNever rename in place. Add new → dual-write → backfill → switch → drop old.
Change typeSame as rename (new column), or ALTER … TYPE only for binary-compatible changes (varchar(50) → text).
Add indexCREATE INDEX CONCURRENTLY, outside a transaction (Flyway: executeInTransaction=false).
Add NOT NULL / FK / CHECKNOT VALID then VALIDATE; FK columns indexed first.
Drop column/tableOnly after no deployed version references it (contract phase); keep a backup/snapshot.
Large data fixBatched job outside the migration tool; idempotent; resumable; throttled.
Where migrations runAt app start (Flyway in Boot — fine with maxUnavailable: 0, since v1 pods keep serving while v2's first pod migrates), or as a pre-deploy Job/init container (clearer, one runner). Set lock_timeout.
TopicWrongRight
Schema and code in one stepRename column + deploy code that uses the new name. Old pods crash during rollout; rollback impossible.Expand/contract across ≥ 2 releases.
"Down" migrations as the rollback planFlyway undo that drops the column — with the data in it.Forward-only migrations; rollback = redeploy the previous app version, which works because the schema is compatible.
Hibernate ddl-auto=updateSchema changes you did not review, in prod, at pod start, by N pods at once.Flyway/Liquibase with reviewed SQL; ddl-auto=validate.
Migration holds a lock at peakALTER TABLE waits behind a long transaction; every query queues; outage.SET lock_timeout='5s' in the migration; retry; run in a quiet window.
Contracting too earlyDropped the old column the same day; a hotfix rollback to v2 needs it.Contract one full release cycle later, after the new path is proven.
Same rules for APIs and events: additive changes only (new optional fields, new endpoints); never rename or change type in place; deprecate with a sunset date; version only when you must. Schema Registry compatibility modes (Kafka sheet) are expand/contract for messages.
Q. Flyway runs at pod start. Two v2 pods start at the same time during a rolling update. Do they both run the migration?
Reveal hint
No. Flyway takes a lock on its history table; the second pod waits, then sees the migration already applied. Keep migrations fast (seconds), set lock_timeout, and give the pod a startup probe long enough — or run migrations as a separate Job before the rollout to remove the question entirely.

4. Rollback — make it a button, know when it won't work

LayerHow to roll backTime
Feature behaviourFlag off.Seconds.
Application (K8s)kubectl rollout undo · Argo CD: sync to previous commit / argocd app rollback · Argo Rollouts: kubectl argo rollouts undo or automatic abort.1–3 min (pods restart).
Application (ECS)Update service to the previous task definition revision · CodeDeploy auto-rollback on alarm · deployment circuit breaker.2–5 min.
Infrastructuregit revert the Terraform change → plan → apply.Minutes–hours; some resources cannot be "un-replaced".

What is the previous known-good artifact?ghcr.io/shop/api@sha256:9f3a… (task def 41 / git commit c0ffee)
Is the schema compatible with it?Yes — V22 is expand-only.
Which flag(s) gate the new behaviour?checkout.new-coupon-engine (currently 0%)

TopicWrongRight
"We'll just fix forward"Debugging in prod for 40 minutes while users see errors.Roll back first (minutes), debug after. Fix-forward only when rollback is impossible or the fix is trivially obvious.
Rollback untestedFirst rollback ever is during the incident; the old task definition references a deleted image tag.Images by digest, retention ≥ 90 days; practise rollback in staging every release.
Rolling back the DBRestoring last night's snapshot over prod loses today's orders.Forward-compatible schema; PITR to a side instance; targeted repair.
Manual cluster rollback under GitOpskubectl rollout undo while Argo auto-sync is on → Argo puts the bad version back in 3 minutes.Revert in git (or argocd app rollback, which pauses auto-sync — then fix git).
One deploy, five changesCan't roll back one without the others.Small deploys; flags for independent features.
Q. You roll back the app to v1 after v2 ran its expand migration. v2 wrote some rows with the new column filled and the old column… what? Is v1 OK?
Reveal hint
Only if v2 dual-wrote (old column kept up to date). That is exactly why dual-write comes before switching reads: it is what makes rollback safe. If v2 had stopped writing the old column, v1 would now see stale data for those rows.

5. GitOps with Argo CD — what it is and how it is wired

GitOps: a git repo holds the complete desired state of a cluster (manifests, Helm values, Kustomize overlays). A controller inside the cluster (Argo CD or Flux) continuously compares live state with git and pulls changes in. CI never needs cluster credentials; every change is a commit; drift is detected and (optionally) reverted.

Argo CD object / conceptMeaning
Application"Deploy this path of this repo at this revision into this cluster/namespace". The unit of sync.
Project (AppProject)Guardrails: which repos, clusters, namespaces, and resource kinds a team's Applications may use. RBAC boundary.
SyncApply git → cluster. Manual or automated. prune deletes resources removed from git; selfHeal reverts manual cluster edits.
HealthArgo knows how to judge Deployments, StatefulSets, Ingress, Rollouts…: Healthy / Progressing / Degraded / Missing.
Sync waves & hooksargocd.argoproj.io/sync-wave: "-1" orders resources (CRDs, namespaces, DB migration Job first); hook: PreSync/PostSync for one-off Jobs.
App of Apps / ApplicationSetOne Application that creates others (bootstrap); ApplicationSet generates Applications from a list/git directories/clusters (one per service × env).
Image UpdaterWatches the registry and commits new tags/digests to git by rule — or let CI commit the digest (simpler, explicit).
NotificationsSlack/Teams/GitHub status on sync/health events.
FluxThe other GitOps controller: Kustomization/HelmRelease CRDs, image automation, more "building blocks", no UI by default. Same model.

Q. Argo CD shows the app Synced but Degraded. What does that combination mean?
Reveal hint
Git and cluster match (synced) but the resources are not healthy — pods crash-looping, Deployment not progressing, Ingress without an address. GitOps did its job; the application is broken. Check kubectl describe/logs — and fix via a new commit (or revert).

# Argo Rollouts canary with ALB (or ingress-nginx) weights and Prometheus analysis
apiVersion: argoproj.io/v1alpha1
kind: Rollout
metadata: { name: api, namespace: shop }
spec:
  replicas: 6
  selector: { matchLabels: { app: api } }
  template: { # … exactly like a Deployment's pod template … }
  strategy:
    canary:
      canaryService: api-canary                 # Rollouts manages the selectors of these two Services
      stableService: api-stable
      trafficRouting:
        alb: { ingress: api, servicePort: 80 }     # or nginx: { stableIngress: api }
      maxSurge: "25%"
      maxUnavailable: 0
      analysis:                                  # background analysis from step 1 onward
        templates: [{ templateName: api-success-rate }]
        startingStep: 1
        args: [{ name: service, value: api-canary }]
      steps:
      - setWeight: 5
      - pause: { duration: 5m }
      - setWeight: 25
      - pause: { duration: 10m }
      - setWeight: 50
      - pause: {}                                # indefinite: a human promotes (kubectl argo rollouts promote api)
      - setWeight: 100
  rollbackWindow: { revisions: 3 }                 # instant rollback to recent revisions (keeps their ReplicaSets warm)
---
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata: { name: api-success-rate, namespace: shop }
spec:
  args: [{ name: service }]
  metrics:
  - name: success-rate
    interval: 1m
    count: 10
    successCondition: result[0] >= 0.99
    failureLimit: 2                               # two bad samples → abort → automatic rollback to stable
    provider:
      prometheus:
        address: http://prometheus.monitoring:9090
        query: |
          sum(rate(http_server_requests_seconds_count{service="{{args.service}}",status!~"5.."}[2m]))
          / sum(rate(http_server_requests_seconds_count{service="{{args.service}}"}[2m]))
  - name: p99-latency
    interval: 1m
    successCondition: result[0] < 0.8
    provider:
      prometheus:
        address: http://prometheus.monitoring:9090
        query: histogram_quantile(0.99, sum by (le) (rate(http_server_requests_seconds_bucket{service="{{args.service}}"}[2m])))

# operate
kubectl argo rollouts get rollout api --watch      # steps, weights, analysis status
kubectl argo rollouts promote api                   # continue past a pause
kubectl argo rollouts abort api                     # back to stable, rollout marked Degraded
kubectl argo rollouts undo api                      # previous revision
kubectl argo rollouts dashboard                     # local UI
# Flagger equivalent (keeps your Deployment "api")
apiVersion: flagger.app/v1beta1
kind: Canary
metadata: { name: api, namespace: shop }
spec:
  targetRef: { apiVersion: apps/v1, kind: Deployment, name: api }
  provider: nginx

  service: { port: 80, targetPort: 8080 }
  analysis:
    interval: 1m
    threshold: 3                                  # failed checks before rollback
    maxWeight: 50
    stepWeight: 10                                # 10 → 20 → … → 50, then promote
    metrics:
    - { name: request-success-rate, thresholdRange: { min: 99 }, interval: 1m }
    - { name: request-duration,     thresholdRange: { max: 800 }, interval: 1m }
    webhooks:
    - { name: load-test, type: rollout, url: http://flagger-loadtester/, metadata: { cmd: "hey -z 1m -q 10 -c 2 http://api-canary.shop/" } }   # generate traffic in staging
Design the canaryGuidance
MetricsSuccess rate and p99 latency at minimum; add business metrics (checkout conversion) for the long steps. Compare canary vs stable at the same time, not vs yesterday.
Step sizesSmall first step (1–5%) long enough to collect statistically meaningful samples (traffic × time ≥ a few thousand requests); then bigger steps.
DurationLong enough for slow failures (memory leaks, cache warm-up): 30–60 min total for important services; minutes for low-risk.
StickinessWeight-based routing sends a user to different versions across requests. If that breaks UX, route by header/cookie (Rollouts setHeaderRoute, Istio) or use flags for the user-facing part.
Background jobs / consumersKafka/SQS consumers can't be weighted by HTTP. Canary by partition share or by one replica + metric analysis; or by flag.
Alerts during rolloutAnnotate Grafana with rollout events; alert on rollout_phase="Degraded" / Flagger canary_status.
TopicWrongRight
Canary without traffic routing1 of 10 pods is "canary" with a shared Service: 10% traffic by luck, no control, no header routing.Ingress/ALB/mesh weights so the % is exact and adjustable.
Analysis on absolute thresholds only"p99 < 800 ms" passes while stable runs at 200 ms — a 4× regression went unnoticed.Compare canary to stable (Kayenta-style or two queries), plus absolute guards.
Too little traffic5% canary on a 10 rps service = 0.5 rps; one error = 100% failure.Longer steps, larger first weight, or synthetic load (Flagger webhook / k6) in low-traffic envs.

Q. The canary analysis fails and Rollouts aborts. What is now running, and what is the Rollout's status?
Reveal hint
100% of traffic is back on the stable ReplicaSet (scaled to full); the canary ReplicaSet is scaled to 0. The Rollout is Degraded with the new pod template still as "desired" — it will not retry until you push a new revision or retry. Argo CD shows it Degraded, which is your signal.

The 7 rules to remember: 1) build once, promote the digest, never rebuild; 2) deploy ≠ release — flags release, default OFF, delete after 100%; 3) every rollout runs two versions at once → expand/contract for DB, additive for APIs/events; 4) rollback is a button (git revert / rollout undo / previous task def), practised, with the previous digest written down before you start; 5) GitOps: CI commits, Argo pulls, selfHeal on, no cluster creds in CI; 6) canary = traffic weights + metric analysis vs stable + automatic abort, not "one new pod"; 7) small deploys, often, with someone watching — and measure the four DORA numbers.
Q. Interviewer: "Blue/green or canary?"
Reveal hint
Canary when you have enough traffic and metrics to judge a small slice — it limits blast radius and automates the decision. Blue/green when you need an all-or-nothing switch with instant rollback (regulated releases, protocol changes, low traffic where a 5% canary is statistically meaningless). Both need a compatible database and both become safer with feature flags on top.
