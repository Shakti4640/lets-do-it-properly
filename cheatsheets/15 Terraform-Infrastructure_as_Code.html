0. What Terraform is (and why you stop clicking in the console)

Infrastructure as Code means your servers, networks, databases, queues, DNS, and IAM roles are described in text files, reviewed in pull requests, and created by a tool — not by hand in a web console. Terraform reads those files, compares them with what exists, shows you the difference, and makes the real world match the files. It talks to clouds through providers (AWS, Azure, GCP, Kubernetes, GitHub, Datadog…).

WordPlain meaning
HCLHashiCorp Configuration Language — the .tf file syntax. Declarative: you write what should exist, not steps.
ProviderA plugin that knows one API (e.g. hashicorp/aws). Downloaded by terraform init.
ResourceOne thing to manage: an S3 bucket, an RDS instance, a DNS record.
Data sourceRead-only lookup of something that exists (latest AMI, an existing VPC).
StateTerraform's record of what it created and the real IDs. The map between your code and the cloud. Stored remotely and locked.
PlanThe diff: what will be created, changed, destroyed if you apply.
ApplyExecute the plan.
ModuleA folder of .tf files you can call like a function with inputs and outputs.
Root moduleThe folder you run terraform in.
DriftReality differs from state (someone clicked in the console).
TerraformvsNote
Declarative, cloud-agnostic syntax, huge provider ecosystem, matureCloudFormation / Bicep / Deployment ManagerCloud-native, one vendor, no state file to manage (the cloud is the state), slower feature lag.
HCL, moderate abstractionPulumi / AWS CDK / CDKTFReal programming languages (Java, TypeScript, Python). More power, more rope.
Provisions infrastructure (creates servers)Ansible / Chef / PuppetConfigures what is on servers (packages, files). Often used together; containers reduce the need.
Terraform (BSL license since 2023)OpenTofuLinux Foundation fork, MPL licence, drop-in compatible (tofu command). Same skills.
 
# the whole loop
terraform init       # download providers + modules, connect to the state backend
terraform fmt        # format files
terraform validate   # syntax and types, no cloud calls
terraform plan       # compare code ↔ state ↔ reality; print the diff
terraform apply      # do it (asks yes/no)
terraform destroy    # remove everything this root module manages
Mental model: your .tf files are the blueprint, the cloud is the building, and the state file is the inspector's notebook that says "wall A in the blueprint is wall #4471 in the building". plan walks the building with the blueprint and the notebook and lists every difference. Lose the notebook and Terraform no longer knows which walls are yours.
Q. If the .tf files describe everything, why does Terraform also need a state file?
Reveal hint
Code says "an RDS instance named shop-db"; the cloud has an instance with id db-0A1B2C and 50 attributes you never wrote. State maps one to the other, records values you did not set (defaults, generated ARNs), tracks dependencies, and lets plan know what to delete when you remove a block. Without it, every run would have to guess which existing resources are "yours".

1. HCL — the blocks you write

# versions.tf — pin the tool and the providers
terraform {
  required_version = "~> 1.9"
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 5.70" }     # ~> 5.70 = >= 5.70, < 6.0
  }
  backend "s3" { }                                               # settings passed at init (Section 3)
}

# providers.tf
provider "aws" {
  region = var.region
  default_tags { tags = { Project = "shop", Env = var.env, ManagedBy = "terraform" } }   # every resource tagged
}
provider "aws" { alias = "us"; region = "us-east-1" }         # second region (CloudFront certs) → provider = aws.us

# main.tf — resources
resource "aws_s3_bucket" "artifacts" {                       # TYPE  NAME  → referenced as aws_s3_bucket.artifacts
  bucket = "shop-${var.env}-artifacts"
  tags   = { Purpose = "build artifacts" }
}

resource "aws_s3_bucket_versioning" "artifacts" {
  bucket = aws_s3_bucket.artifacts.id                        # implicit dependency: Terraform creates the bucket first
  versioning_configuration { status = "Enabled" }
}

resource "aws_security_group" "api" {
  name_prefix = "shop-api-"
  vpc_id      = data.aws_vpc.main.id
  ingress { from_port = 8080; to_port = 8080; protocol = "tcp"; security_groups = [aws_security_group.alb.id] }
  egress  { from_port = 0;    to_port = 0;    protocol = "-1";  cidr_blocks = ["0.0.0.0/0"] }
  lifecycle { create_before_destroy = true }                  # replace without a gap
}

# data.tf — look things up
data "aws_vpc" "main" { tags = { Name = "shop-${var.env}" } }
data "aws_caller_identity" "current" {}                      # → data.aws_caller_identity.current.account_id
data "aws_ssm_parameter" "db_password" { name = "/shop/${var.env}/db/password"; with_decryption = true }

TopicWrongRight
Unpinned providersNo required_providers version → a major provider upgrade rewrites your plan one morning.~> 5.70 plus the committed .terraform.lock.hcl; upgrade on purpose with init -upgrade.
Credentials in filesaccess_key = "AKIA…" in provider.Env vars / SSO / instance role / OIDC. The provider block has no secrets.

Hard-coded namesbucket = "shop-prod-artifacts" in a module used for 3 envs → conflict.Interpolate var.env; name_prefix where supported.
Q. Two resources reference each other's attributes. What happens?
Reveal hint
"Error: Cycle". Terraform builds a directed graph from references and cannot order a loop. Break it: usually one side should not need the other (e.g. a security group rule as a separate aws_security_group_rule/aws_vpc_security_group_ingress_rule resource instead of inline ingress blocks referencing each other).

2. The workflow — init, plan, apply, and reading a plan

terraform init -backend-config=env/prod.s3.tfbackend     # once per machine/clone; again after adding providers/modules
terraform init -upgrade                                  # move to newest allowed provider versions, update lock file
terraform fmt -recursive -check                           # CI: fail if not formatted
terraform validate
terraform plan -var-file=env/prod.tfvars -out=prod.tfplan  # save the plan…
terraform show prod.tfplan                                # …review it (or -json for tooling)…
terraform apply prod.tfplan                               # …apply EXACTLY that plan (no prompt; fails if reality changed since)
terraform apply -target=module.db                        # only part of the graph (emergency use, not routine)
terraform apply -replace=aws_instance.bastion             # force recreation of one resource
terraform plan -refresh-only                             # show drift without proposing changes
terraform plan -destroy                                  # what destroy would do
terraform output -json  ·  terraform output alb_dns_name
terraform console                                        # REPL to test expressions: > cidrsubnet("10.0.0.0/16", 8, 3)
terraform graph | dot -Tsvg > graph.svg                   # dependency graph
TF_LOG=DEBUG terraform plan                               # provider API calls when something is weird

Reading a plan

  # aws_db_instance.main will be updated in-place
  ~ resource "aws_db_instance" "main" {
      ~ instance_class = "db.t4g.medium" -> "db.t4g.large"        # in-place change (may still cause a restart!)
        id             = "shop-prod-db"
    }
  # aws_security_group.api must be replaced
-/+ resource "aws_security_group" "api" {
      ~ name = "shop-api" -> "shop-api-v2"  # forces replacement   ← THE line to look for
    }
  + resource "aws_sqs_queue" "orders_dlq" { … }                  # create
  - resource "aws_s3_bucket" "old_logs" { … }                   # destroy
  <= data "aws_ami" "al2023"                                   # read during apply

Plan: 1 to add, 1 to change, 2 to destroy.
SymbolMeaningRisk
+CreateLow (cost).
~Update in placeMedium — read the attribute; some "in-place" updates restart the service (RDS class, ECS task def).
-/+ or +/-Destroy then create / create then destroy (replacement)High — data loss for stateful resources; downtime unless create_before_destroy. Find the "forces replacement" line.
-DestroyHigh — did you mean to remove the block, or did a rename/move lose track? See moved.
(known after apply)Value computed by the cloud.Normal for IDs/ARNs; suspicious on things you set.
(sensitive value)Hidden.Fine; use nonsensitive() carefully to debug.
TopicWrongRight
apply -auto-approve from a laptopProd changed with no plan review.Plan in a PR (posted as a comment), apply the saved plan file from CI after approval.
Skimming "1 to destroy"The destroyed thing was the production database.Read every - and -/+; prevent_destroy on stateful resources; deletion_protection = true on RDS.
Routine -targetApplying pieces by hand; state and code diverge, hidden dependencies never applied.Full plans. -target only to recover from a broken state, then a full apply.
Skipping init after adding a module"Module not installed".init whenever providers, modules, or backend change.
Plan on stale local codeTeammate merged; your plan deletes their resources.Pull first; better, only CI plans and applies.
Q. plan says "No changes", yet a colleague swears they changed the ALB timeout in the console yesterday. Why no diff?
Reveal hint
Either that attribute is not in your code (Terraform only manages attributes you set, unless the provider defaults it), it is under ignore_changes, or plan ran with -refresh=false. Run terraform plan -refresh-only to see pure drift, and add the attribute to the code so it is enforced.

3. State — remote backends, locking, and the commands you will need

# versions.tf
terraform {
  backend "s3" {
    bucket       = "shop-terraform-state"           # versioned, encrypted, private, in its own account ideally
    key          = "platform/prod/terraform.tfstate" # one key per root module per environment
    region       = "ap-south-1"
    encrypt      = true
    use_lockfile = true                             # Terraform 1.10+: S3-native locking (replaces the DynamoDB table)
    # dynamodb_table = "terraform-locks"           # older versions: lock table with LockID hash key
  }
}
# keep backend values out of the file for multi-env: terraform init -backend-config=env/prod.s3.tfbackend

moved {
  from = aws_security_group.api
  to   = module.api.aws_security_group.this
}

  to = aws_s3_bucket.logs
  id = "shop-logs-bucket"
}
removed {
  from = aws_iam_user.legacy_ci
  lifecycle { destroy = false }     # forget, do not delete

TopicWrongRight
State in gitterraform.tfstate committed: merge conflicts, and it contains secrets in plain text (DB passwords, keys).Remote backend, encrypted, versioned, locked; *.tfstate* in .gitignore; restrict who can read the bucket.
One state for everythingNetwork + DB + 12 services in one state: 20-minute plans, one bad apply breaks all, everyone blocked by the lock.Split by blast radius and change rate: network/, data/, services/orders/… Connect with terraform_remote_state data or (better) SSM/outputs lookups.
Editing state JSON by handTypo → corrupted state, resources orphaned.moved/removed/import blocks, state mv/rm; always state pull a backup first.
force-unlock reflexUnlocking while a colleague's apply is mid-flight → two writers → corrupted state.Check CI/who holds it (the lock info shows who/when); unlock only for dead runs.
Secrets via stateTreating state as safe because the bucket is private.Assume state = secret store. Prefer resources that never put the secret in state (e.g. RDS manage_master_user_password, generated in Secrets Manager).
Q. You renamed resource "aws_instance" "web" to "api". The plan says destroy web, create api. How do you rename without downtime?
Reveal hint
Add moved { from = aws_instance.web to = aws_instance.api } and plan again: "No changes" (just a state move). Commit the block; remove it later after everyone has applied. Same for moving into a module or changing count → for_each keys.

4. Variables, outputs, locals, types, functions

# variables.tf
variable "env" {
  type        = string
  description = "Environment name"
  validation {
    condition     = contains(["dev", "staging", "prod"], var.env)
    error_message = "env must be dev, staging or prod."
  }
}
variable "instance_count" { type = number; default = 2 }
variable "db_password"    { type = string; sensitive = true; ephemeral = true }   # ephemeral (1.10+): never written to state/plan
variable "services" {
  type = map(object({
    cpu    = number
    memory = number
    port   = optional(number, 8080)       # optional with default
    public = optional(bool, false)
  }))
}

# locals.tf — computed names, merged tags, derived maps
locals {
  name        = "shop-${var.env}"
  common_tags = merge(var.tags, { Env = var.env, Owner = "platform" })
  public_services = { for k, s in var.services : k => s if s.public }
  az_count    = var.env == "prod" ? 3 : 2
}

# outputs.tf
output "alb_dns_name" { value = aws_lb.api.dns_name; description = "Public ALB hostname" }
output "db_endpoint"  { value = aws_db_instance.main.address; sensitive = true }

# env/prod.tfvars
env            = "prod"
instance_count = 4
services = {
  orders   = { cpu = 512, memory = 1024, public = true }
  payments = { cpu = 1024, memory = 2048 }
}

Q. A variable is marked sensitive. Is its value kept out of the state file?
Reveal hint
No — sensitive only redacts it in CLI output and plans. State still contains it in plain text. Only ephemeral variables/resources (Terraform 1.10+) are excluded from state and plan files. Treat state as secret regardless.

5. Modules — reuse, structure, registries

# modules/service/  — one ECS Fargate service behind an ALB listener rule
modules/service/
├── main.tf          # aws_ecs_task_definition, aws_ecs_service, aws_lb_target_group, aws_lb_listener_rule, aws_security_group

RuleWhy
A module = one logical unit (a service, a VPC, a database), not one resourceWrapping a single resource adds nothing; a 40-resource "everything" module can't be reused.
No provider or backend blocks inside reusable modulesThe root decides where and with which credentials. Modules only declare required_providers.
Pin remote modules (?ref=v1.4.0, version = "~> 5.0")Unpinned main changes your infra without a code change.
Inputs typed and documented; outputs for everything a caller might wireModules are APIs. terraform-docs generates the README from them.
Public registry modules for commodity infra (VPC, EKS, RDS, ALB)terraform-aws-modules/* encode hundreds of gotchas. Read them; wrap them if you need company defaults.
Private registry / git tags for your own modules; semverTeams upgrade deliberately; breaking changes bump the major.
Test modulesterraform test (1.6+, tests/*.tftest.hcl) with run blocks and assert; Terratest (Go) for real deploys.

Q. You add count = var.enabled ? 1 : 0 to a resource inside a module that was already applied. The plan wants to destroy and recreate it. Why?
Reveal hint
Its address changed from aws_x.this to aws_x.this[0]. Add moved { from = aws_x.this to = aws_x.this[0] } in the module. Same rule when switching count ↔ for_each.

6. Loops, conditionals, dynamic blocks, lifecycle

# for_each over a map (preferred): stable keys → adding/removing one does not shift the others
resource "aws_sqs_queue" "q" {
  for_each = toset(["orders", "payments", "notifications"])
  name     = "shop-${var.env}-${each.key}"
}
# → aws_sqs_queue.q["orders"].arn

module "service" {
  for_each = var.services                       # map(object) from Section 4
  source   = "../../modules/service"
  name     = each.key
  cpu      = each.value.cpu
  memory   = each.value.memory
  port     = each.value.port
}
# → module.service["orders"].target_group_arn   ·   values(module.service)[*].service_name

# count: for N identical things or on/off
resource "aws_instance" "bastion" {
  count = var.env == "prod" ? 1 : 0                # conditional resource
  …
}
# → aws_instance.bastion[0].id   ·   one(aws_instance.bastion[*].id) when it may be absent

# for expressions: reshape collections
locals {
  subnet_ids     = [for s in aws_subnet.private : s.id]                       # list
  subnet_by_az   = { for s in aws_subnet.private : s.availability_zone => s.id }   # map
  big_services   = [for k, v in var.services : k if v.memory >= 2048]           # filter
  env_list       = [for k, v in var.env_vars : { name = k, value = v }]       # ECS wants a list of {name,value}
  all_tg_arns    = flatten([for m in module.service : m.target_group_arns])
}

# dynamic blocks: repeat a nested block from a collection
resource "aws_security_group" "api" {
  dynamic "ingress" {
    for_each = var.ingress_rules                 # list(object({port, cidr}))
    content {
      from_port   = ingress.value.port
      to_port     = ingress.value.port
      protocol    = "tcp"
      cidr_blocks = [ingress.value.cidr]
    }
  }
}

# lifecycle
resource "aws_db_instance" "main" {
  …
  lifecycle {
    prevent_destroy = true                        # plan fails if anything would destroy it
    ignore_changes  = [password]                 # rotated outside Terraform
    precondition {
      condition     = var.env != "prod" || var.multi_az
      error_message = "prod databases must be multi-AZ."
    }
  }
}
resource "aws_ecs_service" "api" {
  …
  lifecycle { ignore_changes = [task_definition, desired_count] }   # CI/CD and autoscaling own these after creation
}
ConstructUseGotcha
for_each (map or set of strings)Named instances; default choice.Keys must be known at plan time (no computed values). Convert lists with toset() or { for i, v in list : v => i }.
countN copies; enable/disable.Removing the middle element re-indexes everything → destroy/create cascade. Use for_each for anything with identity.
[*] splataws_instance.web[*].id — list of an attribute across count instances.Not for for_each; use values(x)[*].id.
dynamicVariable number of nested blocks.Hurts readability; prefer separate rule resources (aws_vpc_security_group_ingress_rule with for_each) when they exist.
ignore_changesAttributes managed elsewhere.Hides drift forever; document why. all is almost always wrong.
create_before_destroyZero-gap replacement.Names must not collide — use name_prefix.
replace_triggered_byRecreate when something else changes (instance when its user_data template changes).—
precondition / postcondition / checkGuardrails with clear messages.check blocks warn, do not fail.
TopicWrongRight
count over a list of namescount = length(var.users); delete the first user → all users recreated.for_each = toset(var.users).
for_each on computed valuesfor_each = aws_subnet.x before subnets exist → "The for_each value depends on resource attributes that cannot be determined until apply".Key on something static (AZ names, var keys), not on created IDs.
Deploying app versions with TerraformEvery image tag bump is a Terraform apply touching the task definition.Terraform creates the service; CI/CD (or GitOps) updates the image; ignore_changes = [task_definition]. Infra and app release cadences differ.
Clever expressionsNested for with try inside merge inside flatten on one line.Break into named locals; test in terraform console.
Q. You switch a resource from count = 3 to for_each = toset(["a","b","c"]). What does the plan show?
Reveal hint
Destroy [0],[1],[2] and create ["a"],["b"],["c"] — different addresses. Add three moved blocks (from = x[0] to = x["a"] …) to keep the real resources.

ApproachHowProsCons
Directory per env (above)Separate roots and state files; shared modules.Explicit, isolated blast radius, different accounts/providers per env, easy to see what prod has.Some repetition in the thin roots (acceptable).
Workspaces (terraform workspace new prod)Same code, state keyed by workspace name; terraform.workspace in expressions.No duplication.Same backend/credentials for all envs; easy to apply to the wrong one; conditionals sprawl. HashiCorp itself advises against them for env separation.
TerragruntWrapper: DRY backend config, dependencies between stacks, run-all.Removes the thin-root boilerplate; strong for many stacks.Another tool and DSL to learn.
Branch per envprod branch deploys prod.—Anti-pattern: code drifts between branches, promotion is a merge, no single view.
Splitting state — guidelines
By change rate: network changes yearly, data monthly, services daily. Don't make a service deploy plan the VPC.
By blast radius: a mistake in services/ must not be able to delete the database.
By ownership: platform team owns network/ and platform/; service teams own their service stacks.
By account: one AWS account per env (dev/staging/prod) with a terraform role in each; CI assumes the right role via OIDC.
Linking stacks: terraform_remote_state (tight coupling to state layout) or publish outputs to SSM Parameter Store / data-source lookups by tag (looser).
TopicWrongRight
Workspaces for prod/stagingterraform workspace select prod forgotten → staging values applied to prod.Directory per env with its own backend key and credentials.
One account for everythingDev experiments can touch prod resources.Account per env; IAM boundary is the strongest isolation.
remote_state everywhereEvery stack reads every other stack's state; one key rename breaks ten plans.Few, well-known interfaces; or SSM parameters as the contract.
Env-specific resources in shared modulesif env == "prod" create WAF inside the module.Module takes enable_waf; env root sets it.
Q. Why is "same Terraform code for every environment" a goal, yet "same state for every environment" a disaster?
Reveal hint
Code sameness means staging actually tests what prod will get. State separation means a bad apply, a lock, a corrupted file, or a leaked state secret affects one environment only. Modules give you the first; per-env roots and backends give you the second.

  execution_role_arn       = aws_iam_role.execution.arn   # pulls image, reads secrets, writes logs

    portMappings = [{ containerPort = var.port }]

# IAM for the app: exactly what it needs
data "aws_iam_policy_document" "task" {
  statement { actions = ["sqs:SendMessage", "sqs:ReceiveMessage", "sqs:DeleteMessage", "sqs:GetQueueAttributes"]; resources = [aws_sqs_queue.orders.arn] }
  statement { actions = ["s3:GetObject", "s3:PutObject"]; resources = ["${aws_s3_bucket.uploads.arn}/*"] }
}
DecisionWhy
Fargate over EC2-backed ECS or EKSNo nodes to patch; right size for a handful of services. EKS when you need the Kubernetes ecosystem (see the K8s sheet).
Task role ≠ execution roleExecution role is for ECS itself (pull image, fetch secret, write logs). Task role is what your Java code can call. Keep the task role tiny.
Secrets via secrets, not environmentResolved at task start from Secrets Manager/SSM; never visible in the task definition or state.
manage_master_user_passwordPassword never passes through Terraform; rotation is AWS's job.
Readiness path for the target groupSpring's /actuator/health/readiness flips during graceful shutdown; ALB drains before the task dies.
ignore_changes on task_definitionCI deploys new images via the ECS API (or aws ecs update-service); Terraform owns the shape, not the version.
Circuit breaker + rollbackA crash-looping deploy is reverted automatically.
Q. Where does the Spring Boot app get DB_PASSWORD from in this design, and who can read it?
Reveal hint
ECS reads the secret from Secrets Manager using the execution role at task start and injects it as an environment variable inside the container. Terraform only ever handles the secret's ARN. Humans with secretsmanager:GetSecretValue on that ARN can read it; nobody can read it from state, the task definition JSON, or the console task view.

9. Terraform in CI/CD — plan on PR, apply on merge, policy, security

# .github/workflows/terraform.yml  (one job per stack via matrix; OIDC to AWS; plan comment on PR; apply on main)
name: terraform
on:
  pull_request: { paths: ['infra/**'] }
  push: { branches: [main], paths: ['infra/**'] }
permissions: { contents: read, id-token: write, pull-requests: write }
concurrency: { group: tf-${{ github.ref }}, cancel-in-progress: false }     # never cancel an apply
env: { TF_IN_AUTOMATION: true, TF_INPUT: 0 }

jobs:
  plan:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    strategy: { matrix: { stack: [envs/prod/network, envs/prod/platform, envs/prod/services] } }
    defaults: { run: { working-directory: infra/${{ matrix.stack }} } }
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with: { role-to-assume: arn:aws:iam::222222222222:role/terraform-plan, aws-region: ap-south-1 }   # read-only role for plans
      - uses: hashicorp/setup-terraform@v3
        with: { terraform_version: 1.9.8, terraform_wrapper: false }
      - run: terraform fmt -check -recursive
      - run: terraform init -backend-config=backend.hcl
      - run: terraform validate
      - run: tflint --init && tflint                                   # lint (deprecated args, invalid instance types)
      - uses: bridgecrewio/checkov-action@v12                           # security misconfig (public S3, open SG, no encryption)
        with: { directory: infra/${{ matrix.stack }}, soft_fail: false }
      - run: terraform plan -no-color -out=tfplan 2>&1 | tee plan.txt
      - uses: actions/github-script@v7                                   # post the plan as a PR comment
        with:
          script: |
            const fs = require('fs');
            const plan = fs.readFileSync('infra/${{ matrix.stack }}/plan.txt','utf8').slice(0, 60000);
            github.rest.issues.createComment({ ...context.repo, issue_number: context.issue.number,
              body: `### Plan — ${{ matrix.stack }}\n\`\`\`\n${plan}\n\`\`\`` });
      - run: infracost breakdown --path . --format table                  # optional: cost diff on the PR

  apply:
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    environment: production                                              # approval gate
    strategy: { max-parallel: 1, matrix: { stack: [envs/prod/network, envs/prod/platform, envs/prod/services] } }   # in dependency order
    defaults: { run: { working-directory: infra/${{ matrix.stack }} } }
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with: { role-to-assume: arn:aws:iam::222222222222:role/terraform-apply, aws-region: ap-south-1 }
      - uses: hashicorp/setup-terraform@v3
        with: { terraform_version: 1.9.8, terraform_wrapper: false }
      - run: terraform init -backend-config=backend.hcl
      - run: terraform plan -no-color -out=tfplan
      - run: terraform apply -no-color tfplan                             # apply the plan just made on main, no prompt
PracticeWhy
Plan on PR, apply on mergeReviewers see the exact diff; nothing changes until approved and merged.
Two IAM roles: plan (read-only + state read) and apply (write)A malicious PR can't change infra by running a plan.
environment: production on applyHuman approval + audit trail for prod.
Pinned Terraform version + .terraform.lock.hcl committedSame binary and providers everywhere.
fmt -check, validate, tflint, checkov/tfsec/trivy configCatch mistakes and insecure defaults before plan.
Policy as code: OPA/Conftest, Sentinel (HCP), Checkov custom policies"No public S3", "all RDS encrypted", "tags required" enforced, not reviewed.
Drift detection on a scheduleNightly plan -detailed-exitcode (exit 2 = changes) → alert.
Atlantis / HCP Terraform / Spacelift / env0Purpose-built: plan comments, atlantis apply from the PR, locking per directory, policy, cost.
infracostCost of the diff on the PR; catches the accidental db.r6g.16xlarge.
TopicWrongRight
Apply from laptopsWho applied what, when, with which code? Nobody knows.CI only (break-glass documented). Laptops get the plan role at most.
Admin credentials in CILong-lived AdministratorAccess key as a secret.OIDC → scoped role; separate plan/apply roles; permission boundaries.
Parallel applies to one stateTwo merges → two applies → lock contention or corruption.concurrency group per stack, max-parallel: 1; the backend lock as the last line.
Plan output nobody readsBuried in CI logs.Posted on the PR, collapsed by stack; resource counts in the title.
Applying a different plan than reviewedMain moved between review and apply.Plan again on main just before apply (above), or save the PR's plan as an artifact and apply that after merge (strictest).
Q. Why apply a saved plan file (apply tfplan) rather than apply -auto-approve?
Reveal hint
The plan file freezes exactly what was reviewed. If reality or state changed in between, apply tfplan fails ("Saved plan is stale") instead of silently doing something different. -auto-approve re-plans and applies whatever it finds — fine for ephemeral dev, wrong for prod.

10. Troubleshooting, drift, recovery, and quick reference

Error / situationMeaningFix
Error acquiring the state lockAnother run holds it, or a crashed run left it.Check who (the message says); if dead, terraform force-unlock ID.
Saved plan is staleState changed after the plan was made.Re-plan.
Provider produced inconsistent final planProvider bug or computed value changed mid-apply.Re-run; pin/upgrade provider; report.
Error: Cycle: …Circular references.Split the resource (separate rule resources), remove the back-reference.
for_each … cannot be determined until applyKeys depend on a resource not yet created.Key on static values; or -target the dependency once, then full apply.
Resource exists but Terraform wants to create it (AlreadyExists)Created outside Terraform, or state lost.import {} block + plan; never delete manually to "let Terraform recreate" a stateful thing.
Everything shows as changed / destroyed after a refactorAddresses changed (rename, module move, count→for_each).moved blocks before applying.
Plan shows changes every run with no code change (perpetual diff)Provider normalizes a value (JSON key order, lower-case, default added), or something rewrites it.jsonencode instead of strings; set the attribute explicitly; ignore_changes as last resort.
Destroy fails: dependency violation / bucket not emptyCloud refuses while children exist.force_destroy = true on buckets (carefully), delete out-of-band children, retry.
Lost / corrupted stateNo notebook.Restore the previous version from the versioned bucket (state push); last resort: import everything.
Error: Unsupported attributeTypo or provider version mismatch.terraform providers; read the provider docs for your pinned version.

The 7 rules to remember: 1) remote, encrypted, locked, versioned state — split by blast radius, never in git, treated as secret; 2) pin Terraform, providers, and modules; commit the lock file; 3) plan on PR with a read-only role, apply on merge through an approval gate with a saved plan; 4) for_each over count, moved/import/removed blocks over state surgery; 5) read every - and -/+; prevent_destroy + deletion_protection on stateful things; 6) secrets never touch tfvars or state — Secrets Manager/SSM, managed passwords, OIDC; 7) Terraform owns infrastructure shape; the CD pipeline owns application versions (ignore_changes on image/task definition).
Q. Interviewer: "Someone changed a security group in the console at 2 am to fix an outage. What do you do the next morning?"
Reveal hint
Run plan -refresh-only to see exactly what changed. If the fix was right, put it in code (PR, review, apply → state and code match). If it was wrong, a normal apply reverts it. Either way the console change becomes a commit, and you add the missing alert/runbook so the next 2 am fix goes through the pipeline (or a documented break-glass path).
