A0. NGINX — what it is and how it is built

NGINX (engine-x) is a web server that is mostly used as a reverse proxy: it sits in front of your Java services, terminates TLS, and forwards requests to them. It also does load balancing, caching, compression, rate limiting, and static file serving. It handles tens of thousands of connections with a few worker processes because it is event-driven (epoll), not thread-per-connection.

TermPlain meaning
Reverse proxyClients talk to NGINX; NGINX talks to your app. The client never sees the app directly.
Forward proxyThe opposite: sits in front of clients (corporate proxy). Not what NGINX usually does.
UpstreamA named group of backend servers NGINX forwards to.
Master / worker processesMaster reads config and manages workers; each worker is single-threaded and handles thousands of connections with an event loop.
Directive / contextA config line (listen 80;) / the block it lives in (http, server, location, upstream).
Virtual hostA server block picked by server_name (the Host header) and port.
TLS terminationNGINX decrypts HTTPS; talks plain HTTP (or HTTPS again) to the app.
OpenResty / NGINX Plus / Kong / Ingress-NGINXNGINX + Lua scripting / commercial build / API gateway built on it / the Kubernetes ingress controller built on it.

Why put NGINX in front of Spring Boot

JobNGINX does it better because
TLSOne place for certificates and renewal (certbot); frees the JVM from crypto work.
Load balancing + health checksSpread traffic over N instances; drop dead ones.
Static files / SPAServes React builds at memory speed; your API stays an API.
Compression, caching, bufferinggzip/brotli; cache GET responses; absorb slow clients so Tomcat threads are freed fast.
Rate limiting, IP allow-lists, WAFProtects before the request reaches Java.
One hostname, many services/api/orders → orders service, /api/users → users service.

nginx -t                  # test the config — always before reload
nginx -s reload           # graceful reload: new workers with new config, old ones finish their requests
nginx -T                  # dump the full merged config
docker run -d -p 80:80 -v ./nginx.conf:/etc/nginx/nginx.conf:ro nginx:1.27-alpine
# files: /etc/nginx/nginx.conf (main) → include /etc/nginx/conf.d/*.conf (one file per site); logs in /var/log/nginx/
Q. NGINX has 4 worker processes. How many concurrent connections can it hold?
Reveal hint
Roughly worker_processes × worker_connections (e.g. 4 × 1024 = 4096 by default, raise worker_connections to 10k+). Each connection is not a thread — it is an entry in the event loop, so the cost is a few KB, not a stack.

A1. NGINX config — server, location, proxy_pass

# /etc/nginx/conf.d/shop.conf
upstream shop_api {
    server 10.0.1.5:8080;
    server 10.0.1.6:8080;
    keepalive 32;                                 # reuse connections to the backends
}

server {
    listen 80;
    server_name shop.example.com;
    return 301 https://$host$request_uri;         # HTTP → HTTPS
}

server {
    listen 443 ssl http2;
    server_name shop.example.com;

    ssl_certificate     /etc/letsencrypt/live/shop.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/shop.example.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;

    client_max_body_size 10m;                     # default 1m → 413 on bigger uploads
    gzip on;  gzip_types application/json text/css application/javascript;

    # SPA static files
    location / {
        root /var/www/shop;
        try_files $uri $uri/ /index.html;          # client-side routing
        expires 1h;
    }

    # API → Spring Boot
    location /api/ {
        proxy_pass http://shop_api;                 # no trailing slash: /api/orders stays /api/orders
        proxy_http_version 1.1;
        proxy_set_header Connection "";             # needed for upstream keepalive
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_connect_timeout 3s;
        proxy_read_timeout    30s;                   # default 60s; longer than your slowest legit request
        proxy_next_upstream error timeout http_502 http_503;   # retry another backend on these
    }

    # hide actuator from the internet
    location /api/actuator/ { return 404; }

    location = /health { access_log off; return 200 "ok"; }
}

Client IPSpring logs 127.0.0.1 / the NGINX IP for every request.Send X-Forwarded-For/X-Real-IP; in Boot set server.forward-headers-strategy=framework (or native) so request.getRemoteAddr() and https redirects are right.

Q. location /api { proxy_pass http://up/; } (no trailing slash in location, slash in proxy_pass). Request /apiary — what happens?
Reveal hint
/api is a prefix match, so /apiary matches it and is rewritten to //ary-ish nonsense upstream. Always end prefix locations for paths with a slash (/api/) unless you mean to catch siblings.

A2. Load balancing, health, caching, rate limiting

upstream shop_api {
    least_conn;                                   # or: ip_hash; hash $request_uri consistent; random two least_conn; default round-robin
    server 10.0.1.5:8080 weight=3 max_fails=3 fail_timeout=10s;   # 3 failures → out for 10 s (passive health check)
    server 10.0.1.6:8080;
    server 10.0.1.7:8080 backup;                   # only used when the others are down
    keepalive 64;
}

# response cache for GET /api/catalog/*
proxy_cache_path /var/cache/nginx levels=1:2 keys_zone=api_cache:10m max_size=1g inactive=10m use_temp_path=off;
location /api/catalog/ {
    proxy_cache api_cache;
    proxy_cache_key "$scheme$host$request_uri";
    proxy_cache_valid 200 5m;
    proxy_cache_use_stale error timeout updating http_500 http_502 http_503;   # serve stale while backend is sick
    proxy_cache_lock on;                          # one refill per key (stampede protection)
    add_header X-Cache-Status $upstream_cache_status;   # HIT / MISS / STALE / BYPASS
    proxy_pass http://shop_api;
}

# rate limiting: 10 req/s per IP, bursts of 20 queued, beyond that 429
limit_req_zone $binary_remote_addr zone=api_rl:10m rate=10r/s;
limit_conn_zone $binary_remote_addr zone=conn_rl:10m;
location /api/ {
    limit_req zone=api_rl burst=20 nodelay;
    limit_req_status 429;
    limit_conn conn_rl 50;
    proxy_pass http://shop_api;
}

# security headers + hide version
server_tokens off;
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
add_header X-Content-Type-Options nosniff always;
add_header X-Frame-Options DENY always;

# structured access log with timings
log_format json escape=json '{"t":"$time_iso8601","ip":"$remote_addr","m":"$request_method","uri":"$request_uri",'
                              '"s":$status,"bytes":$body_bytes_sent,"rt":$request_time,"urt":"$upstream_response_time",'
                              '"up":"$upstream_addr","ua":"$http_user_agent","rid":"$request_id"}';
access_log /var/log/nginx/access.log json;
proxy_set_header X-Request-Id $request_id;        # correlate with app logs

round-robin (default)Next server in turn, weighted.Stateless services of equal size.
least_connFewest active connections.Requests of uneven length.
ip_hashSame client IP → same server.Sticky sessions without a shared session store (fragile behind NAT).

TopicWrongRight
Sticky sessionsip_hash to keep users on one pod because sessions are in Tomcat memory.Stateless JWT or Spring Session in Redis; any pod can serve any request.
Retrying POSTsproxy_next_upstream with non_idempotent → a payment retried on another backend.Default excludes non-idempotent methods; keep it so, or make POSTs idempotent with keys.
Health only passiveUsers are the health check (max_fails only trips after failures).Active checks need NGINX Plus or Ingress/LB; in Kubernetes rely on readiness probes + Service endpoints instead.
Caching with cookies/authCaching /api/me → user A sees user B's data.Cache only public GETs; proxy_cache_bypass $http_authorization; include varying headers in the key.
Rate limit by IP onlyAll users behind one corporate NAT get limited together.Key on an API key or user id header when authenticated; IP as fallback.
Q. Backend returns in 20 ms, but clients see 2 s. $upstream_response_time is 0.02 and $request_time is 2.0. Where did the time go?
Reveal hint
Between NGINX and the client: slow network, a huge response, or TLS handshakes with no keep-alive. The difference between those two variables is exactly the client-side time. Check keepalive_timeout, gzip, body size, and the CDN.

In Kubernetes you usually don't write nginx.conf at all: Ingress-NGINX generates it from Ingress objects and annotations (nginx.ingress.kubernetes.io/proxy-body-size, …/limit-rps, …/proxy-read-timeout). The concepts above are exactly what those annotations set.
NGINX vs the others: HAProxy — pure L4/L7 load balancer, best health checks and stats, no static files. Envoy — modern proxy for service meshes (Istio), gRPC-native, dynamic config via xDS. Traefik / Caddy — auto-TLS, auto-discovery, simpler configs. Cloud ALB/NLB — managed; put NGINX behind it only when you need its features.
Q. Spring Boot runs fine on curl localhost:8080 on the same box, but NGINX gives 502 with "connect() failed (111: Connection refused)". Why?
Reveal hint
Most often NGINX runs in a container (or another host) and localhost in its config means itself. Point proxy_pass at the app's reachable address (host.docker.internal, the service name, or the host IP), and make the app listen on 0.0.0.0.

B4. MongoDB — what it is and when to pick it

MongoDB is a document database. Instead of rows in tables, you store documents (JSON-like, stored as BSON) in collections. A document can hold nested objects and arrays, and documents in one collection do not need the same fields. Writes to a single document are atomic; multi-document transactions exist but are not the default way of working.

SQL wordMongo wordNote
DatabaseDatabaseSame idea.
TableCollectionNo fixed schema (optional JSON Schema validation).
RowDocumentMax 16 MB. Has an _id (default ObjectId, 12 bytes, time-ordered).
ColumnFieldCan be nested: address.city.
JOINEmbedding or $lookupDesign to avoid joins by embedding what you read together.
Primary key_idAlways indexed, unique.
IndexIndexB-tree; compound, multikey (arrays), text, geo, TTL, partial, wildcard.
TransactionSingle-doc atomic; multi-doc ACID transactions on replica sets (4.0+)Use sparingly; model so one document = one unit of change.
Replication / shardingReplica set (primary + secondaries) / Sharded cluster (mongos routers + config servers + shards)Replica set is the minimum for production.
Pick MongoDB whenPrefer PostgreSQL when
Data is naturally a document (order with its lines, product with variable attributes, user profile with settings).Many entities reference each other and you query across them in many ways (reporting, ad-hoc joins).
Schema changes often or differs per record type (catalog, content, events).Strong constraints, foreign keys, and multi-row transactions are central (ledger, inventory, bookings).
Horizontal write scaling across shards is needed early.One big machine (or read replicas) is enough — which is most apps.
Fast iteration; the app owns validation.The team knows SQL well; analysts need SQL access.

Mental model: each document is a self-contained JSON file in a folder (collection). You pull one file and have everything you need for that screen. Design question #1 is always: "what do I read together?" — that goes in one document.
Q. Is MongoDB "schemaless"?
Reveal hint
The database does not enforce a schema by default, but your application always has one (the Java classes). Call it "schema-flexible". Use JSON Schema validation (db.createCollection(…, { validator })) to stop junk from entering, and version your documents (schemaVersion: 2) to migrate lazily.

// updates: operators, never replace the whole doc by accident
db.orders.updateOne({ _id: id }, { $set: { status: "PAID", paidAt: new Date() }, $inc: { version: 1 } })
db.orders.updateOne({ _id: id, status: "NEW" }, { $set: { status: "CANCELLED" } })      // conditional = optimistic
db.orders.updateOne({ _id: id }, { $push: { items: { sku: "C3", qty: 1 } } })                 // $push $pull $addToSet $pop
db.orders.updateOne({ _id: id, "items.sku": "A1" }, { $inc: { "items.$.qty": 1 } })        // $ = the matched array element
db.counters.findOneAndUpdate({ _id: "invoice" }, { $inc: { seq: 1 } }, { upsert: true, returnDocument: "after" })  // atomic counter
db.orders.deleteMany({ status: "CANCELLED", createdAt: { $lt: cutoff } })

// aggregation pipeline: stages run in order, like Unix pipes
db.orders.aggregate([
  { $match: { status: "PAID", createdAt: { $gte: ISODate("2026-10-01") } } },     // filter early → uses indexes
  { $unwind: "$items" },                                                          // one doc per array element
  { $group: { _id: "$items.sku", units: { $sum: "$items.qty" },
              revenue: { $sum: { $multiply: ["$items.qty", "$items.price"] } } } },
  { $sort: { revenue: -1 } },
  { $limit: 10 },
  { $lookup: { from: "products", localField: "_id", foreignField: "sku", as: "product" } },   // left join
  { $project: { sku: "$_id", units: 1, revenue: 1, name: { $first: "$product.name" }, _id: 0 } }
])
// other stages: $addFields/$set, $facet (several pipelines at once), $bucket, $merge/$out (write results), $setWindowFields (window functions)
TopicWrongRight
Replace instead of updatesave(doc) / replaceOne with a stale object → silently overwrites fields another request changed.$set only the fields you changed; version field for optimistic locking (@Version in Spring Data).
Read-modify-write countersRead qty, add 1 in Java, write back.$inc — atomic on the server.
$lookup everywhereNormalized like SQL, then $lookup 5 collections per page.Embed what you read together; $lookup for occasional reporting.
$match latePipeline unwinds a million docs then filters.$match (and $project) first so indexes apply and fewer docs flow.
Deep skipskip(100000).limit(20).Range on an indexed sort key: { createdAt: { $lt: lastSeen } }.
Regex search{ name: /phone/i } on a big collection.Text index + $text, or Atlas Search / Elasticsearch.
Q. { items: { sku: "A1", qty: 2 } } vs { "items.sku": "A1", "items.qty": 2 } vs { items: { $elemMatch: { sku: "A1", qty: 2 } } } — which finds an order with an A1 line of qty 2?
Reveal hint
The first needs an element that is exactly {sku:"A1", qty:2} (no other fields, same order) — fragile. The second matches if some element has sku A1 and some (possibly different) element has qty 2. Only $elemMatch requires both on the same element.

Transactions and write/read concerns

const session = db.getMongo().startSession();
session.withTransaction(async () => {
  const o = session.getDatabase("shop").orders;
  const s = session.getDatabase("shop").stock;

readConcernlocal · majority · snapshot · linearizableHow committed the data you read must be. majority avoids reading data that may roll back.

Q. Index { status: 1, createdAt: -1 }. Query find({ createdAt: { $gt: d } }).sort({ status: 1 }). Is the index useful?
Reveal hint
Barely. The leading field status is not constrained by equality, so the index cannot seek on createdAt; it may still be scanned fully to satisfy the sort. ESR says: equality on status first, then sort, then range. Match the index to the query shape or vice versa.

Replica sets and sharding

PieceMeaning
Replica set1 primary (all writes) + 2+ secondaries (replicate the oplog). Automatic election on primary failure (~seconds). Minimum 3 members for production.

Q. Spring Data saves a BigDecimal and Mongo shows "499.99" as a string. Why, and does it matter?
Reveal hint
Default mapping stores BigDecimal as a string to avoid precision loss. Strings sort and compare lexically ("50" > "499.99") and cannot be summed in aggregations. Use @Field(targetType = DECIMAL128) or set the converter globally.

C8. Observability — the three signals and the stack

Observability means you can ask new questions about a running system without shipping new code. It rests on three signals: metrics (numbers over time), logs (events with text), and traces (the path of one request across services). The modern stack: Micrometer inside the JVM, OpenTelemetry as the wire standard, Prometheus to store metrics, Grafana to draw them, plus Loki/Elastic for logs and Tempo/Jaeger for traces.

D12. SRE practice — reliability as an engineering discipline

Site Reliability Engineering treats operations as a software problem: define how reliable the service must be (SLOs), measure it (SLIs), spend the allowed unreliability (error budget) on change, automate toil away, and learn from every incident without blame. Sections 8–11 gave you the telemetry; this part is what you do with it.

TermPlain meaningExample for the shop API
SLI (indicator)A measured ratio of good events to all events.Requests with status < 500 and latency < 500 ms ÷ all requests.
SLO (objective)The target for the SLI over a window.99.9% over 30 days.
SLA (agreement)A contract with consequences, looser than the SLO.99.5% or credits — you alert on the SLO so you never breach the SLA.
Error budget1 − SLO: the unreliability you may spend.0.1% of 30 days ≈ 43 minutes of full outage, or 43 hours at 1% errors.
Burn rateHow fast you consume the budget relative to "exactly on target".Burn rate 14.4 for 1 hour = 2% of the monthly budget gone in an hour → page.
ToilManual, repetitive, automatable operational work with no lasting value.Hand-restarting pods every Monday.
MTTD / MTTR / MTBFMean time to detect / restore / between failures.Track MTTR per incident; it is the DORA metric you move with runbooks and rollbacks.
Blameless postmortemWritten analysis of an incident focused on systems and decisions, not people."The alert fired 20 min late because the threshold was tuned for old traffic" — not "Asha missed it".

Why burn-rate alerts beat threshold alerts
A fixed "5xx > 2% for 5 min" pages for a 6-minute blip that costs 0.3% of the budget, and sleeps through a 0.5% error rate that quietly burns the whole month. Burn rate pages in proportion to how much reliability you are losing, with a long window to confirm it is real and a short window to stop paging once it is fixed.

Q. 99.9% monthly availability: how many minutes of full downtime is that, and why does the number change the way you argue about releases?
Reveal hint

# the incident loop (every 10–15 minutes)
1. DETECT     alert / customer report / synthetic → acknowledge in < 5 min (MTTD starts here)
2. DECLARE    open #inc-2026-10-25-checkout, set severity, name the IC, start the timeline, post on status page ("investigating")
3. STABILISE  stop the bleeding BEFORE finding the cause: roll back the last deploy, flip the flag, scale up, fail over, shed load
4. DIAGNOSE   dashboards (RED → USE), recent changes (deploys, config, infra, dependencies), logs by traceId, thread dumps if hung
5. FIX        apply; verify with the SLI, not with "looks fine"; keep the workaround until the fix is proven
6. COMMUNICATE every 30 min: impact, what we know, what we are doing, next update time
7. RESOLVE    SLI back in target for N minutes → "monitoring" → "resolved"; thank people; schedule the postmortem within 48 h

# first questions the IC asks

Who is the single owner of the current action?

Incident in DMsEvidence scattered across private chats.One public channel per incident; bot-created from the alert (PagerDuty/Opsgenie/incident.io/Rootly).
"Resolved" when the graph dipsClosed, then it comes back 20 minutes later.Resolve when the SLI holds for a defined window and the cause is understood or the mitigation is durable.
Q. The on-call engineer thinks they know the root cause and wants 15 more minutes to fix it properly. A rollback would take 3 minutes. What does the IC decide?
Reveal hint
Roll back now. 15 minutes of SEV1 is a third of the monthly error budget; a wrong hunch doubles it. Fix properly afterwards, with the system healthy and the timeline intact. The IC exists precisely to make that call when the engineer is too close to the problem.

Q. A postmortem lists "root cause: engineer deployed on Friday evening". What is wrong with that sentence, and what should it say?
Reveal hint
It names a person and a time instead of a system. The deploy exposed that there was no canary analysis to catch the regression, no automatic rollback, and an alert that fired 20 minutes late — any deploy at any time would have failed the same way. Fix those three and Friday evenings become boring.

D15. Resilience patterns, chaos engineering, and the SRE quick reference

PatternWhat it doesIn a Spring service
TimeoutsNever wait forever on a dependency.Every client: connect 1–2 s, read 3–10 s; DB statement_timeout; Kafka/SQS visibility aligned to processing time.
Retries with backoff + jitterSurvive transient failures without a thundering herd.Resilience4j @Retry (3 attempts, exponential, jitter); only idempotent calls; respect Retry-After.
Circuit breakerStop calling a failing dependency; fail fast; probe to recover.@CircuitBreaker(name="payments", fallbackMethod=…); expose state as a metric.
BulkheadIsolate resources per dependency so one slow partner can't take all threads/connections.Separate thread pools / semaphores per client; separate Hikari pools for batch vs web if needed.
Rate limiting / load sheddingDrop excess load early rather than collapsing.Bucket4j / gateway limits; return 429/503 with Retry-After when queues grow.
Graceful degradationServe a reduced experience instead of an error.Recommendations off (kill switch) when the recsys is down; cached prices when the pricing service times out.
IdempotencySafe retries end-to-end.Idempotency keys on POST; dedupe table for consumers; upserts.
Health checks that mean itLiveness = process alive; readiness = can serve now.Readiness fails on pool exhaustion; liveness never checks downstreams.
Capacity headroom + autoscalingAbsorb spikes; N+1 instances across AZs.HPA on RPS/CPU; PDB; maxUnavailable: 0; never run at 90% in steady state.
Chaos engineering — the practiceHow
Hypothesis first"If payments-service returns 500 for 5 minutes, checkout degrades to 'pay later' and the SLO holds." Then test it.
Start in staging, small blast radius, with an abort buttonOne pod, one AZ, one dependency; stop condition on SLI breach.
Game daysScheduled exercises: kill the primary DB (RDS --force-failover), delete a pod, fill a disk, expire a cert in staging, cut a dependency. Practise the runbooks; time the response.
ToolsChaos Mesh / LitmusChaos (Kubernetes: pod kill, network delay/loss, CPU/memory stress, DNS chaos) · AWS Fault Injection Service (EC2/ECS/RDS/EKS faults, AZ power interruption) · Toxiproxy (latency/faults between app and DB in tests) · Gremlin (SaaS) · Resilience4j in tests.
Automate the ones that matterWeekly pod-kill in staging; monthly AZ failover game day; dependency-timeout tests in CI with Toxiproxy/WireMock delays.
LearnEvery experiment ends like an incident: timeline, what surprised you, action items.

SRE in seven lines: 1) pick SLOs users care about and measure them at the edge; 2) page on burn rate, ticket the rest, runbook every alert; 3) mitigate first (rollback/flag/failover), diagnose second; 4) one IC, fixed-cadence comms, one public channel; 5) blameless postmortems within 48 h with owned, dated action items; 6) timeouts, retries with jitter, breakers, bulkheads, idempotency on every dependency; 7) break things on purpose in staging until prod failures are rehearsed, not novel.
Q. Interviewer: "What is the difference between DevOps and SRE?"
Reveal hint
DevOps is the culture and practice set (shared ownership, automation, CI/CD, fast feedback). SRE is one concrete implementation of it, with specific tools: SLOs and error budgets to decide between features and reliability, blameless postmortems, toil limits, and engineers who write software to run systems. Google's phrase: SRE is "what happens when you ask a software engineer to design an operations team".
