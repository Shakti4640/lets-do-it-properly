0. The threat model — where a pipeline gets attacked

Your pipeline turns source into a running container. Every hop is a place an attacker can insert code, steal a secret, or swap an artifact. The point of "supply chain security" is to make each hop verifiable: who made this, from what, and did anyone tamper with it.

Mental model: a chain of custody, like evidence in court. At every hand-off someone signs for the package and records what they received. If any signature is missing or doesn't match, the evidence is thrown out — the cluster refuses to run it.
Q. Your code has zero vulnerabilities according to SonarQube. Are you safe from Log4Shell-style problems?
Reveal hint
No — SAST reads your code; Log4Shell lived in a dependency. That is SCA's job (and container scanning for the jar inside the image). You need both, plus a way to upgrade fast (Renovate/Dependabot) when the next one lands.

Q. Push protection blocked a developer's push because of an "AWS key" that is actually a test fixture. What should happen?
Reveal hint
They request a bypass with a reason (logged, reviewable), or better, replace the fixture with an obviously fake pattern (AKIAEXAMPLEEXAMPLE) / a generated value. Never disable push protection repo-wide for one false positive — tune with an allow-list (.gitleaksignore, GitHub patterns).

- id: controller-without-preauthorize

Q. CodeQL flags jdbcTemplate.query("SELECT … ORDER BY " + sortColumn, …). You can't bind a column name as a parameter. What now?
Reveal hint
Allow-list it: map the user's sort key to a fixed set of column names (Map.of("name","customer_name",…)) and throw on anything else. Then the string is built from constants, the taint flow ends, and the finding goes away for the right reason.

Q. Trivy reports a CRITICAL CVE in a transitive dependency you never heard of. The library's maintainers have not released a fix. Options?
Reveal hint
(1) Check reachability — do you call the vulnerable path? (2) Override the transitive to a fixed version if one exists elsewhere in the tree. (3) Exclude the dependency if unused. (4) Mitigate (WAF rule, config flag like log4j2.formatMsgNoLookups). (5) Suppress with expiry and a ticket. Document the decision; don't just silence it.

5. SBOM — knowing what is inside

An SBOM (Software Bill of Materials) is a machine-readable list of every component in an artifact: name, version, supplier, hashes, licence, and how they relate. When the next Log4Shell lands you query SBOMs instead of grepping 200 repos. Formats: CycloneDX (OWASP, security-oriented) and SPDX (Linux Foundation, licence-oriented). Both JSON.

# generate at build (exact, from the resolved dependency tree)
# Maven
<plugin><groupId>org.cyclonedx</groupId><artifactId>cyclonedx-maven-plugin</artifactId><version>2.9.x</version>
  <executions><execution><phase>package</phase><goals><goal>makeAggregateBom</goal></goals></execution></executions>
</plugin>                                                      <!-- → target/bom.json -->
# Gradle: org.cyclonedx.bom plugin → build/reports/bom.json   ·   Spring Boot 3.3+: spring-boot-starter-actuator exposes /actuator/sbom when the plugin runs

# generate from the image (OS packages + jars)
syft ghcr.io/shop/api@sha256:… -o cyclonedx-json > image.cdx.json
trivy image --format spdx-json --output image.spdx.json ghcr.io/shop/api@sha256:…

# attach to the image as an attestation (travels with the artifact, verifiable)
cosign attest --yes --type cyclonedx --predicate image.cdx.json ghcr.io/shop/api@sha256:…
cosign verify-attestation --type cyclonedx --certificate-identity-regexp 'https://github.com/shop/.*' --certificate-oidc-issuer https://token.actions.githubusercontent.com ghcr.io/shop/api@sha256:… | jq '.payload' -r | base64 -d | jq

# GitHub-native: actions/attest-sbom + "dependency submission" so Dependabot sees the real resolved tree
- uses: advanced-security/maven-dependency-submission-action@v4

# query later: scan an SBOM instead of the image (fast, no registry access)
grype sbom:image.cdx.json  ·  trivy sbom image.cdx.json
# central store: Dependency-Track (OWASP) — upload every build's BOM; it alerts when a new CVE matches any project
SBOM useHow
Incident response ("who uses log4j < 2.17?")Query Dependency-Track / your SBOM store across all services in seconds.
Licence complianceSPDX licence fields; policy in Dependency-Track or FOSSA.
Customer / regulator requirementUS EO 14028, EU CRA: ship the SBOM with the product.
VerificationCompare build-time SBOM with image SBOM: unexpected extras = tampering or a sloppy Dockerfile.
VEXVulnerability Exploitability eXchange: a signed statement "CVE-X does not affect us because …" that scanners honour — the structured version of a suppression.
TopicWrongRight
SBOM as a file in a bucketGenerated once, never looked at, not linked to the image.Attested to the image digest + uploaded to a store that re-scans continuously.
Image-only SBOMShaded/fat jars hide inner dependencies from image scanners.Build-time SBOM from Maven/Gradle (knows the true tree) + image SBOM for OS packages.

Q. Why does an image scanner sometimes miss a vulnerable library that the Maven SBOM lists?
Reveal hint
Shading/relocation (maven-shade-plugin renames packages into your jar), Spring Boot nested jars inside BOOT-INF/lib (most scanners handle these, older ones didn't), or a library with no pom.properties inside. The build tool knows exactly what it resolved; the image scanner is guessing from file names. Keep both SBOMs.

6. Signing and provenance — Sigstore, cosign, SLSA

TermMeaning
SignatureProof that a specific digest was approved by a specific identity. Stored in the registry next to the image (OCI referrers / sha256-….sig tag).
AttestationA signed statement about an artifact: "this SBOM describes it", "it was built by workflow X from commit Y" (provenance), "we reviewed CVE Z" (VEX). In-toto format.
ProvenanceThe attestation that says who/what/how built the artifact: builder id, source repo + commit, build parameters, materials. SLSA defines its format.
SigstoreOpen-source signing infrastructure: cosign (CLI), Fulcio (issues short-lived certs tied to an OIDC identity — your GitHub workflow), Rekor (public transparency log). "Keyless": no private keys to manage.
SLSA (Supply-chain Levels for Software Artifacts)A ladder of build-integrity guarantees. L1: provenance exists. L2: provenance signed by a hosted build platform. L3: build runs on hardened, isolated infrastructure; provenance unforgeable by the project's own maintainers. (L4 was in v0.1; v1.0 stops at 3.)
PolicyThe rule the cluster enforces: "only run images signed by github.com/shop/* workflows on main with SLSA L3 provenance and a scan attestation newer than 7 days".
 
# keyless signing in GitHub Actions (identity = the workflow's OIDC token)
permissions: { id-token: write, packages: write, contents: read, attestations: write }
steps:
  - uses: sigstore/cosign-installer@v3
  - run: cosign sign --yes "${IMAGE}@${DIGEST}"                     # cert from Fulcio, entry in Rekor; nothing to store

  # SLSA L3 provenance — the official generator runs in an isolated reusable workflow
  provenance:
    needs: build
    permissions: { actions: read, id-token: write, packages: write }
    uses: slsa-framework/slsa-github-generator/.github/workflows/generator_container_slsa3.yml@v2.0.0
    with: { image: ${{ needs.build.outputs.image }}, digest: ${{ needs.build.outputs.digest }}, registry-username: ${{ github.actor }} }
    secrets: { registry-password: ${{ secrets.GITHUB_TOKEN }} }

  # or GitHub's native attestations (simpler; L2-ish, L3 with hardened runners)
  - uses: actions/attest-build-provenance@v2
    with: { subject-name: ${{ env.IMAGE }}, subject-digest: ${{ steps.push.outputs.digest }}, push-to-registry: true }

# verify (what the cluster policy and your deploy script do)
cosign verify --certificate-identity-regexp '^https://github.com/shop/shop-api/.github/workflows/ci.yml@refs/heads/main$' \
              --certificate-oidc-issuer https://token.actions.githubusercontent.com \
              ghcr.io/shop/api@sha256:…
cosign verify-attestation --type slsaprovenance --certificate-identity-regexp 'https://github.com/slsa-framework/.*' --certificate-oidc-issuer https://token.actions.githubusercontent.com ghcr.io/shop/api@sha256:…
gh attestation verify oci://ghcr.io/shop/api@sha256:… --owner shop        # GitHub-native
cosign tree ghcr.io/shop/api@sha256:…                                      # what is attached: sig, sbom, provenance

# key-based alternative (air-gapped / no OIDC): cosign generate-key-pair; private key in KMS: cosign sign --key awskms:///alias/cosign …
# sign jars too: Maven Central requires GPG (.asc); Sigstore's maven plugin (sigstore-maven-plugin) adds keyless signatures
Why each piece mattersWithout it
Signature by the workflow identity (not a shared key)A stolen key signs anything forever; an OIDC cert is minutes-lived and names the exact repo/workflow/branch.
Transparency log (Rekor)You can't prove when something was signed or detect a signature made with a compromised identity later.
Provenance from an isolated builder (SLSA L3)A malicious PR to the workflow file could make the build lie about itself. L3 generators run in a separate, trusted workflow the project can't alter.
Verification at admission (Section 7)Signing with no one checking is theatre.

Q. "Keyless" signing — if there is no key, what is the signature made with?
Reveal hint
There is a key — an ephemeral one generated for that signing operation. Fulcio binds its public half to your OIDC identity in a short-lived certificate (minutes), the signature + cert are logged in Rekor, and the private key is thrown away. Verification checks the cert's identity and the log entry's timestamp, so nothing long-lived exists to steal.

Q. The Kyverno policy passes in staging but every prod pod is rejected with "no matching signatures". Images are identical digests. Why?
Reveal hint
Usually the prod cluster cannot reach the registry's signature artifacts or Rekor (egress blocked, private registry without referrers API), or the prod images were promoted by copying (docker pull/push) which drops the attached signatures — use crane copy/cosign copy or re-sign after promotion. Check Kyverno's logs for the exact fetch error.

Q. With GitOps everything is in git. How do secrets get into the cluster without being in git?
Reveal hint
Git holds a reference (an ExternalSecret saying "key shop/prod/db in AWS"), and an operator in the cluster, authenticated by its own cloud identity, fetches the value and creates the K8s Secret. Alternatively git holds encrypted values (Sealed Secrets/SOPS) that only the cluster can decrypt. Either way the plain value never touches the repo.

The 7 rules to remember: 1) protect the source: SSO/MFA, signed commits, branch rules, CODEOWNERS on pipeline and infra; 2) scan on every PR (fast) and every night (deep): SAST, SCA, secrets, IaC, image; gate on new findings; 3) pin everything — actions by SHA, images by digest, dependencies by exact version with verification; 4) build once on ephemeral runners with read-only tokens; OIDC instead of stored cloud keys; 5) sign keyless, attest SBOM and provenance, and verify at admission; 6) secrets live in a manager, reach pods via ESO/CSI/task secrets as files, one role per service, rotation planned; 7) roll out in Audit mode first, then Enforce — security that blocks the team gets switched off.
Q. Interviewer: "What does 'supply chain security' actually prevent that regular security scanning doesn't?"
Reveal hint
Scanning asks "does this artifact contain known-bad things?". Supply chain security asks "is this artifact the one we think it is, built the way we think, from the source we think?" — it defends against tampering and substitution (compromised actions, swapped tags, poisoned builders, malicious dependency releases) that a scanner would happily pass because the malicious code is not a known CVE. You need both.
