A0. Ansible — what it is and when you still need it

Ansible configures machines over SSH: install packages, write config files, start services, deploy a jar — on 1 or 1,000 hosts, in the order you say, with no agent on the target. You describe the desired state in YAML playbooks; each module (apt, copy, systemd…) checks the current state and changes only what differs (idempotent).

TermPlain meaning
Control nodeWhere you run ansible-playbook (laptop, CI runner). Needs Python + SSH. Targets need only SSH + Python.
InventoryThe list of hosts and groups (webservers, db), static INI/YAML or dynamic (AWS EC2 tags, Kubernetes).
PlaybookA YAML file: which hosts, which tasks (or roles), in order.
TaskOne module call with arguments. Reports ok (nothing to do), changed, or failed.
ModuleThe unit of work: apt, copy, template, systemd, user, git, uri, amazon.aws.ec2_instance… thousands.
RoleA reusable folder of tasks/handlers/templates/defaults (roles/java_app/). Shared via Ansible Galaxy or a private collection.
HandlerA task that runs only when notified (restart the service once at the end if any config changed).
FactsAuto-gathered host info (ansible_facts.os_family, memory, IPs) usable in templates/conditions.
VaultEncrypt secrets inside the repo (ansible-vault); key from CI secret or a secrets manager.
CollectionNamespaced bundle of modules/roles (community.general, amazon.aws, kubernetes.core).
Use Ansible forPrefer something else for
Configuring VMs you still have: Jenkins agents, bastions, self-hosted runners, legacy app servers, on-prem boxes.Creating cloud infrastructure → Terraform (Ansible can, but state handling is weaker).
Bootstrapping: users, SSH hardening, monitoring agents, Docker install, kernel params.Deploying containerised apps → Kubernetes/ECS + GitOps.
Baking machine images (Packer + Ansible provisioner) so servers are immutable.Long-running config drift correction on hundreds of mutable servers → bake images instead; or Puppet/Chef if you truly need continuous enforcement.
Orchestrated ad-hoc operations: rolling restarts across a fleet, patching, one-off audits.Application config → the app's own config system / secrets manager.
 
# install and first contact
pipx install --include-deps ansible          # or pip; ansible-core + collections
ansible --version
ansible all -i inventory.yml -m ping             # "pong" from every host = SSH + Python OK
ansible webservers -i inventory.yml -m shell -a "systemctl is-active shop-api"    # ad-hoc command across a group
ansible webservers -m apt -a "name=jq state=present" --become                # ad-hoc module, with sudo
Mental model: a very careful sysadmin with a checklist, SSHing into each box in turn. Before each step they look first ("is jq installed?") and only act if needed, then tick the box. Run the checklist twice and the second run changes nothing — that is idempotence, and it is what makes Ansible safe to re-run.
Q. If Terraform can run remote-exec provisioners, why use Ansible at all?
Reveal hint
Terraform's job ends when the machine exists; provisioners are one-shot, not idempotent, and fail Terraform on error. Ansible models the inside of the machine as desired state you can re-apply any time. Typical split: Terraform creates the EC2 instance from an AMI that Packer+Ansible baked; Ansible (or cloud-init) does only last-mile config.

# site.yml — a playbook
- name: Configure API servers
  hosts: webservers
  become: true                                   # sudo
  serial: "50%"                                   # rolling: half the hosts at a time
  max_fail_percentage: 0                          # stop everything on the first failure
  vars_files: [vars/common.yml, vars/secrets.yml]  # secrets.yml is vault-encrypted
  pre_tasks:
    - name: Drain from the load balancer
      delegate_to: localhost
      amazon.aws.elb_target: { target_group_arn: "{{ tg_arn }}", target_id: "{{ ec2_instance_id }}", state: absent, deregister_unused: true }
  roles:
    - common                                       # users, sshd hardening, chrony, node_exporter
    - java_app                                     # the service itself
  post_tasks:
    - name: Wait for health
      ansible.builtin.uri: { url: "http://localhost:{{ app_port }}/actuator/health", status_code: 200 }
      register: health
      retries: 30
      delay: 2
      until: health.status == 200
    - name: Re-register in the load balancer
      delegate_to: localhost
      amazon.aws.elb_target: { target_group_arn: "{{ tg_arn }}", target_id: "{{ ec2_instance_id }}", state: present }

Q. A playbook reports changed=12 on every run even though nothing is different. What does that tell you?
Reveal hint
Twelve tasks are not idempotent — usually command/shell without creates:/changed_when:, or templates with timestamps/random values. It matters: handlers fire needlessly (restarts!), and you can no longer tell real drift from noise. Target changed=0 on a second run.

A2. Roles, templates, handlers — deploying a Java service

# roles/java_app/
├── defaults/main.yml      # app_name: shop-api, app_user: shop, app_port: 8080, java_heap_pct: 75, app_version: (required)
├── tasks/main.yml
├── handlers/main.yml
├── templates/
│   ├── shop-api.service.j2
│   └── app.env.j2
├── files/                 # static files
├── meta/main.yml          # dependencies: [common, java_runtime]
└── molecule/              # role tests (Docker/Podman scenario)

# roles/java_app/tasks/main.yml
- name: Service user
  ansible.builtin.user: { name: "{{ app_user }}", system: true, shell: /usr/sbin/nologin, home: "/opt/{{ app_name }}", create_home: true }

- name: Release directory
  ansible.builtin.file: { path: "/opt/{{ app_name }}/releases/{{ app_version }}", state: directory, owner: "{{ app_user }}", mode: "0750" }

- name: Download the jar (verified)
  ansible.builtin.get_url:
    url: "https://nexus.shop.example/repository/maven-releases/com/shop/{{ app_name }}/{{ app_version }}/{{ app_name }}-{{ app_version }}.jar"
    dest: "/opt/{{ app_name }}/releases/{{ app_version }}/app.jar"
    checksum: "sha256:{{ app_sha256 }}"
    url_username: "{{ nexus_user }}"
    url_password: "{{ nexus_password }}"
    owner: "{{ app_user }}"
    mode: "0640"
  no_log: true                                      # don't print credentials

- name: Environment file
  ansible.builtin.template: { src: app.env.j2, dest: "/etc/{{ app_name }}/app.env", owner: root, group: "{{ app_user }}", mode: "0640" }
  notify: restart app

- name: systemd unit
  ansible.builtin.template: { src: shop-api.service.j2, dest: "/etc/systemd/system/{{ app_name }}.service", mode: "0644" }
  notify: [reload systemd, restart app]

- name: Point current at the new release
  ansible.builtin.file: { src: "/opt/{{ app_name }}/releases/{{ app_version }}", dest: "/opt/{{ app_name }}/current", state: link, force: true }
  notify: restart app

- name: Keep the last 3 releases
  ansible.builtin.shell: ls -1dt /opt/{{ app_name }}/releases/* | tail -n +4 | xargs -r rm -rf
  changed_when: false

- name: Enabled and running
  ansible.builtin.systemd_service: { name: "{{ app_name }}", enabled: true, state: started }

# roles/java_app/handlers/main.yml  — run once at the end of the play, only if notified
- name: reload systemd
  ansible.builtin.systemd_service: { daemon_reload: true }
- name: restart app
  ansible.builtin.systemd_service: { name: "{{ app_name }}", state: restarted }

Q. Your serial: "50%" rolling deploy fails on host 3 of 4. What state is the fleet in, and what does max_fail_percentage: 0 do?
Reveal hint
Hosts 1–2 (first batch) have the new version and are back in the LB; host 3 failed mid-batch, host 4 may be partially done or untouched; the play stops. With max_fail_percentage: 0 the play aborts at the first failure instead of marching on to the next batch — half the fleet still serves the old version, which is exactly what you want. Fix host 3, re-run with --limit.

Q. Interviewer: "Ansible or Terraform?"
Reveal hint
Different layers. Terraform declares what exists (VPC, instances, databases) and tracks it in state. Ansible declares what is inside a machine (packages, files, services) and needs no state because it inspects the host each run. Most shops use Terraform for infra, Packer+Ansible to bake images, and Ansible ad-hoc for fleet operations — or skip Ansible entirely once everything is a container.

B4. Artifact repositories — why you run one and what goes in it

An artifact repository (Nexus, Artifactory, GitHub Packages, AWS CodeArtifact/ECR, GitLab Package Registry, Harbor) stores the outputs of builds — jars, Docker images, npm packages, Helm charts — and proxies the public repositories your builds pull from. It is the one place between the internet and your pipeline.

Repository typeHoldsExample
Proxy / remoteA cache of an upstream (Maven Central, Docker Hub, npmjs, PyPI). First request fetches and stores; later requests are local.maven-central-proxy, dockerhub-proxy
Hosted / local — releasesYour own immutable versions. Redeploy of an existing version is rejected.maven-releases (com.shop:common:1.4.0)
Hosted / local — snapshotsYour own moving versions; many timestamped uploads per -SNAPSHOT; cleaned by retention.maven-snapshots (common:1.5.0-SNAPSHOT)
Group / virtualOne URL that searches several repos in order (releases → snapshots → central proxy).maven-public — the only URL builds know
OCI / Docker registryImages and anything OCI (Helm charts, cosign signatures, SBOM attestations).ECR, GHCR, Harbor, Nexus docker-hosted
Raw / genericZips, installers, binaries, Terraform modules.raw-tools
WhyWhat it gives you
Speed and reliabilityBuilds don't depend on Maven Central being up or fast; dependencies cached once for the whole company; Docker Hub rate limits disappear.
ControlBlock or quarantine packages (CVE policy, licence policy, typosquats) at the proxy; everything the company uses is in one inventory.
SharingTeam A publishes common-money:2.1.0; team B depends on it like any library.
ImmutabilityRelease repos refuse re-uploads: 1.4.0 is the same bytes forever.
ProvenanceBuild info / metadata, signatures and SBOMs attached to artifacts; who uploaded what, when.
Air gaps / complianceOnly the proxy talks to the internet; audit of everything that came in.
 
# the flow
developer / CI  ──build──▶  jar  ──mvn deploy──▶  Nexus maven-releases (hosted)
                 ◀──resolve────────────────────  Nexus maven-public (group) ──miss──▶ maven-central-proxy ──▶ Maven Central
CI  ──docker push──▶  ECR / GHCR / Harbor (OCI)  ◀──pull──  Kubernetes nodes
Harbor/ECR pull-through cache  ──miss──▶  Docker Hub (no rate limits for you)
Mental model: a warehouse with a receiving dock. Everything from outside comes through the dock (proxy) where it is inspected and shelved; everything you make is shelved with a label that never changes (release) or a "latest draft" label (snapshot). Builds shop only inside the warehouse.
Q. If GitHub Packages / ECR are free with your plan, why would anyone run Nexus or Artifactory?
Reveal hint
Proxying and policy. GHCR/ECR store your artifacts; they don't cache Maven Central or Docker Hub for your builds, don't quarantine vulnerable packages at the door, and don't give one virtual URL across formats. Many shops combine: ECR for images, CodeArtifact or Nexus for Maven with Central proxying.

Q. A teammate deployed common:1.5.0-SNAPSHOT an hour ago with a fix; your build still uses the old one. Why, and how do you get it?
Reveal hint
Maven checks a snapshot's maven-metadata.xml at most once per day by default (updatePolicy: daily), so your local ~/.m2 copy is considered fresh. Run ./mvnw -U (force update) or set the proxy's/your settings' snapshot updatePolicy to always/interval:10 for the snapshots repo.

B6. OCI registries — images, charts, signatures; retention and promotion

ConceptMeaning
OCIOpen Container Initiative: the standard image format and registry API. Any OCI registry stores images and other artifacts (Helm charts, cosign signatures, SBOMs, WASM, Terraform modules) as "OCI artifacts".
Manifest / digest / tagA manifest lists layers + config; its SHA-256 is the digest (immutable identity). A tag is a mutable pointer to a manifest. Multi-arch images use a manifest index pointing at per-platform manifests.
Immutable tagsRegistry setting that refuses re-pushing an existing tag (ECR imageTagMutability=IMMUTABLE, Harbor tag immutability rules).
Pull-through cacheRegistry proxies Docker Hub/GHCR/Quay: ECR pull-through rules, Harbor proxy projects, Nexus docker-proxy. Fixes rate limits and gives you a local copy.
ReferrersSignatures/attestations attached to a digest (OCI 1.1 referrers API or cosign's tag scheme). Copy images with crane copy/cosign copy to keep them.
Lifecycle / retentionRules: expire untagged after 7 days, keep last 50 sha-* tags, keep all v* tags.
ScanningECR basic/enhanced (Inspector), Harbor + Trivy, Artifactory Xray — continuous re-scan of stored images.
ReplicationCross-region/cross-account (ECR replication rules, Harbor replication) for DR and locality.

C7. DNS — how a name becomes an address, and why it breaks

PieceMeaning
Resolver (stub → recursive)Your machine's stub resolver (/etc/resolv.conf, systemd-resolved, the JVM's cache) asks a recursive resolver (your VPC's .2 address, 1.1.1.1, CoreDNS in a cluster), which walks root → TLD → authoritative servers and caches the answer.
Authoritative serverHolds the zone (Route 53 hosted zone, Cloudflare). The source of truth.
Record typesA (IPv4), AAAA (IPv6), CNAME (alias to another name; not allowed at the zone apex), ALIAS (Route 53 apex alias to AWS resources), MX, TXT (verification, SPF/DKIM), SRV, NS, SOA, CAA (which CAs may issue certs).
TTLHow long resolvers may cache. 300 s is a common default; lower it before a planned change, not during.
Negative caching"Does not exist" (NXDOMAIN) is cached too (SOA minimum TTL) — typos haunt you for minutes.
Split-horizonPrivate hosted zone answers db.shop.internal only inside the VPC; public zone answers api.shop.example to the world.
Search domainsresolv.conf search shop.svc.cluster.local svc.cluster.local — api becomes api.shop.svc.cluster.local. ndots:5 in K8s means names with < 5 dots try the search list first (extra lookups for external names).
Routing policies (Route 53)Weighted (canary by DNS), latency, failover (health-checked), geolocation. Coarse: TTLs and client caching make DNS a slow switch.
Java DNS cacheModern JDKs cache successful lookups ~30 s (networkaddress.cache.ttl); negative 10 s. Old JDKs with a security manager cached forever — check if you see stale IPs after a failover.

Q. You changed an A record with TTL 3600 and most users still hit the old server after 20 minutes. Can you speed it up?
Reveal hint
Not for resolvers that already cached it — they will hold the old answer up to the full hour; you cannot push an update. Lesson: drop the TTL to 60 s a day before a planned move, then raise it after. For instant switching use a load balancer or weighted routing behind a stable name.

C8. HTTP — 1.1 vs 2 vs 3, connections, caching headers, status codes that matter

HTTP/1.1HTTP/2HTTP/3
TransportTCP, text framingTCP, binary frames, one connection per originQUIC (UDP), TLS 1.3 built in
ParallelismOne request at a time per connection (pipelining unused) → browsers open ~6 connectionsMultiplexing: many streams on one connection; header compression (HPACK); server push (deprecated)Multiplexing without TCP head-of-line blocking; faster handshakes (0-RTT), connection migration (Wi-Fi → mobile)
Where you meet itMost server-to-server Java clients by default; curl defaultBrowsers ↔ ALB/CloudFront/NGINX; gRPC requires h2; Java HttpClient defaults to h2 with fallbackBrowsers ↔ CDNs (CloudFront, Cloudflare); rare server-to-server
Behind the ALBALB → target is HTTP/1.1 unless you choose h2/gRPC target groupsClient-facing h2 is on by default on ALB/NGINX with TLSCloudFront supports h3 to clients; origin stays h1/h2
Connection mechanics (why pools and keep-alive matter)Detail
TCP handshake1 RTT before any data. TLS adds 1 RTT (1.3) or 2 (1.2). New connection per request = 2–3 RTTs wasted.
Keep-aliveHTTP/1.1 default: reuse the connection. Idle timeouts on both ends must agree (ALB 60 s; make the server's longer — see the AWS/NGINX sheets).
Connection poolsJava HttpClient, Apache HttpClient, OkHttp, Netty all pool; size them (maxConnections, per-route) and set timeouts (connect, read/response, total).
Head-of-line blockingh1: a slow response blocks the connection. h2: a lost TCP packet blocks all streams. h3: streams independent.
Chunked / streamingTransfer-Encoding: chunked (h1) or data frames (h2) — bodies without known length; SSE for server push to browsers.
CompressionAccept-Encoding: gzip, br → Content-Encoding. Do it at the edge (CDN/NGINX) or in Spring (server.compression.enabled).
Caching headersMeaning
Cache-Control: public, max-age=31536000, immutableStatic assets with hashed names: cache forever.
Cache-Control: private, no-storePer-user API responses: never cache (CDN or browser).
Cache-Control: public, max-age=60, stale-while-revalidate=300Semi-static API (catalog): serve cached up to a minute, refresh in the background.
ETag / If-None-Match → 304Conditional GET: save bandwidth; Spring's ShallowEtagHeaderFilter or hand-set ETags; also optimistic concurrency with If-Match on PUT.
Vary: Accept-Encoding, AuthorizationTell caches which request headers change the response.
Last-Modified / If-Modified-SinceTime-based conditional.
Status codes a backend dev must get rightUse
200 / 201 / 202 / 204OK / created (with Location) / accepted for async processing / no content.
301 / 302 / 307 / 308Permanent / temporary; 307/308 keep the method (POST stays POST). Use 308 for permanent API moves.
304Not modified (conditional GET).
400 / 401 / 403 / 404 / 405Bad input / not authenticated (send WWW-Authenticate) / authenticated but forbidden / missing / wrong method.
409 / 412 / 422Conflict (duplicate, version mismatch) / precondition failed (If-Match) / semantically invalid.
429Rate limited — with Retry-After.
500 / 502 / 503 / 504Your bug / proxy got a bad response / overloaded or draining (Retry-After) / upstream timeout. Clients retry 502/503/504 with backoff, never 500 blindly, never non-idempotent POSTs without an idempotency key.

Q. Your API shows p99 of 20 ms in the server logs but clients measure 300 ms. The client is in another region. What dominates?
Reveal hint
Round trips: DNS (if uncached) + TCP handshake + TLS handshake before the first byte, each ~80–100 ms across continents. Fixes: keep-alive/connection reuse (one handshake per many requests), HTTP/2, TLS 1.3 (1 RTT), a CDN/edge in the client's region, or regional deployment. curl -w timings show exactly where the 280 ms goes.

C9. TLS — the handshake, certificates, chains, mTLS

ConceptPlain meaning
TLSEncrypts and authenticates a TCP connection. HTTPS = HTTP over TLS. "SSL" is the old name.
CertificateA signed statement: "this public key belongs to api.shop.example", issued by a CA, valid for a period, with SANs (subject alternative names) listing the hostnames.
ChainLeaf cert → intermediate CA(s) → root CA. The server must send leaf + intermediates; the client has roots in its trust store.
Trust storeThe roots a client trusts: OS store, browser store, the JVM's cacerts ($JAVA_HOME/lib/security/cacerts).
Handshake (TLS 1.3)ClientHello (versions, ciphers, SNI, ALPN, key share) → ServerHello + cert + Finished → client verifies chain, hostname, validity, revocation → Finished. 1 RTT. TLS 1.2 takes 2.
SNIClient names the host in ClientHello so one IP can serve many certs (ALB, NGINX, CDNs rely on it).
ALPNClient and server agree on the application protocol (h2, http/1.1) during the handshake.
RevocationCRL / OCSP (+ stapling) — in practice short-lived certs (90 days, soon 47) are the real answer.
mTLSBoth sides present certificates. Service-to-service identity (service meshes do it automatically with SPIFFE identities); client certs for partner APIs.
Termination vs passthrough vs re-encryptionLB decrypts and sends plain HTTP inward (common) · LB forwards encrypted bytes (NLB, mTLS to the app) · LB decrypts then re-encrypts to the target (compliance).
HSTSStrict-Transport-Security header: browsers refuse plain HTTP for the domain afterwards.

openssl s_client -connect api.shop.example:443 -servername api.shop.example -tls1_3 -alpn h2 </dev/null | grep -E "Protocol|Cipher|ALPN|Verify return"
curl -vI https://api.shop.example 2>&1 | grep -E "SSL connection|subject|issuer|expire"

Q. Your Spring app calls a partner API fine from your laptop but gets PKIX path building failed in the container. Same code. Why?
Reveal hint
Different trust stores. Your laptop's JDK (or OS) trusts the partner's CA (often a corporate proxy's CA injected by IT); the container's minimal JRE has only public roots. Either the partner uses a private/intermediate CA you must add via an SSL bundle, or a corporate TLS-inspecting proxy sits between your laptop and the internet and the container bypasses it. openssl s_client -showcerts from both places shows the difference.

C10. CORS, cookies and the browser security model

CORS (Cross-Origin Resource Sharing) is a browser rule: JavaScript on https://shop.example may read a response from https://api.shop.example only if the API says so in response headers. It protects users from malicious sites using their logged-in browser; it does not protect your API from curl or servers.

TermMeaning
Originscheme + host + port. https://shop.example ≠ https://api.shop.example ≠ http://shop.example ≠ https://shop.example:8443.
Simple requestGET/HEAD/POST with simple headers and content types (application/x-www-form-urlencoded, multipart/form-data, text/plain). Sent directly; the browser blocks reading the response if CORS headers are missing (the request still happened!).
PreflightFor anything else (JSON body, Authorization header, PUT/DELETE) the browser first sends OPTIONS with Access-Control-Request-Method/Headers; the server must answer with the allow headers; cached for Access-Control-Max-Age.
Response headersAccess-Control-Allow-Origin (exact origin or *), -Allow-Methods, -Allow-Headers, -Expose-Headers (which response headers JS may read), -Allow-Credentials: true (cookies/auth allowed — then * is forbidden), -Max-Age.
CookiesSet-Cookie: session=…; HttpOnly; Secure; SameSite=Lax|Strict|None; Path=/; Domain=.shop.example. SameSite=None requires Secure and is the only way cookies ride cross-site requests.
CSRFA malicious site makes the browser send a state-changing request with the user's cookies. Defences: SameSite cookies, CSRF tokens (Spring Security default for session apps), or bearer tokens in headers (not sent automatically) — which is why stateless token APIs disable CSRF.
CSP, X-Frame-Options, Referrer-PolicyOther browser headers: restrict script sources, block framing (clickjacking), limit referrer leakage. Set at the edge (NGINX/CloudFront) or Spring Security headers config.
 
// Spring: CORS belongs in Spring Security's chain (so preflights aren't rejected as unauthenticated)
@Bean
CorsConfigurationSource cors() {
    var c = new CorsConfiguration();
    c.setAllowedOrigins(List.of("https://shop.example", "https://admin.shop.example"));   // exact origins; setAllowedOriginPatterns for *.preview.shop.example
    c.setAllowedMethods(List.of("GET", "POST", "PUT", "DELETE", "OPTIONS"));
    c.setAllowedHeaders(List.of("Authorization", "Content-Type", "X-Request-Id"));
    c.setExposedHeaders(List.of("Location", "X-Request-Id"));
    c.setAllowCredentials(true);                                 // only if you use cookies; then no "*"
    c.setMaxAge(3600L);
    var src = new UrlBasedCorsConfigurationSource();
    src.registerCorsConfiguration("/api/**", c);
    return src;
}
// http.cors(Customizer.withDefaults())  picks up the bean; preflight OPTIONS passes before auth

Q. The browser console says "blocked by CORS policy" — but your server logs show the POST executed and the order was created. How?
Reveal hint
It was a "simple" request (e.g. form-encoded POST without custom headers), so no preflight: the browser sent it, the server processed it, and only the response was hidden from JavaScript. CORS never promised to stop the request. That is why state-changing endpoints need CSRF protection or bearer tokens, not CORS.

# a typical production path for a Spring API
user → DNS (Route 53) → CDN/WAF (CloudFront: TLS 1.3/h3, cache static, block bots)
     → L7 load balancer / reverse proxy (ALB or NGINX: TLS termination, host/path routing, health checks)
     → [optional API gateway: JWT validation, per-client rate limits, API keys]
     → Kubernetes Ingress / Service or ECS target group
     → Spring Boot pod/task (plain HTTP 8080, or mTLS via mesh)
     → east-west calls through the mesh (mTLS, retries) → other services / DB over TLS

# rule of thumb: LB = "which copy"; reverse proxy = "which service + HTTP plumbing"; gateway = "which client may do what"; CDN = "serve it from near the user"; mesh = "secure and observe service-to-service"
DecisionGuidance
ALB alone or ALB + gateway?ALB for routing and TLS; add a gateway when you need per-client quotas, API keys, a developer portal, or centralised auth for many services. Spring Cloud Gateway if the team is Java-first and the gateway is "just another service".
CDN in front of an API?Yes for public read-heavy GETs with proper Cache-Control, for TLS/h3 at the edge, and for DDoS absorption. Pass-through (no cache) for authenticated endpoints still gains edge TLS and WAF.
Service mesh?When you have many services and need mTLS/authz/telemetry uniformly. Not for three services — use a library (Resilience4j) and TLS to the DB.
Where does TLS end?At the edge (CDN/ALB) by default; plain HTTP inside a private network is common and acceptable; mTLS inside when compliance or zero-trust requires it (mesh makes it cheap).
Where do rate limits live?Edge (WAF rate rules) for abuse; gateway for per-client business limits; app (Bucket4j/Redis) for fine-grained rules.

The 7 rules to remember (this sheet): 1) Ansible = idempotent modules over SSH, roles + handlers, --check --diff first, bake images where you can; 2) one artifact repo URL for all builds, immutable releases, snapshots cleaned, proxies with policy; 3) images by digest, immutable tags, pull-through cache, lifecycle rules, copy with signatures; 4) DNS is cached — lower TTL before changes, dig @authoritative to see truth, watch ndots in K8s; 5) reuse connections, set timeouts, use correct status codes and Cache-Control; 6) never disable TLS verification — fix the chain/trust store; auto-renew with an expiry alarm; 7) CORS protects browsers not APIs — authenticate everything, exact origins, CSRF for cookie sessions.
Q. Interviewer: "Reverse proxy, load balancer, API gateway — aren't they the same box?"
Reveal hint
Often literally the same software (NGINX/Envoy can be all three), but the roles differ: a load balancer answers "which of N identical copies", a reverse proxy answers "which service and how to shape the HTTP" (TLS, compression, caching, rewrites), and an API gateway answers "which client may do what, how often" (auth, quotas, keys, portal). Name the role you need; then pick the box.
